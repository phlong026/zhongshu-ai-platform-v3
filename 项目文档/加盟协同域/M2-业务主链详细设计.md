## 2. 对方案的修正

1. **不迁移原 `design` 模块的预算与 AI 引擎**。主链只需要「最近一版参考预算的参数」作为委托依据。M2 只保存小程序提交的方案/预算版本;真实计算继续调用原服务,迁入 `franchise-design` 推迟到用到时(与「AI 是否计费」一起决定)。参考预算只用于沟通,不决定金额:委托费用由业务另填并经标准规则或老板审批,所以信任客户端提交的预算数字不会绕过金额控制。
2. **设计组织固定为总部**。`sales-flow.js:78` 新流程写死总部;门店自设计只存在于历史流程。取唯一启用的 `headquarters` 组织,没有或多于一个时拒绝提交。
3. **接口统一走 `/admin-api/franchise/...`**(M1 第 2 节),请求头带 `tenant-id`、`Authorization`、`X-Post-Id`。
4. **首尾款由财务「推」进度,而不是委托去「拉」**。总部岗位查询时组织范围规则会过滤掉门店付款行,拉不到;待办也无法在 SQL 里按就绪筛选。所以委托表自带进度字段,由 M3 财务模块在核实后调用本域接口写入(§8)。

## 6. 对象规则(移植 `authority-v2.js` / `sales-flow.js` / `growth.js`)

记号:`P` = 当前岗位快照;`has(P,'sales')` = 岗位是 sales 或继承 sales。

| 规则 | 定义 |
|---|---|
| 老板类 `isBoss` | `P.roleCode ∈ {boss, owner}` |
| 负责人管理范围 `teamAccess(x)` | `P` 是负责人岗位且:`P.teamId` 为空 → 管理本组织整条线(含 `team_id` 为空的记录);否则 `x.team_id ∈ P.managedTeamIds`(所在团队及下级) |
| 同团队 `sameTeam(x)` | `x.team_id` 与 `P.teamId` 相同(都为空也算) |
| 客户可见 | 同组织且:老板类;或 `sales-lead` 且(本人经办或 `teamAccess`);或 `sales` 且本人经办 |
| 客户可写(跟进、编辑、方案、提交委托、修改意见、提交移交) | 门店 + `has(P,'sales')` + 同组织 +(本人经办,或 `sales-lead` 且 `teamAccess`)。老板只看不办(与小程序一致) |
| 登记客资 | 门店 + `has(P,'sales')` |
| 登记时自动关联原客户 | 同组织有该手机号客户,且对登记人:老板类、本人经办、`sameTeam`、`teamAccess` 之一成立 → 关联;否则 `LINK_REQUIRED`(`growth.js:30` `findStoreCustomer`) |
| 关联原客户 | 老板类;或 `sales-lead` 且客资 `teamAccess` 且原客户 `teamAccess`;否则提示「交给对应负责人或老板」(`growth.js:62–66`) |
| 作废待关联客资 | 登记人本人,或能关联它的人。小程序原为登记人本人(`growth.js:60`);新流程客资停在待关联时登记人本身无权处理原客户,所以加上负责人和老板 |
| 责任转交 | 老板类,或 `sales-lead` 且客户 `teamAccess`;接手人须为同组织有效 sales 线任职;负责人只能转给自己管理范围内团队的人 |
| 标准设计费用 | 门店 `boss` |
| 委托费用审批 | 门店 `boss`(平台再校验同组织、不能自批) |
| 设计完成 / 成果下发 | `hq-design-admin` + 总部组织 + `commission.design_org_id = P.orgId` |
| 移交接收人可选范围 | 同组织有效工程线任职(engineer 或 project-manager,与 `sales-flow.js:106` 一致),且不是提交人本人 |
| 核查接收 / 退回 | `has(P,'engineer')` + 同组织 + `handover.manager_user_id = P.userId` |
| 委托可见 | 能写该客户的人;同组织老板类;设计行政(同上);任一版移交的接收人 |

- **字段裁剪**:设计行政看到的委托不含金额、收款方,只含首尾款是否就绪;客户手机号不出现在委托里(`fr_customer` 对总部不可见)。
- **新增数据的归属组织一律取当前岗位**(`P.orgId`),不接受请求里的 `company_id`(M1.5 评审结论)。
- **幂等重放**:命中幂等键时,先按上表做对象授权,再返回当前结果;幂等键按「域 + 用户」加前缀存储。

## 7. 委托状态机(`sales-offline-v1`)

```
 submit:匹配标准 ───────────────────────────────▶ DESIGNING
 submit:未匹配 ──▶ FEE_PENDING ──老板批准──────────▶ DESIGNING
                     │ 老板退回                         │ ▲
                     ▼                                  │ │ commission-feedback
                 FEE_RETURNED ──submit(重提)──▶ 同上    │ │
                                     design-complete    ▼ │
                                                 DESIGN_COMPLETED
                                                        │ design-dispatch
                                                        ▼
                                                   DISPATCHED
                                                        │ packet-submit
                                                        ▼
                 HANDOVER_RETURNED ◀──packet-return── HANDOVER_SUBMITTED ──packet-receive──▶ ACCEPTED
                         │                              ▲
                         └──────packet-submit(重提)─────┘
```

| 命令 | 允许的状态 | 关键校验 | 结果 |
|---|---|---|---|
| `commission-submit` | 无委托,或 `FEE_RETURNED` | 客户可写;有最近一版 BUDGET;需求、交付范围非空且勾选核对;`0 < 首款 < 总额 ≤ 1 亿元`,最多两位小数;收款方非空;总部组织唯一 | 新提交版本。**取本门店 version 最大的标准费用,它 `active=true` 且总额、首款、尾款、收款方、交付范围全部相同** → `DESIGNING`;否则须本门店存在「不是提交人」的有效 `boss` 任职(否则拒绝提交,提示先配置老板),发起审批 → `FEE_PENDING` |
| `fee-decide` | `FEE_PENDING` | 门店老板;平台校验不能自批、必须填意见 | 批准 → `DESIGNING`;退回 → `FEE_RETURNED` |
| `design-complete` | `DESIGNING` | 设计行政;`first_ready_at` 非空;勾选确认 | 记 COMPLETE;待处理修改意见置 RESOLVED → `DESIGN_COMPLETED` |
| `design-dispatch` | `DESIGN_COMPLETED` | 设计行政;`tail_ready_at` 非空;接收人、交付清单非空且勾选 | 记 DISPATCH(seq+1),`dispatch_seq` 指向它 → `DISPATCHED` |
| `commission-feedback` | `DISPATCHED` | 客户可写;修改意见非空 | 记 FEEDBACK(PENDING);`dispatch_seq` 清空 → `DESIGNING` |
| `packet-submit` | `DISPATCHED`、`HANDOVER_RETURNED` | 客户可写;请求中的 `dispatchSeq` 等于当前 `dispatch_seq`;四份文件齐全;图纸版本非空;客户确认日期合法且不晚于今天;勾选已收齐、已确认;交底非空;接收人符合 §6 | 新移交版本 → `HANDOVER_SUBMITTED` |
| `packet-return` | `HANDOVER_SUBMITTED` | 接收人本人;原因非空 | 本版 RETURNED → `HANDOVER_RETURNED` |
| `packet-receive` | `HANDOVER_SUBMITTED` | 接收人本人;勾选核对 | 本版 ACCEPTED → `ACCEPTED` |

- `commission-feedback` 只在 `DISPATCHED` 允许:移交退回(`HANDOVER_RETURNED`)后不能再登记修改意见,与 `sales-flow.js:86` 的 `!b.handover` 一致。
- 每个命令请求带 `revision`(首次提交除外),不一致返回「记录已变化,请刷新」;可选请求头 `Idempotency-Key`。
- 显示状态由「存储状态 + 首尾款进度」推出,文案与 `sales-flow.js` 的 `next()` 一致,例如 `DESIGNING` 且首款未就绪 →「首款办理中」;`DESIGN_COMPLETED` 且尾款未就绪 →「设计已完成 · 尾款办理中」。

## 8. 首尾款进度接口(`franchise-api`)

```java
public interface DesignFeeProgressApi {
    /** 财务核实后写入;只接受当前提交版本,已写入的不会被清除 */
    void markFirstReady(long commissionId, int submissionVersion);
    void markTailPaid(long commissionId, int submissionVersion);    // 门店已付足尾款
    void markTailReady(long commissionId, int submissionVersion);   // 门店已付足且总部已核实到账
}
```

- 就绪口径来自 `transfers-v2.js` 的 `condition`:门店实付 ≥ 应付,且总部实收 ≥ 应付;只统计本提交版本的款项。
- 实现在 `franchise-commission`,写入时推进委托 `revision` 并记命令事件(执行人为财务人员的岗位)。M3 财务模块在核实到账的同一事务内调用。
- M2 没有调用方;集成测试直接调用它模拟到账。
