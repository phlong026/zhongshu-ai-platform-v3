## 4. 问题清单

### P2-1 新脚本依赖未入库的 6.4MB fixture，干净检出必失败

- **位置**：`scripts/verify-engineering-site-flow-native.cjs:10`
- **现象**：`const scenes=JSON.parse(fs.readFileSync('qa/engineering-records-20261021/page-scenes.json','utf8'))`。该文件 6.4MB，`git ls-files qa/engineering-records-20261021/` 返回空，`.gitignore:7` 的 `qa/` 规则命中它——**从未入库**。脚本在第 10 行、任何 `try` 之前同步读取，文件不存在即抛 `ENOENT`，连 `results.json` 都不会生成。
- **影响**：任何人（含 CI、含接手者）clone 后执行该脚本 100% 失败，且失败信息是 `ENOENT: no such file or directory`，不指向"你需要先跑某个上游脚本生成 fixture"。这份验收证据因此**只对作者本机有效**。
- **补充**：既有脚本 `verify-engineering-records-native.cjs:30` 也读同一个 fixture，属既有模式，不是本轮首创。但既有脚本有配套的 `prepare:engineering:record-flow:native` 入口（`package.json`），新脚本**既无 prepare 也无入口**，隐蔽性更高。
- **建议**：三选一——(a) 脚本头部加前置检查，文件缺失时打印"请先执行 `npm run prepare:engineering:record-flow:native`"并以专用退出码退出；(b) 把 fixture 精简成只含本脚本用到的 4 个场景（prepare/site/collect/node）后入库；(c) 在 `package.json` 里定义一条 `prepare:*` 串起来。推荐 (a)+(c)，成本最低且不增加仓库体积。

### P2-2 新脚本没有 npm 入口，不在任何回归链路里

- **位置**：`package.json` scripts 段（119 条，无一条指向 `verify-engineering-site-flow-native.cjs`）
- **现象**：全仓所有 native 脚本都有 `check:*:native` 入口（如 `check:engineering:record-flow:native`、`check:engineering:corrections:native`），并大多被 `check:native:all`（`scripts/audit-native-all.cjs`）汇总。新脚本两条都没有，只能靠人记住环境变量名手工敲 `ENGINEERING_SITE_WS=ws://... node scripts/...`。
- **影响**：这个脚本保护的是本轮四个新功能（模板生成、逾期标签、催款分级、拍照入口）。没有入口 = 没人会跑 = 下次改动这四个功能时不会有任何红灯。等于**写了测试但没接进测试体系**。
- **建议**：加 `"check:engineering:site-flow:native": "node scripts/verify-engineering-site-flow-native.cjs"`，并确认 `audit-native-all.cjs` 的清单是否按 `package.json` 扫描；若是硬编码清单，同步加一条。

### P2-4 脚本直写 storage 伪造身份与归属，9 项断言无一条越权用例

- **位置**：`scripts/verify-engineering-site-flow-native.cjs:24`（`grantOwner`）、`:42`（覆写 `session.role`）
- **现象**：
  - `:42` 在真实 UI 登录完成后，直接 `wx.setStorageSync('zhongshu-account-v1', {...session.role=r})`，把会话角色改成目标岗位。脚本头部 `:3-4` 对此有说明（"真实UI的身份切换页在本环境渲染不稳定"），属知情取舍。
  - `:24` `grantOwner()` 把**所有** `recordFlow` 项目的 `managerId`/`assignedEngineerId` 一律改成 `engineering-dual`，同时把 `zhongshu-business-v3` 里所有带 `projectId` 的客户 `managerId` 也改成同一人。
- **影响**：这两处合起来，**"工程人员只能看到自己负责的项目"这条对象级权限在测试中被完全抹平**。若某天有人把 `pages/build/projects/index` 的 owner 过滤删掉，页面会列出全部项目——`grantOwner` 已经把所有项目都变成了"自己的"，断言 `:84` 的 `cards.some(c=>c.pace==='已逾期1天')` 依然通过。同样，角色被直写覆盖后，`own`/`canEdit` 这类基于角色的门禁即使写错也不会被发现。

- **建议**：补 1 条**不调用 `grantOwner`、不覆写 `role`** 的用例：以 `engineering-dual` 正常登录，直接 `reLaunch` 到**他人负责**项目的 `record` 页，断言页面给出拒绝态（`data.error` 非空或 `own===false` 且保存按钮不渲染）。这条用例不需要身份切换页稳定，成本很低，却能覆盖本轮唯一缺失的评审维度。

### P3-1 恢复断言在 try 之外，结果文件与退出码可能自相矛盾

- **位置**：`scripts/verify-engineering-site-flow-native.cjs:111` 与 `:113-116`
- **现象**：`:111` 在 `try` 内最后一行把 `results.result='passed'`；`:113-116` 的存储恢复校验在 `try/catch` **之外**。若 `restored` 为 `false`，`:116` 的 `assert` 抛出，直接跳到 `:120` 的兜底 catch，`:117` 的 `results.errors=errors; save(); await mp.disconnect()` **全部被跳过**。
- **影响**：磁盘上的 `site-flow-results.json` 停留在最后一次 `pass()` 时的快照——`result:"passed"`、无 `restored` 字段；而进程退出码是 1。读 JSON 的人会以为全过，看 CI 的人会看到红灯，两者矛盾。同时 devtool 会话不会被 disconnect，可能影响下一次连接。
- **建议**：把 `:113-119` 整段挪进 `try`（或在 `finally` 里做恢复 + `save` + `disconnect`），并把 `results.result` 的赋值移到恢复校验之后。

### P3-2 `dataIndex` 传了 8000ms 超时，但 `until` 只接受两个参数

- **位置**：`scripts/verify-engineering-records-native.cjs:14` 调用 `until(fn,label,8000)`；`:15` 定义 `async function until(fn,label){const end=Date.now()+30000;...}`
- **现象**：`until` 签名只有 `(fn,label)`，第三个实参被静默丢弃，实际超时恒为 30s。
- **影响**：`findIndexBy` 想表达的"这个列表 8 秒内没出来就算失败"没有生效。真正列表为空时，每次调用白等 30 秒才报错，一个场景里两处调用就是 1 分钟。不产生错误结论，只拖慢失败路径。
- **建议**：`until` 加 `ms=30000` 形参；或把 `dataIndex` 里的 `8000` 删掉，别留一个看起来生效其实没生效的参数。

### P3-4 `templates` 未做空值保护，缺字段时报 TypeError 而非可读断言
