## 4. 问题清单

### P1（必须修）

#### P1-1　开发控制器缺 `@Profile`，生产可匿名建组织（第四轮起未修）

- **位置**：`平台程序/yudao-server/src/main/java/cn/iocoder/yudao/server/dev/FranchiseE2ESetupController.java:29-32`
- **现象**：类上只有 `@RestController` + `@RequestMapping` + `@PermitAll`，**没有 `@Profile`**。第 14 行 `import org.springframework.context.annotation.Profile;` 存在但从未使用——说明作者本意有、落笔漏了。类注释第 26 行却写着「生产严禁出现本控制器（@Profile 双重守卫）」，与代码相反。
- **影响**：`/admin-api/platform/dev-setup/franchise-e2e/**` 在 prod 也可匿名访问，可一键建总部/门店、建任职、模拟首尾款到账。这是本仓最严重的一类越权口子。
- **佐证**：同目录 `DesignDevController.java:41` 有 `@Profile("local")`、`SmsDevController.java:25` 有 `@Profile("local")`，唯独此文件缺失。
- **建议**：补 `@Profile("local")`（与 `DesignDevController` 同口径）。这是 1 行改动。

#### P1-2　`collect` 锁序与设计文档写反，与 `void_` 构成死锁环

- **位置**：`平台程序/domains/franchise/franchise-sales/src/main/java/cn/iocoder/yudao/module/franchise/sales/SaleContractService.java:228`（`stages.lockById`）、`:233`（`contracts.lockById`）
- **现象**：`collect` 先锁 **stage** 行、再锁 **contract** 行。而设计文档 `06-B2板块B业务交易流-需求与验收.md:57` 明确要求「collect 全链同事务+统一锁序（**先合同行锁后 stage 行锁**，void 同序）」。代码与文档相反。
- **影响**：`void_`（`:181` `lockContract` 持合同锁 → `:198-200` 软删 PENDING stage 取 stage 行锁）与 `collect` 形成 **contract→stage** 与 **stage→contract** 的交叉等待。销售办理回款、老板同时作废同一合同，PostgreSQL 会 `deadlock detected`（40P01），Spring 转 `DeadlockLoserDataAccessException`，未被业务码捕获 → **500**。
- **建议**：`collect` 内改为先用 `stage.getContractId()` 锁合同、再锁 stage。但 stage 的 `contractId` 需要先读一次 stage（可无锁 `selectById` 取 `contractId` → 锁合同 → 锁 stage → 重新校验），与文档锁序一致。

### P2（应当修）

#### P2-1　`Long != Long` 引用比较，`revision` 校验在 ≥128 时必然误判

- **位置**：`SaleContractService.java:164`（`sign`）、`:192`（`void_`）
- **现象**：`contract.getRevision() != revision`，两侧都是 `Long`（`SaleContractDO.revision` 为 `Long`，方法入参 `Long revision`）。Java 对两个包装类型不做拆箱，`!=` 比较的是**引用**。字节码为 `if_acmpeq`（见 §1.3）。
- **影响**：当前之所以「能用」，是因为 `Long` 缓存 -128..127：`revision` 从 1 起、MyBatis 与 Jackson 都经 `Long.valueOf` 装箱，小值命中同一缓存实例。**一旦 revision 涨到 128（或换 JDBC/序列化实现），`sign`/`void` 100% 返回「版本冲突」，合同签订与作废功能整体失效**，且现象是"合法请求被拒"，极难排查。
- **建议**：`!contract.getRevision().equals(revision)` 或 `contract.getRevision() != revision.longValue()`。同时排查同源模式：`FinReceiptService.java:142`（`Integer` 对 `Integer`）是同一写法，属存量（非本轮引入），一并改掉。

#### P2-2　`create` 的幂等重放排在「已有有效合同」检查之后

- **位置**：`SaleContractService.java:106-114`
- **现象**：先 `selectActiveByCustomer` 判重（`:106`）→ 再 `commands.replayed`（`:111`）。同一 `Idempotency-Key` 的第二次请求会在判重处直接抛 `CONTRACT_DUPLICATE`，永远走不到重放分支。
- **影响**：客户端网络超时重试（这是幂等键存在的唯一理由）拿到的是「该客户已有一份有效主合同」，而不是首次结果。调用方无法区分"我上次其实成功了"和"真的重复"。
- **建议**：把 `replayed` 提到 `selectActiveByCustomer` 之前（与 `SaleRequirementService.create:48` 的正确顺序对齐）。

#### P2-3　金额非法复用「合同重复」错误码

- **位置**：`SaleContractService.java:100-103`
- **现象**：`totalCents<=0 || firstCents<=0 || firstCents>totalCents || totalCents>MAX` 时 `throw exception(CONTRACT_DUPLICATE)`，即 1_113_000_006「该客户已有一份有效主合同（作废后方可重签）」。行内注释自认「金额非法复用合同码段——由 AC 断言区分」，但 AC 只能断言"返回了 006"，无法让用户看懂。
- **影响**：用户填错金额（如首款大于总额）会被告知"已有合同"，按提示去作废合同，越走越远。
- **建议**：新增 `1_113_000_007 CONTRACT_AMOUNT_INVALID`（`FranchiseSalesErrorCodes` 段内顺延，不与既有冲突），e2e 断言同步改。

#### P2-4　幂等内容指纹被截断为 32 位 `hashCode`

- **位置**：`SaleContractService.java:281-285`（`fingerprintOf`）
- **现象**：`DigestUtil.sha256Hex(canonical).hashCode()` —— 取 64 位十六进制串的 Java `String.hashCode()`，**有效信息只剩 32 位**。设计文档 `06:224` 要求的是「完整 sha256 摘要」。
- **影响**：32 位空间在约 6.5 万次不同内容后碰撞概率过半。一旦碰撞，`(method, transactionNo, receivedDate)` 完全不同的两次请求会被判定为"同键同内容"，静默返回首次收据，**后一笔真实回款丢失**。
- **建议**：直接用 `sha256Hex` 字符串（或取其前 32 hex 字符）作为指纹，不要过 `hashCode()`。

#### P2-5　`items.main` 类型畸形 → `ClassCastException` → 500

- **位置**：`SaleQuoteService.java:60-63`
- **现象**：`(List<Map<String,Object>>) (List<?>) items.getOrDefault("main", List.of())`。若客户端传 `"main": "abc"`，中间 `(List<?>)` 强转即抛 `ClassCastException`；若传 `["a"]`，在 `SaleQuoteMath.normalizeRows:33` 的 `Map<String,Object> row = rows.get(i)` 处抛。两者都不在业务异常体系内。
- **影响**：任何畸形 `items` 都返回 500 而非 400/1_113_000_001，前端只能显示"操作失败"，日志被 CCE 淹没。这是用户可直接触发的 500。
- **建议**：取 `items.get("main")` 后先 `instanceof List` 判定，不符即 `throw exception(QUOTE_TOTAL_INVALID)`；行元素同样先判 `instanceof Map`。

#### P2-6　并发创建触发唯一索引冲突，未转译为业务码

- **位置**：`SaleContractService.java:106-121`（依赖 `uk_fr_sale_contract_active`）、`SaleRequirementService.java:52-59`（依赖 `uk_fr_sale_requirement_version`）
- **现象**：两处都是「先 SELECT 判重/取最大版本，再 INSERT」，中间无锁。并发下第二个请求通过 SELECT 检查后在 INSERT 撞唯一索引，抛 `DuplicateKeyException`，未被捕获。
- **影响**：双端同时点提交 → 500。DB 兜底保证了数据正确，但错误语义完全丢失（用户看到"系统错误"而非"已有合同"/"版本冲突请重试"）。
- **建议**：捕获 `DuplicateKeyException` 按约束名分别转 `CONTRACT_DUPLICATE` / 重试一次取新版本号。

#### P2-7　控制器直接返回 DO

- **位置**：`SalesController.java:96`（`List<SaleRequirementDO>`）、`:123`（`List<SaleQuoteDO>`）、`:269`（`SaleDeliveryDO`）
- **现象**：三个查询端点把 DO 原样序列化给前端。对比同文件 `:143` `createContract` 用 `Map.of(...)`、`:159` `contractsList` 用显式 `LinkedHashMap`，风格自相矛盾。
- **影响**：DO 加字段即等于改接口契约（DB 内部字段泄漏到前端）；后续加 `tenantId`/`deleted` 之类的列会直接暴露。同时与「控制器不得直接返回 DO」的既有规矩相悖。
- **建议**：补 `SaleRequirementView` / `SaleQuoteView` / `SaleDeliveryView` 三个 record + 静态 `of()` 工厂（`926138c` 的 `Customer::of` 已是本仓正确范式）。

#### P2-8　（v3）财务登记每次提交都换新幂等键，网络重试会重复记账

- **位置**：`miniprogram/pages/admin/finance-desk/platform-actions.js:84`（`const idem = financeApi.idemKey(type);`）+ `miniprogram/api/finance.js:15-17`（`idemKey` 每次 `randomHex()`）
- **现象**：`idemKey()` 是纯随机生成，`submitRegister` 在**每次点击提交时**重新调用。失败后 `registerBusy` 在 `.finally` 复位，用户可以再点一次，此时拿到的是**全新的键**。
- **影响**：后端按新键受理 → 同一笔收款/付款/退款/应付被登记两次。财务账重复，且因为键不同，后端幂等三层全部失效，DB 唯一索引也拦不住（`source_ref` 不同或为 null）。这是**会产生错账的缺陷**。
- **对照**：同一批次的 CRM 侧做对了——`platform-crm.js:167` `commandKey` 由 `workflow/index.js:platformCommand` 缓存在 `__cmdKeys`，只在成功后 `platformDropCommand` 丢弃。财务侧应照此实现。
- **建议**：`submitRegister` 首次进入时生成键并挂在 `this.__finCmdKeys[type]`，成功才清除；失败保留以便同键重试。
