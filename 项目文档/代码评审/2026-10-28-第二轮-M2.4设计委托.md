## 1. 总体结论

**M2.4 是全项目到目前为止完成度最高的一块。** 状态机与设计文档 §7 逐条吻合（含"移交退回后不能再登记修改意见"这类细节），首尾款进度按 §8 用"推"而非"拉"，自批拦截、门店无其他老板、幂等重放、设计行政字段裁剪都落到了实现和测试里。`scheme_snapshot` 冻结参考方案、`feeSignature` 让审批内容一变就作废，这两处是加分项。

**但接口层明显退步。** 上一轮在 CRM 指出的"控制器返回 DO"，这一轮复制到了委托模块；更严重的是新增了一个**用 `Map` 接参 + 手工解析的万能命令端点**，把类型错误变成 500，并把三个权限用 OR 糊在一个端点上。

| 等级 | 数量 | 说明 |
|---|---|---|
| P1 | 3 | 万能命令端点（类型错误 500 / 权限粒度失效）、财务进度接口无调用方校验 |

**结论：模块可以继续往下做（M2.5 待办），但接口层建议在 M2.7（小程序接入）之前返工。** 现在改是改一个 controller，等小程序按这个契约写完再改，是改前端 + 后端两处。

## 3. 问题清单

### P1-A　万能命令端点：`Map` 接参 + 手工解析，类型错误直接 500

**位置**：`CommissionController.java` 的 `command(...)` 及其 `str()` / `bool()` / `packet()` 辅助方法

```java
@PostMapping("/commissions/{id}/commands/{action}")
public CommonResult<Detail> command(@PathVariable long id, @PathVariable String action,
                                    @RequestBody java.util.Map<String, Object> body, ...)
```

**现象**：`Integer.parseInt(String.valueOf(body.get("dispatchSeq")))`、`Long.parseLong(...)`、`LocalDate.parse(...)` 对任意客户端输入没有任何保护。

**影响**
- `{"dispatchSeq": "abc"}` → `NumberFormatException` → **500**（应为 400 + 明确提示）
- `{"confirmationDate": "2026/10/28"}` → `DateTimeParseException` → **500**
- `{"managerUserId": 1.5}` → `NumberFormatException` → 500
- 失去 Bean Validation、Swagger 文档、编译期类型检查；同一模块其他 5 个接口都用 record + `@Valid`，此处是唯一例外

**建议**：按 action 拆成 6 个类型化端点（`/design-complete`、`/design-dispatch`、`/feedback`、`/packet`、`/packet-return`、`/packet-receive`），各自用 record + `@Valid`。如果坚持单端点，至少把解析失败统一转成 400 业务错误。

---

### P1-B　一个端点三种权限 OR，HTTP 层失去最小权限

**位置**：`CommissionController.java`

```java
@PreAuthorize("@post.has('franchise:commission:submit') or @post.has('franchise:commission:design') "
        + "or @post.has('franchise:commission:receive')")
```

**现象**：`action` 由路径变量决定，但权限是"三者有其一"。业务员（有 `submit`）可以调 `design-complete`；工程人员（有 `receive`）可以调 `packet-submit`。

**当前不会越权**——service 层二次校验（`isDesignAdminOf` / `canWrite`）挡住了。但这是**把安全边界从声明式降级为命令式**：
- 任何一次 service 校验被放宽（比如将来允许业务负责人代设计行政确认完成），这个端点立刻变成提权通道；
- 审计时看 `@PreAuthorize` 无法回答"谁能确认设计完成"，必须读 service。

**建议**：action → permission 的映射写在一处（枚举或 switch 里的显式断言），或直接拆端点。

---

### P1-C　财务进度接口无调用方身份校验，也无状态守卫

**位置**：`CommissionService.markProgress`（实现 `DesignFeeProgressApi`）

```java
public void markFirstReady(long commissionId, int submissionVersion, PostSnapshot actor) { ... }
```

**现象**
- 只校验 `submissionVersion` 匹配，**不校验 `actor` 是否财务线岗位**；
- **不校验委托状态**：`FEE_PENDING`（费用还没批）时也能写入 `first_ready_at`；
- `actor` 仅用于写命令事件留痕。

**影响**：M3 财务接入后，任何拿到该 Bean 的代码都能把"首款已核实到账"打上。由于 `design-complete` 以 `first_ready_at` 为前置，这等于绕过"钱没到不能开始设计"的唯一闸门。

**建议**：`markProgress` 内断言 `FranchiseRoles.has(actor, FINANCE)`（或 `FINANCE_LEAD`）+ 状态守卫（`DESIGNING` 才允许写首款就绪）。测试补一条"业务员调 markFirstReady 被拒"。

---

### P2-A　金额上限校验自身会抛未捕获异常

**位置**：`DesignPolicyService.requireAmount`

```java
static long cents(BigDecimal yuan) { return yuan.movePointRight(2).longValueExact(); }
...
|| cents(total) > TOTAL_MAX_CENTS) { throw exception(SUBMISSION_AMOUNT_INVALID); }
```

**现象**：`total = 1e30` 时 `stripTrailingZeros().scale()` 为负数（通过校验），随后 `longValueExact()` 抛 `ArithmeticException` → **500**，而不是 `SUBMISSION_AMOUNT_INVALID`。

**建议**：先 `compareTo(BigDecimal.valueOf(TOTAL_MAX_CENTS).movePointLeft(2))` 做范围比较，再转分；或 try/catch 转业务错误。

---

### P2-B　版本号在应用层 max+1，并发撞唯一索引 → 500

**位置**：`DesignPolicyService.save`（`maxVersion + 1`）、`HandoverService.submit`（`maxVersion + 1`）

**现象**：与上一轮 CRM 的 `saveScheme`（P2-3）完全同型——并发时撞 `uk_fr_design_policy_version` / `uk_fr_commission_handover_version`，抛 `DuplicateKeyException` 未捕获 → 500。

**说明**：这是**第三次出现同一模式**，建议抽一个 `nextVersion` 工具（或统一捕获转 `STATE_VERSION_CONFLICT`），否则每个新模块都会复现一次。

---

### P2-C　权限问题报成输入问题

**位置**：`DesignPolicyService.requireStoreBoss`

```java
throw exception(POLICY_INPUT_INVALID); // "请填写总额、首款…、收款方和交付范围"
```

**现象**：非门店老板调用 `save` / `getCurrent` 时，提示用户"请填写总额…"，实际是没权限。

**建议**：加 `POLICY_FORBIDDEN`（"标准设计费用由门店老板配置"）。

---

### P2-D　`scheme_snapshot` 可能不是合法 JSON

**位置**：`CommissionService.schemeSnapshot` / `appendScheme`

```java
snapshot.append("\"").append(kind).append("\":")
        .append(scheme.getPayload() == null ? "null" : scheme.getPayload());
```

**现象**：`fr_customer_scheme.payload` 是 CRM `saveScheme` 接受的任意 TEXT（`CustomerService.normalize` 只校验长度 ≤ 64KB，**不校验 JSON**）。把未校验字符串直接拼进 JSON，一旦 payload 不是合法 JSON（或含未转义引号），`scheme_snapshot` 就是坏 JSON，下游解析会失败。

**建议**：CRM 侧对 `payload` 做 JSON 合法性校验；或此处用 `JsonUtils` 组装、payload 作为字符串值转义存入。

---

### P2-E　委托列表把全部客户 id 塞进 `IN`

**位置**：`CommissionService.visibleCustomerIds` → `CommissionAccess.visibleTo`

**现象**：每次列表查询先 `customerMapper.selectVisible(CustomerAccess.visibleTo(post))` 取出**该身份可见的全部客户**（老板＝全店客户），再拼成 `customer_id IN (...)`。

**影响**
- 老板路径已有 `company_id = ?` 过滤，这个 `IN` 完全冗余；
- 客户量到几千时，SQL 文本与解析开销明显，且 `selectVisible` 无分页（全表拉取）。

**建议**：按岗位分派——老板只加 `company_id`；业务员/负责人仍走客户集合（或改成 `EXISTS` 子查询）。数量大时用 `IN (SELECT ...)` 而非应用层拼 id。

---

### P2-F　客户端声称的方案版本号直接落库

**位置**：`CommissionService.submit` → `setPlanVersion(input.planVersion()).setFacadeVersion(input.facadeVersion())`

**现象**：`budgetVersion` 用的是服务端查到的真实版本（正确），但 `planVersion` / `facadeVersion` 直接用客户端传入值，不校验该版本是否存在。

**影响**：可写入不存在的版本号，追溯时指向空气。

**建议**：与 budget 同样取 `latestScheme(...).getVersion()`，忽略客户端值。

---

### P2-G　控制器直接返回 DO / 内部 record（上一轮 P1-2 的复制）

**位置**：`CommissionController` 返回 `PageResult<CommissionDO>`、`Detail`（内含 4 个 DO + `ApprovalDO`）

**说明**：上一轮已在 CRM 提出（报告 P1-2），本轮在第二个模块原样出现，说明缺的是**团队约定**而非单点疏忽。`Detail` 还带出 `ApprovalDO`（平台审批实体），跨模块实体外泄。

### P3（一致性/可读性）

1. `allowedActions` 返回 `"fee-decide"`，命令日志写 `"commission-fee-decide"`；前端按 actions 渲染按钮，后端按 command 审计，两套命名容易对不上。
2. `detail()` 用 `submissions.stream().map(s -> s.setTotalCents(null)...)` 原地改 DO 做字段裁剪，副作用式写法；同事务内二次查询可能读到被改过的对象。建议 VO 或复制。
3. `CommissionAccess.canRead` 不含"移交接收人"分支（由 `requireReadable` 单独补），语义不完整，新调用方容易漏。
4. `soleHeadquarters()` 要求**恰好一个**总部组织，多于一个时全员无法提交（单品牌假设，建议写进文档或改为配置）。
5. `fr_design_policy.approved_by_user_id` 实际是"保存人"，命名暗示审批人。
6. `command` 未知 action 抛 `COMMISSION_STATE_INVALID`（"当前状态不允许"），应为 404/400。
