## 四、问题清单

### P1-1 设计项目列表接口在"无下一页"时必抛 NPE → HTTP 500

- **文件**：`平台程序/domains/franchise/franchise-design/.../controller/admin/DesignAccessController.java:153`
- **现象**：`return success(Map.of("list", page.list(), "nextCursor", page.nextCursor()));`
  `Map.of` 不接受 null value。而 `nextCursor` 在无下一页时为 null——`DesignProjectService.java:1368`：
  `String next = hasMore ? String.valueOf(...) : null;`
  默认 `limit=20`，门店项目数少于 20 时 `hasMore=false` → 首次调用即 NPE → 全局异常处理返回 500。
- **影响**：`GET /franchise/design/projects`（不带 customerId 的"我的方案"列表）**基本不可用**。同一控制器第 144-153 行的另一分支 `listProjectsForCustomer` 用的是 `LinkedHashMap` 并显式 `put("nextCursor", null)`（`DesignAccessService.java:147`），说明作者知道该字段可为空，只是这一处漏了。
- **建议**：改用 `LinkedHashMap`，或 `Map.of("list", page.list(), "nextCursor", page.nextCursor() == null ? "" : page.nextCursor())`。同类风险：`DesignAccessController.java:139/176/192/253/284` 均为 `Map.of`，当前各字段为原始类型或必填，暂不触发，但建议统一改用 `LinkedHashMap` 以免后续加可空字段时复发。

### P1-2 `FranchiseE2ESetupController` 仍缺 `@Profile`，prod 匿名可达（上一轮 P1 未闭环）

- **文件**：`平台程序/yudao-server/src/main/java/cn/iocoder/yudao/server/dev/FranchiseE2ESetupController.java:29-32`
- **现象**：类上只有 `@Tag` `@RestController` `@RequestMapping("/admin-api/platform/dev-setup/franchise-e2e")` `@PermitAll`，**没有 `@Profile("local")`**（`import ...annotation.Profile` 在第 16 行导入但从未使用，是死导入）。类注释第 25-26 行仍写着"只在 local profile 且非 prod 下注册……@Profile 双重守卫"。
- **本轮新增证据**：同一批的 `DesignDevController.java:37-44` 注释直言"既有控制器缺 profile 守卫的事实已登记 00 预留，**本批不修不继承**"——即团队已知此问题并选择不修。作为对照，`SmsDevController.java:30` 与 `BankFlowDevController.java:25` 都正确加了 `@Profile("local")`，说明团队掌握该手法。
- **影响**：`@PermitAll` 在 yudao 安全配置中对匿名请求放行，因此生产环境任何人可 `POST /admin-api/platform/dev-setup/franchise-e2e/**` 创建总部/门店组织、给任意 userId 指派岗位、模拟首尾款到账。这是账号体系与财务数据的直接入口。
- **建议**：加 `@Profile("local")`（一行），或改为 `@ConditionalOnProperty`；同时删除死导入。若短期不修，至少应在部署清单里加"prod 启动后校验该 Bean 不存在"的断言。

### P1-3 实收修订历史接口无组织过滤，跨组织可读

- **文件**：`平台程序/domains/franchise/franchise-finance/.../controller/admin/FinanceController.java:151-156`；
  `dal/FinReceiptRevisionMapper.java:11-14`（`selectByReceipt` 只按 `receiptId` 过滤）
- **现象**：`GET /franchise/finance/revisions?receiptId=X` 只校验 `@post.has('franchise:fin:query')`，随后 `revisionMapper.selectByReceipt(receiptId)` 无 `company_id` 条件。

### P2-1 business 实收的并发唯一性只有注释，没有索引（未提交代码 vs 已提交迁移）

- **文件**：`FinReceiptService.java:180-183`（**未提交**的 `registerBusinessReceipt`）、`V20261101.804__fr_finance.sql:40`（已提交索引）

### P2-2 付款登记从不写 `fr_fin_txn_no`，流水号防重对付款完全失效

- **文件**：`FinPaymentService.java:78-84`；对照 `V20261101.804__fr_finance.sql:71` 注释与 `:117-128` 建表

- **建议**：在 `register()` 内按 `FinRefundService` 的模式补 `txnNoMapper.find(companyId, txn)` + `insert(ownerType='payment')`；并对已产生的重复数据做核对脚本。

### P2-4 退款列表的 receiptId 过滤用 `==` 比较两个 `Long`

- **文件**：`FinanceController.java:221`
- **现象**：`rows = rows.stream().filter(r -> r.getReceiptId() == receiptId).toList();`，`r.getReceiptId()` 与 `receiptId` 均为 `Long` 包装类型 → 引用比较。`receiptId > 127` 时恒不相等。
- **影响**：`GET /franchise/finance/refunds?receiptId=X` 在雪花 ID 场景下**恒返回空列表**，前端会误显示"该收款无退款"，而实际存在退款 → 可退余额判断被误导。
- **建议**：改 `Objects.equals(r.getReceiptId(), receiptId)`。全仓建议加一条静态检查规则（spotbugs 的 `ES_COMPARING_STRINGS_WITH_EQ` 类规则对 Long 有对应项）。

### P2-5 员工停用是账号级全局操作，但校验只有"本组织有任职"

- **文件**：`StaffOrgAdminController.java:167-179`；`YudaoSystemDirectory.setUserActive` → `adminUserService.updateUserStatus`

### P2-7 金额入参无正数/上限校验，全靠 DB CHECK 兜底
