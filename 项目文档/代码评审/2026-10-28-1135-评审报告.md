### P1-1 `dev-setup` 控制器缺 `@Profile`，prod 匿名可写

**位置**：`后端程序/yudao-server/src/main/java/cn/iocoder/yudao/server/dev/FranchiseE2ESetupController.java:14`（未使用的 import）、`:25-26`（注释）、`:28-32`（类注解）

```java
// :25-26 注释声称
* 只在 local profile 且非 prod 下注册；@PermitAll 是因为搭建发生在员工登录之前。
* 生产严禁出现本控制器（@Profile 双重守卫，与 StubWechatStaffClient 同口径）。

// :28-32 实际注解 —— 没有 @Profile
@Tag(name = "开发 - 加盟域端到端搭建")
@RestController
@RequestMapping("/admin-api/platform/dev-setup/franchise-e2e")
@PermitAll
public class FranchiseE2ESetupController {
```

**现象**：
1. `org.springframework.context.annotation.Profile` 被 import 了（`:14`）却从未使用——说明注解本来打算加，漏了。
2. `YudaoServerApplication:17` 扫描 `cn.iocoder.yudao.server`，本控制器在任何 profile 下都会注册。
3. `YudaoWebSecurityConfigurerAdapter:168-169` 判定 `handlerMethod.getBeanType().isAnnotationPresent(PermitAll.class)` 即加入 permitAll 列表，**与 profile 无关**。所以 `application-local.yaml` 里那条 `permit-all_urls` 是冗余的，真正让接口匿名的是类上的 `@PermitAll`。
4. 同包 `DevDataSeeder:23` 写的是 `@Profile("zsdev & !prod & !production")`；注释里点名的 `StubWechatStaffClient` 用的是**运行时** `environment.acceptsProfiles` 判断（`:20`），也不是 `@Profile`。两种口径都不是"什么都不写"。

**影响**：prod 部署后，`POST /admin-api/platform/dev-setup/franchise-e2e/setup` 无需任何凭证即可调用，一次调用会创建 1 个总部/1 个门店组织、2 个团队、5 个后台用户、5 条任职；`/fee-settlement` 更严重——它直接把 `first_ready_at` / `tail_paid_at` / `tail_ready_at` 写成当前时间，而这三个字段是设计 §7 里"钱没到不能开始设计 / 不能下发"的**唯一闸门**。等于生产环境存在一个匿名接口，可以跳过财务核实把任意委托推进到设计完成、成果下发。

**建议**：类上加 `@Profile("local & !prod & !production")`（与注释自述一致），或按 `StubWechatStaffClient` 的口径在方法内做运行时判断；同时补一条断言"dev 包下的控制器必须带 profile 守卫"的测试（`ControllerWiringContractTest` 扫的是 `cn.iocoder.yudao.module`，扫不到 `server.dev`，见 P3-7）。

### P2-1 `fee-settlement` 兜底身份是伪造快照，审计留痕落到 `org_id=0`

**位置**：`FranchiseE2ESetupController.java:91-96`

```java
var actor = requestPost.orElseGet(() -> {
    AdminUserDO financeUser = adminUserMapper.selectOne(AdminUserDO::getMobile, "1380000004");
    long financeUserId = financeUser == null ? 0L : financeUser.getId();
    return new PostSnapshot(0, financeUserId, 0, "store", "finance", null, false, Set.of());
});
```

**现象**：
- 手机号 `1380000004` 写死，而 `setup()` 的 `mobilePrefix` 是**可传参**的（`:67-68`）。只要调用方传了非默认前缀（比如 `batch` 之外想换号段），`selectOne` 必然返回 null → `financeUserId=0`。
- 即便查到人，`orgId` 仍固定为 `0`、`postId` 固定为 `0`、`managedTeamIds` 为空。
- `FranchiseCommands.record()`（`FranchiseCommands.java:44-52`）会把这个快照原样写进 `pf_command_event`：`org_id=0`、`actor_post_id=0`、`actor_role_code='finance'`。该表 `org_id BIGINT NOT NULL` 且无外键（`V20261022.701__pf_command_event.sql:13`），**不会报错，能落库**。
- 审计索引是 `idx_pf_command_event_org_time (org_id, occurred_at)`。`org_id=0` 的行按门店查永远查不到，等于"首尾款到账"这条最敏感的操作在门店审计视图里是隐形的。

**影响**：M2 验收期间产生的到账事件在审计上不可归属；如果这套兜底被沿用进 M3 联调，会留下无法追溯的"钱已到账"记录。

**建议**：兜底改为**拒绝**——没有 `X-Post-Id` 就直接返回业务错误（例如"请以财务岗位身份调用"），而不是伪造一个 orgId=0 的岗位。若确实需要脚本免登录，把财务岗位 id 通过 setup 返回值带出来，由脚本显式带上 `X-Post-Id`（脚本第 7 步本来就是这么调的，兜底分支实际用不上）。

### P2-2 `permit-all_urls` 用列表覆盖，顶掉基础配置

**位置**：`yudao-server/src/main/resources/application-local.yaml:241-243`

```yaml
    permit-all_urls:
      - /admin-api/platform/dev-setup/**
```

**现象**：`application.yaml:295-296` 已定义 `permit-all_urls: [/admin-api/mp/open/**]`。Spring Boot 对**列表属性不做合并**，profile 文档里的同名列表会整体替换基础值。以 `local` 启动后，`/admin-api/mp/open/**` 不再免登录。

**影响**：本地环境若有公众号回调联调，会突然 401。生产不受影响（`application-prod.yaml` 不含该键），因此不升级为 P1。这类"加一行配置、静默删掉另一行"的问题很难在联调时定位。

**建议**：改成索引写法 `permit-all_urls[1]: /admin-api/platform/dev-setup/**`，或在同一个 `application.yaml` 里合并后按 profile 开关。另外，若采纳 P1-1 的 `@Profile`，这一行可以直接删掉（`@PermitAll` 已经生效）。

### P2-3 e2e 脚本不可重复执行

**位置**：`后端程序/script/franchise-m2-e2e.py:118-120`（第 4 步）、`:158-166`（第 12 步）

```python
lead = act(sales, 'POST', '/franchise/leads', {...'phone': '13900001111'...})
assert lead['result'] == 'CREATED', lead
```

**现象**：`batch` 只让组织名唯一，客资手机号 `13900001111` / `13900002222` 是写死的。`LeadService:36-37` 的登记结果是 `CREATED | LINKED | LINK_REQUIRED`，第二次运行时同一手机号、同一业务员 → `本人经办` 成立 → 走关联分支返回 **`LINKED`**，`assert ... == 'CREATED'` 立刻失败。第 12 步更彻底：`13900002222` 上一轮已有一张 `FEE_PENDING` 的委托，而 `commission-submit` 只允许"无委托或 `FEE_RETURNED`"，第二次提交直接 `STATE_INVALID`。

**影响**：`setup` 的注释写"保证脚本可重复执行"（`:46`、`:65`），实际只能跑一次。开发想复跑必须手工清库或改手机号——而"改手机号"要改的是脚本常量，等于每次都要改代码。

**建议**：手机号也带上 `batch` 后缀（如 `139` + batch 后 8 位），或脚本入口接受 `--phone-prefix`；`batch` 已由 `time.time()%10000` 生成（`:71`），把它同时用于手机号即可一次性解决。注意 11 位手机号格式约束。

### P2-4 `/setup` 对组织与团队不幂等

**位置**：`FranchiseE2ESetupController.java:70-75`

```java
java.util.List<Long> existingHq = orgService.listActiveOrgIds("headquarters");
long hq = existingHq.size() == 1 ? existingHq.get(0) : orgService.createOrg(...);
long store = orgService.createOrg("store", ...);        // 每次都建
long salesTeam = orgService.createTeam(store, null, ...); // 每次都建
long engineeringTeam = orgService.createTeam(store, null, ...);
```

**现象**：只有总部做了"存在即复用"，且判据是 `size() == 1`——一旦库里有 2 个总部组织（手工建过、或早期脚本留下的），就会再建第 3 个。门店与两个团队**无条件新建**，`@Operation` 里写的"幂等：手机号已存在则复用账号与任职"只覆盖了员工账号这一层。

**影响**：一天调试跑 20 次，库里多 20 个门店组织、40 个团队、每个用户多 20 条任职。这些孤儿组织是"启用"状态，会进入 `listActiveOrgIds` 等按组织类型查询的结果集；总部判据 `size()==1` 一旦被打破就永久失效。

**建议**：门店按 `(orgType, name)` 查存在即复用（`OrgService` 目前没有按名查的方法，需要补一个，或让脚本用固定 `storeName` + 存在则跳过）；总部判据从 `size()==1` 改为 `isEmpty() ? create : first()`，多出来的总部用日志告警而不是再建一个。

### P2-5 v3 把 248KB 的 xlsx 库静态 require 进页面首屏

**位置**：`miniprogram/pages/build/record/index.js:1`、`miniprogram/pages/build/schedule-import.js:4`

```js
// record/index.js:1
const R=require('...'),...,Files=require('...'),SI=require('../schedule-import');
// schedule-import.js:4
const XLSX=require('./vendor/xlsx.mini.min');
```

**现象**：`SI` 在页面模块顶层被 require，`schedule-import` 顶层又 require 了 248KB 的 vendored xlsx。小程序在**进入工程记录页**时就要解析这 248KB（不是按需、不是分包异步），而真正会点"从 Excel 导入"的用户是极少数。

**影响**：工程记录页是 M2 主链最高频入口，首屏多一次 248KB 脚本解析，低端机上会有可感知的进入延迟。

**建议**：改成 `importPlan()` 内 `const SI=require('../schedule-import')`（小程序支持函数内 require，且同一模块只解析一次）。这一行改动成本极低，收益是整个页面的常驻启动开销。
