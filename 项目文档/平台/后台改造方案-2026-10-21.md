# 众墅之家 AI 赋能平台 · 后台改造方案(平台底座 + 业务域)

> 日期:2026-10-21
> 输入:`zhongshu-ai-platform-v3-main/`(小程序,M0 起改名为 `小程序/`)、`管理后台/`、`后端程序/`(复制自众墅设计小程序)
> 方法:只读代码与文档分析,未运行、未改代码

## 0. 目标与已确认前提

**改造目标**:把现有后台(yudao 后端 + Vue3 管理后台)改造成**可复用的平台底座**。赋能小程序的门店协同业务作为**第一个业务域**接入;以后的其他业务域按同一套约定开发,直接复用组织、账号、权限、待办、审批、文件、AI 等平台能力。

| 决定 | 结论 |
|---|---|
| 与众墅设计小程序的关系 | 各自独立,后端分开。本后端改造为赋能平台专用;灵感库、AI 出图、预算的代码复用,数据各管各 |
| Web 后台的用户 | 第一阶段以**加盟商各部门**为主,较重的功能放到 Web;随后持续加入总部各部门 |
| 一期业务范围 | 组织与账号权限、业务主链到移交、工程与财务闭环、创作获客与绩效,四条线都做 |
| AI 视频、数字人、平台发布 | 一期只保存记录,不接真实 AI;AI 平面/立面/预算复用现有真实能力 |

## 2. 总体架构:三层

```
┌──────────────────────────────────────────────────────────────┐
│ 业务域层  domains/                                          │
│   加盟协同域 franchise(本期)   │  未来业务域 …(按约定接入)  │
│   客户/委托/工程/财务/绩效/方案     │                          │
├──────────────────────────────────────────────────────────────┤
│ 平台能力层  platform/  ← 所有业务域共用                      │
│   组织   账号与登录   对象授权   命令与事件   待办   审批中心 │
│   通知   文件   AI 能力   审计                                │
├──────────────────────────────────────────────────────────────┤
│ 框架底座  yudao-framework + system + infra(原样保留)        │
│   用户 部门 角色 菜单 数据权限 字典 文件 定时任务 日志        │
└──────────────────────────────────────────────────────────────┘
```

**分层原则**:

1. **底座不改**:yudao 的 system、infra、framework 原样保留,后续能跟上游升级。需要扩展时在平台层包一层,不改底座源码。
2. **平台层不含业务名词**:不出现「委托」「工程」「加盟商」,只提供通用能力和扩展接口。
3. **业务域只依赖平台层**:业务域之间不直接读对方的表,需要协作时通过对方 `api` 包或平台事件。
4. **一个域 = 一组后端模块 + 一组后台页面 + 一组菜单和角色模板 + 一组迁移脚本**,可以整体加入或拿掉。

## 3. 平台能力层(可复用部分)

| 平台模块 | 提供什么 | 基于 | 加盟协同域怎么用 |
|---|---|---|---|
| `platform-org` 组织 | 组织(公司)、团队、员工、岗位模板、兼岗、离岗交接、责任转交;组织类型可扩展(字典) | yudao 部门、用户、角色 | 组织类型 `headquarters`/`store`;13 个岗位作为本域岗位模板 |
| `platform-identity` 账号与登录 | Web 登录(手机号/密码/短信);小程序微信登录并绑定员工;**多小程序 AppID**;当前岗位切换 | yudao OAuth2 令牌、现有 `wechat_identity`(已有 `appid` 列) | 赋能小程序 `wxe584f6fad7b54487` |
| `platform-authz` 对象授权 | 组织范围自动过滤(`company_id`/`team_id` 数据权限规则);对象级规则扩展接口 `ObjectAccessPolicy`;通用规则:不能自批、不能自核、回避本人 | yudao 数据权限 | 移植 `authority-v2.js`:本人客户、本团队、指派人员、设计回避 |
| `platform-command` 命令与事件 | 命令基类(校验 → 新状态 → 事件)、`revision` 乐观锁、业务事件表、幂等键 | MyBatis | 每个小程序动作对应一个命令 |
| `platform-todo` 待办 | 待办投影扩展接口 `TodoProvider`;统一待办列表、计数、跳转地址(Web 与小程序各一个) | 平台事件 | 移植各模块 `tasks()` |
| `platform-approval` 审批中心 | 审批扩展接口 `ApprovalProvider`;审批记录、版本签名、审批人规则(如「本组织某岗位」) | 平台事件 | 正式报价、设计服务费、付款等金额事项,老板独占 |
| `platform-notify` 通知 | 站内消息、小程序订阅消息、公告 | 现有公告、消息代码 | 待办提醒、到账通知 |
| `platform-file` 文件 | 上传、凭据、图纸版本、访问授权 | yudao 文件 + 现有 COS 接入 | 付款凭据、施工图、交付资料 |
| `platform-ai` AI 能力 | AI 任务、生图、文本润色、调用记录与计费口径 | 现有 `ai-orchestration` + `ai-runtime` | AI 平面/立面;视频创作一期只存任务与作品 |
| 审计 | 操作日志、数据导出审计 | yudao 操作日志 + 现有 export 审计 | 全链路留痕 |

**为什么组织放在平台层**:几乎所有业务域都要回答「这个人属于哪个组织、什么岗位、能看哪些数据」。组织结构是通用的,岗位模板和组织类型则由各业务域注册,例如加盟协同域注册「总部 / 门店」和 13 个岗位。

### 3.1 组织模型:单一平台租户 + 部门树

此处修正文档 41 的「一个加盟商一个租户」建议。原因有两个:

- 加盟协同业务大量跨组织。总部设计行政要处理门店委托,总部财务要核实门店付款,小程序中有 60 处跨组织字段引用。按租户隔离,总部几乎每个操作都要绕开隔离。
- 岗位由平台和业务域统一定义,加盟商不需要自建角色。

```
平台(唯一租户)
├── 众墅之家总部            ← 组织,类型 headquarters
│   ├── 设计部 / 财务部 / 运营部   ← 团队
├── 湖北加盟商              ← 组织,类型 store(老板、门店负责人挂组织根)
│   ├── 业务部(可再分组)/ 工程部 / 财务部
└── …
```

- 组织 = 部门树第二层,扩展表记录组织类型、门店资料、启用状态。
- 业务表统一带 `company_id` 和 `team_id`;跨组织对象再带显式字段,如 `design_org_id`。
- 现有 `DataPermissionConfiguration` 已经把用户和部门管理限制在本部门子树,「门店老板只管本店人员」可以直接用。

### 3.2 身份模型:一个员工一个账号,Web 和小程序通用

- 员工即 yudao 后台用户,挂在所属组织或团队下,由老板或总部在 Web 上建档。
- 小程序微信登录后,用微信手机号匹配员工账号并绑定 openid,签发与 Web 相同的令牌。
- 没有员工档案的微信用户只能看游客页。
- 会话记录「当前岗位」,服务端校验该岗位确实属于本人,对应小程序的身份切换。
- Web 与小程序共用同一套角色、菜单权限和数据范围。

## 4. 业务域约定(以后开发新业务域照此执行)

| 约定项 | 规则 | 加盟协同域示例 |
|---|---|---|
| 域编码 | 小写英文,全局唯一 | `franchise` |
| 后端模块 | 放在 `后端程序/domains/<域>/` 下,每条业务线一个模块,另建一个 `<域>-api` 放对外接口 | `franchise-crm`、`franchise-commission` … |
| Java 包名 | `cn.iocoder.yudao.module.<域>.<业务线>` | `…module.franchise.commission` |
| 数据表 | 统一前缀 `<缩写>_`;必须带 `company_id`;走 MyBatis Mapper,不用手写 JDBC | `fr_customer`、`fr_commission` |
| 迁移脚本 | 独立 Flyway 目录 `db/migration/<域>`,每个脚本配回滚脚本 | `db/migration/franchise` |
| 接口路径 | 员工两端都走 `/admin-api/<域>/…`;`/app-api/<域>/…` 只留给 C 端(见 M1 设计第 2 节修正) | `/admin-api/franchise/commissions/{id}/commands/design-complete` |
| 权限码 | `<域>:<资源>:<动作>` | `franchise:commission:dispatch` |
| 菜单与岗位 | 由本域迁移脚本写入:一个一级菜单 + 本域岗位模板(角色) + 组织类型 | 一级菜单「加盟协同」;13 个岗位 |
| 平台能力 | 待办 `TodoProvider`、审批 `ApprovalService`、命令留痕 `CommandLog`、对象规则 `Access`、当前身份 `CurrentPost` | 全部使用 |
| 后台页面 | `管理后台/src/views/<域>/`、`src/api/<域>/`、`src/router/modules/<域>.ts` | `views/franchise/` |
| 启用方式 | `yudao-server` 引入该域依赖即启用;不引入则菜单和接口都不存在 | — |
| 跨域协作 | 只能调对方 `<域>-api` 或订阅平台事件,不读对方的表 | — |
| 测试 | 每个命令要有越权用例(其他组织、其他团队、本人自批) | 移植小程序 `scripts/` 的规则检查 |

**新建一个业务域的步骤**:复制域模板骨架 → 注册组织类型和岗位 → 建表和命令 → 实现待办、审批扩展接口 → 加后台页面 → 在 `yudao-server` 引入。组织、登录、权限、待办、审批、文件、通知都不用再做。

## 7. 改造后能实现的功能

**平台层面(以后所有业务域都能用)**

1. 一套组织、员工和岗位体系,Web 和多个小程序共用一个账号。
2. 服务端强制的三层授权:功能权限、组织范围、对象规则。
3. 统一待办中心、审批中心、消息通知、文件凭据和操作审计。
4. 新业务域按约定接入,不用重复建设以上能力。

**加盟协同域(本期)**

5. **真正的多人协作**:业务员提交委托后,总部行政、门店财务、总部财务、工程负责人各自在手机或电脑上收到待办并办理,数据实时一致。
6. **加盟商组织自管**:老板在 Web 上建团队、加员工、分岗位和兼岗、办离岗交接。
7. **门店之间数据隔离**:总部只看委托给总部的事项和全网汇总。
8. **规则由服务端强制执行**:本人客户、不能自批、不能自核、金额只能老板审批、设计回避,换设备或改本地数据都绕不过去。
9. **财务真实对账**:门店付款和总部到账分别登记、分别核实,项目账、往来账、结清可查可导出。
10. **重功能上电脑**:客户台账、施工计划、财务对账、报价单与报表导出、绩效配置在 Web 完成。
11. **AI 设计能力变成真的**:灵感库、AI 平面/立面、快速预算接入现有真实服务;视频创作先存作品和发布记录。
12. **全链路留痕**:每个动作都有人员、岗位、时间和版本,同时作为绩效来源。

**M0 范围调整说明(2026-10-22)**:原计划 M0 删除激活码、点数、充值。核查后发现它们和 AI 出图深度耦合:

- commerce 通过 infra 中的 `PointLedgerPort`、`PricingPort`、`UsagePricingPort` 给 AI 生成提供预扣、结算、退回;
- AI 生成入口还校验激活码授权(`design_access_grant`);
- 而「加盟商使用 AI 是否计费」尚未决定。

因此这三项留到 M1,与 AI 能力、登录改造一起处理,不在 M0 留下删一半的状态。另外,yudao 的 infra 模块里已被加入众墅专用代码(`module/infra/zhongshu/`),「底座不改」原则从 M1 起执行,这部分到时迁到平台层。

**计费能力去留决定(2026-10-28,用户确认)**:点数、充值、激活码**保留**,AI 对加盟商**继续计费**。因此 §1.2 与 §6.1 中「删除 commerce 点数/充值/虚拟支付/出图定价」「删除 identity 激活码」的处置作废,这些能力保留并按以下方式演进:计费口径统一收编到 `platform/platform-ai`(去耦合时保留预扣-结算-退回链路),加盟协同域经平台接口调用计费,不直连 commerce 表;管理后台对应页面(zs/accesscode、points、recharge、generation-pricing、usage-pricing)继续使用,后续按 §6.2 拆分时迁入平台目录而非删除。此决定同时解锁 `franchise-design`(灵感库、AI 平面/立面、快速预算),排入 M3 之后与工程财务并行评估。

M1 是关键:平台能力先稳定,后面的业务域才能放心复用。M1 涉及登录、授权和组织隔离,属于高风险代码,实施前出详细设计并人工评审。

## 9. 目录结构建议

### 9.1 现状问题

- `zhongshu-ai-platform-v3-main/` 是 GitHub 压缩包解出来的,**不是 git 仓库**,目录名带 `-main` 后缀。
- 三个部分平级散放,没有统一的仓库、文档和部署说明。
- `管理后台/`、`后端程序/` 里仍是众墅设计小程序的名称、文档和配置,其中 `.env` 含真实密钥。
- 后端模块平铺在根目录,分不出哪些是底座、哪些是平台、哪些是业务。

### 9.2 建议结构

```
众墅之家AI赋能平台/
├── README.md                     ← 三端总说明、本地启动、部署
├── 小程序/                       ← 由 zhongshu-ai-platform-v3-main 改名,内部不动
│   └── miniprogram/api/          ← 新增:数据访问层
├── 管理后台/
│   └── src/
│       ├── views/platform/       ← 平台通用页面:组织人员、待办、审批、审计、通知、AI
│       ├── views/franchise/      ← 加盟协同域页面
│       ├── views/system/、infra/ ← yudao 原有
│       ├── api/platform/、api/franchise/
│       └── router/modules/platform.ts、franchise.ts
├── 后端程序/
│   ├── yudao-dependencies/、yudao-framework/        ← 框架底座,不动
│   ├── yudao-module-system/、yudao-module-infra/    ← 框架底座,不动
│   ├── platform/                 ← 平台能力层(聚合 pom)
│   │   ├── platform-org/、platform-identity/、platform-authz/
│   │   ├── platform-command/、platform-todo/、platform-approval/
│   │   └── platform-notify/、platform-file/、platform-ai/
│   ├── domains/                  ← 业务域层
│   │   ├── _template/            ← 新业务域骨架
│   │   └── franchise/            ← 加盟协同域(聚合 pom)
│   │       ├── franchise-api/、franchise-org/、franchise-crm/、franchise-design/
│   │       └── franchise-commission/、franchise-engineering/、franchise-finance/、franchise-performance/
│   └── yudao-server/             ← 启动层,按依赖决定启用哪些业务域
├── ai-runtime/                   ← AI 出图运行时(需要时从设计小程序复制)
├── 项目文档/
│   ├── 平台/                     ← 平台能力说明、业务域开发手册
│   └── 加盟协同域/               ← 本域方案、接口约定、验收记录
└── .gitignore                    ← 排除 node_modules、dist、target、.env*
```

### 9.3 要点

- **按层分目录**:`platform/` 和 `domains/` 分开,新人一眼看出哪些能复用、哪些是业务。
- **底座目录不动**:yudao 原有模块保持原名和原位置,方便以后升级。
- **小程序内部不重排**,只改外层目录名。
- **命名与众墅设计小程序一致**(小程序/管理后台/后端程序/项目文档),两个项目切换时不容易混。
- **一个 git 仓库管三端**,同一功能的前后端改动在同一个提交里。小程序原远程仓库 `phlong026/zhongshu-ai-platform-v3` 的历史可以作为子目录导入保留,也可以只留原仓库归档,需要你定。

## 10. 风险与待定事项

| 项 | 说明 | 建议 |
|---|---|---|
| 平台层抽象过度 | 只有一个业务域时,容易把平台能力设计得过于通用 | 平台层只抽加盟域确实用到的能力;第二个业务域接入时再补 |
| 规则移植工作量 | 小程序规则代码密集(utils 约 500KB),新旧流程并存 | 只移植新流程,用小程序检查脚本作为验收用例 |
| 历史本地数据 | 演示数据只在测试手机本地 | 不迁移,服务端从空数据开始,用种子脚本重建演示数据 |
| 文档 41 结论 | 本方案将租户策略改为单租户 + 部门树 | 在文档 41 补一段更正说明 |
| 微信登录绑定 | 用微信手机号匹配员工 | 确认是否要求员工先由老板在 Web 建档 |
| 线下事实 | 付款、签认、交付仍是线下发生、线上登记 | 一期不接银行和电子签章,保留凭据上传 |
| 高风险代码 | 登录、授权、组织隔离、财务 | 详细设计 + 人工评审;越权测试先行 |
