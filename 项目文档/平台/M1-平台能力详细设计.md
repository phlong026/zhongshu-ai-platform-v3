## 2. 对方案的两处修正(读底座源码后发现)

1. **员工在小程序上也走 `/admin-api`**。yudao 按接口路径判断令牌类型:`/admin-api` 只认后台用户令牌,`/app-api` 只认会员令牌(`TokenAuthenticationFilter`、`WebFrameworkUtils.getLoginUserType`)。员工是后台用户,所以两端都调 `/admin-api/<域>/...`。`/app-api` 留给以后面向业主、访客的 C 端接口。方案第 4 节的接口约定同步修改。
2. **数据范围不用 yudao 自带的「部门数据权限」**。yudao 的规则基于用户唯一的 `dept_id` 和角色的数据范围,而小程序中一个人可以兼多个岗位,每个岗位属于不同团队,并且办理时只按「当前岗位」判断。所以平台自己实现一条按「当前岗位所在组织」过滤的数据规则(第 6.3 节),挂在 yudao 的数据权限框架上。

## 3. 数据模型

单一租户(yudao 种子数据的租户 1)。平台表统一前缀 `pf_`,不带 `tenant_id`。

### 3.1 组织与团队:复用 `system_dept`,加一张扩展表

```
system_dept(yudao 原表)              pf_org_unit(扩展)
  id ─────────────────────────────── dept_id  PK
  parent_id                          kind      ORG | TEAM
  name                               org_id    所属组织(ORG 行等于自身)
                                     org_type  组织类型,如 headquarters / store(仅 ORG 行)
                                     domain    注册该组织类型的业务域,如 franchise
                                     line      条线,如 sales / engineering(仅 TEAM 行,可空)
                                     status    ACTIVE | DISABLED
```

- 组织 = 部门树中标记为 `ORG` 的节点;团队 = 组织下标记为 `TEAM` 的节点。
- 部门树仍由 yudao 维护,后台「部门管理」页面可以继续使用。

### 3.2 岗位模板:由业务域注册

```
pf_post_template
  role_code       = system_role.code(角色即岗位,菜单权限挂在角色上)
  domain          franchise
  org_types       允许的组织类型,如 ["store"] / ["headquarters","store"]
  line            条线
  lead            是否负责人
  inherits        负责人继承的专员岗位,如 sales-lead → sales
```

加盟协同域在 M2 用迁移脚本写入 13 个岗位(角色 + 模板 + 菜单)。

### 3.3 任职:一个人一个岗位一条记录

```
pf_staff_post
  id
  user_id         system_users.id
  org_id          任职组织
  role_code       岗位
  team_id         所在团队(可空)
  managed_team_ids 负责人管理的团队(JSON 数组,可空)
  status          ACTIVE | REVOKED
  revoked_at / revoked_by
```

- 兼岗 = 同一人多条记录。
- 撤销任职后,该岗位的会话在下一次请求时立即失效(对应小程序「停用、撤回成员或岗位后,旧会话立即失效」)。
- 任职变更同步维护 yudao 的 `system_user_role`,保证后台菜单权限一致。

### 3.4 命令事件

```
pf_command_event
  id, domain, aggregate_type, aggregate_id
  revision           执行后的版本号
  command            命令名,如 commission-submit
  org_id, actor_user_id, actor_post_id, actor_role_code
  payload            输入快照(JSON 文本,不含密钥)
  payload_hash       payload 的 SHA-256,用于判断幂等重放内容是否一致
  idempotency_key    UNIQUE,可空
  occurred_at
  UNIQUE(domain, aggregate_type, aggregate_id, revision)
```

> 实施说明(M1.2):payload 用 TEXT 而非 JSONB。项目没有 JSONB 类型处理器,而日志只做审计回看、不按 JSON 查询;以后需要查询时再换。

### 3.5 审批

```
pf_approval
  id, domain, org_id
  subject_type, subject_id, subject_version
  signature          金额、版本、依据等关键字段的摘要;任一变化即需重新审批
  amount_cents
  status             PENDING | APPROVED | RETURNED | SUPERSEDED
  submitter_user_id, submitter_post_id
  approver_role_code 由业务域规定的审批岗位,如 boss
  approver_user_id, approver_post_id, decided_at, note
```

规则:提交人不能审批本人提交的事项;同一事项同一签名只有一条有效记录;签名变化则旧记录变为 `SUPERSEDED`。

## 4. 命令与事件(`platform-command`)

- 业务聚合表统一带 `revision BIGINT`。
- `CommandExecutor.execute(command)` 在一个事务内完成:
  1. 按 `id + 预期 revision` 加锁读取;版本不一致抛「记录已变化,请刷新」。
  2. 业务域校验权限和规则,计算新状态。
  3. 写回新状态,`revision + 1`。
  4. 追加 `pf_command_event`。
  5. 通过现有 `ReliableEventPort` 追加事件,供其他模块订阅(**M1.2 未做**:目前没有订阅方,等第一个跨模块订阅出现时再接)。
- 带幂等键的命令重放时直接返回第一次的结果,不重复执行。
- M1.2 实际提供的是 `CommandLog`(事件追加、幂等判断、按聚合查询)和 `Revisions.requireUpdated`(乐观锁检查),而不是通用执行器:聚合的读写由业务域自己的 Mapper 完成,平台不做通用聚合存储,避免过度抽象。

## 5. 员工登录(`platform-identity`)⚠ 待评审

### 5.1 Web

沿用 yudao 账号密码 / 短信登录。员工账号由老板或总部在后台建档。

### 5.2 小程序

```
小程序                                   后端
wx.login → code ───────────────────────▶ code2session → openid
                                         查 pf_wechat_binding(appid, openid)
                                          ├─ 已绑定且有有效任职 → 签发令牌
                                          └─ 未绑定 → 返回「需要绑定手机号」
getPhoneNumber → phoneCode ────────────▶ 换取微信手机号
                                         查 system_users.mobile 且有有效任职的员工
                                          ├─ 唯一命中 → 写绑定 → 签发令牌
                                          └─ 未命中 / 多人命中 → 拒绝,提示联系老板建档
```

- 令牌用 yudao `OAuth2TokenApi` 签发后台用户令牌,与 Web 相同。
- 绑定表 `pf_wechat_binding(appid, openid, unionid, user_id, status, bound_at)`,`(appid, openid)` 唯一;支持多个小程序 AppID。
- 微信调用代码从旧 identity 模块复制必要部分(code2session、手机号),不依赖旧模块。
- 员工离职(全部任职撤销)后,绑定保留但登录被拒绝。

### 5.3 待评审的风险点

| 风险 | 处理 |
|---|---|
| 用微信手机号自动匹配员工,手机号录错会让他人登录 | 只匹配**有效任职**的员工;多人同号直接拒绝;首次绑定写审计 |
| 老板改员工手机号后旧绑定仍有效 | 改手机号时撤销该员工的微信绑定 |
| 本地开发 `mock-enable: true` 可伪造登录 | 仅 `local` 配置开启,`prod` 为 `false`;部署检查项加入此条 |

## 6. 授权(`platform-authz`)⚠ 待评审

### 6.1 当前岗位上下文

- 请求头 `X-Post-Id` 指明当前岗位;不带时,只有一个有效任职的员工自动使用该岗位,有多个则返回「请选择工作身份」。
- 每次请求都校验:任职属于当前登录用户、状态有效、所在组织启用。校验结果按请求缓存。
- 得到 `PostContext { userId, postId, orgId, orgType, roleCode, teamId, managedTeamIds }`,对应小程序 `authority-v2.js` 的 `context()`。

### 6.2 功能权限:只看当前岗位

- yudao 的 `@ss.hasPermission` 取用户所有角色的权限并集,兼岗人员会拿到其他岗位的权限。小程序的规则是「只能办理当前岗位的事」。
- 平台提供 `@post.has('<域>:<资源>:<动作>')`,只检查当前岗位对应角色的菜单权限。业务域接口一律用它。

### 6.3 组织范围:自动过滤

- 平台实现 yudao `DataPermissionRule` 的一条规则 `OrgScopeRule`。业务域登记「表 → 归属组织列(+ 额外组织列)」:

```java
rule.register("fr_customer", "company_id");
rule.register("fr_commission", "company_id", "design_org_id"); // 总部设计可见委托给自己的
```

- 查询自动追加 `(company_id = :当前组织 OR design_org_id = :当前组织)`。
- 没有岗位上下文时(未登录、定时任务)返回空结果;定时任务需要跨组织时显式使用 `OrgScope.ignore(...)`,并写审计。

### 6.4 对象规则:业务域实现

平台定义扩展接口 `ObjectAccessPolicy<T>`(能否读、能否执行某命令),提供通用判断:同组织、本人、本团队、管理的团队、不能自批、不能自核。加盟协同域在 M2 把 `authority-v2.js` 的规则逐条移植进来。

## 7. 待办与审批扩展接口(`platform-workflow`)

- **待办即时计算**:业务域实现 `TodoProvider.list(PostContext)`,平台汇总、排序、计数。不建待办投影表:加盟商约 10 人规模,即时计算最简单,也不会出现待办和业务状态不一致。数据量变大后再加投影表。
- 待办项字段:`key`、标题、状态、金额(可空)、是否可办理、Web 跳转地址、小程序跳转地址。
- **审批**:平台提供 `ApprovalService.submit / decide / latest`,强制「不能自批」和签名失效规则;审批人是否合格(如「本组织老板」)由业务域的 `ApprovalPolicy` 判断。

## 8. 测试

每块能力都用 Testcontainers 的 PostgreSQL 做集成测试,至少覆盖:

- 命令:版本冲突、幂等重放、事件落库、事务回滚时事件也回滚。
- 组织与任职:兼岗、撤销任职、组织停用、团队归属。
- 审批:不能自批、签名变化使旧审批失效、重复审批被拒。
- 授权:他组织数据查不到、`X-Post-Id` 指向他人任职被拒、已撤销任职被拒、兼岗人员只拿到当前岗位权限。
- 登录:未建档拒绝、多人同号拒绝、离职拒绝、绑定后免手机号登录。

> 本机 macOS 系统 SOCKS 代理会被 JVM 继承,导致测试连不上容器里的数据库。运行测试时加 `-DargLine="-DsocksProxyHost= -DsocksNonProxyHosts=localhost|127.*|[::1]"`。

## 10. 需要确认的问题

1. 小程序员工首次登录用「微信手机号匹配员工档案」,是否接受?另一种做法是老板在后台生成一次性邀请码,员工输入后绑定,更安全但多一步。
