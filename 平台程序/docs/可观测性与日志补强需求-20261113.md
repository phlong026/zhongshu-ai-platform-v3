# 可观测性与日志补强需求（2026-11-13）

> 目标：把"运行期出问题能发现、能定位、能追溯"补齐到可上线标准。
> 现状结论：**后端 HTTP 请求层能采到绝大部分报错，但做不到"所有"**；最大盲区是**小程序前端完全没有错误采集**。

## 一、现状盘点（代码实证）

| 能力 | 实现情况 | 证据 |
|---|---|---|
| 未捕获异常兜底 | ✅ 全部 `Throwable` → `ERROR` + 完整堆栈 | `GlobalExceptionHandler.defaultExceptionHandler`（`log.error("[defaultExceptionHandler]", ex)`） |
| 业务异常 | ✅ `ServiceException` → `WARN` + 首帧栈 + 业务码 | `serviceExceptionHandler` |
| 异常入库 | ✅ 异步写 `infra_api_error_log`：URL、参数、用户、IP、traceId、异常类/消息/根因/全栈/文件/行号 | `createExceptionLog()` → `apiErrorLogApi.createApiErrorLogAsync` |
| 访问日志 | ✅ 默认开启（`matchIfMissing=true`），生产未显式关闭 → `infra_api_access_log` | `YudaoApiLogAutoConfiguration:25` |
| 日志文件 | ✅ root=INFO；异步 appender `discardingThreshold=0`（不丢）；按天 + 10MB 滚动；保留 30 天 | `yudao-server/src/main/resources/logback-spring.xml` |
| 定时/异步任务异常 | ⚠️ 框架默认 `ERROR`，但无业务上下文（不知哪个组织/哪个任务） | Spring 默认处理器 |
| 小程序前端异常 | ❌ 完全没有 | `miniprogram/app.js` 仅有 `onLaunch`/`watchUpdate`，无 `onError`/`onUnhandledRejection` |
| 日志集中采集 | ❌ 无（无 ELK/Loki/CLS） | 仓库内无相关配置 |
| 日志告警 | ❌ 无（仅健康拨测脚本，未确认已部署） | `deploy/ops/probe-health.sh` |
| 日志表清理 | ❌ 无任何定时清理 | 全仓无 `cleanApiAccessLog` 类实现 |

## 二、缺口与需求

### G1 小程序前端错误零采集（优先级 P1，建议提审前做最小版）

**现象**：页面白屏、JS 报错、接口异常后的用户侧表现，后端日志里完全没有记录。

**影响**：线上问题只能靠用户口述；机型/版本相关的兼容问题无法复现与统计。

**方案（最小可用版）**：
1. 新增后端端点 `POST /admin-api/platform/client-error/report`（`@PermitAll`，限流：单 IP 每分钟 N 条）
2. 落库新表 `platform_client_error`（或复用 `infra_api_error_log`，但建议独立表，避免污染服务端错误统计）
3. 小程序 `app.js` 注册 `App.onError` 与 `App.onUnhandledRejection`，上报：错误消息、栈、页面路径、AppID/版本、机型、时间
4. 上报失败静默（不得因上报本身影响用户体验），本地只保留最近 N 条待补报

**验收标准**：
- 人为在体验版某页面抛异常 → 后端表内 5 分钟内可见该记录，含页面路径与版本号
- 断网状态下抛异常 → 不弹错、不影响操作，恢复网络后能补报
- 单用户上报量有上限（防刷）

### G2 生产日志路径未配置（优先级 P0，上线前必须）

**现象**：`logback` 使用 `${LOG_FILE}` 但**无默认值**，`deploy/env.prod.template` 也没有该键。缺省时 logback 会写到名为 `LOG_FILE_IS_UNDEFINED` 的文件——本机仓库根目录已产生 16 个此类文件，属实证。

**影响**：生产日志落盘位置不可预期，排障找不到日志；滚动策略虽生效但文件名混乱。

**方案**：env 增加 `LOG_FILE=/opt/zhongshu/logs/zhongshu.log`；部署脚本 `mkdir -p /opt/zhongshu/logs` 并确保 `zhongshu` 用户可写；确认 `maxHistory=30` 与磁盘水位匹配。

**验收标准**：重启后 `/opt/zhongshu/logs/zhongshu.log` 有当日日志；`logrotate` 或 logback 滚动后旧文件按策略清理；`/opt/zhongshu/LOG_FILE_IS_UNDEFINED*` 不再新增。

### G3 无集中采集与告警（优先级 P0 告警 / P1 采集）

**现象**：日志只在本机文件与数据库；服务不可用、ERROR 突增均无人知。

**影响**：故障发现依赖用户投诉，MTTD 不可控。`deploy/ops/probe-health.sh` 已具备拨测+企微告警能力，但需部署。

**方案**：
- **P0**：部署 `probe-health.sh`（每 5 分钟，`ZS_OPS_WEBHOOK` 配企业微信群机器人），先解决"服务挂了没人知道"
- **P1**：接 Loki+Grafana（或腾讯云 CLS），采集 `/opt/zhongshu/logs/*.log`；配两条告警：`ERROR` 数量 5 分钟环比突增、`/actuator/health` 非 200
- 已有 `actuator` 暴露 prometheus，可作为指标源

**验收标准**：
- 停掉服务 5 分钟内企微群收到告警；恢复后收到恢复通知或冷却期结束
- 人为制造 10 条 ERROR → 告警触发一次（不刷屏，30 分钟冷却）

### G4 日志表无清理策略（优先级 P1）

**现象**：`infra_api_access_log` / `infra_api_error_log` 全量落库，无任何清理任务。

**影响**：按全量请求记，表体积线性增长，数月后拖慢数据库与后台查询。

**方案**：新增定时任务（每日低峰），按时间保留：访问日志 30 天、错误日志 90 天；分批删除（每批 ≤5000 行）避免长事务；记录删除行数日志。

**验收标准**：任务执行后两类表行数符合保留期预期；删除过程无长事务锁表（`pg_stat_activity` 无 >5s 的 DELETE）。

### G5 上游错误细节缺失（优先级：不修，安全设计）

微信/SMS/COS 的日志只记 `errcode`，不记上游 `errmsg`、响应体；手机号打码、验证码永不打印。这是**有意为之的安全边界**（密钥/签名 URL/验证码不得入日志），排障时需结合 `traceId` 与上游控制台（腾讯云短信、mp 后台）交叉定位。**不要为了排障便利放开该限制。**

## 五、验收方式（整体）

1. 人为制造后端异常 → 文件日志有 ERROR、`infra_api_error_log` 有记录、告警不误报
2. 停服 → 5 分钟内收到企微告警
3. 体验版前端抛异常 → 后端表可查（G1 完成后）
4. 跑一次 `backup-postgres.sh` → 生成非空 gz，且能在临时库恢复成功
