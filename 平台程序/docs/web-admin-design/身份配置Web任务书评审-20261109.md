## 三、评审结论与必须修订项

**当前结论：需修改后再作为可直接开发的身份配置任务书使用。** 方案已覆盖业务主题，但接口、权限与交付边界存在阻断项。独立代码/契约评审为 REQUEST CHANGES，独立架构评审为 BLOCK；本节综合了两路发现与主线核验。

### R1／高：本人任职与短信登录路径写错

- 原文第21、244行：GET /platform/my/post；实际 MyPostController.java:25、40 为 GET /platform/posts/mine。
- 原文第243行：POST /platform/auth/sms-login；实际 PlatformAuthController.java:30、61 为 POST /platform/auth/sms/login；发送验证码为 /platform/auth/sms/send。
- 应统一注明 API 前缀由请求层处理（常见部署为 /admin-api），不得重复拼接；逐条核对方法、参数、返回包络与错误码。

验收：Web 网络请求与当前 Controller 契约一致；不以页面出现或 mock 返回代替真实 API 对接。

### R2／高：组织管理权限码与当前实现不一致

- 原文第75行使用 franchise:org:manage。
- StaffOrgAdminController.java:112、123、151 等实际采用 @post.has('platform:org:query/manage')；权限种子 V20261031.703 与之相同。
- 原文所述按权限显示菜单没有说明当前岗位权限如何取得。MyPostController.StaffPost 返回岗位、组织、部门等字段，不直接携带权限码列表。必须明确复用的权限来源，缺少读取契约时列为后端小缺口，而不是从 system 角色权限或文档硬编码推断。
- 当前 user store 取 system 权限集合，StaffPost 又会将多任职角色同步到底座；直接复用 checkPermi 得到的是账号角色权限并集，不能作为当前岗位的菜单/按钮能力。fr 工作区需要独立的 current-post 能力来源，system 权限仅用于平台门户。

验收：按钮和路由使用正确权限；直接请求仍由后端按岗位和组织拒绝。隐藏按钮不能替代 403 与跨组织负向测试。

### R3／高：平台组织开通与门店人员管理混在老板菜单中

- 原文第75、248行把 OrgOnboard/组织开通挂入 boss 的组织管理范围。
- V20261104.707 迁移第8–17行已创建 `/platform-org/onboard` 动态菜单、关联 `zs/platform-org/index` 组件并授予底座超管；因此不能按「完全没有菜单接线」重建，更不能为方便访问将其下放给门店 boss。
- OrgOnboardController.java:48 需要平台权限 @ss.hasPermission('platform:org:onboard')；组织内员工管理使用的是 @post 和本组织范围，二者不能混用。
- 最终规则 R02 要求授权的平台人员核实组织并指定首任管理员，组织 boss/owner 再管理本组织部门与任职。

修订：平台运营门户提供组织开通与首任管理员表单；组织管理门户提供本组织部门、员工、岗位与交接。普通组织 boss 不因拥有 org:manage 自动获得全局开通能力。该项是方案权限边界风险，不代表服务端已经允许越权。

### R4／高：Web 员工身份会话与切岗隔离缺少可执行约束

原文第19–24、243–246行只写登录、切换 X-Post-Id、重新加载菜单。仍需补充：平台管理员会话与员工业务会话如何区分；首次任职未加载、无任职、多任职、岗位失效、401、普通403的状态；切岗/退出后的旧请求、详情、缓存、导出和文件权限如何失效。

验收：A岗位请求挂起后切B，A迟到响应不得覆盖B的人员/菜单/数据；改组织后旧详情和待提交表单不能继续使用；退出不保留上个账号的可见敏感内容；钱包会话沿用既有隔离语义。

当前员工登录仍使用既有 ADMIN OAuth token。最小方案优先复用该 token/刷新链，用 portalMode、selectedPostId、身份代次和当前岗位能力集合隔离上下文；不要在没有同时保留两账号需求时直接新增两套 token 与刷新队列。

### R5／高：停用、恢复与业务任职模型需要明确

- system_users/system角色/底座岗位是通用账号管理，pf_staff_post 才是小程序消费的业务任职，不能用普通用户编辑表单代替。
- StaffOrgAdminController.java:184–217 已明确：组织级停用撤本组织全部任职；其他组织任职保留；全局账号停用由平台管理员执行。组织停职恢复须重新指派岗位，不能直接翻转全局 active。
- 原文「停用启用」操作应改成明确的作用范围、确认文案、失败状态和恢复路径；不得制作一个含义不清的统一开关。
- 当前成员列表基于有效任职；全部撤岗者会从该列表消失。任务书须明确用已有手机号重新录入/指派作为恢复入口，或明确补充历史成员查询；不能给一个刷新后已消失的行设计「恢复」按钮。
- 交接结果须分别呈现 HANDED_OVER、NONE、PENDING_UNASSIGNED、NOT_INTEGRATED、SCAN_FAILED。紧急撤权先收权，再扫描/待分配；扫描失败不能误报成撤权失败，也不能把未集成域当交接成功。

验收：同一员工有门店A和B任职，A组织撤岗/停职后B仍可用；全局停用由专门授权的管理员执行且各组织能力均回收；再次任职按指定部门和岗位恢复。

### R6／中：P2 页面卡不足以直接分工实施

现有 P2 仅用几行概述团队树、员工表和抽屉，没有字段/接口映射、分页或数据量边界、错误状态、按钮权限、任务依赖、验收案例与完成证据。后端已有能力也不等于所有部门 CRUD、调部门或岗位模板编辑接口都已提供。

修订：先收口本模块最小闭环，不等待整套24页门户。不能先重新开发已存在的建员/任职/交接后端；UI超出现有契约的需求必须单列差额。

### R7／中：状态记录与交付证据不一致

总表第33行记录 M12-T02 第一批已交付，而 Web 方案第248行仍称组织开通为孤儿页。原文件分属不同基线，必须补「当前页面/路由/API/测试/部署/真实角色验收」逐项状态；不能把 67/67 收口、接口存在或类型检查通过扩展成 Web 功能可用。

### R8／高：已有平台开通菜单会被当前前端侧栏裁剪

菜单不存在与菜单被隐藏是两件事。V707 已有菜单；`admin-ui/src/store/modules/permission.ts:66` 仍用 buildProjectMenus 组装展示项，而 `src/utils/projectNavigation.ts:35–46` 的 supportPaths 不含 `/platform-org/onboard`，第54–59、101行会将该授权动态菜单移除。

主线直接执行当前真实 TypeScript 函数，传入 SQL 对应的 `/platform-org/onboard` 授权菜单，且 can() 恒为 true，结果仍为空数组，证实此展示入口被裁剪。这里只测菜单函数，不等同真实数据库已迁移或用户已获权限。

修订要求：将现有平台管理员菜单纳入合适的平台门户展示/搜索与授权路由链；不简单复制到组织 boss 的 fr 菜单。以「有权限可见可点，无权限不可见且直达被拒」分别验收。

## 六、必须写入修订任务书的验收场景

1. 平台运营开通门店并指定首任 boss，重复请求不重复建组织或任职。
2. boss创建部门、录入手机号员工；已有手机号复用同一账号，不创建影子账号。
3. 同人多岗/多组织；员工登录仅看到已授权有效任职，不自行选择未授权岗位。
4. 任职部门不属当前组织、无管理权限、伪造orgId/postId均被后端拒绝。
5. 部门列表、人员列表、空组织、加载中、接口失败都保留页面结构并明确状态。
6. 追加同岗位重复提交幂等；部门冲突有明确错误，不能虚假提示已调部门。
7. 撤销单岗、本组织停职、全局账号停用分别验证作用范围与旧令牌结果。
8. 组织停职后重新指派有效岗位恢复；全局停用不能由门店管理员直接启用。
9. 正常交接、失败回滚/重试、紧急撤权、待分配、跨部门接收分别记录结果，不改写历史经办或已确认业绩。
10. A请求挂起→切B→A返回，页面、按钮、缓存和请求头保持B；退出和换号同样验证。
11. Web改任职→小程序刷新岗位→正确工作台；清缓存首次登录、岗位失效和组织停用均有明确落点。
12. 页面/接口本地证据、浏览器实际操作、部署版本、真实微信/短信及手机验收分别记录。只有一类证据不得整链标绿。
