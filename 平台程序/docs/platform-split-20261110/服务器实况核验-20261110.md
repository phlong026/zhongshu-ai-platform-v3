## 二、本地两仓库分叉实况

约定：**A** = `众墅之家设计小程序/后端程序`；**B** = `众墅之家AI赋能平台/平台程序`。

### 2.1 模块结构

| | A | B |
|---|---|---|
| Maven 模块数 | 9 | 11 = A 的 9 个 + `platform` + `domains` |
| franchise 子模块 | 无 | `domains/franchise/` 下 12 个 |
| admin-ui | 独立目录 | `平台程序/admin-ui` |

### 2.2 代码同源性与分叉

- **B 整体复制了 A 的设计线**，并做定向改动；同名模块文件数近似（design 104→105，identity 64→60，commerce 39→39，ai 24→24，infra 186→188，system 419→422，server 15→20）。
- **B 独有**：`yudao-module-design/.../FranchiseDesignAdapter.java`（`implements DesignServicePort, AssetAccessPort`，进程内注入 design 服务并 `JdbcTemplate` 直查 `ai_job/design_candidate/budget_estimate/asset`）、`AssetEntranceIsolationTest`、`FranchiseDesignAdapterReferenceTest`、identity 的 `AccountProvisionAdapter`、`IdentitySessionIssuePortAdapter`、5 个 dev Controller、52 个迁移。
- **A 独有**：`yudao-module-identity/` 的整条激活申请链路（`ActivationRequestService`、两个 Controller、4 个 VO、契约测试）+ 3 个迁移（`platform/V20261029.606`、`identity/V20261029.110`、`design/V20261022.605`）。
- **依赖方向不对称**：
  - A 全仓无 `franchise` / `platform` / `domains` 引用，`A/yudao-module-design/pom.xml` 不依赖 franchise-api → **A 可独立编译**。
  - `B/yudao-module-design/pom.xml:28` 反向依赖 `yudao-domain-franchise-api` → **B 的设计模块不能脱离赋能线单独编译**。

### 2.3 配置差异

| 项 | A | B |

| Flyway locations | `application-pg.yaml:19` 5 段（platform/identity/design/commerce/ai-orchestration），80 个 SQL | `application-pg.yaml:21` 8 段（多 `pf` 7xx、`franchise` 8xx、`franchise-system` V85x），132 个 SQL |

### 2.4 跨系统调用现状（进程内，非 HTTP）

`B/domains/franchise/franchise-design/.../DesignAccessController.java:37`，`@RequestMapping("/franchise/design")`（实际前缀 `/admin-api/franchise/design/**`），约 24 个端点：

## 三、四个硬阻塞（"直接重推 A 的 jar"为何不可行）

| # | 阻塞 | 证据 | 后果 |
|---|---|---|---|
| 1 | Flyway 校验失败 | A locations 仅 5 目录/80 迁移；生产 history 133 条含 52 条 B 独有迁移。现 unit 的 `ignore-migration-patterns=*:missing` 会覆盖默认 `*:future`，而 20261101–20261105 的迁移版本高于 A 本地最高版（20261029.606），属 future 类 | 服务启动即失败（`Detected applied migration not resolved locally`） |
| 2 | 赋能线整体消失 | DesignAccessController 24 端点 + `/pf/**`、`/franchise/**` 全部依赖融合 jar | 员工小程序全链路 404 |
| 3 | 两仓行为已分叉 | A 有"提交即开通"（0513c76b），B 删除激活申请；B 有平台开通/会话适配与 11-07~11-09 身份修复 | 账号/开通语义不一致，B 侧修复丢失 |
| 4 | 配置/凭据混用 | `env.merged` 两线键混排；B 的 `RealServiceWiringPolicy` 缺键快速失败 | 两侧无法共用同一份配置启动 |

## 四、与 v5.0 方案的关系

- 本次核验**独立验证**了 v5.0 的现状判断（单 jar 单库、两线耦合、进程内调用、契约迁移闭包 3 文件）。
- 补充了三项 v5.0 未记录的生产事实：
  1. `api2.zszhj.com` 已配置但**未真正隔离**（反代同一 48080）；
  2. 服务器存在未启用的 `zhongshu-v2.service:48081`，可作为"轻量止血"的现成载体；
  3. `ignore-migration-patterns` 的参数值本身是陷阱（`*:missing` 替换默认 `*:future`），P0 必须改为 `*:missing,*:future` 并分库/分 history 表。
- **结论不变**：按 v5.0 P0–P4 实施；不得以覆盖方式重推设计线 jar。

## 五、建议的启动顺序（不改 v5.0 分期）

1. P0 的三个 spike 先行，其中 Flyway 双库/双 history 表方案作为 spike 0（新增，先于契约迁移）；
2. 轻量止血可选：启用 `zhongshu-v2.service:48081` + api2 改指向 48081 + 拆 env + Redis db 0/1（1–2 天，库仍共用，不算隔离）；
3. 生产 `admin/admin123` 改密作为独立事项并行推进。
