## 1. 确认边界与推荐主线

唯一跨应用业务是**灵感库、AI 设计、快速预算**。素材访问、服务调用方标识、幂等收据和任务状态是这三项业务的支撑面；不增加客户数据或 CRM 回流。赋能侧的客户关联、预算存档和业务附件归赋能平台本地处理。

推荐源码归属：A（设计独立项目）维护设计小程序、设计管理后台和设计后端；B（赋能平台）维护赋能后端及总部运营后台；v3 维护员工小程序。协议通过小型契约包或版本化 OpenAPI 共享，不把共享业务实现或同仓双构建作为已确认前提。

## 2. 当前状态与目标部署

截至本轮晚间核验，线上仍为融合后端、共用库，`api`/`api2` 均到 48080。静态后台与 A 最新产物匹配，后端审批 class 与 B 本地构建匹配且使用 `PENDING`，即 **A 管理后台+B 融合后端的混合发布组合**。P0 先将这个有效组合变成可复现发布基线，再做拆分，不能用 A 整包覆盖。单 class/hash 比对不证明整 jar 的精确 Git SHA；完整证据、时间与范围见新基线。

B 必须旁路新建独立目录、Linux service user、systemd unit、端口、数据库及独立权限、Redis 实例或独立 ACL、COS 策略、环境密钥和后台站点。A 保持 `api`→48080 及 `zszhj.com/admin`；B 建议 `api2`→48081，新增独立管理 host（如 `admin.zszhj.com`），核验 cookie、CORS 与权限。48081 只是建议，启用前复核；不得启用现成 v2 unit（仍用同 jar、旧 env）。不得以双进程共用设计库写入作为零停机捷径。

制品在隔离环境构建后部署到 B 新目录，禁止在生产机原地 npm/maven 构建、安装依赖或升级 JDK/Node/PG/Redis。同机 CPU、内存、IO、连接池与并发必须有硬限制，B 启动不能抢占 A 资源；容量不足优先缩小 B 或用独立服务器，不削减或停止 A 腾资源。压力测试、全量扫描和全量迁移演练只在隔离环境执行；生产源数据采样与搬迁读取须只读、低负载，并经预演证明可接受，仅 B 目标库接收导入。共享 nginx 仅新增或调整 B 虚拟主机，先验证语法与路由隔离，再优雅 reload，不全局 restart，不隐含任何影响 A 的操作。

设计管理后台沿 A 最新版本维护，负责设计用户、审批、设计点数/充值、灵感内容和 AI 运营。赋能总部后台负责组织开通、员工支持、平台钱包/充值/订单/流水/异常核对、能力定价、成本监控、配置审计；未来供应链总部功能也归赋能后台，不归设计后台或按 `/zs` 目录机械判定。

## 3. P0 必须先解决的发布与行为差异

1. **固定发布证据**：登记 A/B/v3 HEAD、dirty 状态、制品 SHA-256、构建来源和生产部署映射。逐项比较文件/提交/数据库迁移，不能同名目录整包覆盖。
2. **审批推荐基线**：推荐设计侧采用人工审批，向 B 当日恢复的 `PENDING` 语义对齐；这是作者建议，不是用户已指定业务规则。A 的 `ActivationRequestService.submit` 仍直接 `APPROVED+ACTIVE`，与只处理 `PENDING` 的审批方法不闭合，今日前端提交没有修复后端。
3. **审批与赠点分开验收**：A 管理页先审批再独立调点，调点失败不会回滚开通。推荐由服务端持久化赠点意图、金额及处理状态，提供查询与补偿；即使浏览器关闭或第二次请求没有到达，也能恢复待办。开通与赠点可以分步骤，但不能只靠前端提示或浏览器连续请求兜底。同申请赠点使用稳定键 `activation-request:<id>`，确保最多一次授予。P0 隔离回归覆盖丢失第二请求和失败重试，P2 验证独立设计后台/账本仍保持该闭环；本轮不实现。
4. **资料来源一致**：A `AppProfileController` 仍只查激活码兑换；管理员资料已取兑换/申请两源。B `AccountAdminController` 合并申请未筛 `APPROVED`，而 `AppProfileController` 只认 `APPROVED`，待审/驳回展示可能不一致。推荐统一有效激活来源、两源取新与补录规则，B 修复选择性吸收。B 缺 activation 页面/路由/API 只说明现状分叉；设计审批入口最终归 A 最新管理后台，不在 B 再建混合设计后台。
5. **定点合入**：将经验证的设计相关修复定点合入 A；B 保留员工身份、组织、岗位与绑定修复。两仓支付和账号类部分对象相同不代表其所有目录、迁移及行为相同。
6. **数据闭包**：A 独有 `identity/V20261029.110__activation_request.sql` 纳入迁移 manifest；`account.avatar=asset:<id>` 需要保留素材映射，不能仅拷贝用户表。

## 4. 设计能力协议与构建隔离

### 4.1 HTTP 边界

推荐版本前缀为 `/internal-api/design/v1/`，实际端点清单由现有 `DesignAccessController` 和 `DesignServicePort` 逐项生成，不以文档示例替代实现合同。

internal HTTP、服务身份和独立计费可能需要设计侧代码适配，不能承诺现有设计线上完全零改动即可全部拆完。先在隔离环境证明现有接口是否可复用；缺接口则列为独立的设计兼容性发布前置任务，完整证明不中断、不退化且另获授权后才可触及设计生产。未满足即阻断相关 B 能力上线，不绕过独立身份或钱包，不假定已有可用蓝绿/影子方案，也不以换路由宣称零停机。

| 面 | 合同必须包含 | 明确排除 |
|---|---|---|
| 灵感库 | 列表、风格、详情、收藏；分页、可见范围、稳定错误码 | 赋能 CRM 用户档案 |
| AI 设计 | 项目、素材票据、任务提交/取消/查询、选定、结果版本、修改、润色；异步状态与结算摘要 | B 直查 A 数据库、B 运行 A 的设计任务 |
| 快速预算 | 规则版本、编制输入、输出快照、状态与费用结果 | A 写入 B 客户/销售数据 |
| 支撑接口 | 服务身份/资源属主映射、收据查询、任务终态、素材访问与撤销 | 共享登录 token、跨应用身份互认 |

A 校验服务调用凭据及资源归属；B 校验员工、有效岗位与组织后建立最小调用上下文。不能把前端 token 转发给 A 当作服务身份。协议需冻结字段、枚举、金额/点数单位、错误码、超时、重试条件、分页与兼容窗口。超时数值须由实际接口和任务耗时确定，不承诺同步等待 AI 生成完成。

### 4.2 稳定幂等与异步结算

- 写请求的业务幂等键在首次发送前生成并持久化，重试保持相同。作用域至少包含调用应用、组织与业务类型；同键异请求指纹返回冲突。**nonce 只用于防重放，重试必须换 nonce，不能派生或降级为业务幂等键。**
- 若旧客户端未提供稳定键，应在前端/业务发起入口补齐；计费及创建任务入口不得以随机请求键兼容。无键的受保护写请求应拒绝并给出可恢复错误，兼容范围需契约测试证明。
- B 在同一本地事务保存业务命令、报价快照、点数预留/流水及本地审计；A 在自身事务保存收据和对应业务状态。现有 `DesignServicePort`/`DesignAccessService` 的调用方同库事务不能跨 HTTP 延伸；远端返回 `replayed` 不得导致 B 跳过尚未完成的审计或本地落账。远端超时先标记 `UNKNOWN` 并查收据/任务，不能直接退款再重提。
- 收据记录完整可恢复结果、指纹和任务映射；保留期覆盖重试、结算及对账期限，存在未决命令时不得清理。
- A 返回终态、有效结果数量、单调版本及累计结算事实；B 按创建时的自身价格计算权益差额，不能照抄 A 成本。结算既校验版本，又与已结算累计值对比，避免不同版本重复退补。取消请求不等于已取消，失败、部分成功、取消分别验收。
- A 的设计用户点数路径与平台服务调用成本路径分开，计费主体/模式随任务持久化。提交、prompt 预留、预算、usage、后台重试与 `AiJobSettlementService` 均使用正确归属；不能只替换一次扣款调用。内部成本账、收费方式和月结均为待确认建议。

### 4.3 服务安全、构建与 Runtime

推荐请求签名覆盖 method、path、规范化 query、timestamp、nonce、业务幂等键和 body hash；先验证再占用防重放记录，明确密钥轮换、时钟窗口和故障策略。使用项目现有成熟实现与安全评审，不新增自制认证协议承诺。

历史调查中的 `DesignServicePort`、`AssetAccessPort`、`FranchiseDesignErrorCodes` 三文件是**编译解耦的一部分**。还需检查全部消费方、静态 import、测试、资源、Spring 自动装配、`spring.factories`、`RealServiceWiringPolicy`、计费、资产、迁移和 Runtime。推荐以版本化协议包/OpenAPI 承载合同，包归属经 P1 设计评审确定，不直接认定移入 infra 即完成拆分。

B 构建须移除 A 的 design/commerce/AI 实现依赖，通过 HTTP adapter 替换进程内 `FranchiseDesignAdapter` 调用；本地业务附件不能再绕到 `DesignServicePort.validateAsset`。A 最终移除 B 的 platform/franchise 历史依赖属于后置清理目标，不是首期换包条件；首期保留 A 现有融合包，验证 B 写源、任务与权限已逻辑隔离。下述 Runtime/worker 职责拆分先在隔离环境验证，不能据此停启或替换设计生产进程。

AI Runtime、`ZhongshuJobDriver`、`ExportWorker`、调度、队列、锁、临时文件及 AI 回调处理必须有唯一所属应用。当前 `ZhongshuJobDriver` 同时承担 AI 和支付订单/inbox 恢复，必须按职责拆分，不能整类移走。`RuntimeAssetController` 的资产校验与签名访问也须纳入归属。A 的 Runtime 只接收 A 的任务与凭据，回调只更新 A 的任务；B 自有后台任务不能继续读取设计库或复用 A 的工作目录。存量任务的唯一执行者、重试与回调路由纳入迁移清单，不能在新旧进程各执行一次。

## 5. 赋能自有钱包、支付与资产

### 5.1 身份与钱包

优先复用 B 已有 `ADMIN` 登录态和岗位鉴权；v3 `api/wallet.js` 当前先换设计 token 再请求设计钱包，实施时必须显式改为 B 自有钱包调用。钱包每请求重新核验用户可用、当前岗位有效、组织一致及操作权限；撤岗/停用后旧登录态不得继续消费。两侧 token、OAuth client、会话、密钥及权限缓存独立，不迁移登录 token，迁移后重登。`WalletSessionRevocationAdapter` 直查设计 `account.external_key` 的耦合须移除。总部开通沿 `OrgOnboardController` 的 `@ss` 管理权限，组织内操作沿 `@post`，两种授权不可混用。

旧 `/wallet/session` 或 `/app-api/design/...` 路径只在证明必要时提供有期限的兼容层；不为“零前端”新建钱包 JWT，不把 `@PermitAll` 加控制器内自行验 token 作为默认方案。余额、预留、追加账本、订单、通知 inbox、退款和异常核对均归 B 自有数据模型，具体表名以实现设计和迁移评审为准。

### 5.2 支付事实、权益落账与历史订单

- 当前 stub/关闭开关只能说明配置，不能证明没有历史真实订单、余额、退款或预留。当前聚合也不替代渠道真单确认，P0/P3 须核对实际账户/渠道归属与未决项。
- 支付最终事实（渠道实付、退款、撤销）与点数/权益落账分开记录，各自幂等，并能补偿“已实付未入账”。金额、币种/点数单位、订单和付款归属核对后才授予权益。
- 下单需要的微信换码、`session_key`、付款人绑定、验签/解密、主动查单、通知 inbox、退款及重试均按真实渠道验证。任何应用都不能借用另一应用的用户会话或渠道配置。
- 历史订单由原系统继续负责，或通过明确的转移对照表交接唯一 owner；按订单逐笔决定。渠道通知与主动查单都进入相同幂等处理。未知订单先可靠保存并定位 owner，告警和人工核对不能替代支付事实处理，不得直接丢弃。
- 旧服务账号余额和预留按归属核验后迁移或结清，登记期初流水与历史追溯关系；在途 AI、充值、退款各有唯一结算者。关闭旧公开钱包消费入口和旧会话后，确保余额不能在两边重复消费，旧任务仍按清单完成退款/结算。

### 5.3 业务资产与基础资源权限

B 自有工程、财务、销售合同、内容等业务资产元数据及上传/下载鉴权；A 保留设计素材。历史 `asset` 必须按所有引用和属主映射划分，保留 ID/object key/状态与引用关系；同时处理 `account.avatar=asset:<id>`，不只迁移业务附件。

同 COS 桶前缀隔离必须落实独立 CAM 身份与策略限制，包括上传、读取、列举和删除权限；不能发整桶凭据。旧对象若不能通过准确策略授权，应迁移或使用受限服务访问，迁移完成前不得声明已隔离。

Redis 不同 db 仅为命名空间划分，不是权限隔离；pub/sub 也不按 db 隔离。按产品版本验证独立 ACL 用户、key/channel 范围与禁止危险命令，无法达标则分实例。PostgreSQL 两库使用不同应用账号，验证连接、schema、表和序列授权及默认权限，运行账号不持有跨库或超级用户权限。

## 6. 数据迁移、切换与回滚

### 6.1 迁移 manifest 与全量证据

为每张表/序列/迁移记录登记归属、引用闭包、源目标、转换规则、唯一 owner、校验和回滚方式。涵盖 A 独有审批迁移、system 用户/角色/菜单/岗位关系、基础字典、`pf_wechat_binding_event`（保留组织过滤）、资产/头像、支付与账本、AI 任务/收据、平台命令、inbox/outbox、调度配置与审计。资金表只迁移经核实属于 B 的对象；零对象主路径与非零备用路径都需可重复验证。

新库选择一种可复现建库方式：迁移建结构后导数据，或经过评审的 baseline/重建方案；不得混用带业务结构的 dump 与重复建表的 Flyway。逐项核实生产已应用迁移与发布制品的版本/checksum/位置差异，设计和平台各有自己的迁移历史。**不全局设置 missing+future ignore 掩盖迁移缺失，不以 repair 或空迁移伪造通过。** 历史例外须列明精确版本、原因、范围和验证证据。

校验不只比行数：主外键与属主、金额/点数/预留汇总、订单状态、资产引用、任务状态、序列 ownership/步长/`is_called`、迁移 checksum 均需匹配。历史表保留多久、备份存放与回滚数据保留期限由 P3 风险评审确认，不能默认两周后删除。

### 6.2 仅 B 定向停写与回调接收

`api`/`api2` 当前均指向融合服务，不能凭域名认定 `api2` 全为 B 流量。切换前须核设计小程序、支付/退款回调、Runtime 回调、素材 URL 等实际依赖，A 请求保持原落点；归属未核实就禁止全量切走 `api2`。

首次赋能切换仅冻结、迁移经过归属证明的 B 写源和流量；A 设计用户、任务、付款和回调持续运行，设计资金留原地。`api2` 切到 B 不代表旧融合 A 中 B 接口、旧 token、worker、定时补偿及通知消费者已停写；必须逐项证明全部旧 B 写入口已定向停用或移交唯一 owner，且不影响 A。当前融合进程能否定向暂停 B 写源尚未验证；没有可行的定向开关及一致性迁移方案就阻止切换，不以停止整个 A 或保留双写替代。

仅对 B 使用迁移 manifest、备份、冻结点、水位/增量清单及订单/任务 owner 对照。B 支付通知在冻结期间仍须可靠接收、验签、持久化，由唯一 owner 消费；须证明重试和主动查单可补全，不得丢弃事件或重复授予权益。B 历史资金、权益或任务若非零且不能在 A 持续运行下完成一致性迁移，阻断上线，不承诺无中断。全量演练在隔离环境，生产不做全库切换；开放 B 写入前校验路由、权限、账本、队列和迁移结果。

### 6.3 回滚边界

| 文档/P0–P2 开发与测试 | 回退源码或测试制品、恢复测试库 | 不接生产流量，不修改生产数据；外部测试付款单独追踪 |
