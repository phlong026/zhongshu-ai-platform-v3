## 一、用户已确认的边界

| 项 | 已确认内容 |
|---|---|
| 两套应用 | 设计 AI 与赋能平台是不同应用主体、独立运营应用；可以共用物理服务器，但各自有 Web、后端、数据库与身份体系 |
| 点数与充值 | 两应用各自拥有点数、充值与支付业务；不得继续用设计消费者钱包代替赋能钱包 |
| 唯一跨应用业务 | 赋能调用设计的灵感库、AI 设计、快速预算；素材、服务调用方标识、收据、任务状态是支撑接口 |
| 客户数据 | 不做设计自然人客户向赋能 CRM 回流；赋能本地保存当前设计结果或预算的客户关联不属于该回流 |
| 本轮范围 | 只评审与修订方案；不实施、不部署，不推定已取得开工或生产切换授权 |
| 设计生产保护 | 用户要求“进行部署的时候不能对现有部署的AI设计小程序造成影响，破坏现有的运行环境”；A 可用性、登录审批及已开通权限、灵感/AI/预算、充值退款/回调、数据资产保持正常。这是后续验收要求，不是现在开工授权 |
| 冻结保护基线 | 以现有 `48080 + zhongshu.service + zhongshu_design` 为运行事实；保护服务制品、目录、env、数据库/schema、支付配置、Runtime。指纹及备份仅正式获准阶段采集；B 发布不得覆盖 jar/admin-dist/env、停启 A service/Runtime、切 api 或现有 /admin、改 A schema/身份/余额/支付渠道、清理旧 fr/pf 表或设计残留 |
| 首期与后置清理 | 首期保持 A 现有融合包，不按源码规划换包；系统逻辑隔离与 A 历史依赖/旧表清理分阶段，后者单独授权，不宣称 A 源码已解耦 |

“不同应用主体”不自动推出不同法律主体、同一公司、具体商户归属或月度结算安排。这些需要业务与渠道证据。

## 二、推荐实现，尚非用户拍板

| 议题 | 推荐方向 | 确认或验证条件 |
|---|---|---|
| 源码归属 | A 维护完整设计应用及其最新管理后台；B 维护赋能应用和总部后台；v3 维护员工小程序 | 固定三仓基线、定点合入与迁移 manifest；不整包覆盖同名目录 |
| 设计审批 | 推荐人工审批，与今天 B 后端恢复的 `PENDING` 语义对齐 | A 源码仍自动开通；需业务确认并验证审批/赠点/资料展示，而非认定用户已指定 |
| 当前发布基线 | 先复现线上 A 管理后台+B 融合后端的有效组合，再拆分 | 页面哈希和单 class 比对不代表整个后端来自精确 Git SHA |
| 协议共享 | 小型契约包或版本化 OpenAPI，跨应用走 HTTP | 三文件迁移只解决部分编译耦合，还需装配、计费、资产、Runtime 与回调隔离 |
| 总部 Web | 赋能总部管理组织开通、员工支持、钱包套餐、订单/流水/异常、能力定价、成本与配置审计；未来供应链总部功能归 B | 缺少的页面和 API 明确待建；设计审批和设计用户运营留 A，不按 `/zs` 前缀判业务归属 |
| 加盟商业务入口 | 日常业务优先 v3 小程序；`/fr` 去留、应急身份页和后续 Web 投入再确认 | 不把“停止 `/fr` 建设”或“小程序已全部闭环”记为决议 |
| 钱包鉴权 | B 复用已有 ADMIN 身份及每请求岗位授权，修改 v3 `api/wallet.js` | token 不共享；撤岗/停用即时失权；不为零前端新增钱包 JWT |
| 支付归属 | 各应用按实际渠道独立配置，设计完整保留自身可能使用的 xpay | 核验 appid/商品/商户/回调；不能整体迁走 xpay 配置 |
| 资金切分 | 若账户归属全集复核证实平台历史资金和任务为零，则 B 钱包新建初始化、设计资金原地保留 | 当前仅 `fr-service:` 口径为零；全库有资金，24 预留点来源待核。发现非零平台归属即触发迁移备用路径 |
| 域名与端口 | A 必须保留 `api`→48080 和现有 `/admin`；B 建议 `api2`→48081 及独立管理 host | 48081 启用前复核；禁止启用同 jar、旧 env 的现成 v2 unit；共享 nginx 只改 B 虚拟主机，验证语法/路由隔离后优雅 reload，不全局 restart |
| 旁路隔离 | B 新建目录、Linux service user/systemd unit、端口、DB/权限、Redis 实例或独立 ACL、COS 策略、env/密钥及后台站点 | 隔离环境产出制品；禁止生产原地 npm/maven 构建、装依赖、升级 JDK/Node/PG/Redis；CPU/内存/IO/连接池/并发设硬限额，资源不足缩 B 或独立服务器，不能削减或停止 A；不以双进程写设计库替代隔离 |
| 内部成本 | 设计用户点数与平台服务调用成本分开记录 | 具体结算方式、成本账形态及是否月结待业务确认 |

## 三、复审状态与实施授权

R1、R2、R3 均为 **FAIL**；v5 是第三轮后修订稿，原先未经复审。旧稿“全部已拍板”“不再复审即可开工”均作废。本轮 [Codex R4 及补充](./Codex复审-R4-20261110.md)已归档，旧 v5 仍为 FAIL（6 P1+1 P2），未批准 v6；工具正常退出和作者修改均不是通过证据。

P0–P4 均待批准，阶段与验收约束同步如下；详细门禁见主方案及基线 A17–A20。

| 阶段 | 保护要求及验收门禁 |
|---|---|
| P0/P1 | 保护现有发布组合；先在隔离环境证明 internal HTTP、服务身份与独立计费接口可复用。缺接口则列独立设计兼容性发布前置任务，完整证明不中断/不退化且另获授权才触及 A 生产；不承诺零改动，不假定蓝绿/影子方案，不绕过独立身份或钱包 |
| P2/P3 | 资金留 A 原地；隔离环境全量演练及压测，生产不压测/全量扫描迁移，源端采样和搬迁读取只读低负载且预演可接受。仅冻结经归属证明的 B 写源；旧 B 接口/旧 token/worker/通知消费者须定向停用或交唯一 owner，A 用户、任务、付款、回调继续运行；不能定向暂停或非零 B 历史不能一致迁移即阻断，不停整个 A、不保留双写 |
| P4 | B 旁路上线；上线前、启动 B 时及切换后持续比对 A 登录审批/已开通权限、灵感/AI 终态/预算、付款退款回调、延迟/错误率/资源及数据资产/余额不变量；只读或授权测试账号/渠道，阈值由预演实测，不虚构 SLA。A 任一功能或数据异常立即停 B 发布和新增负载，保留 A 并按预案隔离排错 |
| B 回退 | 仅操作新增 B 服务/配置/流量和 B 账本恢复，不恢复设计库快照、不换旧设计 jar、不覆盖设计静态资源；B 已写入/充值不得简单把 api2 指回旧融合钱包，须保持唯一 owner 和账本一致，否则暂停 B 入口、继续 A |

`api`/`api2` 当前同指融合服务，切换前须核设计小程序、支付/退款回调、Runtime 回调、素材 URL 对 `api2` 的实际依赖；归 A 的请求保持原落点，归属未核实禁止全量切走 `api2`。换路由本身不证明停写隔离或零停机。

取消固定工期、停机不超过 60 分钟、两端前端及 MP 配置零改动承诺。正式排期和窗口由实际开发范围、资源测量、渠道验证及全量演练确定；本轮没有执行任何生产变更。
