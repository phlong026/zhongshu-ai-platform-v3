### 2.1 system 关系与跨组织历史

- 组织主键是 `pf_org_unit.dept_id`，根组织满足 `org_id=dept_id`；不能假设存在 `pf_org_unit.id`。`pf_staff_post` 同时连接 `user_id`、`org_id`、`team_id` 和 `role_code`。
- `system_users`、`system_user_role`、`system_role`、`system_role_menu`、`system_menu`、`system_user_post`、`system_post`、`system_dept`、`system_tenant`、`system_tenant_package` 按 B 身份/组织闭包保留 ID。菜单父链、数据权限部门集合、tenant package 菜单集合也属于引用。
- bootstrap 会播种部门、角色、菜单、字典等公共行；导入前比对主键与业务键内容。相同内容去重，冲突生成逐行决议；不使用无条件 upsert 覆盖，也不整体复制旧 system 表。bootstrap-admin 与历史用户导入的先后顺序必须由 build owner 协调，避免管理员 ID/用户名冲突。
- 共享人员在 A 的登录时间/IP等运行字段可以继续变动，但 B 只接收审定的业务身份快照。角色、停用、组织等业务字段如果仍允许 A 修改且要求同步 B，就没有完成停写：需先确定主写方和变更交接，不能以“公共表”豁免。
- 不迁移 `user_session`、OAuth access/refresh/code/approve、验证码、Redis token/权限缓存。B 重登；公共 OAuth client/社交 client 的注册元数据按新应用重新配置，凭据不随数据文件复制。
- `pf_wechat_binding_event` 按 **org_id** 过滤，不按 user_id 把一个人的全部组织事件一起导入。`binding_id/previous_binding_id` 指向绑定历史；保留撤销记录。`org_id=0` 为无任职记录的特殊审计，须单独授权归属，不自动并入任一组织。
- 实际组织过滤实现是 `platform/platform-identity/src/main/java/cn/iocoder/yudao/module/platform/identity/PlatformIdentityConfiguration.java` 注册 `pf_wechat_binding_event → org_id`，查询由 `WechatBindingEventMapper` 进入 `OrgScopeRule`。迁移后必须用真实组织范围测试证明甲组织查不到乙组织及 org=0 记录。

历史“41 钱包、13743 可用、24 预留、3 笔成功订单”等聚合仅是方案引用的历史快照，不能证明 B 零资金。本轮没有复核它们，更不能清零 24 预留。

| 预留/用量 | `ai_task_charge/ai_job_settlement/service_usage_charge/refund_order` → 审定 B charge/refund 或留 A 唯一结算 | 按 biz_type/biz_id/charge state 拆明预留成因；冻结期间保持总额，不靠置零消差 |

| 通知 | `payment_notification_inbox` → 持久接收端 + 明确 consumer | 冻结期间仍验签持久化，按支付/退款类型重查可信事实；收到/处理/授予权益三个水位分开 |

冻结证明至少记录：manifest/hash、scope version、各进程/worker gate epoch、当前请求/事务/外呼租约数量、每类待决对象 ID、快照标识、每表行数/键集合摘要/内容摘要、按钱包和状态分组的金额与预留、通知接收/消费水位、已授予权益集合、任务 settlement version。单看 `max(id)` 或 `update_time` 无法覆盖旧行状态更新，也不能证明无在途写。

非零方案须在 A 连续服务下二选一并明确范围：旧 A 继续负责审定历史在途直到结清，B 不接手同一权益；或在可靠接收仍运行时完成消费者封锁、重放水位和所有权转移。两种方式都未演练；不能在无法满足唯一 owner 时承诺“无中断迁移”。

### 4.3 最小开关契约（拟实现，尚未决定字段/代码）

建议单个旧B gate，状态 `OPEN → DRAINING → FROZEN`；不要复用 `platform.legacy-design-bridge.enabled`，该属性决定本地/远端装配，不是写入冻结。

- OPEN 保持旧融合行为；DRAINING 阻断新B请求、新旧B会话铸造/刷新和新后台领取，已登记在途由原 owner 收口；FROZEN 只在全部 writer 与外呼租约完成排空后成立。A请求和任务不受状态切换影响。
- B支付回调在DRAINING/FROZEN仍验签和持久接收，其 consumer 按明确owner执行或留待恢复。状态展示必须区分“入口已封锁”“后台已排空”“通知接收仍推进”，不能一个true冒充三者完成。
- scope是审定manifest的org/account/order/job/command映射，来自服务器受控配置，不能接受前端自称app=B或任意Header来决定归属。缺失/冲突对象失败并列出阻断项；未知不能按A放行后宣称全部B冻结。
- 在claim的SQL中过滤后再LIMIT，执行写事务再次核对状态/epoch；否则前50条都是冻结B会饿死A任务，或旧线程在切换后仍落账。
- 配置需要可热加载并带版本/hash、状态变更审计和本机受控管理方式；纯启动时 `@Value` 必须重启A才能改变，不满足“不停A”切换要求。不新增公开无鉴权的切换接口。具体热切实现需鉴权/并发独立审查后编码。
- 多实例各自确认同一scope/epoch；仅内存锁不能证明跨进程停写。当前生产实例数、活动线程、请求队列及可用管理入口均未核实。
- FROZEN之后工具只读取B快照，不恢复A库、不修改A账号状态来伪造停写。解除冻结不是失败后自动动作；B已有写入后必须按账本恢复方案处理。

## 11. 热停写门禁：G1本地内核已实现，业务接线与完整冻结尚未完成

本节依据前述已定位代码收敛，不扩大源码扫描。主线已明确旧commerce/identity及ZhongshuJobDriver在B工作树可以另划实现范围；`AiJobSettlementService`、billing、`AssetService`仍由原作者持有。先在**B工作树的融合兼容基线**验证门禁，A最终移植由兼容作者协调。本地测试通过不能证明现生产已有可热切门禁。

### 11.1 三个必须分开的判断

1. **请求来自谁**：ADMIN/旧设计用户/Runtime/新能力服务身份。
2. **写的是谁的数据**：目标org、account、order、refund、job、asset、system关系的归属。
3. **当前由谁执行**：旧融合A、新B或A的设计能力服务。B消费的设计资源仍可由A执行；不能因调用来自B就封锁新A能力服务。

判定返回 `A`、`B_LEGACY` 或 `UNKNOWN`，附scope版本和匹配规则。A保留来源包括设计消费者及已获授权的新平台服务成本/设计资源路径。`B_LEGACY`包括核准清单内的旧B对象和明确旧B专属控制器/后台业务。`UNKNOWN`拒绝涉及迁移对象的写入并阻断冻结证明；不能用“未在B列表”当作已证A。

account归属不能只看 `fr-service:`：该前缀是B的正向线索，但历史非前缀映射必须纳入审定scope。新A用户继续注册/登录，须由服务端已有原生A身份来源及已核应用标识正向确认；若需要新增来源证明，列为identity作者的明确工作，不通过请求Header或前端传来的appId猜测。普通A身份与旧B共用同一账号而无法按对象分离时，**不得进入FROZEN或上线B**。

### 11.2 热控制通道与故障行为

采用受OS权限保护的**固定本机控制目录**，不新增HTTP开关、不修改数据库schema。G1安装属性为 `platform.legacy-b-write-control-directory`，另有固定 `platform.legacy-b-write-instance-id`、`platform.legacy-b-write-scope-sha256`。目录内文件固定为 `control.properties`、`checkpoint.properties`、`writer.lock`；控制内容不能指定其他路径、SQL、类名或回调URL。当前没有修改任何运行配置启用门禁。安装代码/初次配置仍需后续兼容发布，本轮不执行生产安装。

控制文件采用严格键值格式，仅四键：`format=legacy-b-control-v1`、单调递增 `generation`、`state`、`scope_sha256`。重复/额外键、坏值、空文件、超过2MiB均拒绝；不是通用Java Properties或JSON解析器。目录需当前用户所有且权限不超0700，文件不超0600，拒绝末级符号链接，依赖受保护的本机父目录及支持文件锁/fsync/原子替换的本地文件系统。更新使用同目录0600临时文件、文件force、ATOMIC_MOVE和目录force。G1没有实现真实owner scope加载、线上拓扑发现或回执收集，不能把hash当作归属全集证据。

读取器使用组件自有单线程按秒加载，不注册为Spring共享TaskScheduler/ScheduledExecutorService，销毁时关闭。A明确归属的准入在B锁、B文件访问之前返回。B准入和状态变化在B专用锁内持久化checkpoint，成功后才返回permit；因此B有本机磁盘延迟，这不是所有请求都无文件I/O。首次加载/每次进程重建后，B必须重新校验当前控制文件才可准入。

- 未配置门禁时是 `NOT_INSTALLED`，兼容旧启动行为；不得导出FROZEN证明。
- 已安装后，加载失败、同generation异内容、generation倒退、scope hash不匹配不能变为OPEN；保留最后有效状态并告警。首次启动无有效控制状态时对已识别旧B关闭准入，冻结证明为不就绪；不关闭A进程、不全局禁调度。
- 如果连scope都无法加载，涉及未能确认归属的共享写入失败且门禁不就绪；这是会影响共享业务的异常，必须在发布前负向测试并阻断迁移，不承诺“所有故障都不影响A”。恢复时只加载核准scope，不能默认全属A。
- scope在一次DRAINING/FROZEN期间固定，不能通过替换B账号集合绕过冻结。调整scope必须走新的独立审核轮次，并重新取得实例/对象证据。
- 第一版不提供FROZEN→OPEN的自动或热解冻功能。回滚不自动重开旧B；解冻需确认B无新写或已完成账本恢复，另行设计/授权。
- 不调用 `/actuator/refresh`、不公开本机管理HTTP、不开全局security matcher豁免，不把开关塞到用户可控制的Header。控制文件权限、所有者、符号链接和原子替换行为纳入独立review。

### 11.3 状态机及在途工作

| 状态 | 旧B新HTTP/新token/新业务写 | 已准入旧B事务或外呼 | B通知接收 | A设计和支付 |
|---|---|---|---|---|
| OPEN | 原行为 | 原行为 | 原行为 | 原行为 |
| DRAINING | 拒绝；旧token也不能继续调用有写副作用的GET | 仅已登记的原操作允许按原owner收口；不扩展为新业务提交 | 验签、去重、持久接收；消费遵循明确owner策略 | 持续运行 |
| FROZEN | 拒绝 | 不允许残留未交接业务写；发现晚到写立即阻断证明 | 可继续可靠接收，消费方单独记录 | 持续运行 |

FROZEN明确表示“**旧B业务写源已排空/移交**”，不是所有B相关表完全不变。支付接收inbox是允许继续变化的例外，单独采集接收水位；不得将其放入需要完全静止的业务表快照后声称全表一致。

G1使用有界的活动工作登记器（最多10000项，同时受文件2MiB限制）。准入与状态切换在同一B专用锁内完成；其中包括本机checkpoint持久化，不做DB/HTTP，不持门禁锁等待业务事务。A明确归属直接返回A permit，不获取B锁、不读B文件。B同步磁盘开销和真实吞吐仍未压测。

G1 permit是进程内不可由请求字符串重建的对象；checkpoint保存固定scope/generation及UUID→writer/operation/unknown记录。writer/operation只允许有界技术标签，不能写token、真实个人信息或支付凭据。`fork`在父操作仍有效时预登记子工作，`close`幂等；UNKNOWN关闭后仍保留，UNKNOWN落盘失败时也保留内存未知标记，防止随后close误删。在磁盘上至少保留原已登记工作，进程重建不会凭空完成它。G1不提供未知终态自动解除或fault复位工具。

以下事务/afterCommit/业务接线仍属于后续G2/G3要求；G1不会自动安装Spring事务回调，也没有真实业务对象owner解析。不能只用ThreadLocal：方法返回后事务可能仍在提交，异步事件也可能随后执行。

- 公共服务入口在实际变更前取得permit；事务已有时登记到事务完成回调，直到提交/回滚后才释放事务部分。外呼与其CAS收口也属于同一操作的活动范围。
- 原操作内部嵌套事务可以继续，但必须继承已登记父操作；DRAINING之后没有父permit的新B调用拒绝。禁止将任意传入operationId视为合法父permit。
- system删/停用事件的待执行工作必须在生产事务提交前登记；after-commit监听器接续登记的工作并在REQUIRES_NEW事务结束后释放。回滚必须释放预留。不能先让system提交、再由监听器看到FROZEN而静默skip，不能吞撤权事件来凑active=0。
- 控制状态设为DRAINING只表示关闭新准入；活动计数归零不能单独证明没有任务。还要检查已知持久任务、外呼lease、内容provider任务、待处理通知与已发布异步事件。超时只返回排空失败，绝不强制清零计数、预留或lease。
- 旧B未领取队列任务可以停止领取后逐条移交；已提交到外部provider的任务必须有原owner收口或经过评审的交接规则。第一版不自行重发UNKNOWN请求，也不凭providerTaskId缺失判定从未外呼。

### 11.4 多实例冻结证明与水位

门禁每实例产生只含状态/计数/摘要的本机状态回执：instanceId、bootId、control generation、scope hash、applied state、active操作数、待交接对象计数、最近错误和单调递增状态序号。实现不得靠“扫描到一份回执”自动推断线上只有一个实例。

冻结工具流程为：发送DRAINING→取得**已核实例集合的全部**同generation确认→等待活跃事务/外呼/事件排空→核对持久任务owner→申请FROZEN→取得所有实例FROZEN确认→建立业务快照和通知接收水位。任一步缺失、实例重启、scope变化或出现新的未登记写源，冻结证据无效。

bootId改变后即使内存active=0，也必须重新查询持久lease/任务并登记；不能利用重启丢失计数获得FROZEN。若新增实例未获同scope门禁配置，禁止其接入旧B流量。当前实例拓扑仍未核实，因此这里只能用两个本地实例/合成scope演练。

通知水位同时记录接收集合与处理集合，含channel/event标识、订单/退款关联、处理状态及摘要；单个max(id)不足以证明旧行状态变更。接收期间继续写的inbox先后快照需要增量重放与唯一consumer交接；在这项恢复未实现前，不允许启用非零历史支付迁移。
