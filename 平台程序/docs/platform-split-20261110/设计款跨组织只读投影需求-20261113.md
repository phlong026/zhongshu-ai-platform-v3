## 0. 结论摘要

| # | 问题 | 结论 |
|---|---|---|
| 1 | 关联键是否成立 | **成立**。`fr_commission.id`（设计委托号）是门店与"设计款"之间的既有权威关联键：委托行同时持有 `company_id`（门店归属）与 `design_org_id`（总部收款归属）；设计来源收款的 `source_ref` 恒为 `commissionId:version:stage`。 |
| 2 | 现有 `designFeeProgress` 能否直接给加盟商用 | **不能**。端点把"当前岗位 orgId"当作 `designOrgId` 传入，加盟商调用恒返回全 0；且聚合不按提交版本过滤，费用退回重提后会重复计入旧版本收款。 |
| 3 | 是否需要新权限码 | **不需要**。门店 `finance`/`boss`/`owner` 已有 `franchise:fin:query`；缺的是数据投影，不是权限。但**不能**复用 `/franchise/commissions`（门店 `finance` 无 `franchise:commission:query`，且 CRM 对象权限也会拒绝）。 |
| 4 | 是否改 `OrgScopeRule` 全局规则 | **不建议**。`fr_fin_receipt` 当前完全未注册 OrgScope，只有 `company_id` 一个组织列（值=总部 designOrgId），没有"付款门店"列；注册第二列必须新增列。即使列表/聚合查询因显式 `eq(company_id, 当前组织)` 而不会立即泄露，按主键读取路径（`lockById`/`selectById`）仍依赖后续组织校验，**不能把"已显式 eq"当作全局不变量**；扩展全局规则仍会改变所有查询的语义（未来漏写 `eq` 即越权，UPDATE/DELETE 同步放宽），风险不可控。改用**专用只读投影端点 + 显式双重校验**。 |
| 5 | A 端（设计平台）是否需要新增能力 | **金额进度不需要**：设计款账本在 B（`franchise-finance`），A 无此数据。**设计阶段**若要在同一视图展示，A 现有 `listProjects/getProject` 无 `commissionId` 契约，需 A 确认或改用 B 侧 `fr_customer_scheme.design_project_id` 间接映射。 |
| 6 | 历史数据能否投影 | **有条件可以**：`source_type='design'` 的唯一写入点会强制覆写 `source_ref`，格式可回填；但**必须同时通过四道硬校验**（G1 格式、G2 委托存在、G3 版本存在、G4 收款组织 == 该版本 `submission.design_org_id`），任一失败即该行**不可自动投影**、进人工清单。若存在 `manual` 设计款、孤儿版本或错组织收款，历史部分不能全量自动回填。 |

**推荐方案（一句话）**：在 `franchise-finance` 新增门店视角只读投影端点，入参只接受 `commissionId`，服务端先经 `franchise-api` 读取委托头并校验 `company_id == 当前 orgId`，再用**当前提交行**的 `design_org_id` + 提交版本聚合 `fr_fin_receipt`，返回白名单 DTO；不改 OrgScope 全局规则，不扩大任何既有财务查询的可见面。

## 1. 问题与目标

### 1.1 现象（已实证）

1. 设计来源收款写入时，记账组织被强制设为**总部设计组织**：
   - `FinReceiptService.register` 的 design 分支：`companyId = fee.designOrgId()`（`domains/franchise/franchise-finance/src/main/java/cn/iocoder/yudao/module/franchise/finance/FinReceiptService.java:84-89`）；
   - 同一分支强制 `post.orgId() == fee.designOrgId()`，即**只有总部财务能登记**（`FinReceiptService.java:163-166`）。
2. 查询端点把**调用者当前组织**当作 `designOrgId`：
   - `accountService.designFeeProgress(currentPost.require().orgId(), commissionId)`（`.../controller/admin/FinanceController.java:496-501`）。
3. 因此门店（加盟商）用自己的 `orgId` 查询时：SQL 条件为 `company_id = 门店 org AND source_type='design'`，命中 0 行，接口**静默返回全 0**（`FinProjectAccountService.java:64-86`），前端无法区分"没有设计款"与"越权/不存在"。
4. 门店财务岗位**有**财务查询权限（`franchise:fin:query`，见 `franchise-org/src/main/resources/db/migration/franchise-system/V20261101.852__fin_permissions.sql:14-23`），所以这不是权限问题，而是**数据归属 + 投影缺失**问题。
5. 门店侧没有任何"设计付款"记录：`fr_fin_payment`/`fr_fin_payable` 无 `commissionId` 关联（`franchise-finance/src/main/resources/db/migration/franchise/V20261101.804__fr_finance.sql:52-95`），仓内财务域对设计只有"总部收款"一侧（`grep 设计` 命中仅 `FinProjectAccountService`/`FinReceiptService`/错误码）。

### 1.2 业务目标

让加盟商在 Web 端看到**"我的设计委托款，总部确认到账到哪一步"**，同时：

- 不扩大加盟商的数据可见面（不能看到其他门店、不能看到总部内部凭证/流水/客户信息）；
- 不改动既有总部财务页面与对账口径；
- 口径可解释、可对账（应收/已收/已退/未收/最近到账日期），并能明确标注"总部已核实到账"而非"门店已付"。

### 1.3 非目标（本期不做）

- 不做门店侧"设计付款登记"（当前无数据模型；若产品要"我已付/未付"，是另一条独立需求）。
- 不做总部→门店的设计费退款申请/审批流（现有退款仍走线下登记，`FinRefundService`）。
- 不做跨应用（A↔B）的设计费数据交换。
- 不做历史数据修复（只给核对 SQL 与回填建议，执行放运维窗口）。

### 1.4 术语与口径

| 术语 | 定义 | 数据来源 |
|---|---|---|
| 应收（门店视角的"应付"） | 当前提交版本约定的首款/尾款/总额 | `fr_commission_submission.total_cents / first_cents`（当前 `version`） |
| 已收（总部已核实） | 总部已登记且状态为"已登记"的设计收款金额合计 | `fr_fin_receipt.amount_cents`，`source_type='design'`，`status='已登记'` |
| 已退 | 上述收款下"已核实"的退款合计 | `fr_fin_refund`，`status='已核实'`，`receipt_id` 命中 |
| 净收 | 已收 − 已退 | 计算值 |
| 未收 | `max(0, 应收 − 净收)` | 计算值 |
| 最近到账日期 | 当前版本已登记收款的 `max(received_date)` | `fr_fin_receipt.received_date`（业务日期，非 `registered_at`） |

> **口径警示**：现有端点自我描述为"设计费净额"，但返回的是"已收毛额 + 已退额"四个字段，由调用方自行相减（`FinanceController.java:496-497` + `FinProjectAccountService.java:59-61`）。新投影必须直接返回 `netReceivedCents`，避免重蹈歧义。
>
> **重复登记口径**：设计收款**没有**"同期款唯一"约束（`V20261102.810__fr_receipt_business_unique.sql:4-5` 的唯一索引只覆盖 `source_type='business'`），同一 `commissionId:version:stage` 可被重复登记整笔期款（`FinanceController.java:229-239` + `FinReceiptService.java:84-104`）；流水号相同会被 `uk_fr_fin_txn_no` 拒绝，但流水号不同或为空时无拦截。投影**不做静默去重**：`received` 按已登记行求和（会计事实），同时返回 `receiptCount` 与 `overReceivedCents` 暴露异常；`unpaid` 仍取 `max(0, 应收 − 净收)`，不因超收变负。

## 2. 现状实证

### 2.1 写入链路：设计来源收款如何落库

`FinReceiptService.register`（`FinReceiptService.java:70-113`）对 `sourceType='design'` 的处理：

| 步骤 | 行为 | 证据 |
|---|---|---|
| 门禁 | 必须传 `designCommissionId` + `designStage ∈ {first, tail}`，否则 `DESIGN_SOURCE_INVALID` | `FinReceiptService.java:147-152` |
| 委托存在且费用已批准 | `commissions.findCurrentFee(commissionId)`，`feeApproved()` | `FinReceiptService.java:153-159` |
| 组织门禁 | `post.orgId() == fee.designOrgId()`，否则 `ORG_MISMATCH` | `FinReceiptService.java:163-166` |
| 记账组织 | `companyId = fee.designOrgId()`（总部） | `FinReceiptService.java:86` |
| 金额 | `amountCents = fee.stageCents(stage)`（首款=`firstCents`，尾款=`totalCents-firstCents`，**服务端取价，不信客户端金额**） | `FinReceiptService.java:87`；`CommissionQueryPort.java:27-30` |
| 关联串 | `sourceRef = commissionId + ":" + submissionVersion + ":" + stage` | `FinReceiptService.java:88` |
| 其他字段 | `projectId`、`customerId` 来自客户端且**不校验**、允许为空 | `FinReceiptService.java:96-98` |
| 名称 | `"设计首款/尾款 · " + name` | `FinReceiptService.java:89` |

关键结论：**收款行没有"付款门店"列**，唯一的门店线索是 `source_ref` 前缀（= commissionId），再经 `fr_commission.company_id` 反查。

| 口径项 | 实际行为 | 证据 |
|---|---|---|
| 入参 | `(designOrgId, commissionId)`；`designOrgId` 决定 `company_id` 过滤 | `FinProjectAccountService.java:64-68` |
| 返回 | `commissionId, submissionVersion, firstReceived, firstRefunded, tailReceived, tailRefunded`（**毛额 + 退款分列**，无 net/unpaid） | `FinProjectAccountService.java:59-61, 86` |
| 有效实收 | 仅 `status='已登记'`；`待登记`/`已撤销` 不计 | `FinProjectAccountService.java:74-76` |
| 退款 | 每行实时查 `status='已核实'` 的退款并汇总 | `FinProjectAccountService.java:89-92`；`FinRefundMapper.java:14-17` |
| 版本 | `currentVersion(rows)` 取**所有命中行**的最大版本，但金额循环**不按版本过滤** | `FinProjectAccountService.java:77-85, 94-106` |
| 空结果 | 无行时返回 `{commissionId, 0, 0,0,0,0}`，不报错 | `FinProjectAccountService.java:69-86` |

**两个必须修的口径缺陷（投影不能原样复用）**：

1. **版本串账**：费用被退回后重提（`version=2`），`version=1` 的已登记收款仍会被计入 `firstReceived/tailReceived`，导致金额虚高。当前实现只在 `submissionVersion` 字段上返回最大值，金额却是跨版本求和。
2. **命名与语义不符**："净额"端点实际返回毛额；且不返回"应收/未收"，无法直接支撑 UI。

### 2.4 现有权限与可见性矩阵

权限种子（`V20261101.852__fin_permissions.sql:5-25`）：

| 角色 | `franchise:fin:query` | `franchise:commission:query` | 现状能否看到设计款 |
|---|---|---|---|
| 总部 `finance` / `finance-lead` | ✅ | ❌ | ✅ 通过现有 `/design-fee-progress`（org=总部） |
| 总部 `boss` | ✅ | ✅ | ✅ |

对象权限二次收口：

- `CommissionAccess.canRead`：同组织 `boss/owner`，或总部设计行政，或**能读该客户**的人（`CommissionAccess.java:36-45`）；

- 结论：门店 `finance` **即使补上 `franchise:commission:query`，也读不到委托**。投影端点不能复用委托控制器。
- 另：`submit` 只允许门店业务岗（`CustomerAccess.canWrite` 要求 `atStore && has(SALES)`，`CustomerAccess.java:59-62`；`CommissionService.java:169-180`），因此**当前业务上不存在 `company_id=总部` 的委托**；但投影仍需拒绝任何非本组织行（防脏数据/未来总部自营）。

### 2.7 两个数据缺口（与本次投影同源）

1. **委托就绪时间在生产不会被写入**：`DesignFeeProgressApi`（`markFirstReady/markTailPaid/markTailReady`）的唯一调用点是 `@Profile("local")` 的 dev 控制器（`yudao-server/.../dev/FranchiseE2ESetupController.java:32,91-108`）与单测；`franchise-finance` 未引用该 API。而 `complete`/`dispatch` 分别以 `firstReadyAt`/`tailReadyAt` 为前置（`CommissionService.java:267-275,290-298`），故：
   - 生产环境 `first_ready_at/tail_paid_at/tail_ready_at` 恒为空（除非运维另有脚本，**待确认**）；
   - `CommissionService.displayStatus` 依赖这三个字段，展示会长期停在"首款办理中"（`CommissionService.java:524-542`）。
   - **投影必须以 `fr_fin_receipt` 为唯一事实源**，不得用委托就绪字段，也不要复用 `displayStatus`。
2. **`customerId` 不可作为收款侧的关联字段**：design 分支的 `customerId` 直接取客户端入参、不校验、可空（`FinReceiptService.java:96-98`），且与 `designCommissionId` 无一致性校验。任何依赖收款 `customer_id` 的投影都会漏数或串数。

### 2.8 上游阻断项：总部组织变更后的设计收款登记（前置修复）

> 本节是独立于投影实现的**上游依赖**，评审时必须单独排期；投影端点本身不负责修复它。

| 维度 | 结论 |
|---|---|
| 触发条件 | 总部组织被停用/重建，`fr_commission.design_org_id`（创建时固化）与当前唯一总部不一致 |
| 失败链路 | 新总部读旧委托 → `CommissionOrgScope.java:17-18` 的 `(company_id, design_org_id)` 规则过滤 → `CommissionQueryAdapter.toView` 读不到委托头降级 `FEE_PENDING`（`:36-37`）→ `FinReceiptService.designGate` 抛 `COMMISSION_NOT_APPROVED`（`:153-159`） |
| 影响面 | 总部变更前创建的全部委托：**新总部无法登记设计收款**；`CommissionAccess.isDesignAdminOf` 要求 `design_org_id == post.orgId()`（`:57-60`），新总部也不能完成/下发；旧总部若已停用则无人可办 |
| 与投影的关系 | **不阻塞投影端点开发与历史读取**；但只要存在此类委托，投影展示的就是停滞数据。若目标租户发生过总部变更，**必须在投影上线前同批修复**（§7 上游修复、§10 Q8） |
| 修复候选 | a) 重提时同步更新 `commission.design_org_id`（需评估历史收款归属与数据迁移）；b) `CommissionQueryAdapter` 经显式跨组织只读端口读委托头（带授权校验，不做全局放宽）；c) 总部变更时提供显式"委托迁移"管理动作；d) 运维约束"总部组织 ID 不可重建" |
| 建议 | 先做 d) 止血，再做 a) 或 c)；b) 仅作为读取侧的兜底，不能替代归属修复 |

**两条失败路径都拒绝登记**：
- 未重提：旧提交行被组织规则过滤 → `findCurrentFee` 返回 null → `FinReceiptService` 抛 `COMMISSION_NOT_APPROVED`（`:154-156`）；
- 已重提：新提交行（`design_org_id=新总部`）可见，但委托头（`design_org_id=旧总部`）不可见 → 状态降级 `FEE_PENDING` → `feeApproved()` 为假 → 同样抛 `COMMISSION_NOT_APPROVED`（`:157-159`）。

**注意**：这不是"重提后收款记入新总部"——当前链路在读取委托头时就被组织规则拦下，收款根本不会产生。

## 3. 关联键方案比较

### 3.1 候选清单

| 候选 | 关联表达式 | 准确性 | 可行性 | 隐私风险 | 结论 |
|---|---|---|---|---|---|
| **A. 委托单号（运行时解析 `source_ref`）** | `fr_commission.id = split(source_ref,':',1)` 且 `source_type='design'` | 高 | 高（零迁移） | 低 | ✅ 可用作 MVP |
| **B. 委托单号（物化列 + 回填）** | 新增 `fr_fin_receipt.design_commission_id/design_submission_version/design_stage` | 最高 | 中（1 迁移 + 回填） | 低 | ✅ **推荐** |
| C. 客户 ID 映射 | `fr_commission.customer_id`（UNIQUE）↔ `fr_customer_scheme.design_project_id` | 中 | 中 | 中（可枚举他店 customerId） | ❌ 不推荐 |
| D. 手机号 + 项目号 | `fr_customer.mobile` + `fr_commission.customer_name`/项目号 | 低 | 低 | 高（PII、重名、跨组织） | ❌ 否决 |

### 3.2 方案 A：委托单号（运行时解析 `source_ref`）

**成立依据**：

- `source_ref` 是设计收款**唯一**的关联串，且由服务端强制生成：`fee.commissionId() + ":" + fee.submissionVersion() + ":" + stage`（`FinReceiptService.java:88`）；
- `source_type='design'` 的写入点全仓只有这一处（`grep` 唯一命中），不存在其他格式；
- 前缀匹配 `likeRight(sourceRef, commissionId + ":")` 不会被"更大 ID"误命中（`123:` 不匹配 `1234:...`），现有实现依赖该语义（`FinProjectAccountService.java:68`）；
- `source_type` + `source_ref` 已有索引（`V20261101.804__fr_finance.sql:34`）；但 `LIKE '前缀%'` 能否走普通 btree 取决于数据库排序规则（非 C 排序下通常需要 `text_pattern_ops`），**不能假定一定走索引**——这也是推荐方案 B 物化列 + 专用索引的原因之一。

**优点**：零迁移、零回填、上线快。
**缺点**：

- 字符串耦合业务语义，格式变更会静默漏数；
- 版本/阶段**可以**在 SQL 中用 `split_part` 解析（附录 B 的 B3/B6 即如此），但解析依赖字符串格式、无法用索引/约束保障；解析成功也不等于关联正确（仍需 G3/G4 校验）；列表页仍会退化为"每委托一次查询"（N+1）；
- 无法为"按委托聚合"建索引；
- 若未来出现第二条写入设计收款的路径，格式约束无数据库级保障。

### 3.3 方案 B：委托单号（物化列 + 一次性回填）——推荐

**做法**（下一期实施，本文件不写迁移）：

1. `fr_fin_receipt` 增加三列（均可空，仅 design 来源使用）：
   - `design_commission_id BIGINT NULL`
   - `design_submission_version INT NULL`
   - `design_stage VARCHAR(8) NULL`
2. 登记时在 design 分支同时写这三列（与 `source_ref` 同源，避免二次解析）。
3. 历史回填：从 `source_ref` 正则解析，**只更新 G1–G4 全通过的行**（§3.7）；任一失败保持 NULL 并输出清单人工处理。
4. 索引：`(company_id, design_commission_id, status)`，覆盖"总部侧按委托聚合"。
5. 迁移必须提供 undo（删列/删索引），并按仓内 `migration-undo` 约定放置。

**优点**：口径进 SQL（版本过滤、聚合、分页都可下推）；列表页 2 条查询（委托分页 + 收款分组）即可；不依赖字符串；可审计/可校验。
**缺点**：一次迁移 + 回填窗口；回填前需只读核对（附录 B）。
**风险控制**：列可空、只增不改；回填脚本幂等（`WHERE design_commission_id IS NULL`）；旧代码不读新列，回滚安全。

**替代实现**：独立关联表 `fr_fin_receipt_design_ref(receipt_id PK/FK, commission_id, submission_version, stage)`。它不污染通用收款表，但多一张表 + 一次 join，回填与回滚的运维面更大；本文件仍推荐列方案（KISS）。

### 3.4 方案 C：客户 ID 映射（不推荐）

- `fr_commission.customer_id` 有 `UNIQUE`（`V20261022.803__fr_commission.sql:45`），当前"一客户一委托"成立；
- 但"客户"是**门店 CRM 的私有对象**，不是设计款标识。用 `customerId` 作为投影入参会把"猜 ID"变成越权探测面（即使服务端校验归属，也等于对外暴露一个可枚举键）；
- 委托已经是最小必要的业务对象，没必要退到客户粒度；
- 且 `fr_customer_scheme.design_project_id` 只在方案回写后存在（`V20261102.807:5-9`），并非所有委托都有。

**结论**：仅在"同一客户多委托"未来成为现实、需要按客户聚合时才考虑，且必须服务端从 `customerId` 反查本店委托集合，不接受单独作为授权键。

### 3.5 方案 D：手机号 + 项目号（否决）

**实证不支持**：

- `fr_commission` 只有 `customer_name`，**没有手机号**（`V20261022.803:33`；`CommissionDO.java:33-36`）；
- `fr_fin_receipt` 没有手机号、没有"项目号"（`V20261101.804:5-34`；`FinReceiptDO.java:20-40`）；
- 手机号在 `fr_customer`，且 `fr_customer` 对总部不可见、对象权限只到 boss/sales（`CustomerAccess.java:45-56`）；
- 用姓名/手机号模糊匹配会引入重名、换号、跨店重复客户等误归属，且属于 PII 跨组织比对。

**结论**：不可行。若未来确需"无委托号的线下设计款"归属，应新增显式绑定字段（由登记人选择委托），而不是靠手机号推断。

### 3.6 推荐与理由

**推荐 B（物化列），MVP 可先 A（运行时解析）后平滑升级到 B。**

理由：

1. 委托号是既有、权威、服务端生成的键，不需要新造业务概念；
2. `fr_commission` 已经同时持有门店与总部两个组织归属，天然满足"跨组织投影"的两端；
3. 物化后用一条 SQL 即可完成版本过滤 + 分页 + 聚合，避免 N+1 与"版本串账"；
4. 格式来源确定（唯一写入点），但**关联正确性必须靠 G1–G4 硬校验**；失败行可回滚。

### 3.7 历史数据核对与补数据方案

上线前由运维在只读账号执行附录 B 的 7 条 SQL。**只有同时通过 G1–G4 的行才允许自动回填**；任一门禁失败即该行不可投影。

| 门禁 | 校验内容 | 不满足时处置 |
|---|---|---|
| G1 | 形态 + 数字范围：G1a 形态 `commissionId:version:stage`；G1b `commissionId` 为正 Long（≤19 位且 ≤ `9223372036854775807`）、`version` 为 `1..2147483647`、`stage ∈ {first,tail}` | 不回填、不投影；保持 `design_commission_id=NULL`，进人工清单；解析 SQL **必须先判范围再 `::bigint/::int`**，禁止让超范围值触发 SQL 报错 |
| G2 | 解析出的 `commissionId` 在 `fr_commission` 存在 | 同上（孤儿收款） |
| G3 | 解析出的 `version` 在 `fr_commission_submission(commission_id, version)` 存在 | 同上（孤儿版本；DDL 无该关联外键约束） |
| G4 | 收款行 `company_id` == 该 `version` 的 `submission.design_org_id` | 同上（错组织收款；说明登记时组织已漂移或有脏写） |
| G5 | 当前版本 `submission.design_org_id` ≠ `commission.design_org_id` | **可回填**；投影读取以提交行为准（§2.8），并入差异清单 |

**预期分布**：G1–G4 失败数应全部为 0、`auto_backfillable = design_receipts`。**超范围样例**（如 `1:2147483648:first`：形态合法但 `version` 超 int 上限；或 19 位且大于 bigint 上限的 commissionId）必须计入 G1（`g1_range_fail`）并进人工清单，**不能被 SQL 报错中断**。任何非零类别都必须逐行解释；**不得用默认 org/默认版本兜底**，也不得把失败行按"当前总部"强行归属。

| 核对结果 | 处置 |
|---|---|
| G1–G4 全部通过 | 自动回填 |
| G1/G2 失败 | 人工清单；不投影 |
| G3 失败（版本不存在） | 人工清单；需人工确认对应委托版本后决定是否补提交记录，**禁止猜版本** |
| G4 失败（组织不一致） | 人工清单；需财务确认该笔收款实际归属，**禁止按当前总部改写** |
| 存在 `manual` 来源但名称以"设计"开头的收款 | 无法自动归属；财务逐笔确认后补 `design_commission_id`（人工工单） |
| G5 漂移 | 可回填；记录差异清单，投影以提交行为准 |

**绑定时点**：设计收款登记时由服务端从 `CommissionFeeView` 取 `commissionId/submissionVersion/designOrgId` 写入物化列，**不接受客户端传归属字段**；物化列与 `source_ref` 同源生成。
**历史回填**：一次性脚本 + 幂等条件（`WHERE design_commission_id IS NULL`）；只更新 G1–G4 全通过的行，不改变金额、状态、`source_ref`；失败行输出 CSV 清单。

## 4. 授权模型

### 4.1 谁能发起、看哪些字段、行级范围

| 维度 | 设计 |
|---|---|
| 发起者 | 门店岗位：`finance`/`finance-lead`/`boss`/`owner`（持有 `franchise:fin:query`）；总部岗位调用同一端点应得 404（非本店） |
| 权限码 | 复用 `franchise:fin:query`（不新增迁移）；如安全评审要求更细粒度，再加 `franchise:fin:design-view`，默认不扩 |
| 行级范围 | `fr_commission.company_id == currentPost.orgId()` **且** 仅返回该委托的聚合；列表端点只枚举本组织委托 |
| 列级范围 | 见 §5 白名单；`design_org_id/company_id/customer_id` 一律不返回 |
| 组织切换 | 以 `X-Post-Id` 对应的当前任职 org 为准（`CurrentPost.require()`，`CurrentPost.java:13-26`）；不信任任何客户端 org 参数 |

### 4.2 方案 A：专用只读投影端点（推荐）

**端点形态**（新控制器 `DesignFeeProjectionController`，仍在 `franchise-finance`）：

```java
@RestController
@RequestMapping("/franchise/finance/design-fee-projection")
@Validated
public class DesignFeeProjectionController {

    @GetMapping("/{commissionId:\\d+}")   // 数字约束，避免与 /page 冲突
    @PreAuthorize("@post.has('franchise:fin:query')")
    public CommonResult<DesignFeeProjection> detail(@PathVariable long commissionId) { ... }

    @GetMapping("/page")
    @PreAuthorize("@post.has('franchise:fin:query')")
    public CommonResult<PageResult<DesignFeeProjectionItem>> page(...) { ... }
}
```

**服务端固定校验顺序（不可调换）**：

1. `PostSnapshot post = currentPost.require()`（无任职 → `POST_REQUIRED`）；
2. 经 `CommissionQueryPort` 取委托头（**不直接读 `fr_commission`**，遵守 `franchise-api/package-info.java:4-5` 的模块边界；财务域已有该端口依赖：`FinReceiptService.java:54`）；
3. `head.companyId() != post.orgId()` → **抛"不存在"业务码**（不是 403，避免探测）；同时记录 `warn`（不含金额）；
4. 再按 `head.designOrgId()`（当前提交版本的 `design_org_id`）+ `head.submissionVersion()` 聚合收款；
5. 返回白名单 DTO。

> 顺序的意义：先校验归属、后查金额。反过来（先查收款再校验）会在日志/耗时/异常上泄露"该委托是否存在"。

**为什么不需要 `executeIgnore`**：`fr_fin_receipt` 当前未注册 OrgScope（§2.5），显式 `eq(company_id, designOrgId)` 即可跨组织读。
**但仍建议显式 `DataPermissionUtils.executeIgnore(...)` 包裹收款查询**，理由：① javadoc 要求的"跨组织必须显式"意图可读；② 防止未来有人给 `fr_fin_receipt` 注册 `(company_id)` 后，投影**静默变空**；③ 配套回归测试锁定"注册前后结果一致"。
**风险**：`executeIgnore` 会关闭全部数据权限规则，因此**必须**在包裹前完成第 3 步归属校验，且包裹范围内只做只读聚合，不做任何写入。

### 4.3 方案 B：给 `OrgScopeRule` 注册第二列（不推荐）

**事实**：`register(table, col1, col2)` 语义已被测试锁定（`OrgScopeRuleIntegrationTest.java:39,89-118`），委托三表已用双列（`CommissionOrgScope.java:17-19`）。但用于收款表有三道硬障碍：

1. **没有第二列可注册**：`fr_fin_receipt` 只有 `company_id`（值=总部 designOrgId），没有"付款门店"列（`V20261101.804:5-34`）。必须先新增列（等于做方案 B 的迁移），此时已无"零改动"优势。
2. **扩展全局规则会改变所有查询语义，风险不可控**：规则对 SELECT/UPDATE/DELETE 全部生效（`OrgScopeRule.java:20-22`），表达式为 `(company_id=org OR payer_org=org)`（`:55-70`）。列表与聚合查询显式 `eq(company_id, 当前组织)`（`FinReceiptMapper.java:27-28`、`FinReconciliationService.java:48-51`）；按主键读取路径依赖后续组织/对象校验（`lockById`/`selectById`，例如 `FinReceiptService.java:173-181` 先 `lockById` 再比对 `companyId`），因此**不能把"已显式 eq"当作全局不变量**。对显式 eq 的列表/聚合路径，追加 OR 后交集仍是 `company_id=org`、**不会立即泄露**；但任何未来漏写 `eq(company_id)` 的查询都会变成跨组织可见，UPDATE/DELETE 也被同步放宽（当前服务层校验是"每处新代码都要记得写"的脆弱约束）。投影只需"按委托读一条聚合"，用全局规则换取面状可见性不成比例。
3. **对账口径需要重新定义**：`FinReconciliationService.monthReconciliation` 按传入 `companyId` 显式过滤（`FinReconciliationService.java:48-51`），当前不会因规则叠加而串账；但一旦注册第二列，"门店实收现金"与"总部代收设计费"是否应合并统计将成为新的口径决策（`FinanceController.java:457-464`），不应由一次 OrgScope 扩展顺带改变。

**结论**：技术上可落地，但收益（省一个端点）远小于全局语义风险；**不采用**。

### 4.4 方案 C：放宽现有 `/design-fee-progress` 接受 `orgId` 参数（否决）

客户端传 `orgId` 或 `designOrgId` 等于把授权交给调用方；即使服务端再校验，也会形成"参数存在即被尝试"的探测面。现有端点签名保持不动（总部专用），新增门店专用端点。

### 4.5 失败语义

| 场景 | 返回 | 理由 |
|---|---|---|
| 委托不存在 | `1_102_000_028`（新）"设计委托不存在或不属于当前组织" | 与"他店委托"同一响应，防枚举 |
| 委托存在但属他店 | 同上 | 不暴露存在性 |
| 无 `X-Post-Id`/无有效任职 | 现有 `POST_REQUIRED` | 复用框架 |
| 无 `franchise:fin:query` | 403 | `@PreAuthorize` 统一 |
| `pageSize>100`/`pageNo<1`/非法 `status` | 400 `BAD_REQUEST` | 复用 `FinanceController.pageParam` 语义（`:196-206`） |
| 收款表异常 | 500 + error 日志（含 `commissionId`、`designOrgId`，不含金额） | 可观测性 |

## 5. 脱敏与字段白名单

### 5.1 可见字段（响应白名单，逐字段显式映射）

| 字段 | 类型 | 说明 | 来源 |
|---|---|---|---|
| `commissionId` | long | 委托编号（唯一业务标识） | `fr_commission.id` |
| `customerName` | string | 客户姓名（本店客户，见 §5.2） | `fr_commission.customer_name` |
| `status` | string | 委托原始状态（8 枚举，不改写） | `fr_commission.status` |
| `submissionVersion` | int | 当前提交版本 | `fr_commission.submission_version` |
| `payable.totalCents/firstCents/tailCents` | long | 应收（总额/首款/尾款） | 当前版本 `fr_commission_submission` |
| `received.firstCents/tailCents` | long | 总部已核实到账（毛额） | `fr_fin_receipt` 已登记 |
| `receiptCount` | int | 当前版本已登记收款行数（异常提示，不参与金额计算） | `count(fr_fin_receipt)` |
| `overReceivedCents` | long | 超收 = `max(0, 净收 − 应付总额)`；>0 说明重复登记或金额异常 | 计算 |
| `refunded.firstCents/tailCents` | long | 已核实退款 | `fr_fin_refund` |
| `netReceivedCents` | long | 净收 = 已收 − 已退 | 计算 |
| `unpaidCents` | long | 未收 = `max(0, 应收 − 净收)` | 计算 |
| `lastReceivedDate` | date | 当前版本最近到账业务日期 | `max(received_date)` |
| `otherVersionsNetCents` | long | 非当前版本的净收款（仅提示，不计入 `unpaid`；见 §10 未决问题） | 计算 |
| `asOf` | timestamp | 聚合时点（防缓存误读） | 服务端时间 |

### 5.2 不可见字段（硬禁）

| 字段/对象 | 原因 |
|---|---|
| `company_id`、`design_org_id` | 内部组织标识，暴露可被用于横向探测 |
| `customer_id` | 可枚举代理键（即使属于本店也没必要暴露） |
| 收款单号 `fr_fin_receipt.id` | 无业务价值，且可用于拼接其他端点 |
| `transaction_no`、`method`、`voucher_file_id`、`registrar_user_id`、`registered_at` | 总部内部凭证与经办信息 |
| 收款名称 `name`（"设计首款 · XX"） | 含拼接文本，可能与客户名重复；不返回 |
| 委托的 `note/feedback/recipient/scope/attachment/scheme_snapshot` | 设计行政内部意见与交付范围 |
| 费用审批意见（`Approval.note`） | 门店内部审批，但非本投影职责；不返回 |
| 成本、其他门店委托、总部自营项目 | 越权面 |

### 5.3 姓名/手机号脱敏规则

- **手机号**：本投影**不返回**。数据源（`fr_commission`/`fr_fin_receipt`）均无手机号；如未来要加，必须单独做隐私评审，且默认脱敏为 `138****0000`。
- **姓名**：
  - 门店查询**本店**委托：返回全名（客户数据本就属于该门店，脱敏反而妨碍对账）；`customer_name` 是**提交时快照**（`CommissionService.java:196-199`），CRM 改名不会回写，UI 需接受这一点；
  - 若未来开放"总部看门店"或"跨店"视图：统一 `保留首字 + *`（如"张*"），且必须另行评审；
  - 本投影**不读 CRM、不校验 `customer_id` 归属**，一律以 `commission.company_id` 为准；若上线前核对发现 `customer_id/company_id` 跨组织的脏数据，列入清理清单，不在投影层引入 `finance → crm` 新依赖。
- **禁止日志落 PII**：错误/告警日志只记 `commissionId`、`orgId`、异常类型，不记 `customerName`、金额。

### 5.4 与既有"字段裁剪"先例的一致性

仓内已有按角色裁剪金额的先例：总部设计行政看委托时，`totalCents/firstCents/recipient/policyId` 被置空（`CommissionService.java:151-166`；响应注释见 `CommissionRespVos.java:15-18`）。本投影沿用同一思路——**在服务端做字段白名单，而不是把 DO 直接序列化**。这也是不能复用 `/receipts/page` 的原因：它直接返回 `FinReceiptDO`（`FinanceController.java:107-124`）。

### 6.2 分页端点

```

```

| 参数 | 必填 | 约束 | 说明 |
|---|---|---|---|
| `pageNo` | 否 | ≥1，默认 1 | 复用 `FinanceController.pageParam` 校验（`:196-206`） |
| `pageSize` | 否 | 1–100，默认 20 | 超过 100 → 400 |

```sql
                          AND (NOT t.commission_in_range OR NOT t.version_in_range)) AS g1_range_fail,

                          AND c.id IS NULL) AS g2_commission_missing,
       count(*) FILTER (WHERE t.shape_ok AND t.commission_in_range AND t.version_in_range
                          AND c.id IS NOT NULL AND s.commission_id IS NULL) AS g3_version_missing,
       count(*) FILTER (WHERE t.shape_ok AND t.commission_in_range AND t.version_in_range
                          AND s.commission_id IS NOT NULL
                          AND t.company_id <> s.design_org_id) AS g4_org_mismatch,
       count(*) FILTER (WHERE t.shape_ok AND t.commission_in_range AND t.version_in_range
                          AND s.commission_id IS NOT NULL
                          AND t.company_id = s.design_org_id) AS auto_backfillable
FROM typed t
LEFT JOIN fr_commission c ON c.id = t.commission_id
LEFT JOIN fr_commission_submission s
       ON s.commission_id = t.commission_id AND s.version = t.version;
```

**判定**：先跑 B3/B4/B6/B7。只有 B7 的 `g1_format_fail`、`g1_range_fail`、`g2..g4` 全为 0，才允许"全量自动回填"；否则仅回填 `auto_backfillable` 行（这些行仍逐行满足 G1–G4），失败行按 B2/B6 输出 CSV 进人工清单，**不得猜版本、不得按当前总部改写归属**。B5 非空 → `manual` 设计款需财务人工确认。B4 非空只影响 G5 差异清单，不阻断回填。

**超范围样例与预期分布**：`1:2147483648:first` 形态合法但 `version` 超出 int 上限；解析 CTE 中 `version_in_range=false`、`typed.version=NULL`，该行归入 `G1_RANGE` 并出现在 B2/B6 清单，**不会执行 `'2147483648'::int`，因此不会中断脚本**。同理，19 位且大于 `9223372036854775807` 的 commissionId 也归入 `G1_RANGE`；`source_ref IS NULL` 归入 `G1_FORMAT`（COALESCE 后为 FALSE），不会被三值逻辑漏计。预期 `auto_backfillable = design_receipts`，其余类别为 0。
