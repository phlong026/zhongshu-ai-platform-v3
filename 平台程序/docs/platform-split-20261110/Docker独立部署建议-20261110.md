## 1. 结论与三种部署位置

推荐采用“现有设计应用保持运行，赋能后端及其专属基础服务使用独立 Docker Compose 项目”的形态。Docker 解决打包与运行隔离；业务依赖、数据库、身份、钱包和接口边界仍须按拆分方案完成。把当前融合 JAR 放入容器不能算两套应用独立。

| 部分 | 部署和发布位置 | 责任 |
|---|---|---|
| 赋能小程序前端 | 微信开发者工具上传代码，小程序账号的微信公众平台审核及发布，用户在微信中运行 | 页面、交互、平台身份和 API 调用；不是部署到服务器的 Web 静态站 |
| 赋能 Java 后端 | 服务器独立 Docker 容器 | 组织、员工、业务、权限、独立钱包及支付；HTTPS API 供小程序和总部 Web 使用 |
| 赋能总部 Web 后台 | 独立静态站点，可选专属 Nginx 容器 | 总部开通组织、充值/订单/对账、运营及配置；微信公众平台不能替代这套业务管理后台 |

用户提及的“微信公众号后台”在此应理解为**小程序账号对应的微信公众平台**。公众号和小程序的账号类型、发布能力不同；既有小程序继续使用自己的 AppID 和发布流程。总部 Web 的容器是可选部署方式，总部业务管理能力仍需建设。

## 3. 推荐的最小部署布局

```text
赋能小程序（微信发布） ── HTTPS ── 赋能 API 域名/经核验的路由
                                              │
总部浏览器 ── 独立赋能 Web 后台 ── HTTPS ───────┤
                                              ▼
                              宿主 nginx：仅转发已确认的 B 流量
                                              │
                              127.0.0.1:48081（建议，部署前查占用）
                                              │
                         独立 Compose 项目：backend-b
                                   ├── postgres-b（独立数据卷/账号）
                                   └── redis-b（独立数据卷/认证）
                                              │
                          经授权的设计能力 API：灵感/AI/预算
                                              ▼
                       现有设计应用 A、数据库和 Runtime 保持运行
```

- 推荐 B 使用独立 Compose project、专属网络和具名持久卷。B 数据库及 Redis 运行在专属容器中，不连接 A 的生产数据库或复用 A 的 Redis；版本由兼容性与迁移演练确定。
- B 后端可采用 `127.0.0.1:48081:48080` 的宿主/容器端口映射，前提是独立后端确实监听容器 48080 且宿主端口空闲。PostgreSQL/Redis 只在项目网络中提供服务，不发布宿主 5432/6379，避免与 A 冲突。
- 宿主现有 nginx 继续承担 HTTPS。只新增/调整 B 虚拟主机或确认归属的路径，经语法和路由检查后优雅 reload；不占用其宿主 80/443，不重启 nginx 或修改 A 站点。若 Web 也容器化，其宿主端口同样只绑定回环且单独核验占用。
- `api2` 当前并不是已隔离的 B 专属入口。必须核实 A 的支付/退款回调、素材地址、小程序和 Runtime 是否依赖它；A 依赖保持原落点，未经归属证明不得整域切换。
- Linux 容器内的 `localhost/127.0.0.1` 指容器自己。B 访问宿主设计 API 时，可评估 `host-gateway` 映射，但须验证实际监听、网络可达、调用鉴权与请求属主；宿主仅监听回环的服务不会因映射就自动可达。禁止把容器网络连通当成已有设计能力 API，或将 A 的端口直接开放公网作为捷径。

## 4. 保护设计环境的容器约束

1. A 的 JAR、后台目录、env、服务、数据库、支付配置及 Runtime 不迁进 Docker、不覆盖、不停启。B 只使用自己的发布目录、镜像、卷、密钥和网络；不挂载 A 数据目录、Docker socket，不使用 privileged 或 host network。
2. 镜像在开发/构建环境产出，固定版本或 digest，以非 root 运行；只将所需制品放入镜像，不将真实凭据写入 Dockerfile、镜像或仓库。生产仅部署已核验镜像，不在生产原地构建、装依赖或升级 Docker/JDK/数据库。
3. 分别设置 B 后端、PG、Redis、可选 Web 的 CPU/内存/PID 限制，限制日志增长、连接池、后台任务并发和可用磁盘占用。JVM 堆须为非堆及原生内存留余量；限额按隔离测试确定，不能照抄旧 Dockerfile 的堆参数。Docker 与 A 仍共享宿主内核、CPU、磁盘和网络，不自动保证互不影响。
4. 以 healthcheck 和依赖就绪条件区分“容器已运行”与“应用可服务”，并保留应用自身的连接恢复机制。Compose 的启动次序和 restart 策略不等于完整可用性验收。
5. PG/Redis 使用专属具名卷，必要的本地上传文件也应持久化。持久卷不是备份，必须有独立备份与恢复演练。部署命令限定 B 项目；不得使用会删除数据卷的操作或全局 prune 作为常规升级步骤。
6. 回退只针对 B 镜像/服务/流量及经验证的 B 数据恢复；数据库变更或支付写入后不能只换旧镜像，也不能把 B 流量切回原设计共享钱包。不得恢复 A 库快照、替换 A 包或停止 A 来处理 B 故障。
7. 资源不足或 A 出现功能、延迟、错误率、数据/资金异常时，停止 B 发布及新增负载，保持 A 运行。不能通过削减 A 资源满足 B 部署；必要时改用独立宿主。

## 5. 下一步顺序与微信前端配合

1. 按 v6.1 先完成源码与线上基线对齐、能力协议、独立身份/钱包和数据归属。设计侧若缺新接口、独立计费支持或旧 B 写源定向停止能力，仍须单独设计兼容性发布并验证、授权；Docker 不能跳过这项前置条件。
2. 为独立 B 制品准备生产 Dockerfile、`.dockerignore`、Compose 配置、配置清单、健康检查、备份和仅影响 B 的回退说明；本轮尚未生成这些实现文件。
3. 隔离环境验证 B 后端/PG/Redis、设计能力调用、支付、撤权和恢复；检查镜像架构、迁移、卷权限、网络/端口冲突及资源限额。随后取得部署授权，再在生产旁路启动，不立即接管现有流量。
4. 为赋能小程序配置实际 HTTPS request/upload/download 等合法域名；若有 WebSocket 使用对应 WSS 配置。更新钱包鉴权/接口等必要前端代码，开发者工具上传、体验验证、公众平台审核发布。前端由微信分发不等于接口无需修改，发布期间需明确新旧客户端兼容与回退边界。
5. 独立部署赋能总部 Web 并验证 API、登录、权限和跨域。验证 A 持续正常、旧 B 写源唯一归属及全部 v6.1 门禁后，才按批准窗口切换 B 已确认流量。
