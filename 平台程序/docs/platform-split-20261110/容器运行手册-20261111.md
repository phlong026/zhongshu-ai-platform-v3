状态：部署代码保持冻结。主线本机隔离联验已完成原 Compose 数据服务 67/67 检查、ops 备份与重启持久化，以及 PG 恢复 22 项、手工 Redis 恢复 30 项；原 Compose 的 PG/Redis 当前为 healthy 空库。证据及范围见[实施记录与验收清单](./实施记录与验收清单-20261111.md)。本次仅同步文档，不重跑服务；这些结果不代表生产部署、真实渠道或业务账本恢复验收。本手册不是生产授权，继续继承《后端拆分方案-20261110.md》§1.1、§6 和《Docker独立部署建议-20261110.md》的 A 保护约束。

## 1. 固定边界与文件

所有实现位于 `deploy/platform/`；回归检查是 `script/verify-platform-deploy.py`。不修改旧 `script/docker/`、pom、server 源码或 A 的任何文件。

| 项目 | 约定 |
| --- | --- |
| Compose project / network | `zhongshu-platform-b` / `zhongshu-platform-b_private` |
| 卷 | `zhongshu-platform-b_pgdata`、`zhongshu-platform-b_redisdata`，非 external |
| API | `yudao-platform-server/target/yudao-platform-server.jar`；容器 48080，唯一宿主映射 `127.0.0.1:48081:48080` |
| PG | `postgres:16.15-bookworm`；`postgres-b:5432/zhongshu_platform_b`，不发布宿主端口 |
| Redis | `redis:7.4.11-bookworm`；`redis-b:6379`，不发布宿主端口 |
| Java | 构建探针使用 `eclipse-temurin:17.0.17_10-jdk-jammy`，运行使用对应 `jre-jammy` |
| 身份 | API UID/GID 10001；PG/Redis UID/GID 999；补充组 GID 20000 仅用于外部 secret 文件读取 |

生产 Compose 没有 build，所有服务 `pull_policy: never`。镜像必须提前在隔离环境构建、核验架构/漏洞/来源后导入；标签本次未联网核验或拉取，生产应登记实际 digest，禁止覆盖已有版本标签。无 host network、privileged、Docker socket、A 目录挂载或 A 数据库连接配置。

`Dockerfile.dockerignore` 默认拒绝整个上下文，只放行 Dockerfile、探针源码与指定独立 JAR。构建上下文必须是 `平台程序/`，并使用 `-f deploy/platform/Dockerfile`，Docker 才会采用相邻的专用 ignore 文件。镜像只 COPY JAR 与探针 class。JAR 自身仍须由 launcher 制品检查证明不携带设计资源、凭据或旧生产配置；Docker allowlist 不能替代 JAR 内容审计。

资源初值（不是容量结论）：API 1 CPU / 1536 MiB / 256 PID，PG 1 CPU / 1024 MiB / 128 PID，Redis 0.5 CPU / 384 MiB / 64 PID；API JVM 堆最多 60%，Redis maxmemory 192 MiB、noeviction。三个服务根文件系统只读，数据仅在独立卷和有界 tmpfs；日志各最多 3×10 MiB。连接池最多 20，PG 最多 60 连接。宿主磁盘配额、卷增长、Redis fork/COW 余量、备份空间和与 A 共机容量必须实测，不能凭这些参数承诺可用性。

## 2. 外部配置与凭据

复制 `deployment.env.example` 到代码和发布目录之外，例如 `/etc/zhongshu-platform-b/deployment.env`，填入所有值。文件不得 world-readable。不要把真实 env、properties、口令或备份放入仓库。

| 必填变量 | 文件或值 |
| --- | --- |
| `PLATFORM_API_IMAGE` | 已导入的独立 API 固定版本标签或 `@sha256:` digest |
| `PLATFORM_PG_BOOTSTRAP_PASSWORD_FILE` | PG 初始化超级用户口令文件；只挂 PG，不挂 API/迁移容器 |
| `PLATFORM_PG_OWNER_PASSWORD_FILE` | `platform_owner` 迁移口令文件；只挂 PG 和显式迁移容器 |
| `PLATFORM_PG_APP_PASSWORD_FILE` | `platform_app` 应用口令文件 |
| `PLATFORM_REDIS_APP_PASSWORD_FILE` | Redis ACL `platform_app` 独立口令文件 |
| `PLATFORM_REDIS_BACKUP_PASSWORD_FILE` | Redis ACL `platform_backup` 独立口令文件 |
| `PLATFORM_CONFIG_FILE` | B 专属业务 `platform.properties`；无 optional 导入，不提供生产默认值 |

五个口令必须各不相同，32～256 字节、可打印 ASCII、无空格或结尾换行。可由密码管理系统生成；本仓库没有可用示例口令。Compose 使用 file secret，**不能依赖 YAML 的 uid/gid/mode 自动改宿主权限**。在目标 Linux 上由部署管理员把六个 secret 文件设置为专属组 GID 20000 可读、其他用户不可读（例如 root:20000、0640）；确认该组没有无关成员，父目录只允许获准管理员访问。`ops.py config` 在 Linux 会检查文件组/权限；macOS 离线检查不证明 Linux bind mount 或命名卷权限正确。

容器固定路径：

- API：`/run/secrets/spring.datasource.dynamic.datasource.master.password`、`/run/secrets/spring.data.redis.password`、`/run/secrets/platform.properties`。
- 迁移：`/run/secrets/spring.flyway.password`、`/run/secrets/platform.properties`。不挂 API/Redis 密码。
- 非敏感部署设置：`/etc/platform/runtime.properties`。
- 显式导入参数：`--spring.config.import=file:/etc/platform/runtime.properties,file:/run/secrets/platform.properties,configtree:/run/secrets/`。

`platform.properties` 只配置 B 自有业务渠道及独立密钥，不放 owner/超级用户密码，不覆盖强制连接目标、profile 或自动建表开关。当前 launcher 的真实渠道门禁包括：

- `platform.identity.wechat.provider=real`；`platform.identity.wechat.apps[0].appid` / `.secret` 以及需要的其他 App。
- `platform.identity.sms.provider=real`；`platform.identity.sms.sdk-app-id`、`sign-name`、`template-id`、`secret-id`、`secret-key`、`region`。
- `zhongshu.content.provider=real`、`zhongshu.content.task-sweep-enabled=true`。
- 生产资产存储：`zhongshu.franchise.asset.storage.provider=cos`；`zhongshu.franchise.asset.storage.cos.endpoint`、`region`、`bucket`、`secret-id`、`secret-key`、`path-style-access`、`api-call-timeout-ms` 使用 B 独立策略与凭据。`local` 仅用于测试，不能作为生产文件持久化方案。
- 设计远程服务：`zhongshu.design.remote.enabled=true`；`zhongshu.design.remote.origin`、`zhongshu.design.remote.caller-app-id`、`zhongshu.design.remote.active-key-id` 及匹配当前 key ID 的 `zhongshu.design.remote.keys.<active-key-id>` 必须完整。密钥只放外置 `platform.properties`，使用专用服务密钥的 Base64 编码，禁止复用 A 消费者或 Runtime secret。
- 钱包/支付等其他密钥按各模块最终配置契约审核。不能复制 A 的渠道密钥、会话、COS 整桶凭据或支付回调配置充数。

设计远程配置的部署约定：launcher 已提供 `origin=${PF_DESIGN_ORIGIN:}`、`caller-app-id=${PF_DESIGN_CALLER_APP_ID:}`、`active-key-id=${PF_DESIGN_ACTIVE_KEY_ID:}` 环境变量别名，但**当前 Compose 不转发 `PF_DESIGN_*`**。在 Compose 的 `.env` 中新增这些变量不会自动注入容器。本模板使用已必填挂载的 `/run/secrets/platform.properties`，直接填写上述完整属性键；无需新增 Compose 环境变量或把服务密钥放进 env。`active-key-id` 的值必须与 `keys.` 后缀完全匹配，密钥不提供示例值或生产默认值。

启用后必须 fail closed：缺少 origin/caller/active key、当前 key 无对应专用密钥、Base64 无法解码、解码后密钥长度不在 32～128 字节时，拒绝 API 启动。origin 必须是固定 HTTPS origin，不含用户名、密码、业务路径、query 或 fragment；caller 不得为空。完整凭据只满足启动配置门槛，仍需核验 A 侧对该 caller/key 的独立授权、轮换和网络可达性。不得以关闭远程服务或复用 Runtime 密钥伪装验收通过。

本轮通过源码核对上述拒绝逻辑：`CapabilityTransportConfiguration` 必须找到当前 key 并解码；`CapabilityTransportSettings` 校验 origin、key ID 与解码后长度；`RemoteDesignGateway` 校验 caller。既有配置测试覆盖缺少专用密钥、当前 key 缺失与 HTTP origin 拒绝，本部署分支未运行 Maven 或真实渠道调用，不把源码核对当作运行验收。

Compose 只能验证这些文件必填及本地文件策略，不能验证真实渠道是否有效、权限是否属于 B。launcher 的启动校验和授权渠道联验仍是门禁。

## 3. 数据库策略与初始化

PG 官方 entrypoint 仅在空卷初始化时执行 `postgres-init.sh`。初始化超级用户不允许 TCP 登录；`pg_hba.conf` 仅允许 `platform_owner`、`platform_app` 连接 B 库，其他库/用户拒绝。PG 的非 root OS 用户与数据库角色是两个层面，应用始终使用非超级用户 `platform_app`。

- `platform_owner`：LOGIN、非超级用户、不能创建数据库/角色、无复制或 BYPASSRLS；拥有 B 数据库和 `public` schema，用于受控迁移、dump 和空库恢复。
- `platform_app`：仅 B 库 CONNECT、public USAGE、业务表 SELECT/INSERT/UPDATE/DELETE、序列 USAGE；无 schema CREATE、数据库 CREATE/TEMP、TRUNCATE/REFERENCES/TRIGGER、其他角色成员资格或跨库 CONNECT。
- `postgres-policy.sql` 在每次迁移/恢复后以 owner 执行：检查角色属性、跨库权限、schema 权限、表/序列 owner 和应用权限；明确撤销 `flyway_schema_history` 的应用/PUBLIC 权限。通过前 API 必须保持停止。
- 默认授权只适用于 `platform_owner` 创建的对象；若迁移创建其他 schema、额外 owner 或安全定义函数，必须单独评审与补充检查，不能向应用授予 owner。

B launcher 的 `PlatformEnvironmentPolicy` 同时校验 API 的 `spring.datasource.dynamic.datasource.master.url` 和迁移的 `spring.flyway.url`。JDBC URL 必须指向 B 专属 `zhongshu_platform_b` 数据库，并遵守以下规则；部署模板的固定连接目标不变。

| URL 内容 | 当前守卫行为 |
| --- | --- |
| 身份/凭据参数 `user`、`password` | 拒绝，不允许覆盖独立配置的数据库身份或携带口令 |
| 连接目标/服务参数 `PGHOST`、`PGPORT`、`PGDBNAME`、`host`、`port`、`dbname`、`service`、`options` | 拒绝，防止通过 URL 参数改变连接目标或连接配置 |
| URL 的 userinfo、fragment | 拒绝 |
| 普通参数 `connectTimeout`、`socketTimeout`、`sslmode`、`currentSchema` | 允许这些参数名；仍须满足数据库目标及其他校验，不代表任意参数值都能成功连接 |

参数名在 URL 解码后按不区分大小写的方式检查，编码或大小写变化不能绕过上述禁止项。账号继续使用专用身份配置键：API 的 `spring.datasource.dynamic.datasource.master.username` 固定为 `platform_app`，迁移的 `spring.flyway.user` 固定为 `platform_owner`；密码分别通过 `/run/secrets/spring.datasource.dynamic.datasource.master.password` 与 `/run/secrets/spring.flyway.password` 专用 configtree 文件提供。不得把账号或密码拼入 JDBC URL，文档示例不提供真实凭据。

build lane e589 已取得 PostgreSQL 官方 Driver 参数覆盖绕过实证，并完成先失败后通过的 12 项测试；c31 独立审查仍在进行。此处同步当前实现与已报告证据，不将待审状态写成审查通过，也不重新执行构建或数据服务验证。

API 强制关闭 Flyway、Spring SQL init、Hibernate DDL、Flowable schema update、Quartz init。没有通用 SQL 执行器，也没有 clean/repair 或自动破坏性恢复路径。

独立迁移调用同一 launcher：`java -jar /opt/platform/app.jar migrate --spring.profiles.active=pg,migration ...`，通过 `compose.migrate.yaml` 隔离 owner 密码，无发布端口、无 HTTP/Redis/worker 上下文。固定 `spring.flyway.url=jdbc:postgresql://postgres-b:5432/zhongshu_platform_b`、`spring.flyway.user=platform_owner`，`clean-disabled=true`、`validate-on-migrate=true`、`baseline-on-migrate=false`。system/infra/quartz 基线由 launcher 专属 `db/migration/platform-bootstrap` 的 `V20260904.001`、`V20260904.002` 真实迁移创建，先于业务迁移；全新库直接 migrate，不预先导入 bootstrap dump。未知非空库不得自动 baseline，空库复现与 checksum 验证未通过前阻止上线。

## 4. 本地验证和授权后的运行顺序

以下是获准操作窗口使用的步骤。主线已完成的本机数据服务联验按第 6 节及实施记录引用，本次文档更新不重复启动或操作服务。后续运行仍须有对应的主线联验或生产窗口授权。示例发布根目录为 `/opt/zhongshu-platform-b/release`，须核对实际路径和文件校验和。

本地回归（无需 Docker daemon；假凭据在授权目录中的临时子目录生成并自动删除）：

```sh
python3 -I -B /绝对路径/平台程序/script/verify-platform-deploy.py
```

配置检查（只调用 Compose config，不连接 Docker daemon）：

```sh
python3 -I -B /opt/zhongshu-platform-b/release/deploy/platform/ops.py config \
  --env-file /etc/zhongshu-platform-b/deployment.env
```

1. 关闭所有上线门禁，确认 A 基线和 B 端口/网络/卷名称无冲突。加载并核验已构建镜像；不在生产拉取、构建或装依赖。首次应检查相关命名资源不存在或确为同一 B 项目，不能认领遗留同名卷。
2. 只启动 B PG/Redis。使用显式 project/env/file 和 `--no-build --pull never`，不依赖工作目录的隐式 Compose 文件。

```sh
docker compose --project-name zhongshu-platform-b \
  --env-file /etc/zhongshu-platform-b/deployment.env \
  -f /opt/zhongshu-platform-b/release/deploy/platform/compose.yaml \
  up -d --no-build --pull never --wait postgres-b redis-b
```

3. 先查看迁移计划，再由获准操作人执行。`--writes-frozen` 是对 B API、旧 B 写源、任务、消费者和渠道回调已经按主线方案冻结/移交的明确声明；脚本只能实测当前项目 API 已停，不能自动证明旧融合进程已定向停写。

```sh
python3 -I -B /opt/zhongshu-platform-b/release/deploy/platform/ops.py migrate \
  --env-file /etc/zhongshu-platform-b/deployment.env

python3 -I -B /opt/zhongshu-platform-b/release/deploy/platform/ops.py migrate \
  --env-file /etc/zhongshu-platform-b/deployment.env \
  --execute --confirm-target zhongshu-platform-b/zhongshu_platform_b --writes-frozen
```

4. 迁移成功且权限 SQL 验证通过后，使用同样的显式 Compose 前缀执行 `up -d --no-build --pull never --wait api`。正常 API 使用 `pg,prod`，不挂 owner 凭据。
5. 检查容器健康、B 业务闭环与 A 持续正常；之后才能按另行批准的路由计划接入流量。不要直接切整个 `api2` 域名。

健康探针由 Java 17 标准库实现，1 秒连接超时、3 秒请求超时，只接受 `GET http://127.0.0.1:48080/actuator/health/readiness` 返回 HTTP 200 且无详情的 `{"status":"UP"}`。launcher 应提供匿名可探活、无敏感详情的 readiness，包含 `readinessState,db,redis`。API 依赖 PG 真实账号 `SELECT 1` 和 Redis ACL PING 均 healthy；healthy 不证明支付、数据归属或 A 保护门禁已通过。

## 5. 备份、恢复与 B 回退

所有运维动作默认仅计划，不隐式停服务。`--execute` 必须同时明确 `--confirm-target zhongshu-platform-b/zhongshu_platform_b --writes-frozen`。实际执行会核对当前容器的 project/service 标签、网络、运行 UID、挂载和 B 卷/network 的 Compose 所属标签，并要求 PG/Redis healthy、API 已停。不能通过变更 project/volume 或目标 URL 操作 A。

备份：选择外部、尚不存在的绝对目录；父目录由获准管理员准备。`ops.py backup --backup-dir /专属备份父目录/本次唯一目录` 加上 env/执行确认参数后，导出 owner 的 PG custom dump（不带 owner/ACL）和 Redis ACL `platform_backup` 的 RDB，通过 manifest 记录固定 project/database、冻结声明和两文件 SHA256。失败不产生完成 manifest；目录保留供排查，不能拿作已完成备份。脚本不记录密码，不自动清理旧备份。

Redis 自身开启 AOF everysec + RDB，实例只属于 B；默认用户关闭，应用 ACL 移除 `@dangerous` 后仅显式补回 Actuator 所需的 `INFO`，备份 ACL 仅 PING/复制快照命令。容器健康同时检查认证 PING 和 INFO server；依据本地 Spring Boot 3.5.15 源码，`RedisHealthIndicator` 使用 INFO，reactive 版本使用 INFO server。独立实例内使用 `~* &*` 兼容现有会话/缓存键，不能因此接入 A 或共用实例。AOF 持久化不等于异地备份，也不代表零数据丢失。主线已完成本机备份、重启持久化和有界恢复验证，范围见第 6 节；生产备份的受控加密、异地复制、保留期/容量监控及业务级恢复仍需对应证据。

`ops.py restore --backup-dir ... --confirm-sha256 <可信manifest的SHA256>` **仅恢复 PostgreSQL**，验证固定 B 目标、manifest 来源/文件摘要以及目标没有业务对象，随后以 owner 在单事务执行 pg_restore。禁止覆盖非空库，不清库、不删除卷、不使用 clean。恢复后重新运行权限 SQL，API 保持停止。备份归档属于可执行 SQL 输入，SHA256 只证明文件一致，执行前必须确认归档来源可信、迁移版本正确且已审查；不得恢复未经审查的外部 dump。

Redis 恢复没有自动执行器。主线已完成隔离环境手工 Redis 恢复 30 项检查，覆盖范围为字符串/TTL；PG restore 22 项检查也已通过，包含拒绝非空目标、不覆盖数据。后续业务级恢复仍须在获准隔离环境核对序列化兼容、session/锁/队列和业务 owner。旧 AOF 可能优先于 RDB，因此不提供向既有卷覆盖文件的命令。当前合成对象恢复结果不能当作业务账本或全系统联合恢复验收，相关门禁关闭前不得据此恢复生产流量。

镜像回退：`ops.py rollback --image <已导入旧B镜像> --schema-compatible` 加上 env/执行确认参数。脚本检查旧镜像已存在，只用 `--no-deps --no-build --pull never` 替换 B API 并等待 healthy，不改 PG/Redis、A、nginx 或路由。`--schema-compatible` 必须有旧镜像与当前 schema/账本兼容证据；已有 B 写入、支付或不兼容迁移时，不能只换镜像。回退失败保留日志并保持 B 流量隔离，不能转回 A 旧共享钱包。

任何运维脚本都没有删除数据卷或全局资源清理入口。恢复、权限策略和回退不能撤销外部真实渠道副作用；这些操作需单独账本/回调核对。
