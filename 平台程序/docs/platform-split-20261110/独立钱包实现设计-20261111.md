# 独立钱包实现设计（安全审阅输入，2026-11-11）

## 实施边界

B 新模块 `platform/platform-wallet`，artifact `platform-wallet`，包 `cn.iocoder.yudao.module.platform.wallet`。只依赖现有 platform-authz、franchise-api、platform-test-support 等既有模块，不引入第三方 Maven 依赖，不依赖旧 commerce/design/ai/identity jar。root/platform 聚合注册由主线处理。消费者原代码保留。

首先实施无外呼部分：组织钱包、只追加积分账本、charge 幂等业务单、ADMIN 查询、旧桥接条件装配及 B 本地服务资源映射。支付外呼、认证、通知处理在安全审阅明确通过前不启用，不以 stub 或跳过测试宣称真实支付完成。迁移使用 `V20261111.901` 起，901–909 当前未发现已占用；迁移位于 `db/migration/platform-wallet`，提供对应 undo。

## 本地余额与授权

- `pf_wallet` 的 `org_id` 唯一，包含 tenant/status。钱包 org 仅来自 `CurrentPost.require()`；操作时通过 `StaffPostService` 重新验证有效任职、用户与组织状态，并核 tenant。不能信任客户端 wallet/org。
- ADMIN OAuth + `X-Post-Id`，没有第二 token。读取与充值沿现有 `platform:org:manage` 的岗位语义；种植 `platform:wallet:read` / `platform:wallet:recharge` 到当前已有管理权限的角色，不自动扩张到所有员工。
- 复用旧 `PointAccountService` 条件 UPDATE + `RETURNING` + 本地事务、`PointLedgerPortAdapter` 调用方式；改变为 tenant/wallet 作用域，余额表 `pf_point_account`，流水 `pf_point_ledger`。可用和预留余额均有数据库非负约束。
- 只追加账本；余额与流水同一事务。持久 idempotency key 同时比对 canonical request hash、tenant/wallet、金额、actor、业务标识，键相同请求不同必须拒绝，不返回其他钱包流水。
- `pf_wallet_charge` 唯一业务单先占位并行锁，reserve/consume/release 在同一业务事务内执行；重复请求只能读取相同单，终态互斥。原 reserve/release 原语不得单独暴露；控制器不接受任意扣点。
- B `StoreServiceAccountPort` 使用 `pf_org_service_account` 的稳定资源 ID，验证 tenant/org/status；它是资产归属映射，不能登录，不创建旧 account/designgrant。保留端口供 asset lane 使用。
- 旧 WalletSessionService/Controller/RevocationAdapter/StoreServiceAccountService 统一 `@ConditionalOnProperty(name="platform.legacy-design-bridge.enabled", havingValue="true", matchIfMissing=true)`；B 配置 false。所有新 B 钱包组件/控制器反向条件为该配置显式 false；即使 franchise-design 将钱包 jar 传递到 A，也不会与旧 commerce 的同名 bean 冲突或暴露新接口。platform-org 已使用 ObjectProvider，可无旧撤权适配器运行，独立钱包靠实时岗位校验撤权。

## 支付设计（等待安全审阅，不启用外呼）

复用并修正旧 RechargePaymentService / PaymentPort / PaymentFactValidator / RefundRecoveryJob / ManualPointAdjustmentService 与 xpay VirtualPaymentAdapter / WechatXPayProperties 的成熟源码，不新造支付框架。

1. `pf_recharge_order` 创建时固化 tenant/org/wallet/actor/post、付款人 appid/openid、套餐报价快照（金额/基础点/赠点/版本）、B 专用 `PFW` 订单号。客户端仅提交 planId、稳定 idempotencyKey；一次性 code 仅在专用支付参数调用消费。创建后不能换 payer 或报价。
2. 外呼前短事务验证授权、领取 lease 并持久请求状态；释放事务后调用渠道，返回后短事务复验岗位/用户/组织可用性与 lease 所有权后写入。撤岗后的响应不得下发支付凭据。未知外呼结果进入 UNKNOWN 待查，不能伪装失败或随意重提。
3. 真实 session_key 必须由专用 code2session 获取，并核对当前员工仍有效的 appid/openid 绑定；仅在内存短暂使用，不进入表、日志或响应。RealWechatStaffClient.openid 不含 session_key，不能冒充会话密钥。
4. `pf_payment_notification_inbox` 先验签再持久原始通知/摘要/渠道上下文，之后处理。未知订单消息也必须走可恢复 inbox。金额与 transactionId 必须取可信渠道查询事实，不能取通知体，也不能回落到订单声明；旧 PaymentFactValidator / VirtualPaymentAdapter 的 fallback 不迁移。
5. `pf_payment_transaction` 唯一键为 `(channel, appid, offer_id, environment, transaction_id)`，核对同一 order。支付事实和 `pf_recharge_credit` 分离，支付确认后入账失败可恢复；只有已验证事实能触发积分，信用记录和账本同事务。
6. `pf_refund_order` 固定原支付事实/金额/点数/退款请求号。查询只有订单总体状态不能证明具体退款成功，缺少可信退款事实时进入 UNKNOWN；UNKNOWN 不得退款重提。渠道最终事实到达后才消费预留或明确释放。
7. `pf_payment_anomaly_audit` 记录冲突与不可判定事实；不含敏感 code/session_key。`pf_manual_point_adjustment` 保留申请/审批与操作者分离，人工不能覆盖渠道事实。
8. 独立 `WalletRecoveryJob` 按事件类型补偿，以有界 batch + lease 领取支付查询、credit、通知、退款事件，不搬运 AI 混合 driver。通知为独立公开入口，仅允许渠道验签，不开放管理接口；后台 read/recharge/refund/adjustment 细分权限。

### 官方接口核验补充（文档 lane 回传）

- `query_order` 的 `wx_order_id` 为微信内部单号，`wxpay_order_id` 为支付交易号，`channel_order_id` 为商户单号；不能混用。`paid_fee` 的单位当前证据仍不足，自动入账保持关闭，不猜测其等于分。
- 退款必须用 `refund_order` 返回的退款单号逐笔 `query_order`，核对 type、原单关联、refund_fee 和退款号。status=5 只是商户扣款完成，status=8 才是用户到账；SDK 4.8.6 的 REFUNDED=5 不作为可信依据。type=1 普通退款、type=8 Apple 退款；Apple 不允许开发者主动退款。
- refund_order 要求 left_fee/refund_fee（分）、biz_meta、req_from；reason 是 0–5 枚举。UNKNOWN 不重提退款。退款通知字段是 MchOrderId/MchRefundId/WxRefundId/RefundFee/RetCode，不套用发货通知 OutTradeNo。
- 明文 Token 签名不覆盖 body，只允许触发可信查单，不能直接确认到账。安全模式 AES 解密必须显式验证 appid；不照搬 SDK 中被注释的 appid 检查。
- 依据：[query_order](https://developers.weixin.qq.com/miniprogram/dev/server/API/VirtualPayment/api_query_order.html)、[refund_order](https://developers.weixin.qq.com/miniprogram/dev/server/API/VirtualPayment/api_refund_order.html)、[虚拟支付](https://developers.weixin.qq.com/miniprogram/dev/platform-capabilities/business-capabilities/virtual-payment.html)、[消息推送](https://developers.weixin.qq.com/miniprogram/dev/framework/server-ability/message-push.html)。

## B 微信 xpay 通知 HTTP 合同（已落地，真实渠道仍有门禁）

实现位于 `platform/platform-wallet` 的 `WalletXpayNotifyController`、`WalletXpayNotifyConfiguration`、`VirtualPaymentAdapter` 与 `WalletRecoveryJob`。以下描述当前代码行为；本地测试通过不代表真实渠道验收完成。

### 路径、验签与读取边界

唯一公开渠道路径为 `/app-api/platform/wallet/payments/xpay/push`，仅 GET 地址验证、POST 接收通知两个方法标记 `PermitAll` / `TenantIgnore`。调用不需要 ADMIN Authorization 或 `X-Post-Id`；该豁免不扩展到相邻路径、其他 HTTP 方法或钱包管理接口。以下应答直接使用 HTTP 状态与渠道格式，不包裹 `CommonResult`。

| 项目 | 当前合同 |
| --- | --- |
| 验签元数据 | URL query 中的 `signature`、`timestamp`、`nonce`，三者均须非空白。不是 HTTP header，也不从表单或 JSON/XML body 提取。 |
| 长度限制 | `signature` 长度恰为 40；`timestamp` 最多 32 字符；`nonce` 最多 128 字符。整个未解码 query 最多 4096 字符。 |
| query 解码 | 按 UTF-8 URL 解码；任意参数名解码后重复、非法转义或 query 超长均拒绝。 |
| 签名算法 | 将服务端配置的 `push-token`、`timestamp`、`nonce` 按字符串顺序排序，拼接后按 UTF-8 求 SHA-1，生成小写十六进制摘要并以常量时间比较。服务端 token 缺失或空白时验签失败。 |
| 加密模式元数据 | query 只要出现 `encrypt_type` 或 `msg_signature`，即使值为空，也拒绝验签；当前仅支持明文推送。 |
| 原始 body | POST 必须为 1–65536 字节；GET 不要求 body，但同样受 65536 字节上限约束。入口在共享 body 缓存和访问日志之前限长；有 Content-Length 时先检查，无 Content-Length/分块请求最多读取 65537 字节以判断超限。 |

签名只覆盖 token/timestamp/nonce，不覆盖 body。当前实现不做 timestamp 新鲜度判断或 nonce 去重；接收重放由渠道上下文与原文摘要去重。通知只能提供查单提示，不能证明金额、付款人或到账状态。

入口有界读取后，将原文和 query 保留在本地请求属性中供 Controller 使用，对下游通用请求读取隐藏 body/query；两个方法同时关闭 API 访问日志。拒绝或持久化失败日志只记录操作与异常类型，不记录 token、签名、原始通知或异常原文。

### GET 地址验证

调用形式为 `GET /app-api/platform/wallet/payments/xpay/push?signature={signature}&timestamp={timestamp}&nonce={nonce}&echostr={echostr}`，花括号仅表示参数位置，不提供密钥或可用签名示例。

除上述验签条件外，`echostr` 必须存在且非空白。验签成功返回 HTTP 200、`text/plain`，响应体为 query 解码后的 `echostr` 原值，不再 trim 或改写；验签失败、缺少验签参数或缺少有效 `echostr` 返回 HTTP 403、`text/plain`、`verify failed`。GET 不写 inbox，也不查渠道。进入 Controller 之前发生的 query/读取错误遵循下表的前置入口错误合同。

### POST 通知与 ACK

调用形式为 `POST /app-api/platform/wallet/payments/xpay/push?signature={signature}&timestamp={timestamp}&nonce={nonce}`，body 为渠道原始 JSON 或 XML 通知。Controller 以原文 UTF-8 解码、trim 后是否以 `<` 开头选择 XML/JSON 应答，不根据请求 Content-Type 选择，也不在 HTTP 请求内解析业务事件或查单。

| 应答 | HTTP / Content-Type | 精确响应体 |
| --- | --- | --- |
| JSON 成功 | 200 / `application/json` | `{"ErrCode":0,"ErrMsg":"success"}` |
| XML 成功 | 200 / `application/xml` | `<xml><ErrCode>0</ErrCode><ErrMsg><![CDATA[success]]></ErrMsg></xml>` |
| JSON 失败 | 下列非 2xx 状态 / `application/json` | `{"ErrCode":1,"ErrMsg":"process failed"}` |
| XML 失败 | Controller 内的非 2xx 状态 / `application/xml` | `<xml><ErrCode>1</ErrCode><ErrMsg><![CDATA[process failed]]></ErrMsg></xml>` |

错误状态按实际处理阶段区分：

- 前置入口：body 超限返回 413；query 超长、解码错误、重复参数或 body 读取 IOException 返回 400。此阶段统一返回 JSON 失败体，包括 XML 请求，不读取完整超限 body 来决定应答格式。
- POST Controller：空 body、验签失败、明文入口收到加密模式元数据，以及服务参数或幂等冲突等 `ServiceException` / `IllegalArgumentException` 返回 400，并按已读原文选择 JSON/XML 失败体。
- POST Controller：数据库写入/事务提交失败、`notification-tenant-id` 未配置等其他运行时失败返回 503，并按已读原文选择 JSON/XML 失败体，不返回成功 ACK。

接收顺序固定为「有界读取 → 验签 → 原文、摘要和配置渠道上下文写入 inbox 的事务提交 → 成功 ACK」。未知订单也先持久化；同渠道上下文、相同原文字节的合法重放命中同一 inbox，在确认原租户一致后仍可成功 ACK。原文摘要使用 SHA-256，唯一维度为 `(channel, appid, offer_id, environment, body_hash)`；JSON 空白等字节变化会形成不同摘要。

ACK 只表示持久接收成功，不表示业务事件已识别、支付/退款成功或积分已处理。`WalletRecoveryJob` 在后续批次解析原文：发货事件 `xpay_goods_deliver_notify` 使用 `OutTradeNo`，退款事件 `xpay_refund_notify` 使用 `MchOrderId` / `MchRefundId` 定位；这些字段只作提示。事件无法解析、订单未知或查单事实不足时保留待恢复状态，不能依据通知金额发点或冲正。HTTP 接收阶段不调用 `queryOrder`、`queryRefund`、积分入账或退款接口。

### 配置边界与仍未开放的能力

| 配置 | 当前边界 |
| --- | --- |
| `platform.legacy-design-bridge.enabled` | 必须显式为 `false`；缺失或 `true` 时不装配 B 通知 Controller/前置过滤器。 |
| `platform.wallet.payment.enabled` | 必须显式为 `true`，默认 `false`。与上一条件同时满足才发布通知入口；开启入口不代表下列真实渠道门禁已解除。 |
| `platform.wallet.payment.push-token` | 明文推送验签使用的服务端配置；由受控配置提供，不从请求传入，本文不提供密钥示例。 |
| `platform.wallet.payment.notification-tenant-id` | 固定接收租户，必须大于 0，默认 0 时 POST 持久接收失败。GET 地址验签不检查该值，GET 成功不能证明 POST 配置完整。 |
| `platform.wallet.payment.appid` / `offer-id` / `environment` | inbox 的固定渠道上下文：channel 为 `XPAY`；appid、offer-id 必须非空白且分别不超过 64/128 字符；environment默认0；充值、退款订单表限定0/1。通知入口当前不单独校验此枚举，部署配置须保持一致。不从通知体或 HTTP 租户头选择这些值。 |
| `platform.wallet.recovery.enabled` | 默认 `false`；需要自动消费 inbox 时另行显式开启。定时任务默认首次延迟 30000 ms、批次间隔 60000 ms，分别由 `platform.wallet.recovery.initial-delay-ms` / `interval-ms` 配置，每批每类最多领取 50 条。未开启时成功接收的通知仍持久留存，不在请求内补做消费。 |

inbox 的 `tenant_id` 只在接收时由 `notification-tenant-id` 固定，恢复时不可改写。订单 lookup 同时限定该持久 tenant 与 orderNo/channel/appid/offer/environment，bind/finish 的行锁和 lease CAS 也带原 tenant。HTTP `tenant-id`、body 中的租户声明或其他租户的订单号不能改变归属；配置租户 A 的通知即使提示租户 B 的订单，也不绑定、不因该提示查 B 的渠道订单或发点，保持未知待定位。同租户绑定后的原文重放继续幂等；修改配置租户后重放同渠道上下文、同 body，会因原 inbox 归属不符而冲突，不能接管原记录。本实现没有跨租户动态路由。

以下真实渠道门禁仍待证据与独立验收，不因 HTTP 入口存在或本地测试通过而解除：

- `paid_fee` 单位未确证，`platform.wallet.payment.paid-fee-unit` 默认 `UNVERIFIED`，适配器不提供可入账金额。取得单位证据前不能将其猜作分或改为 `FEN`，也不能回退使用订单报价或通知金额。
- AES 推送尚未启用：入口拒绝 `encrypt_type` / `msg_signature`，后台解析也拒绝含 `Encrypt` 的原文；仍须补齐可信解密及 appid 校验，不能依赖 SDK 中被注释的校验。
- 真实开发者主动退款仍在冻结积分之前拒绝；`req_from`、`biz_meta` 和逐笔退款原单关联尚待核实。退款恢复只查单、不重发；当前 SDK 查询结果缺少已证实的原单关联时仍返回 UNKNOWN，不能确认终态或释放冻结。

## 前端 DTO 契约（本地部分先交付）

本节 ADMIN 接口响应走既有 `CommonResult<T>`；所有数据库 ID 用字符串，时间使用 ISO-8601；请求带 ADMIN Authorization 与 X-Post-Id。渠道通知使用上节独立 HTTP 合同。

- `GET /admin-api/platform/wallet/account` → `{walletId, orgId, status, availablePoints, reservedPoints, version}`。无 wallet/org 请求参数。
- `GET /admin-api/platform/wallet/ledger?pageNo=1&pageSize=20` → `{list:[{id,type,delta,availableAfter,reservedAfter,bizType,bizId,actorId,reason,createTime}],total}`。pageSize 1–100，默认 20。
- `GET /admin-api/platform/wallet/recharge-plans` → `[{id,name,priceFen,basePoints,bonusPoints}]`。
- `GET /admin-api/platform/wallet/recharge-orders?pageNo=1&pageSize=20` → `{list:[Order],total}`；`GET .../recharge-orders/{id}` → `Order`。均只读本地已验证事实，不能以客户端支付成功回调改状态。
- `POST /admin-api/platform/wallet/recharge-orders` 请求 `{planId:string,idempotencyKey:string}` → `Order`。创建前必须已有当前员工有效微信绑定，固定原 actor/post/binding 与报价快照。重复同键同请求返回原订单；不同请求拒绝。
- `POST /admin-api/platform/wallet/recharge-orders/{id}/pay-params` 请求 **`{code:string,idempotencyKey:string}`** → `{signData:string,mode:string,paySig:string,signature:string}`。字段必须叫 `code`，复用既有全局凭据脱敏；不接受 `wxLoginCode` 别名。关闭该方法的请求/响应访问日志，服务端手工校验 code，避免 Bean Validation 异常打印 rejectedValue。不得返回 session_key、第二 token、openid。
- `Order = {id:string,orderNo:string,status:string,creditState:string,priceFen:number,basePoints:number,bonusPoints:number,createTime:ISO}`。status 为 CREATED/PENDING/UNKNOWN/SUCCEEDED/CLOSED/FAILED；creditState 为 NOT_READY/PENDING/CREDITED/BLOCKED。到账展示需 status=SUCCEEDED 且 creditState=CREDITED。
- 幂等 key 长度 1–128，建单 key 与支付 attempt key 分开持久保存。建单网络重试复用原 key。pay-params 不保存 code/指纹/签名参数，任何已存在 attemptKey（包括成功）一律409，要求 fresh code + new attempt key；不得重放旧签名或重复消费 code。409只更换支付尝试，不能清除已有 order 意图。
- 错误码：503 支付通道未启用/参数不可用，409 attempt 已使用/处理中/失效，403 当前岗位无权限；1120000001 钱包/原 payer/绑定不可用，1120000002 幂等冲突，1120000003 点数不足，1120000004 状态不允许，1120000005 参数无效，1120000006 充值套餐不可用且本意图未建单，1120000007 总余额上限。只有 createOrder 的006可让前端清理未落单意图后重选；已有同key订单优先重放原快照，套餐后来下架不触发006。通用005/网络/UNKNOWN不能据此清意图。沿现有 `CommonResult` 返回，不把业务错误码当 HTTP 状态假设。
- 支付配置 `platform.wallet.payment.enabled=false`、`paid-fee-unit=UNVERIFIED` 为默认值；证据与真实渠道适配均具备前建单/签名显式返回503，不制造可支付假订单。查询与已验证事实的积分恢复保持独立。
- 账户 status 可为 ACTIVE/FROZEN；FROZEN 只冻结新增支出，保留查询与已发生业务的结算恢复。

## 独立安全审阅冻结合同（主线回传后实施）

- 创建订单从当前 ADMIN 有效微信绑定固定 appid/openid/bindingId、tenant/wallet/actor/post 与报价；无有效绑定拒绝。pay-params 只允许原 actor 与原有效 post，每次 fresh code 与独立 attempt key；换绑/撤岗不修改旧 payer。外呼后短事务锁后复验 user/post/org/binding 与当前岗位权限，lease CAS；该最终事务是签发线性化点，不承诺已发渠道凭据即时失效。
- payment fact、credit、refund channel、point reversal 状态分开。订单唯一 credit；余额与基础/赠点流水原子入账。已发生支付事实的补偿依据持久订单与已验事实，不能依赖 CurrentPost 或原操作者仍在岗。
- 整单主动退款仅 SUCCEEDED+CREDITED；占位与冻结基础赠点同事务，不足时零外呼。同订单非失败退款唯一，换 key 不可绕过；PROCESSING/UNKNOWN 保持冻结、不重提，可信逐笔失败才释放，逐笔状态 8 才冲正，5 仍处理中。
- 退款先于 credit 则阻断发点；外部已退但点数不足时保留退款事实、标记待追偿并冻结钱包支出，不能负余额。每条订单 SQL/幂等重读显式 tenant+wallet；通知 tenant 在接收时由固定服务配置写入 inbox，恢复只能在该持久 tenant 内定位订单，不能按通知提示跨租户改绑；交易唯一渠道字段全部 NOT NULL。

### 904 退款回滚守卫

`V20261111.904__undo_pf_wallet_refund.sql` 仅用于隔离或已停写环境。它在单个 PostgreSQL `DO` 块内，要求当前事务隔离级别为 `READ COMMITTED`，随后对 `pf_recharge_order`、`pf_payment_notification_inbox`、`pf_refund_order` 取得 `ACCESS EXCLUSIVE` 表锁，再检查三表是否均为空。其他隔离级别直接拒绝，防止外层事务的旧快照看不到刚提交的通知而误判为空。任一表有记录即抛出异常，拒绝删除退款表；不区分订单、退款或通知的终态，未定位的 inbox 同样受保护。支付 attempt/transaction/credit/anomaly 通过外键依赖充值单，已有充值单即阻断回滚。

锁覆盖检查至 DROP 的整个事务，避免检查后插入通知或退款的竞态。数据拒绝、锁获取失败或依赖阻断均不允许留下本脚本的部分 schema 变更。脚本不包含 `COMMIT`，独立执行时由单条语句保证原子性，在调用方事务中执行时参与该事务；失败后调用方须回滚事务并停止后续回滚步骤。Spring 脚本执行器需将整个 `DO` 块交给 PostgreSQL 解析，不能按块内分号拆开。

只有上述三表为空且数据库依赖允许时，才使用普通 `DROP TABLE pf_refund_order`；不使用 `CASCADE`，不删除支付、通知或积分事实。901–906 的隔离空库验证按 `906 → 905 → 904 → 903` 撤销，再按正序重建；提前撤 903 会被仍存在的退款外键阻断，退款表存在额外依赖时也必须先处理依赖。外层事务 rollback 的回归通过原表 OID 恢复验证，不能仅用重建后表结构相似代替原子性证据。

本次只加固 904 undo，不改变 forward 迁移、生产 Java、通知合同或其他 undo 的安全保证。迁移 manifest 的“禁止自动执行”策略保持有效；守卫通过不构成生产回滚许可，也不代表当前 A/B 联验包已更新。最终重包由统一构建 owner 处理。
