## 一、首轮原文

**GATE FAIL：旧v5不能直接实施。**“已定稿、无需复审、问题已关闭”没有用户授权依据；《架构决议》第1项“单后端终态”也与第5项“两套独立系统”冲突。本轮不批准尚未提交的新方案。

本地核实A=`94185124`、B=`8eadadba`。以下A指设计仓，B指赋能仓，源码路径省略包目录。服务器仅采用15:20–16:10附录；17点本地提交及当前工作区修改均不代表部署事实，最新线上状态未知。

1. **[P1] 设计开通基线仍然自相矛盾。**  
   【代码】A `ActivationRequestService.java:61–89`仍自动写入APPROVED和ACTIVE；A后台 `activation/index.vue:178–196`先审批、再独立调点，调点失败保留开通。B同服务`:62–87`已恢复PENDING，`AppProfileController.java:86–96`支持两种绑定来源；A该控制器`:103–107`仍只查兑换记录。  
   **后果：**17点文案/input修复不能证明审批闭环成立。**建议：**A作为独立设计产品主线，选择性引入B的审批、绑定修复；明确“开通与赠点原子完成”或“开通成功、赠点待补偿”的服务端状态及稳定幂等键，不能依赖浏览器连续请求兜底。

2. **[P1] 基线整合与后台交付范围不完整。**  
   【代码】B `admin-ui/src/router/modules/zs.ts:77–90`仍有激活码路由；定向搜索未发现activation页面、路由/API，用户详情`:143–146`仍取`accessCode`。  
   【文档】v5 §8主要描述裁菜单、拆构建，未覆盖独立赋能运营闭环。  
   **后果：**后端审批恢复后仍缺管理入口；菜单隔离不等于可运营。**建议：**逐文件登记“A保留/B选入/赋能专属/弃用”，禁止整仓覆盖；分别列出设计审批运营，以及赋能组织开通、人工充值、账本、定价、支付异常与对账页，并落实权限、接口和验收。不重建加盟商日常业务Web。

3. **[P2] 钱包新JWT尚未证明必要。**  
   【代码】B `WalletSessionController.java:37–43`已有平台岗位鉴权；`StaffPostServiceImpl.java:200–219`已有用户、岗位、组织有效性检查。`TokenAuthenticationFilter.java:71–91`说明未知token可能不建立登录用户，但不能证明新增钱包认证方案完整。  
   **后果：**v5 §5.2为保旧路径增加控制器自验认证面及撤权负担。**建议：**优先评估平台钱包使用现有ADMIN登录态、岗位权限及服务端组织归属，允许修改员工端路径；与专用JWT按隔离、撤权、维护成本比较后选定。“零前端改动”降为偏好。

4. **[P1] nonce退化幂等会造成重复扣费。**  
   【文档】§5.4缺键时使用`nonce+path+body-hash`，§5.5要求重试更换nonce；【代码】B `DesignAccessController.java:174–179`允许缺少业务幂等键。  
   **后果：**同一操作重试可产生新命令、新扣款。**建议：**收费写入必须绑定持久化业务操作ID，跨客户端、平台、设计收据保持稳定；同键异内容拒绝。nonce仅防重放。旧端缺键时须补客户端操作ID或可恢复的预建命令协议，不能用告警代替资金正确性。

5. **[P1] Flyway与权限隔离仍缺可执行依据。**  
   【文档】§6.3全局忽略missing，附录又建议同时忽略future；服务器附录记录历史133条迁移、A/B迁移集合不同。  
   **后果：**启动放行可能掩盖遗漏或来源不明；双库同一高权限账号、Redis不同db索引均不能形成授权隔离。  
   **建议：**先逐条列迁移版本、来源仓/提交、校验值、目标库及处置，明确底座导入与Flyway建表集合互斥；异常逐项处理。两库独立最小权限角色；Redis落实独立ACL及key/channel边界，必要时分实例。

6. **[P1] worker、Runtime与支付不能按整模块搬迁。**  
   【代码】B `ZhongshuJobDriver.java:71–76`同时运行AI处理和支付订单/inbox恢复；`RuntimeAssetController.java:64–74`直接校验资产并签下载URL。  
   【用户提供比对】两仓六个支付/身份文件blob相同，不能据此判定设计侧不再需要xpay。  
   **后果：**§5.3整类移到设计侧、§7把xpay整体迁走，可能遗漏赋能恢复任务或破坏设计支付。  
   **建议：**按两应用主体建立appid、换码、订单、回调、查单退款、worker/Runtime及COS归属矩阵；拆支付恢复职责。COS整桶凭据不满足隔离，历史对象需受限授权或迁移。归属须在双服务启动前确定。

7. **[P1] 资金切账与回滚仍未闭合。**  
   【文档】§6.5关闭旧退点、拒绝未知旧订单回调；§12承诺反向转换新账，但未明确两应用的新旧订单及渠道事实如何合并。  
   **后果：**停应用不能阻止渠道迟到支付、退款；旧AI任务仍可能结算，简单回切jar无法恢复资金事实。  
   **建议：**仅迁移明确属于赋能的服务账号余额与权益，保留C端资金；逐单登记原系统、渠道/appid、切账批次、唯一处理方。旧订单持续可查单、接收回调并幂等处置；在途AI收敛或明确移交。回滚须覆盖新订单、新流水、回调、补偿与任务，演练失败则禁止带“可整体回滚”承诺上线。

推荐分期如下，均为后续实施顺序建议，本轮不执行：

- **P0文档基线：**撤销免审表述，完成选择性对齐清单、后台职责矩阵、迁移台账、运行归属及资金协议，再形成新版实施稿。
- **P1设计基线修复：**先闭合审批、赠点/补偿、绑定展示；保留A产品行为，逐项吸收B修复并验证。
- **P2隔离与最小纵向链路：**独立身份、数据库权限和后台；先只读灵感库，再接稳定幂等的预算/AI收费与终态结算，最后接独立充值支付。
- **P3演练后切换：**验证双角色越权、重复请求、断网重试、worker恢复、真机支付、迟到回调、期初对账及资金回滚，再安排生产窗口。

仍需验证：最新部署来源、渠道/appid与回调归属、迁移校验清单、实际权限边界及在途清单。本轮仅做源码和所给文档审查，未运行构建、测试或线上操作；修订计划不等于验证通过。
## 二、实时证据补充评审原文

1）**旧 v5 仍为 GATE FAIL（6P1+1P2），未批准新 v6。** 新证据收敛了部署来源和资金现状的未知项，未消除独立系统与单后端冲突、nonce 退化为业务幂等键、全局 ignore Flyway、xpay 整体迁走、钱包 JWT“零前端改动”承诺、资金回滚未验证等问题。本轮无行为验收，不应销项。

2）**已核实与仍未知：**

- 运行进程持有的 jar 与磁盘文件 inode 一致，已记录其哈希；仍含 design、franchise/platform 模块。申请服务 class 与 B 产物一致，INSERT 常量为 PENDING；线上后台入口及审批脚本与 A 产物一致。支持“混合发布”判断，但不能证明整个后端对应 B 的某个完整源码提交，也不能据此认定实际审批行为通过。
- api/api2 均指向 48080；v2 未运行、48081 空闲；未见独立赋能后台站点。A 本地后端仍为 APPROVED 自动开通，不能整仓直接重推。
- 只读快照确认：唯一业务库、133 条成功迁移；fr-service 账号及对应钱包、充值、任务均为零；全库钱包可用 13743、冻结 24，三笔充值与支付汇总金额一致，无所列未决支付、已支付未到账及在途 AI 任务。
- 仍未知：完整源码 SHA、全部账户与资金的业务归属、冻结点原因、真实审批/付款链路、回滚效果。资源规格和 8081 runtime 已确认，但不等于双应用容量或隔离验收；Redis 配置与隔离尚未核实。

3）**新计划应采用 A 设计+B 赋能的选择性整合，保留现有 48080 设计服务，新增独立赋能服务，避免覆盖。** A/B 只能作为候选来源，须逐项核对线上差异、依赖和迁移兼容性。目标应明确为独立 Web、后端、库、身份及钱包充值；赋能仅经约定接口调用设计灵感库、AI 设计、快速预算，无 CRM 客户回流。48081 可作为候选端口，尚未获上线验证。

4）**可条件采用“赋能新建钱包、不迁历史余额，设计资金原位保留”，目前仅是候选方案。** fr-service 为零不足以穷尽证明赋能没有历史资金。进入实施门禁前须补齐：

- 全量账户、钱包、充值、支付与任务归属映射，解释冻结 24 的来源及责任，确认设计资金留存清单。
- 独立身份、JWT 与前端接入方案；充值回调、业务幂等、跨系统调用权限及结算边界。
- 按服务明确 Flyway 基线与校验策略；梳理 xpay 依赖，保留设计支付链路。
- 隔离环境验证审批、充值到账、重复回调、冻结释放及回滚，并定义切换核对与失败恢复步骤。

上述材料经复审后才能判断新计划是否可实施；上线与真实用户验收另设门禁。
