## 一、背景与目标

员工端消息中心（v3 `pages/account/index?view=messages`）当前为纯本地态：消息存本地 storage（`account.messages`），加上本地派生通知（design/performance-notifications）合并展示；已读状态只落本机。换设备即丢，业务域也无法触达员工。

本项建**平台消息通道**：`pf_message` 表（按人持久化）＋ 发送 Port `MessageSender`（业务域注册通知的进程内入口）＋ `/platform/messages` 列表/已读/未读数三件套（4.3 后端）；v3 消息中心页接入随批推进（§十）。**本批交付「通道 + API + 前端接入」，消息数据由 e2e 经 dev-setup 种子端点注入**——各业务域（工程进度、财务到账、绩效发布等）发送方随其所属批次注册（D-基2-i）。

与待办的口径分界（F10）：**待办=要我办的**（按岗位算、无状态即时计算）；**消息=给我看的**（按用户收、持久化落表）。同一业务事件既产生待办又发消息是合法的，各走各的，不做互转。

## 四、REST 接口契约（`/admin-api/platform/messages`）

响应统一 `CommonResult` 包装。断言口径（同基-3）：成功 `(HTTP 200, body.code=0)`；未认证 `(HTTP 200, body.code=401)`；业务失败 `(HTTP 200, body.code=业务码)`。e2e 显式断言二元组。

消息视图 `MessageView`（列表元素与单条已读响应同构）：

```json
{ "id": "1234567890123456789", "type": "BUSINESS", "route": "customer", "objectId": 987,
  "title": "客户跟进提醒", "description": "林女士的回访即将到期", "read": false,
  "createTime": "2026-11-01T09:20:00+08:00" }
```

- `id`：ASSIGN_ID 雪花 id，**超 JS 安全整数，经 `NumberSerializer` 序列化为 JSON 字符串**（`objectId` 为普通业务 id，数值较小保持数字；雪花量级业务 id 同理落地为字符串）。前端与 e2e 将 `id` 当**不透明字符串**处理，不得按数字类型断言（objectId 断言同理——按响应实际类型比较）。

- `objectId`：业务对象 id（Long，可空=null）；指**后端域**对象 id——与 v3 本地演示数据的字符串 id（`customer-lin` 等）**不同域**，跳转边界见 §十。
- `createTime`：ISO 8601；前端展示格式化在接入层做（蓝本 `date` 字段由纯函数生成，后端不背展示格式）。
- `type/route`：英文常量（§三 D-基2-c 白名单）。

### GET `/platform/messages?beforeId=&limit=`

本人消息列表，`id` 倒序。`beforeId` 缺省=从最新开始；返回 `id < beforeId` 的前 `limit` 条。`limit` 缺省 20，clamp [1,100]（D-基2-h）。响应 `CommonResult<List<MessageView>>`。

已知限制：`beforeId` 传非数字由 Spring 类型转换兜底返回 **`(HTTP 200, body.code=400)` 通用码**（`methodArgumentTypeMismatchExceptionHandler` 经 CommonResult 写出，不设 HTTP 状态码；读接口无副作用、调用方为自有前端，不另设业务码）；`limit` 用 Integer 接收在 service 内 clamp，无此问题。

### GET `/platform/messages/unread-count`

本人未读数，COUNT 实时（D-基2-g）。响应 `CommonResult<UnreadCountView>`，`{ "count": 3 }`。

### POST `/platform/messages/{id}/read`

标记单条已读。仅当消息存在**且属于登录者**时生效；不存在或非本人一律 `(200, 1_105_000_000)`（不区分「不存在」与「非本人」，不泄露他人消息 id 存在性）。已读重放幂等 `(200, 0)`，`read_time` 保持首次值。响应：已读后的 `MessageView`。

### POST `/platform/messages/read-all`

本人全部未读置已读（批量 UPDATE，仅 `read=false` 行）。响应 `CommonResult<ReadAllView>`，`{ "updated": 2 }`（实际更新行数；无可读时 `updated=0`，幂等成功）。

### 5、dev-setup 种子端点（e2e 专用，非生产契约）

`POST /admin-api/platform/dev-setup/message/seed`（`yudao-server` dev 包，守卫照抄 `SmsDevController`：类级 `@Profile("local")` + `@PermitAll`——生产不注册、e2e 免 token 调用，F17）。请求体：

```json
{ "userId": 123, "orgId": 456, "senderDomain": "e2e", "type": "BUSINESS",
  "route": "customer", "objectId": 987, "title": "标题", "description": "描述",
  "dedupeKey": "e2e:key-1" }
```

内部**调用 `MessageSender.send`**（走完整校验+幂等代码路径，而非 psql 直插）；`deduplicated` 由控制器在调 send **前**经 `MessageStore.findByDedupe` 预查得出（send 返回 MessageDO 不带标志）。响应 `{ "message": MessageView, "deduplicated": false }`（`deduplicated=true` 表示命中既有行）。校验失败（白名单/格式违例）抛 `IllegalArgumentException`，经 `GlobalExceptionHandler.defaultExceptionHandler` 落为 **`(HTTP 200, body.code=500)` 通用码**（编程错误语义，e2e 不依赖该路径）。守卫：**类级 `@Profile("local")` 照抄 `SmsDevController` 模板**（F17：生产不注册；勿仿 `FranchiseE2ESetupController`——它类上无 @Profile，@PermitAll 全环境放行）。**此端点属 e2e 基建，不计入生产 API 面积**（同 `sms-captcha` 先例）。

## 六、pf_message 表设计（迁移 `V20261101.705__pf_message.sql`）

```sql
CREATE TABLE pf_message
(
    id            BIGINT        NOT NULL,
    user_id       BIGINT        NOT NULL,              -- 收件人（按人收，D-基2-b）
    org_id        BIGINT        NOT NULL,              -- 归属组织（过滤/审计维度）
    sender_domain VARCHAR(32)   NOT NULL,              -- 发送方域（受控登记）
    type          VARCHAR(16)   NOT NULL,              -- BUSINESS/LEARNING/SYSTEM
    route         VARCHAR(32)   NOT NULL,              -- 跳转路由键（白名单）
    object_id     BIGINT        NULL,                  -- 业务对象 id（可空；后端域雪花 id）
    title         VARCHAR(100)  NOT NULL,
    description   VARCHAR(500)  NOT NULL,
    dedupe_key    VARCHAR(128)  NOT NULL,              -- 发送方拼的业务幂等键
    read          BOOL          NOT NULL DEFAULT FALSE,-- PG 非保留字，合法列名
    read_time     TIMESTAMPTZ   NULL,
    create_time   TIMESTAMPTZ   NOT NULL DEFAULT now(),
    CONSTRAINT pk_pf_message PRIMARY KEY (id),
    CONSTRAINT ck_pf_message_type CHECK (type IN ('BUSINESS', 'LEARNING', 'SYSTEM')),
    CONSTRAINT ck_pf_message_route CHECK (route IN ('customer', 'course', 'personal-performance',
                                                    'privacy', 'design-dispatch', 'design-progress')),
    -- 已读必有读时间，未读必无
    CONSTRAINT ck_pf_message_read CHECK ((read AND read_time IS NOT NULL) OR (NOT read AND read_time IS NULL))
);

-- 同一发送域内业务键唯一：事件重放/并发重发不产生重复消息
CREATE UNIQUE INDEX uk_pf_message_dedupe ON pf_message (sender_domain, dedupe_key);
CREATE INDEX idx_pf_message_unread ON pf_message (user_id) WHERE NOT read;   -- 未读数 COUNT
CREATE INDEX idx_pf_message_list ON pf_message (user_id, id DESC);           -- 游标分页

COMMENT ON TABLE pf_message IS '平台员工消息：业务域经 MessageSender 推送、按人收、已读持久化';
COMMENT ON COLUMN pf_message.dedupe_key IS '发送方拼的业务幂等键（如 fr-fin:receipt-confirmed:123）；同 (sender_domain, dedupe_key) 重发返回既有行';
COMMENT ON COLUMN pf_message.route IS '前端跳转路由键（白名单见需求文档 11 §五.2）；新增先登记';
```

成对 undo `V20261101.705__undo_pf_message.sql`（**V 前缀**，全仓 migration-undo 惯例；10 文档 §五.1 的 U 前缀为笔误，V3 纠偏）：`DROP TABLE IF EXISTS pf_message;`（附丢失说明注释，对齐 703 undo 惯例）。org_id NOT NULL 理由：对齐 pf_approval 惯例；发送方必有组织上下文；纯平台级无组织消息属未来演进（§九③）。

## 七、代码结构（platform-workflow 模块内）

```
workflow/message/
  MessageSender.java      @Service：send(SendRequest) → MessageDO；白名单/格式断言 + 幂等 + DuplicateKeyException 重查。
                          契约注释写明：**调用方必须在事务外调用**（事务内调用时并发撞键幂等退化为异常透传，D-基2-e）
  SendRequest.java        record(userId, orgId, senderDomain, type, route, objectId, title, description, dedupeKey)
  MessageConstants.java   type/route/sender_domain 常量与白名单集合（D-基2-c，校验与 CHECK 同源）
  MessageService.java     读侧：list(beforeId,limit)/unreadCount/markRead/markAllRead（clamp、幂等、NOT_FOUND）
  MessageStore.java       接口：findByDedupe/insert/findById/findPage/countUnread/markRead/markAllRead（单测 Fake 边界，仿基-3 StaffProfileStore 模式）
  DbMessageStore.java     @Repository 实现，包 MessageMapper
workflow/dal/
  MessageDO.java          @TableName("pf_message") @TenantIgnore，IdType.ASSIGN_ID
  MessageMapper.java      BaseMapperX + default 查询（selectByDedupe/selectPage/updateIfUnread…）
workflow/controller/admin/
  PlatformMessageController.java   四个端点（F15 惯例，record 视图）
yudao-server/dev/
  MessageDevController.java        @Profile("local") 种子端点（§四.5）
```

校验分层：**HTTP 入参**（limit clamp、id 路径变量）在 MessageService；**发送入参**（type/route 白名单、title≤100、description≤500、dedupeKey≤128 非空、senderDomain 格式、userId/orgId>0）在 MessageSender 以断言快速失败——发送方是进程内受信代码（D-基2-i 本期=空），参数错=编程错误。读侧 MessageService 方法可加 @Transactional（markRead 一次 UPDATE + 可能一次 SELECT，无 catch 重查路径，无 abort 风险）；唯 MessageSender.send **禁止 @Transactional**（V2 修订 1）。

> e2e 前提：server 以 `local,pg,zsdev` 运行（改后端后 `clean package` 重启，确认 jar 含 pf_message，07 §六）；dev-setup 唯一 batch/mobilePrefix。

| # | 断言 |
|---|---|
| AC1 | `mvn clean package -DskipTests` 全量编译过；迁移 705 + undo 成对落库，`docker psql \d pf_message` 结构与 §六 一致（含 3 约束 + 3 索引） |
| AC2 | 未认证四端点（list / unread-count / read / read-all）均 `(200, 401)`；登录后 GET list → `(200,0)` 空数组起步 |
| AC3 | 种子注入 3 类消息（BUSINESS/LEARNING/SYSTEM 各一，route 取 customer/course/privacy；orgId 用 dev-setup 响应的 `storeOrgId`）→ list 可见且字段齐（id/type/route/objectId/title/description/read=false/createTime）；unread-count=3；id 倒序（最新在前） |
| AC4 | 幂等重发：同 senderDomain+dedupeKey 再次 seed → 响应 `deduplicated=true` 且消息 id 与首次相同；list 不出现重复行；unread-count 不变 |
| AC5 | 单条已读：POST read → `(200,0)` 返回 read=true 视图；unread-count 减 1；查库 `read=true AND read_time IS NOT NULL`；**重复已读幂等** `(200,0)` 且查库 read_time 与首次相同 |
| AC6 | 不存在/他人：POST `/platform/messages/{不存在id}/read` → `(200, 1_105_000_000)`；**跨用户隔离**：boss 对 sales 的消息 id POST read → `(200, 1_105_000_000)`（同码，不泄露存在性）；boss 的 list 不含 sales 的消息；sales 的未读消息不计入 boss 的 unread-count |
| AC7 | read-all：再注入 2 条未读 → POST read-all → `(200,0)` 且 `updated` 与本人未读数一致；unread-count=0；查库本人全部 `read=true AND read_time 非空`；**再次 read-all → updated=0**（幂等） |
| AC8 | 游标分页：注入共 24 条 → list（缺省 limit）返回**最新 20 条**且 id 倒序；`limit=3` 从头逐页翻（`beforeId=<本页最后一条id>`）取完 24 条，**不重不漏**；`limit=0` → 收敛 1 条（clamp 下界）；`limit=1000` → 一次返回现有全部 24 条（≤100 上界内）；clamp 上界行为（>100 收敛 100）由单测断言（e2e 不注 100+ 条，控制时长） |
| AC9 | 用户隔离正面：boss 自己 seed 1 条 → boss unread-count=1 且 list 仅含本人消息；sales 的列表/未读数不变 |
| AC10 | 真 PG 并发：两线程并发 seed 同 dedupeKey → 两请求均成功且返回同一 id，查库该 key 恰 1 行；两线程并发 POST read 同一未读消息 → 均 `(200,0)`，查库 `read=true` 且 read_time 单值（二次更新 0 行不覆盖首次时间） |
| AC11 | 单测全绿（**纯 Fake Store，无 Spring**）：MessageSenderTest（落库参数/幂等命中返回既有行/并发 DuplicateKey→重查/白名单与字段断言 fail-fast）+ MessageServiceTest（clamp 边界含 >100→100、游标参数透传、markRead 幂等与 NOT_FOUND、read-all 行数） |
| AC12 | v3 接入（§十）：`node scripts/verify-message-api.cjs` 绿（纯函数断言：MessageView→蓝本形态映射、三源合入去重排序、未读合计）；`npm run check` 主套件回归过 |
