## 二、迁移语义（严格前置，宁可阻塞不遗漏）

**可迁条件（三者同时满足）**：`available_points > 0`、`reserved_points = 0`、映射 `CONFIRMED`。

| 情形 | 处置 |
|---|---|
| 有 `reserved_points > 0`（在途预留） | **阻塞整个 execute**，清单要求先承接在途（任务书 R1-P1） |
| 无 CONFIRMED 映射（含 CANDIDATE/未映射） | **阻塞整个 execute**，要求先完成 B-15 人工确认 |
| 已迁移账号（`migration:{accountId}` 已存在） | 幂等跳过，不重复加点 |

**为什么用"阻塞"而不是"部分迁移"**：部分迁移会让同一账号的 `available` 与 `reserved` 跨边界（个人已清零、在途还在个人侧），结算退差会落到错误账户；阻塞到"在途清零"后再迁，跨边界问题不存在，也省掉逐笔归属判定。

## 三、守恒与审计

- 池侧：`org_point_ledger` 一条 `MIGRATION`（bizKey=`migration:{accountId}`，actor=账号，ref=`design_account`）。
- 个人侧：`design_point_ledger` 一条 `MIGRATION_OUT`（delta=-amount，available_after=0）。
- `execute` 结束断言：`Σ个人迁出 == Σ池迁入 == 上次累计 + 本次`，不等即抛错。
- 个人账户 `available_points` 清零（无 status 列，清零即停用；不再充值——充值链在生产为关闭状态）。

## 四、验收（4/4 绿）

1. `dryRun` 按 org 聚合（50 点/2 账号）+ 在途与未确认各 1 例阻塞清单
2. 有阻塞时 `execute` 整体拒绝
3. 正常迁移：2 账号/50 点，个人清零、池余额到位、双账留痕、守恒成立
4. 幂等重跑：第二次 `migratedAccounts=0`，池余额不变，守恒仍成立

commerce orgpoint 全套 **57/57** 绿（含既有个人点数契约 15 例，确认 CHECK 扩展无回归）。

## 五、回滚

- 账户级回滚：按 `migration:{accountId}` 反查池流水 → 池写反向 `MANUAL_ADJUST`、个人恢复 `available_points`（人工核对后执行，脚本不自动化以免误伤）。
- 迁移脚本 undo：存在 `MIGRATION_OUT` 时 RAISE EXCEPTION，禁止回滚（保护审计）。
- 代码回滚：revert 提交；无对既有业务表的破坏性变更（仅 CHECK 扩类型）。
