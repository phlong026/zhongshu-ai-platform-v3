# B1 财务账簿与到账 · 需求文档与验收标准

> 批次：后端化工程 · B1（franchise-finance 域）　日期：2026-10-31　状态：V6（吸收 Codex R1-R5：15+7+5+4+1 P1 与全部 P2）
> 流程：需求文档 → Codex 评审循环至 PASS → 开发 → 提交；决策类不确定点记 §11。

## 一、背景与目标

小程序管理账簿承载加盟商全部资金流。本批在 monorepo 建 **franchise-finance 域**（`domains/franchise/franchise-finance`），提供账簿全链 HTTP 接口。**B1 是全平台收付底座**：B2 业务回款、B3 工程收付、B6 提成/经营全部消费本域。

## 二、退款专项结论（用户点名 + 2026-10-31 拍板：线下事实登记制）

**可达性核实结论**：小程序里退款线上流程是**封存残留**——`model.js apply()` 入口断言拦截全部 refund 前缀动作（"该事项在线下办理"）、`authority-v2.admin()` 对 deferred 视图拒绝进入、`refundRequests` 申请单零创建入口；批次 D（feat/boss-workspace-d-20261029，9e6b581+627a880）已摘除退款死按钮与封存待办生成代码（未合并至当前基线）。

**B1 退款口径（用户拍板）**：
1. **线下事实登记制**：财务单方登记退款（金额 ≤ 原实收可退余额 + 原因 + 凭证 + 流水号），**登记即"已核实"**——语义="只登记线下已发生退款，不发起转账"（页面原文）。
2. **不建申请-审批双单链**（refundRequests/refund-approve 等封存流程不移植）。
3. 登记错误走**作废重登**：仅财务负责人/老板可作废（留痕原记录），作废释放可退余额。
4. **下游联动保留**（数据消费端在役）：净收款=原实收−已核实退款；回款提成基数扣减（B6 消费）；经营报表支出项；绩效指标扣减。

## 三、数据表设计（fr_fin_*，Flyway `db/migration/franchise/` 续 8xx；权限种子新增 franchise-system 段 V*.852）

**公共约束（全部表）**：金额列 `BIGINT CHECK (amount_cents > 0 AND amount_cents <= 1000000000000)`；状态列 `VARCHAR CHECK (status IN (...))`；公共列 `tenant_id BIGINT NOT NULL DEFAULT 1, creator, create_time, updater, update_time, deleted`；员工引用一律 `system_users.id`。**交易身份与更正链**：`fr_fin_txn_no(company_id, txn_no, owner_type, owner_id)` 表，`UNIQUE(company_id, txn_no)` **不含 deleted 条件**（软删不释放）。txn_no 行代表**稳定交易身份**而非具体记录：
- 新登记：INSERT txn_no 身份行（owner 指向新记录），同事务。
- **作废**：身份行保留（owner 不变），业务记录标已作废（void 字段）。
- **更正重登（替代权统一落在原记录上）**：新记录携带 `replaces_id`（指向被作废记录 A）；服务端同事务内按序执行：①校验 A 存在且已作废、同 company、同 receipt/payment 上下文；②**争抢替代权：`UPDATE fr_fin_refund SET replaced_by_id=新记录ID WHERE id=A AND replaced_by_id IS NULL`**（CAS，检查行数=1，失败整笔回滚——同号/换号更正均经此步，"同一被作废记录至多一个有效替代"由 A 上的唯一标记保证）；③同号更正：条件 UPDATE 身份行 owner（当前 owner 仍须=被替代记录，行数=1）；**换号更正**：INSERT 新号身份行（owner=新记录）并作废旧号身份行关闭标记；④任一步失败全回滚。
- 无关对象抢用已占用旧号：身份行 owner 不匹配且无更正关联 → 拒绝；成功替代后再次对 A 发起替代 → CAS 失败拒绝。
- receipt 的交易号：业务表 `UNIQUE(company_id, transaction_no)` 保留但**允许软删记录占用**（部分唯一索引去掉 deleted 条件改为全量唯一）——更正场景由身份行切换保证，不同号正常登记。

| 表 | 关键字段与约束 |
|---|---|
| `fr_fin_receipt` 实收 | company_id, project_id(可空), customer_id(可空), source_type CHECK(business/engineering/intercompany/design/manual), source_ref(如 `commissionId:version:stage`), name, amount_cents, status CHECK(待登记/已登记/已撤销——**生效终态=已登记**；核算/备案整段退役不建模【历史账不迁移故无兼容需求】，reconcile 独立核算为封存逻辑), received_date, registered_at, registrar_user_id, method CHECK( bank/cash/other ), transaction_no(可空——现金无流水；**非空时归一化去空格后** `UNIQUE(company_id, transaction_no)`), voucher_file_id→fr_fin_file, revision_version INT NOT NULL DEFAULT 1, void_reason |

**索引**：每表 `(company_id, status, create_time DESC)`；receipt `(source_type, source_ref)`；refund `(receipt_id)`；payment `(payable_id, status)`；bank_flow `(company_id, status)`。项目账用单条聚合 SQL（GROUP BY），禁逐笔 N+1。

## 四、状态机与资金不变量

**实收状态机**（完整迁移表；**生效口径：`已登记` 及之后全部状态均计入有效实收**，核算/备案是财务内部标记，不构成业务生效门槛）：

```
待登记（intercompany 移交事件自动生成，计入"预期应收"，不计入有效实收统计）
  → [财务登记 incoming-register] 已登记（收款即生效）
已登记 → [修订：财务直接改，全留痕免审] 金额更新 + revision_version+1（**状态不变**，无核算/备案迁移）
待登记 → [撤销（仅跨端来源，财务负责人）] 已撤销
```

**资金不变量（不变量 I-1，同一数据库事务内 `SELECT ... FOR UPDATE` 锁 receipt 行后分支校验）**：
- **退款登记**：`Σ已核实退款(不含已作废) + 本次退款 ≤ 当前 amount_cents`，且 **receipt.status 必须=已登记**（待登记/已撤销拒绝退款，防"有效实收为零而退款大于零"）。
- **修订生效**：`Σ已核实退款 ≤ 新 amount_cents`（与版本校验同事务；反例：实收 100 已退 40 修订 30 → 40≤30 不成立拒绝；合法调增/调减均有用例）。
- 修订生效与退款登记竞争同一行锁串行化；base_revision_version 不符即失败。

**付款不变量（I-2）**：`Σ(fr_fin_payment.status = '已核实').amount ≤ fr_fin_payable.total_cents`（登记即已核实，无在途占用），登记与作废在同一 payable 行锁事务内校验；作废释放额度并留痕。

**到账核对规则**：
- 流水生产：模拟接口 `POST /franchise/finance/bank-flows`（dev/e2e 用；prod 由对账导入替代，不在 B1）。
- 预期应收来源：intercompany 移交事件（既有）自动建 `fr_fin_receipt(status=待登记, source_type=intercompany)`——已存在机制，B1 落到 fr_fin_receipt。
- 确认 = 财务对 bank_flow 选定待登记 receipt（金额=流水金额才可确认）→ **更新该 receipt 为已登记** + 建 bank_confirm（**唯一入账**：bank_flow_id UNIQUE 与 receipt_id UNIQUE 双约束防重复认领/重复匹配）。
- 金额不符：不改变 bank_flow 状态（保持可匹配），**失败尝试独立留痕表 fr_fin_match_attempt**（flow_id, tried_receipt_id, reason, at，独立事务写入不随确认回滚），可重试换 receipt；待登记 receipt 被撤销后，其迟到确认 → 业务异常拒绝。

**动作矩阵**（权限码 `franchise:fin:{query|register|refund-void|payment-void}`，种子 franchise-system V*.852；finance/finance-lead=query+register；**finance-lead=query+register+payment-void+refund-void；boss/owner=query+refund-void（仅退款作废，不含付款作废）**；engineer/project-manager/sales/hq-design-admin=无任何 fr-fin 权限；bank-flow 注入接口走 dev 守卫非权限码）：
- 所有写操作：Service 内**三重归属校验**——当前岗位 org/company、目标对象 company_id、关联链（refund→receipt→company；payment→payable→company）一致；JdbcTemplate 所有查询显式 `WHERE company_id=?`。
- `tenant_id`：**B1 明确单租户（恒 1）**。底座租户插件挂载于 MybatisPlusInterceptor，**不覆盖 JdbcTemplate**——fr_fin_* 全部 SQL 以**显式 company_id 条件**为真实隔离手段（写入恒带、查询恒带、聚合恒带），tenant_id 列恒写 1 由服务端固定（非隔离机制）。

## 五、API 规划（`/admin-api/franchise/finance/*`）

**通用约定**：全部写操作要求 `Idempotency-Key` 头，作用域=`fr-fin:{动作}:{对象id或新登记uuid}`，命令记录与资金变更**同事务**；幂等重放返回首次结果；权限重验在重放时仍执行。错误码段 `fr-fin` 专属（1_102_0xx）：余额不足、流水重复、状态冲突、对象不存在、越权、凭证不可用、幂等内容冲突（同 key 不同指纹）。

| 接口 | 说明 |
|---|---|
| GET `/receipts?companyId&projectId&status&pageNo&pageSize(≤100)` | 分页，稳定排序 create_time DESC,id DESC |
| POST `/receipts` | 登记实收：source_type 仅允许 manual/design（**intercompany 不走本接口**——由移交事件内部创建，外部伪造该来源 → 异常）；**design 来源时 body 携带 source_ref=commissionId:version:stage，服务端门禁五项：①委托存在 ②submission_version 匹配当前版本 ③receipt.company_id 必须等于委托的 design_org_id（总部收款侧；委托 company_id 是门店，见 CommissionOrgScope——AC9 用不同组织 ID 的门店与总部验证） ④委托费用已批准（FEE_PENDING/已驳回拒绝）⑤stage ∈ 该版本费用方案的合法期款（first/tail）**——未批准/非法期款/旧版本/跨公司四类拒绝；intercompany 由移交事件自动建（不走本接口）；交易号归一化查重 |

## 六、验收标准（可执行）

**node 无（后端批次）；单测（Mockito，业务分支）：**

| # | 断言 |
|---|---|
| AC1 | 登记：交易号（归一化后）重复 → 异常；幂等键重放 → 同一条；同 key 不同指纹 → 幂等冲突 |
| AC2 | **封存回归**：POST review/filing 类接口不存在（404）；receipt 状态域仅 待登记/已登记/已撤销 三值 |
| AC3 | 修订：baseRevisionVersion 不符 → 乐观锁冲突；生效后 revision_version+1 且历史可查；金额更新即时生效 |
| AC4 | 退款：金额超可退余额 → 异常；**对待登记/已撤销 receipt 退款 → 异常**；登记即已核实；作废（无权限角色）→ 异常；作废后经更正链同号重登成功、无关对象抢用旧号失败、并发更正仅一次成功 |
| AC5 | 付款：累计超 payable.total → 异常；作废释放；payable_id 缺失 → 校验异常 |
| AC6 | 到账确认：重复认领同一 bank_flow → 唯一约束异常；确认后 receipt 状态=已登记且计入有效实收；金额不符流水可重试换 receipt；被撤销 receipt 的迟到确认 → 异常 |
| AC7 | 归属校验：跨 company 的 refund/payment/bank_confirm 操作 → 拒绝（关联链校验）；查询隐式限定 company_id |
| AC8 | 权限逐接口矩阵断言（×角色 finance/finance-lead/boss/owner/engineer）：
| 接口组 | finance | finance-lead | boss/owner | engineer |
|---|---|---|---|---|
| query（receipts/payables/payments/refunds/revisions/bank-flows/project-accounts/design-fee-progress） | ✓ | ✓ | ✓ | 403 |
| register（receipts/payments/payables/revision/void-pending/bank-confirms） | ✓ | ✓ | 403 | 403 |
| **files 上传/下载（显式例外：用 query 权限）** | ✓ | ✓ | ✓ | 403 |
| **refunds/{id}/void（refund-void）** | 403 | ✓ | ✓ | 403 |
| **payments/{id}/void（payment-void）** | 403 | ✓ | 403 | 403 |
**不存在 verify/review/filing 接口（封存逻辑未移植的回归断言）**；POST /refunds 归 register 权限 |

**Python e2e（script/franchise-fin-b1-e2e.py，真实 PG + 多岗位 HTTP）：**

| # | 步骤 |
|---|---|
| AC9 | 全链正向：dev-setup（含**门店+总部两个不同 org id**）→ 标准费用 → 非标准委托（FEE_PENDING）→ 老板批准 → **总部财务以 source_type=design 登记首款**（五项门禁通过；幂等重放验证；**门店归属登记被拒、company_id≠design_org_id 断言**）→ 财务修订（baseRevisionVersion 校验+留痕）→ 净额查询仅计入总部侧（design-fee-progress 数字精确断言）与项目账聚合 |
| AC10 | 退款并发（真 PG）：两路并发各登记 `余额/2+1` → 恰一路成功一路余额异常；串行两笔各退一半成功；作废后可再退 |
| AC11 | 修订与退款竞争（实收 100、已退 40）：并发「修订 30」与「退款 30」→ **退款成功**（40+30=70≤100）、**修订失败**（40≤30 不成立）；「修订 60」与「退款 30」并发 → 互斥恰一成功（谁先锁谁生效，后者按新状态校验失败）；「修订 80」后「退款 30」→ 两序皆可成功；行锁串行化无死锁 |
| AC12 | 付款并发：两路并发付款合计超 total → 一路成功一路异常；作废释放后可再付 |
| AC13 | 到账：dev 注入流水（**dev 守卫接口，仅 local profile**，prod 无此 bean）→ 同流水并发认领 → 恰一成功；确认后 finance 岗待办事项按 key 消失（/platform/todos 断言） |
| AC14 | 事务回滚：构造幂等记录成功但资金写入失败的注入场景 → 命令记录与资金同回滚（无孤儿命令） |
| AC15 | 待办契约：**finance 岗** `/platform/todos` 返回 `fr-fin:*` 事项（到账待确认），字段（key/domain/actionable/appPath/amountCents）齐全；事项办理完成后按 key 精确断言消失；boss 岗不出现 fr-fin 可操作事项（矩阵：fr-fin 全部为 finance 系职责） |
| AC16 | 越权抽查：工程岗 403；跨公司 403/业务异常 |

**回归**：monorepo 既有测试 + 三支冒烟（org-admin/sms/todos）全过；编译 clean package 成功。
