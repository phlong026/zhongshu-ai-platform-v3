## 二、匹配规则（唯一可靠桥）

```
access_code_redemption.account_id            -- 旧设计账号
  contact_phone                              -- 唯一可靠身份桥（V20261010.107 增列）
      → system_users.mobile（deleted=0）        -- 员工账号（手机号唯一才算命中）
      → pf_staff_post(user_id, status='ACTIVE') -- 有效任职 → org_id（唯一才算命中）
```

**歧义一律不猜**：手机号无匹配/多匹配、员工多岗位/无有效岗位 → `UNMATCHED` + 说明，交人工确认。
批次信息（`issued_by` / `purpose_note`）只作报告佐证，**不作归属依据**（批次表确无 org_id）。

## 三、状态机与过渡策略

| 状态 | 含义 | 后续动作 |
|---|---|---|
| `CANDIDATE` | 手机号唯一 + 单一有效任职，**待人工确认** | 人工核对后 `confirm` → CONFIRMED |
| `CONFIRMED` | 人工确认归属（员工+组织） | B-16 迁移的唯一依据 |
| `UNMATCHED` | 缺手机号/无员工/多员工/多岗位 | 进过渡清单：**保留既有 grant 只读续期，不自动断**；人工补齐后 confirm |
| `REJECTED` | 人工判定无法归属 | 同上，保留只读授予，登记处置原因 |

## 四、验收（7/7 绿）

1. 唯一手机号 + 单一有效任职 → CANDIDATE（PHONE）
2. 缺手机号 → UNMATCHED（说明“缺少联系手机号”）
3. 同手机号多账号 / 同员工多岗位 → UNMATCHED（歧义不猜）
4. 生成幂等：二次执行 `skipped`，**不覆盖已确认结论**
5. 驳回 → REJECTED 且进入报告未匹配清单
6. 未生成行直接确认 → 拒绝
7. 报告口径：total/confirmed/candidate/unmatched/rejected + byMatchType + 未匹配清单（≤500）

identity 模块全量回归 **94/94** 绿。

## 五、操作流程（上线前执行）

1. `POST /identity-mapping/generate`（可重复执行，只补新行）
2. `GET /identity-mapping/report` → 导出未匹配清单，由加盟商/运营补齐手机号或归属
3. 对每条 `CANDIDATE` 人工核对后 `POST /{accountId}/confirm`（员工+组织）
4. 无法归属的 `POST /{accountId}/reject`（保留只读授予）
5. 全部处置完成后再执行 B-14（退役）与 B-16（迁移）

## 六、边界（本批不做）

- 不修改/撤销既有 `design_access_grant` 与 `access_code`（退役在 B-14）。
- 不做点数迁移（B-16）。
- 手机号缺失的存量账号无法自动映射——这是数据现实，只能人工补录（报告已列出）。
