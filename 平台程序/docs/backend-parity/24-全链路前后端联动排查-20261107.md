## 1. 总览结论

主链可以按岗位联调，路径没有整段缺失。挡住联调验收的是两处小程序行为，都在 `3c7fdcab`，改动面小，但不在本分支能改的树上。

1. **财务凭证在 local/zsdev 字节通道不带当前岗位。** 生产签名 URL 的 PUT 已在 `3c7fdcab` 按文件字节算 SHA。开发态 `POST /platform/dev/design/assets/{id}/bytes` 仍是自组 `wx.request`，只有传入 `helperUser.post` 才写 `X-Post-Id`。财务台调用 `uploadVoucher(filePath)` 不传 helper，`@post.has` 拒绝。工程凭据走 `http.post`，头是齐的。
2. **正式方案徽标仍不读详情里的 `stage`。** 后端 `CrmRespVos.Scheme` 已回 `stage`（空则 `reference`）。`platform-crm.js` 的 `detailView` 不映射该字段；`workflow/index.js` 刷新时用本会话 `__promoted` 覆盖 `formal`。刷新后徽标消失，「转正式」再次出现。接口本身成功，S1-20 的跨会话展示验收过不了。

另外三处假设已在小程序尖端收口，不必再当缺口返工：

| 假设 | 复查结果 |
|---|---|
| crm 转交指纹注释 vs 后端 | 后端 `CustomerService.transfer` 的重放指纹已是 `TransferCommand`（`targetUserId` + 规范化 `reason`），与 `record` 同构。`api/franchise/crm.js` 注释仍写「已知后端重放指纹缺口 S1-11b」，注释过时，行为对齐 |
| growth 仅 API 岗位 | `4ff71684` 起获客页用 `currentApiPost()`。无 token，或不是门店的 sales / sales-lead / boss / owner，直接去访问提示。演示会话不再开门 |
| 账号页平台登录门禁 | `3c7fdcab` 用 `platformSession = token && currentApiPost()`。资料、消息、身份等守卫页接受平台会话，不再只认本地 `session.loggedIn`。登录后 `afterRealLogin` 先清岗位再拉 `posts/mine` 并写入首岗 |

会话与岗位头（全站，走 `api/http.js` 的调用）：

- 有 token 时带 `Authorization: Bearer`，有当前岗位时带 `X-Post-Id`，`tenant-id` 缺省 `1`。
- HTTP 401 与 body `code=401` 同一条清会话路径；请求发起时的会话代次与当前代次不一致则静默丢弃，不冲掉新登录。
- 岗位失效码 `1_103_000_002` 走 `recoverPostInvalid`：拉最新任职，切到另一有效岗；没有替代则登出并复用 401 引导。
- 业务台写操作的 `catch` 先 `handle401` 再判过期。签约等写操作在会话代次前进时会先清 `busy`，不会卡在提交中。这是 `3c7fdcab` 修过的点。

幂等：业务台、工程、财务、内容写接口在客户端带 `Idempotency-Key`。客资登记、客户编辑的键可选，与控制器 `required = false` 一致。销售、工程、内容创建在服务端 `requireIdem`，客户端缺键会自己生成。财务登记用表单级粘性键，取消或成功后换新键。

## 3. 阻断级清单（联调前必须修）

两处都在小程序 `3c7fdcab`，本分支未改。建议在 `feat/production-mock-removal-20261107` 上修，不要把两条历史合并进后端分支。

### 阻断 1 · 财务凭证 local 字节通道缺少 `X-Post-Id`

- 位置：`miniprogram/api/finance.js` 的 `uploadVoucher`；调用方 `pages/admin/finance-desk/platform-actions.js` 的 `uploadVoucher(form.voucherPath)`。
- 现象：`uploadUrl` 为 `local://` 或含 `/platform/dev/` 时，自组请求不带当前岗位。`DesignDevController.putBytes` 要求 `franchise:design:use` 或 `franchise:asset:bytes`。没有头时岗位上下文为空，财务岗即使有 858 的窄码也会被拒。签票和 complete 走 `http.post`，头是齐的，断在中间这一跳。
- 生产：签名 URL 的 PUT 不需要岗位头，SHA 已按文件字节计算。联调若走 COS，这条不挡登记。联调若走 local/zsdev（仓库默认的开发字节通道），带凭证的实收/付款登记失败。
- 改法：无 helper 时使用 `http.currentPostId()` 与 `http.tenantId()`，并按 `http.post` 的方式判断 body `code===0`。不要把老板/店主加进 `asset:bytes`，除非产品决定他们在 local 也要上传凭证；类型矩阵已经允许他们签票，字节门没有跟上，那是另一条权限决策。

### 阻断 2 · 正式方案徽标不读 `stage`

- 位置：`miniprogram/utils/platform-crm.js` 的 `detailView`；`miniprogram/pages/workflow/index.js` 加载详情时 `formal: this.__promoted[s2.id]||false`。模板 `index.wxml` 用 `item.formal` 显示「正式」，并用 `saleWrite && !item.formal` 显示「转正式」。
- 现象：`POST .../promote` 成功后本会话看得到徽标。重新进入详情后徽标丢失，按钮回来。后端已把 `formal` 落在方案上并随客户详情返回。再点一次升级是幂等的（已是 formal 不再改阶段），验收仍会判 S1-20 失败。
- 改法：`schemesList` 增加 `formal: sc.stage==='formal'`。加载时保留服务端结果，本会话标记只作为当次点击的即时反馈，不要在刷新时写成 `false`。
