**R1 纠正的现状事实**：
- `ai_task_charge` **无 `charge_id` 列**；关联方向是 `ai_job.charge_id → ai_task_charge.id`。
- `ai_job` **没有 `SUBMISSION_UNCERTAIN` 状态**；deadline 驱动按 ACCEPTED 结算。
- `PARTIALLY_SUCCEEDED` **可能 ACCEPTED=N**（取消请求下只要有有效结果就标 PARTIAL）。
- `BillingPriceCatalog` **尚未注册 `AI_PROMPT`**（未知科目会被拒绝）——需作为实施项补登记。
- 分项预算（`ItemizedBudgetService`）是独立入口，必须纳入。

## 二、路由分流方案（批 C 落地）

### 2.1 计费上下文必须**持久化**（R1-P1-1）

入口参数不足以支撑异步 prompt/结算/恢复，因此：

1. 新增桥侧计费归属表（或给 `ai_job`/`design_*` 加列）：`design_billing_binding`
   `(ref_type, ref_id, origin(BRIDGE|APP), org_id, actor_user_id, actor_post_id, operation_id, biz_key, subject, created_at)`。
   - 创建 job/estimate 时**同一事务**写入绑定行（origin=BRIDGE 才写）。
   - 异步 prompt、终态结算、恢复 Job 一律**读绑定行**决定路由；找不到绑定行 → 按 origin=APP 处理（存量兼容）。
2. `billingOrigin` 仍作显式入口参数（用于创建时写绑定行），但**不作为异步路径的判定依据**。
3. 绑定行同时承载审计三要素（org/actor/ref），与 `org_point_ledger` 的 operation 一一对应。

### 2.2 分科目路由规则

| 科目 | BRIDGE → | APP → | 备注 |
|---|---|---|---|
| `ai_flat` / `ai_elevation`（含修订链新建 job） | `OrgPointPort.reserve(subject, quantity=张数, ref=jobId)`；终态 settle/release | 原 `createJobWithCharge` 不变 | 桥侧**不写** `ai_task_charge`/`ai_job.charge_id` |
| `budget_estimate`（含分项） | `reserve(quantity=1, ref=estimateId/budgetId)` + 同步 settle | 原 `chargePrepared` 不变 | 桥侧**不写** `service_usage_charge` |
| `AI_PROMPT`（桥 job） | 见 §2.3 独立状态机 | 原 reserve/finish 链不变 | 与图片 job **分开两个 operation** |
| `note_polish` | 首批**不计费**（登记）；如需计费升 v2 | 同左 | 需 D8 拍板 |

### 2.3 两套终态映射（R1-P1-2，禁止统一套用）

**A. 图片 job（ai_flat / ai_elevation）**

| 业务终态 | 公司池动作 |
|---|---|
| SUCCEEDED（ACCEPTED=N） | `settle(actualQuantity=N)` |
| PARTIALLY_SUCCEEDED（ACCEPTED=1..N-1） | `settle(actualQuantity=ACCEPTED)`（退差） |
| **PARTIALLY_SUCCEEDED 且 ACCEPTED=N**（取消但全有效） | `settle(actualQuantity=N)`（**不退款**） |
| FAILED / CANCELLED（ACCEPTED=0） | `release`（全退） |

**B. prompt 调用（AI_PROMPT）——独立状态机，不随图片 job 终态**

| prompt 结果 | 公司池动作 | 收据要求 |
|---|---|---|
| `SUCCEEDED` | `settle(actualQuantity=1)` | callId + responseHash + fencing token |
| `DISPATCHED` / `UNKNOWN` | **保持 PENDING**（禁自动退款、禁重投） | fencing token 落库；由核对流程人工确认 |
| `NOT_SENT` | `release`（仅释放该次预留） | 允许后续重试（新 operation） |

**红线**：图片 FAILED **不得**连带释放 prompt 预留（两者可能并存，已有合同测试验证）。

### 2.4 公司池核对闭环（零写旧表后的承接）

桥侧停写 `ai_task_charge`/`service_usage_charge` 后，对账依据改为：
- `org_point_ledger`（逐笔）+ `operations` 合并视图（PENDING/COMPLETED/RELEASED）；
- `design_billing_binding`（业务 → operation 映射）；
- 长期 PENDING 扫描：`operations` 按 operation_time 超阈值告警 + 人工核对端点（确认未执行→release / 确认交付→settle），**超时不自动退款**；
- 结算失败重试：按 `biz_key` 幂等重放（批 A 模式），扫描范围覆盖 design 绑定（复用批 A 的 `org_point_ledger` 查询，不改内容域扫描器）。

## 三、切换条件（红线）

1. **禁止双链**：桥侧同一笔只允许公司池记账；`ai_task_charge`/`service_usage_charge` 在桥侧零写入（验收断言）。
2. **存量在途**：切换前已用个人池预扣的任务，按 **`ai_job.charge_id → ai_task_charge.id`** 是否存在判定（R1 纠正），存在即走原退差链；NULL 不能证明属于公司池（历史无扣费创建路径也不写 charge），需结合 `design_billing_binding` 是否存在双重判定。
3. **App 链行为不变**：`origin=APP` 全部路径保持现状（回归断言）。
4. **失败不外呼**：公司池 reserve 短事务提交后才允许外呼。
5. **prompt 独立**：不得凭图片结果释放/结算 prompt。
