## 1. 怎么对的

- 前端：`miniprogram/**/*.js` 里 `http.get/post/put/delete/request` 以及 `http.upload`。`auth.js` 的微信登录是多行调用，手工补进清单。路径参数一律写成 `{id}`。
- 另计一处不走 `http.*` 的生产调用：`api/finance.js` 用 `wx.request` 打 dev 字节通道（与工程上传同一路径）。
- 后端：`平台程序` 下 `*Controller.java` 的方法级映射。业务控制器写 `/franchise/**`、`/platform/**`，运行时由 admin 包前缀拼成 `/admin-api/...`。`DesignDevController` 在 dev 包，映射自带绝对路径 `/admin-api/platform/dev/design`。
- 前端 `config/env.js` 的 `API_BASE` 约定带 `/admin-api`。因此前端路径 `/franchise/...` 与控制器 `/franchise/...` 是同一条。
- 请求头：`api/http.js` 在有登录态时带 `Authorization`、`X-Post-Id`、`tenant-id`（缺省 `1`）。加盟写接口用 `@post.has`，与该头一致。`/platform/profile/mine` 不要求岗位头。

路径级结果：**185 条方法+路径全部能落到现有控制器，没有整段缺失的生产接口。** 挡住联调的是三处「路径在、行为或编译不对」。

## 2. 本批关闭

| 项 | 现象 | 改动 |
|---|---|---|
| dev 字节通道编译 | `DesignDevController` 调用 `AssetAccessService.channelAllowed`，方法不存在，`yudao-server` 编不过。财务凭证与工程凭据的 local 字节上传走 `POST /platform/dev/design/assets/{id}/bytes` | 增加与 `requireChannelPermission` 同源的静态判定。已知类型按 8xx 消费矩阵；未知类型（含设计稿）放行，避免误伤 `design:use` |
| 方案 `stage` 读不回（S1-20） | `POST /franchise/sales/schemes/{id}/promote` 回 `stage`，`GET /franchise/customers/{id}` 的方案对象不带 `stage`。刷新后正式方案徽标丢失 | `CrmRespVos.Scheme` 增加 `stage`；空或空白归一为 `reference` |
| 报价/交付幂等指纹（S1-23 余项） | 报价指纹不含地址、价目口径、宽/深/层/面积；交付指纹不含 `requirementId`。同键改这些字段会回放旧单，而不是 `1_099_000_000` | 两边 `record` 与 `replayed` 共用同一份指纹 |

发版注意：已经落库的旧报价/交付幂等键，若在发版后用原键重试，指纹对不上，会报键复用。应换新键。当前无生产存量时无影响。

cd 平台程序
./mvnw -pl yudao-server,domains/franchise/franchise-asset,domains/franchise/franchise-sales,domains/franchise/franchise-crm -am test \
  -Dtest=AssetAccessServiceTest,SaleCommandFingerprintTest,SchemeViewTest,SaleQuoteMathTest -DfailIfNoTests=false
