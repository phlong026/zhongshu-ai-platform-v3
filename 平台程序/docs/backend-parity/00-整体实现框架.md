## 二、现状结论（勘察事实，浓缩）

- **已对齐**（后端有、小程序未接）：1.1/1.2/1.9 客资客户委托、4.1/4.4 登录选岗待办——`miniprogram/api/` 骨架契约与后端完全对应（`{code:0,data,msg}` + Bearer + `X-Post-Id` + `Idempotency-Key` + `revision`）。
- **全缺口**：业务交易流（1.3-1.8）、设计赋能员工端（1.10-1.12）、内容创作获客（1.13-1.16）、工程全周期（2.1-2.9）、财务账簿（3.1-3.6）、绩效提成经营（3.7-3.11）、我的服务（4.2/4.3/4.5）。
- 小程序 17 个功能域跑本地 Storage，`miniprogram/api/` 是预置脚手架。

## 三、总体架构

不引入新架构，沿用既有模式：

```
v3 小程序（逐页从 Storage 切到 miniprogram/api/）
   │  /admin-api（Bearer + X-Post-Id + Idempotency-Key + revision + tenant-id）
   ▼
yudao-server 单体 FatJar :48080
   ├── platform-*（复用：待办 pf_approval / 岗位 authz / 员工微信绑定）
   ├── franchise-crm / commission（已有 M2：映射表 1.1/1.2/1.9）
   ├── franchise-sales        ← 新增：业务交易流（1.3-1.8）
   ├── franchise-design       ← 新增：设计赋能员工端接入层（1.10-1.12，经 Port 复用 design/ai-orchestration）
   ├── franchise-content      ← 新增：内容创作获客（1.13-1.16，AI 经 ai-orchestration）
   ├── franchise-engineering  ← 新增：工程全周期（2.1-2.9）
   ├── franchise-finance      ← 新增：财务账簿（3.1-3.6）
   └── franchise-performance  ← 新增：绩效提成经营（3.7-3.10）
   ▼
PostgreSQL 16（唯一真相源）+ Redis（缓存/锁）
```

**关键决策：**

1. 新域全部走 `domains/franchise-*` 独立 Maven 树模式（同 M2），模块间零依赖、经 Port/领域事件协作；yudao-server pom 增量挂载。
2. 持久化沿用 JdbcTemplate 手写 SQL（本仓库约定），公共列 `tenant_id/creator/create_time/updater/update_time/deleted`，JSONB 存 payload。
3. Flyway 续 fr 段（8xx）：`db/migration/franchise/`，命名 `V<日期>.<段号>__<slug>.sql`，成对 undo。表前缀：`fr_sale_* / fr_eng_* / fr_fin_* / fr_perf_* / fr_content_* / fr_service_*`。
4. 待办复用 platform-workflow：各批业务动作（费用审批/到账复核/付款审批/修订审批等）注册 pf_approval，统一 `/platform/todos` 出。
5. 命名避坑：`fr_commission` 已被"设计委托"占用；回款提成命名 `fr_perf_commission_*`。
6. 设计赋能不重建案例/预算/AI 生成表——经 Port 复用 yudao-module-design 与 ai-orchestration，franchise-design 只做员工端接入层与方案回写。
7. 金额一律分（integer）；员工走 `/admin-api`，`/app-api` 留给 C 端设计线。
