## 五、工程纪律（红线，全程有效）

1. **双仓库纪律**：后端/管理端改动只进 monorepo（`平台程序/`）；小程序改动只进 v3 库。绝不交叉。
2. **禁入清单**（00 §四b）：退款审批双单链、收款更正链、付款复核、绩效申诉、成本确认、项目结清 8-blocker 等**一律不建模**。
3. **错误码段位**：finance=1_102、crm=1_110、commission=1_111、design=1_112、sales=1_113 → 阶段 0 新代码：消息/profile 走平台共享段（1_099/现有 platform 段）或按需新排段并登记。
4. **迁移号续号**：franchise 8xx（**下一个 811**）、franchise-system 85x（**下一个 855**）、pf 7xx（**下一个 704**）、identity 1xx（110）；成对 undo；已执行迁移文件不可再编辑。
5. **命名避坑**：fr_commission 已被设计委托占用；新表前缀 fr_ 域内自明（消息是 pf_ 平台段）。
6. **Modulo 惯例**：MP Mapper+DO+@TenantIgnore+显式 company_id+OrgScopeCustomizer（franchise 域）；JdbcTemplate+TransactionTemplate（design 惯例）；写命令 FranchiseCommands replay/record；审计 record 用雪花 revision。

## 五b、分支策略（每阶段一分支，完成快进合回主线 + 打 tag）

拓扑（阶段 0 已就位）：

```
feat/m2-franchise-platform   01e4245   后端 M2 基线（合并决策点，先不动）
└─ feat/backend-miniapp-parity   043dcea   ★ 工程主线（集成线，始终包含所有已完成阶段）
   └─ feat/stage0-common-base-20261101   b361560   阶段 0 工作分支（当前开发位置）
```

规矩：
1. **每阶段开一个工作分支**（命名 `feat/stageN-<模块>-<日期>`），阶段内所有项都在该分支推进，不按项细切。
2. **阶段完成时快进合回主线 + 打 tag**（四条命令，`--ff-only` 禁止产生 merge commit，单人线性开发保持历史线性）：

```bash
git checkout feat/backend-miniapp-parity
git merge --ff-only feat/stage0-common-base-20261101
git tag stage0-done && git -c http.proxy=socks5://127.0.0.1:27890 push origin stage0-done
git -c http.proxy=socks5://127.0.0.1:27890 push origin feat/backend-miniapp-parity
```

3. **下阶段从合回后的主线拉新分支**：`feat/stage1-business` → `feat/stage2-engineering`……依此模式；v3 库同理（当前主线 `feat/login-dual-channel-20261031`）。
4. **并行例外**：阶段 1.5 与阶段 2 若真并行，各占分支先后合回；后完成者合回前先在主线上快进前序阶段。
5. **可弃性**：某阶段方向作废 → 整支丢弃，主线不受污染（tag 提供阶段内回滚点）。
6. **主线合流决策不动**：`feat/backend-miniapp-parity` → `feat/m2-franchise-platform`（→ 最终收口 main）保持单独拍板，届时开 PR 当合并说明书；阶段分支永不直接碰 m2-franchise-platform / main。
7. 单人项目不开"每批次/每项"细粒度分支——commit 粒度已足够回溯。
