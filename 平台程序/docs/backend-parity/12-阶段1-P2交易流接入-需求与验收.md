## §一、背景与目标

B2 板块 B 后端（franchise-sales 域，R1-R14）已交付并通过 e2e；v3 `api/franchise/sales.js` 骨架已预置。本批把 **workflow 页 API 态**的交易流视图接入真实后端：需求登记、报价测算（服务端算价）、合同签约与两期计划展示、交付四节点、方案「转正式」、报价导出（P4 并入）。

**范围裁剪（08 §三 P2 定稿）**：回款办理（R11 collect）**不在业务页开放**——业务页 stages 只读展示（入口归属记 §十一 S1-14）；设计委托链（franchise-commission，demo commission 页 sales-offline-v1 协议）**不在本批**。五态判定沿用 P1：`platform-crm.pageMode(token,post)` 判 api 态={sales,sales-lead,boss,owner}（**owner 为 API 只读态，不回落 demo**）；**本批新增能力判定 `saleWrite`={sales,sales-lead,boss}**（854 种子：write 不含 owner；finance 系不在 workflow 页出现——finance 系用户打开 workflow 视图按 P1 五态回落 demo 原样，此为既定行为单独声明）。

## §四、字段映射细则

### 表单 → items 编译（确定性；与 demo 公式同口径）

真实 budget 表单字段：宽/深/层数/占地 footprint/面积 area/基础 foundation/结构 structure/屋顶 roof/外装勾选 exterior{window,paint,stone,light,waterproof,lightning}（6 项，insurance 为第 7 项勾选）。**编译规则**：按 Design.budget 公式逐行直译，**quantity=1、unitPriceCents=round(行金额×100)**（行金额=demo 公式的 quantity×unitPrice 乘积，demo quantity 可能小数而后端须整数，行金额直译避免精度损失）；**行内携带展示字段 `qtyText`（原始工程量字符串）与 `unitText`（原始单价元字符串，两位小数）——后端 items 透传未知字段（已核实 SaleQuoteService.items 原样落库/回显/exportSheet 原样返回，隐式契约登记 S1-20b）**，供 P4 导出渲染「工程量/单价」列：
- main：`基础 · {foundation}`（footprint×单价180/220/320）、`结构 · {structure}`（area×850/680）、`屋顶 · {roof}`（roofArea×240/180；roofArea 默认=footprint×1.1 保留 demo 逻辑）
- decor：勾选的外装行（门窗120/墙漆55/文化石45/灯光20/防水25/防雷10，area×单价）
- **保险勾选 → items.insuranceCents=round(行金额×100)；managementCents 恒 0**（两者必传）
- **提交前前端逐行校验**：unitPriceCents∈[0,10^9]（行金额≤1000 万元——面积 11764.70㎡×850 元=**999999500 分**可通过、11764.71㎡→1000000350 分拦截）、total∈(0,10^12]、label≤32 字；越界**零请求**+文案「单项金额超过上限，请核对面积与配置」；**roofArea 默认=Math.round(footprint×1.1)（取整，与 demo 现行一致）**，roofArea 可编辑且人工修改优先；核定勾选 budgetChecked 必选后方可提交（沿用 demo 必需条件）
- priceVersion='sales-v1-表单口径'；address 本批不填；表单校验沿用 demo（尺寸 3-40/层数 1-6/面积两位小数 ≤10^7——10^7 极端值由逐行校验拦截）

### DO → 渲染模型（platform-crm 扩展纯函数）

- `requirementRow(DO)`：{id,version,style,sizeText(width×depth×floors),note,date}

## §六、写命令契约（八命令幂等 / revision / 错误三分类）

- **幂等命令清单（八命令）**：requirement/quote/contract-create/sign/void/promote/delivery-create/delivery-advance；键=`sale-{动作}-{16位hex}` 命令快照制（语义同 09 §六：网络失败保留快照重试同键、确定性业务失败丢弃快照、字段变更/成功后丢弃、双击 busy 锁、切岗清快照）；**advance 键按节点绑定**（快照 per node）
- **revision**：sign/void 带 contract.revision（R7/R9 后**重拉 R8** 获取新 revision）；冲突 1_099_000_001 → 文案+表单保留+自动重拉+不自动重提（快照丢弃重建）
- **后端幂等顺序缺陷（S1-21，登记不阻塞）**：contract-create 先查有效合同再查幂等记录——首次成功但响应丢失后，原键重试撞 006。**本批协议**：网络异常（结果未知）→ 重拉 R8 核对——**一次空读仅表示「尚未查到」**（原 POST 可能晚提交），**保留原命令快照**；用户重提**保持原键**（重放语义成立时返回首次；撞 006 时同样进入 R8 核对流程，不判失败不自动作废）；AC9 补「R8 空读后原 POST 晚提交成功」用例。**同键异内容冲突（1099000000）的承诺范围**：后端指纹覆盖不完整（quote 指纹漏 address/priceVersion/尺寸、delivery-create 漏 requirementId——缺口 S1-23）——客户端仍严格「同键必同内容快照」；服务端可能对部分字段变更返回首次对象而非冲突——**客户端以响应 quoteId/deliveryId 后重拉列表为准**，AC 区分客户端快照证据与服务端副作用证据
- **错误码映射（platform-crm.errorMessageSales）**：1_113_000_001→「报价明细不合法，请核对金额与行数（单项不超过一千万元）」；1_113_000_003→「交付节点须按顺序登记」；1_113_000_004→「引用对象不存在或不属于本客户」（R14 限定场景=空态）；1_113_000_006→「该客户已有一份有效主合同，作废后方可重签」；1_099_000_000/1/403/-1/未知 → 沿用 P1 errorMessage；R14 的 004 仅在 R8 已确认归属时渲染「尚未创建交付」空态
- **降级**：单区块失败独立降级重试（§三聚合加载规则）；POST 成功+刷新失败 → toast「已保存，列表刷新失败」
