## 四、本项关键设计决策点（需求文档必须先回答）

| # | 决策 | 选项 | 推荐默认 |
|---|---|---|---|
| D-基2-a | 表归属（07 §四 D-基2-1 已定） | platform-workflow 扩展 vs 新 platform-message 模块 | **platform-workflow**（复用其 Controller/鉴权/错误码段惯例，避免为一张表开模块） |
| D-基2-b | 收件人身份 | 按 userId（跨岗位共享）vs 按 postId（岗位隔离） | **userId**——消息是「给我看的」，人换岗位不丢消息；org_id 仅作过滤维度（对齐 F4 蓝本按公司 scoped） |
| D-基2-c | type/route 字典 | 自由字符串 vs 受控枚举 | **受控常量**（type/route 各一张小字典，后端校验白名单、前端映射图标与跳转）；route 取值对齐 v3 现有路由键（F4），新增路由先登记 |
| D-基2-d | 发送 Port 形态 | platform-workflow 直接暴露 `MessageSender` @Service vs franchise-api 定义 Port | **直接 @Service 注入**（平台模块消费方=platform/franchise 同仓，无跨包边界；franchise-api Port 留给 franchise 域与底座解耦的场景，本项不属） |
| D-基2-e | 幂等去重 | 业务键唯一约束 vs 允许重复 | **业务键幂等**：`(sender_domain, dedupe_key)` 部分唯一索引（仿 pf_approval uk 惯例）；`dedupe_key` 由发送方拼（如 `fr-fin:receipt-confirmed:123`）；同键重发返回既有行（幂等返回，不报错） |
| D-基2-f | 已读模型 | 单条已读+全部已读 vs 批量带版本 | 单条 `POST /platform/messages/{id}/read` + `POST /platform/messages/read-all`；**已读幂等**（重复已读 200）；read-all 走批量 UPDATE（WHERE user_id AND read=false） |
| D-基2-g | 未读数 | COUNT 实时 vs 冗余计数 | **COUNT 实时**（单用户消息量小，KISS；量大再优化） |
| D-基2-h | 分页 | 全量 vs 游标 | **游标分页**（id 倒序 `beforeId` 参数，仿仓库既有 CursorQueryOrgScope 惯例）；v3 消息页蓝本为全量列表，接入层一次拉一页即可 |
| D-基2-i | 谁能发 | 任何后端代码 vs 白名单域 | `sender_domain` 受控登记（与 type 字典同源）；**本期发送方=空（纯建通道）**，各业务域注册随其所属批次（如工程批次发进度通知）——即本项交付「通道+API+前端」，消息数据由 e2e 注入 |
| D-基2-j | 派生通知（F4 的 design/performance-notifications） | 后端化后是否保留本地派生 | **本批不摘除**（本地派生照旧）；API 消息合入列表（`utils/platform-messages.js` 纯函数合并+排序，仿 scoped 模式），摘除时机随对应域后端化批次 |
