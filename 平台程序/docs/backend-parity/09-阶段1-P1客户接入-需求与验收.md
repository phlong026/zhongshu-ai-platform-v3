## §一、背景与目标

`pages/customers`（客户列表页）与 `pages/workflow` 的 `customers/customer/transfer` 视图及 `register/edit/follow` 弹层当前数据来自本地 Storage 演示账（utils/business.js + utils/sales-workspace.js）。B2 后端 CRM（franchise-crm 域）已全量交付并通过 e2e。

本批目标：**后端登录具备对应能力的岗位时，客户列表、客户工作区、跟进登记、客户登记/编辑、责任转交走真实后端（api/franchise/crm.js）**；未登录后端（guest/no-post）或无能力岗位时页面保持演示数据原样、零请求。**纯 v3 库工作，monorepo 零改动**；接入中发现的后端缺口记 §十一 待决（S1-11），不在本阶段修。

## §二、接口契约表（api/franchise/crm.js；已对 CustomerController/LeadController/CustomerService/序列化配置核实）

**序列化事实（全表通用，前端按此处理，不做任何假设性转换）**：
- `LocalDate`（nextVisitDate）→ JSON 数组 `[年,月,日]`（如 `[2026,11,5]`；jackson `write-dates-as-timestamps:true` 无格式化器覆盖）
- `OffsetDateTime`（createTime/lastFollowAt）→ 毫秒时间戳（非 nanoseconds）
- `Long`（ID/revision/ownerUserId 等）→ **严格区间外输出字符串**（NumberSerializer：`|v| ≥ 2^53-1` 即输出字符串，**边界值 9007199254740991 本身也是字符串**）；前端一律按不透明值处理：只做 String 相等比较与透传回传，禁止 `Number(id)` 等数值化
- follows 排序 `createTime ASC, id ASC`；schemes 排序 `kind, version ASC`（均升序返回）

| 方法 | 路径 | 参数/体 | 响应（data） |
|---|---|---|---|
| customers.page(pageNo,pageSize,keyword) | GET /franchise/customers | PageParam + keyword 按称呼/手机号 | `PageResult<Customer>`：`{list:[],total}`；Customer=`{id,name,phone,wechat,source,province,city,summary,status,ownerUserId,nextVisitDate(数组\|null),lastFollowAt(毫秒\|null),revision,createTime(毫秒)}`；status ∈ REGISTERED/FOLLOWING |
| customers.get(id) | GET /franchise/customers/{id} | — | `CustomerDetail={customer,follows[],schemes[]}`；Follow=`{id,customerId,note,nextVisitDate(数组\|null),authorUserId,createTime(毫秒)}`；Scheme=`{id,customerId,kind(BUDGET/PLAN/FACADE),version,title,payload,width,depth,floors,area,totalCents,authorUserId,createTime(毫秒)}` |
| customers.update(id,data,idemKey) | PUT /franchise/customers/{id} | `{name,wechat,province,city,summary,revision}`（**phone 不可改、source 不可改**；**客户端带 revision**） | `CustomerDetail` |
| customers.follow(id,data,idemKey) | POST /franchise/customers/{id}/follows | `{note,nextVisitDate(数组，可空)}`（**客户端不传 revision**；服务端以读取时 revision 做条件更新并自推进） | `CustomerDetail` |
| customers.saveScheme(id,data,idemKey) | POST /franchise/customers/{id}/schemes | `{kind,title,payload,width,depth,floors,area,totalCents}`（revision 服务端自取） | `Scheme`（本批无 UI 入口，只读 schemes） |
| customers.transfer(id,data,idemKey) | POST /franchise/customers/{id}/transfer | `{targetUserId,reason,revision}`（**客户端带 revision**） | `CustomerDetail`。**已知后端缺口 S1-11b**：重放校验指纹=TransferCommand(targetUserId,reason)，成功记录指纹={fromUserId,toUserId,reason}，同键同内容重放会误报 1_099_000_000（§六协议降级） |
| leads.capture(data,idemKey) | POST /franchise/leads | `{name,phone(11位必填),need(需求摘要必填),source}` | `Capture={leadId,customerId,result}`；result ∈ **CREATED**（新客户）/ **LINKED**（关联登记人可见的同手机号原客户；「可见」不保证——canAutoLink 接受同团队，但普通 sales 只能读本人客户，LINKED 打开失败处理见 §四）/ **LINK_REQUIRED**（customerId=null，等负责人关联） |

本批 UI 不接入：`leads.pending / link / invalidate`（客资待关联处理页=内容/线索流页面，不在 P1 页面范围，见 §十一 S1-6）。

## §三、岗位能力矩阵与双体系五态判定

### 岗位能力矩阵（后端权限种子 V20261022.851 + CustomerAccess 核实；前端入口显隐以此为准，服务端兜底）

| 能力 | sales | sales-lead | boss | owner | 依据 |
|---|---|---|---|---|---|
| 查询列表/详情（customer:query） | ✓ | ✓ | ✓ | ✓ | 种子 45-48 行 |
| 读范围（canRead） | 仅本人客户 | 本人+管理团队 | 全店 | 全店 | CustomerAccess.canRead |
| 登记客户（lead:capture） | ✓ | ✓ | ✗ | ✗ | 种子 39-40 行 |
| 跟进/编辑/方案（customer:write→canWrite） | 本人客户 | 本人+管理团队客户 | ✗（老板只看不办） | ✗ | 种子 49-50 行 + CustomerAccess.canWrite |
| 责任转交（customer:transfer） | ✗ | ✓（本批 UI 隐藏，S1-11a） | ✓ | ✓ | 种子 51-53 行 |
| 客资待关联处理（lead:handle） | ✓ | ✓ | ✓ | ✓ | 种子 41-44 行（本批无 UI） |

### 五态判定（复用 finance-desk 模式；**同时校验 token 与岗位**）

| 态 | 判定 | 行为 |
|---|---|---|
| guest | `http.token()` 为空（**岗位缓存仍在也按 guest**——currentApiPost 不校验 token，判定必须先查 token） | 整页 demo 原样，零请求 |
| no-post | 有 token 但 currentApiPost() 为空 | 同 guest |
| **api（目标态）** | 有 token 且 currentApiPost().roleCode ∈ {sales, sales-lead, boss, owner}（FranchiseRoles） | §四矩阵内动作走后端；**任何路径不得读写 demo Storage**（AC9 执行链 spy：读+写+删三类计数） |
| non-role | roleCode 为其他岗位（finance/engineer/…） | 整页 demo 原样，零请求 |
| expired | 请求返回业务 401（**两种形态统一处理**：后端 AuthenticationEntryPointImpl 走 HTTP 200 + body code=401；另有真实 HTTP 401 形态由 http 层清会话后 reject） | 见 §六 401 协议 |

实现载体：新建 `utils/platform-crm.js` 纯函数模块（零 wx/Storage 依赖，参照 utils/platform-finance.js），`pageMode(token, post)` 返回 `'api' | 'demo'`（guest/no-post/non-role 归并为 demo 行为），能力判定 `can(post, ability)`；页面 onShow 以 `auth.currentApiPost()` + `http.token()` 判定后分叉。岗位/组织一律取 API 任职，不读本地角色。

## §五、字段映射细则与语义差异

### 列表行映射（platform-crm.customerRow(Customer, ctx)；ctx 含 today 字符串。输出字段与 customers/index.wxml 现有消费逐一对齐）

| 输出字段 | 来源/规则 |
|---|---|
| id | 原样透传（不透明值，可超安全整数字符串）；wx:key 用它 |
| name / initial | name；initial=name.slice(0,1) |
| status / stageName | REGISTERED→已登记 / FOLLOWING→跟进中 / 其他原样兜底（两键同值，兼容 wxml badge 与 tab 判定） |
| phone（**拨号原值**）/ phoneText（**展示值**） | phoneText=掩码 `138****0628`；无 phone 时 phoneText=wechat 或「暂无联系方式」、phone='' |
| searchText | [name,phone,city,summary].join(' ') |
| city / summary | 原样 |
| brief | [city, source（非空且≠未记录）].join(' · ')；**不含宽深层数**（列表 VO 无 scheme） |
| fresh | !lastFollowAt |
| appointment | nextVisitDate→'YYYY-MM-DD'；无则 '' |
| next | appointment ? '客户回访' : '' |
| cue / cueTone / rank | 与 demo listCue 语义对齐：nextVisitDate<today 且 canWrite→`逾期 N 天`(danger,0)；=today→`今天 回访`(warning,1)；>today→`MM-DD 回访`(3)；无 lastFollowAt→`新客户`(2)；有 lastFollowAt→`N 天未跟进`/`今天已跟进`(muted,4)；无 canWrite 且 rank≥2→压为 5（只读） |
| sortKey（确定性） | rank0/1/3：appointment（'YYYY-MM-DD' 字典序）；rank2：createTime→'YYYY-MM-DD HH:mm'（新客户先来先排）；rank4：lastFollowAt 同格式（未跟进最久在前）；**rank5（只读压缩）保留压缩前按原 rank 规则算得的 sortKey**；**同 rank 同 key → id 字符串字典序稳定兜底** |
| detail | 新客户→「待首次沟通」；有预约→「下次：MM-DD 客户回访」；否则「上次：MM-DD」 |
| canFollow / action / url | canFollow=canWrite；action=canFollow?'写跟进':'看记录'；url='/pages/workflow/index?view=customer&id='+encodeURIComponent(id)（新客户且 canFollow 时 `&modal=follow`） |
| hasPhone | !!phone |

## §六、写命令契约（revision / 幂等 / 错误三分类 / 401 协议）

- **revision 逐接口**：update/transfer 客户端带读取时 revision，冲突码 **1_099_000_001**「数据版本已过期」→ 文案「数据已更新，请刷新后重试」+ 表单保留 + 自动重拉详情（重拉成功后**不自动重提**，用户确认后手动重提）；follow/saveScheme **客户端不传 revision**（服务端读取时自取并做条件更新），**并发仍可能返回 1_099_000_001**——处理同上：保留表单、重拉详情、手动重试。
- **幂等键=命令快照制**：提交意图时生成 `crm-{动作}-{16位随机hex}` 命令键并保存快照 `{key, customerId, payload}` 到页面实例；**同键必含目标 customerId 的随机命令身份，跨客户/跨页面/页面重建无碰撞**（随机量而非内容哈希）。失败重试**复用快照**（同键同内容）；**修改任一字段/关闭弹层/成功后丢弃快照**，下次提交生成新键；**双击由 busy 提交锁 + 快照复用**（第二次点击命中进行中命令直接忽略）；**重试中切岗/卸载** → 快照随 postKey 变化清理，回调按乱序规则丢弃。**快照生命周期按错误类型区分**：网络异常（结果未知）保留原快照供重试；**确定性业务失败（含 1_099_000_001 版本冲突、字段校验错误）丢弃快照**——重拉详情成功且用户确认后，下一次提交以新 revision/新键重建快照（避免旧 revision 快照反复冲突）。服务端重放语义（对 FranchiseCommands 核实）：键查找作用域=**域+用户+键**（聚合不参与匹配），命中后以 payload hash 校验一致性；**同键同指纹不重复写副作用，按当前资源重建响应**（follow 重放=当前 CustomerDetail；capture 重放按当前客资状态推导，可能≠首次响应）；同键异指纹 **1_099_000_000** → 文案「请刷新后重新填写」，不得自动换键重提。**transfer 已知重放指纹缺口（S1-11b）**：重放指纹（TransferCommand）与记录指纹（{fromUserId,toUserId,reason}）不一致，同键同内容重试会被误报 1_099_000_000——按「结果未知→刷新确认是否已转交」处理，缺口修复前不承诺转交幂等重放；capture/follow/update 指纹一致、正常承诺。
- **错误码映射（platform-crm.errorMessage(err, action)）**：1_110_000_000→「客户不存在或已转移，请刷新列表」；1_110_000_001→「当前岗位不能办理该客户」；1_110_000_003→「请填写称呼、11位手机号、需求和来源」；1_110_000_004→「已有该手机号客资待关联，请由负责人处理」；1_110_000_008→**按动作映射**：follow→「请填写沟通内容（500字以内）」、transfer→「请填写转交原因（500字以内）」、其他→「请填写内容或原因（500字以内）」；1_110_000_009→「预约日期不能早于今天」；1_110_000_010→「请检查客户资料（称呼必填、长度不超限）」；1_110_000_011→「请填写方案名称与有效尺寸」（预留 P2/P3）；1_110_000_012→「接手人须为本组织在岗业务人员」；1_099_000_001→「数据已更新，请刷新后重试」；1_099_000_000→「请刷新后重新填写」；403→「没有该操作权限」（**业务码 403 走 CommonResult body（HTTP 200），保留会话**）；code:-1（网络）→「网络异常，请刷新确认」；未知 code→err.message 兜底。
- **前端输入约束（提交前拦截，非法零请求）**：name≤64、wechat≤64、province/city≤32、summary/need≤500、source≤64、transferReason≤200；phone `/^1\d{10}$/`；nextVisitDate≥today。
- **401 协议（两形态 × 当前/迟到，四组合判定）**：页面在发起请求时记录 `requestGen=http.sessionGeneration()`；回调收到 `err.code===401` 时按组合处理——
  1. **业务 401／当前会话**（HTTP200+code401，requestGen===sessionGen）：`http.clearSession()`（http 层未清 token）+ 页面清理（清空 API 数据与表单、busy 复位、退出 platformMode 回 guest）。
  2. **业务 401／迟到**（重登/切岗后旧请求到达，requestGen!==sessionGen）：**整体丢弃**——不清 token、不清数据/表单/busy、不退出 platformMode（保护新会话现场）。
  3. **真实 HTTP 401／当前会话**：http 层已清会话并 reject（无 silent），页面执行页面级清理；token 已空，不再 clearSession。
  4. **真实 HTTP 401／迟到**：http 层 reject 带 `silent:true`，整体丢弃。
  即：**页面清理与 clearSession 都只发生在「请求属于当前会话代次」时**；迟到 401（无论形态）一律丢弃。清 token 后岗位缓存（zs-api-posts-v1）保留不动。
- **降级**：列表/详情 GET 失败 → 降级文案 + 重试按钮（API 态不回落数据，清空显示降级态）；POST 成功后刷新失败 → toast「已保存，列表刷新失败」。

## §七、乱序隔离（继承 01/03 契约三元组）

页面级 `loadGen`（每次列表/详情/候选加载 +1，响应回写前校验）+ 全局 `http.sessionGeneration()` + `postKey`（postId 字符串，onShow 变化时清空 API 数据、表单与命令快照）。每个异步回调（success/error/**finally**）回写前校验「loadGen+sessionGen+postKey+请求归属」，旧回调不得清掉新请求的 busy/表单态；**401 的处理按 §六四组合表执行**（迟到 401 整体丢弃，页面清理仅限当前会话代次的 401）。覆盖：列表加载、详情加载、orgStaff 候选拉取、四写命令提交回调（提交中切岗/登出 → 丢弃响应、不刷新表单、busy 复位、快照清理）；卸载后迟到响应丢弃。验收场景含 A→B→A、同岗重登（sessionGen）、手动重试覆盖、页面重建（navigate 返回重进）。
