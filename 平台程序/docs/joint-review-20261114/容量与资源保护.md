# 容量与上线验收方案

## 规模与判定

用户在本次审查中确认：200 家组织、1000 名员工、峰值 200 人在线、100 人同时发起 AI 生成。并发数、每秒请求数与任务完成耗时分别记录，不互相替代。

该规模是验收目标，不是已证实容量。当前本地100线程资源保护测试只证明进程内并发上限与拒绝行为，不证明200在线业务的p95，也不证明供应商同时完成100个任务。

## 场景矩阵

| 场景 | 数据/注入 | 通过标准 | 证据状态 |
|---|---|---|---|
| 组织隔离 | 200组织，每组织5员工，各自客户、财务与公司积分 | 列表/详情/导出/附件/任务不得读写其他组织；改X-Post-Id不扩大权限 | 待全规模HTTP验证 |
| 日常200在线 | 200不同会话；首页/客资/财务分页/待办，记录思考时间与请求率；稳定运行30分钟 | 统计p50/p95/p99、5xx/429/超时、DB池与CPU/内存，不以health endpoint代替业务 | 待隔离全链压测 |
| 100AI突发 | 同步起跑；20组织各5人以及单组织热点两组；慢/超时/429/连接中断stub | 所有请求明确受理/繁忙；无不明重复扣费；同幂等键仅一次外呼；资源占用有界 | 本地资源门禁测试与网关验收分别记录 |
| AI与财务混合 | 100AI突发同时保留100业务会话 | 普通业务延迟不被全部远程等待线程耗尽；与无AI基线对比 | 待隔离全链压测 |
| 超时后重试 | 远端已成功但丢响应；原key重试 | 先查持久收据；同任务ID、同扣费事实；UNKNOWN不盲重发 | 原有契约与本轮测试需绑定最终候选 |
| 资金一致性 | 同键20并发、不同键100并发、余额不足 | 一次命令/一次资金事实；余额+预扣+已结算守恒；拒绝不扣款 | 后端测试报告 |
| 验证码并发 | 同手机号20并发、不同手机号并发、同码双消费 | 同手机号仅1发送；不同手机号互不阻塞；验证码仅消费一次 | 后端Redis集成测试 |
| 真实渠道 | 微信、短信、COS、AI供应商 | 同一候选与真实资源审批、配额和费用记录绑定；全角色真机通过 | 未执行，不用stub代替 |

响应时间与成功率阈值需结合真实供应商合同和产品承诺确认；本方案不伪造已确认的SLA。即使全部请求快速返回429，也不能称100人AI生成容量通过。

## 本轮资源保护实现边界

B到A设计调用在持久化命令/计费前申请非阻塞许可；默认每B进程最多16个在途调用，每组织最多4个。额外请求返回业务码429，客户端保留原业务键重试；不引入无界队列。成功、失败、超时均释放；后台恢复也受同一门禁约束，受限时不改变持久命令状态。

这两个值是保护默认值，非供应商容量承诺。每进程保护不等于多副本全局配额；扩大副本或修改值前，结合Tomcat64线程、DB池20、供应商quota测量。首发要100个全部受理时，仍需验证持久排队/供应商容量，不靠把线程数调大宣称达标。

## 发布门禁

- 最终源码两仓SHA、B jar/镜像及Web dist hash绑定，验证使用split的`yudao-platform-server`，不发布历史融合包。
- B独立进程、DB、Redis、端口、密钥挂载；A设计小程序原运营不受影响。
- 当前角色×组织矩阵完成真机与Web验收：老板、财务及负责人、业务及负责人、工程及负责人、总部设计/财务与组织管理员按实际授权列全。
- 数据库备份在隔离新库恢复成功并核对核心表与账本，保留失败恢复路径；Compose配置测试不能代替恢复。
- 真实短信、微信登录、COS上传下载、AI计费/超时/重试通过；B充值仍关闭。
- 本次仅本地开发与验收，不自动等同推送、合并、部署、上传、提审或发布。
