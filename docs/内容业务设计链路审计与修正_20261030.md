# 内容创作—业务—总部设计—工程移交链路审计与修正

审计日期：2026-10-30

审计对象：以“周建国家”这一名客户和一个 `projectId`，从内容创作、发布登记、内容咨询、客户跟进、参考预算、设计委托、设计完成、客户修改、V2 成果下发，到业务移交和工程接收连续办理。目标客户是 5–20 人、岗位兼任普遍、要求当天事项能快速接续的中小乡墅公司。

## 1. 审计结论

主链的业务身份和成果版本总体可靠：同一内容作品生成的咨询保留 `workId / contentId / publicationId / publishedUrl`；咨询直接成为经办业务本人的客户；客户和项目在设计委托、修改、移交、退回补充及工程接收期间不重建；V1 修改为 V2 时不重复生成设计费和付款；工程接收只能接收总部实际下发且经客户确认的同版文件。

本轮检出并修正两个会影响小公司的真实缺口：

1. 新可视委托旅程的工程接收页只显示“接收并创建项目”，未渲染“退回补充”的原因输入和按钮。领域层虽支持退回，但工程人员在前端无法操作。旧六角色脚本因此绕过页面直接调用命令，形成“测试通过、用户点不到”的假闭环。
2. 内容咨询首次建客户时，客资先写入、客户后建档；如果客户建档失败，系统会留下一个未完成的半截客资。小团队随后再次登记会遇到重复联系人提示，却找不到可继续办理的客户。

修正后，工程人员可以在接收页填写具体缺件原因并点击“退回补充”；业务员从原客户、原项目和原 V2 成果继续补件，不需要重建委托。咨询转客户失败时同时回滚客资、客户和管理责任状态，可安全重试。

## 3. 连续身份与版本核对

连续测试在每个关键节点保存完整状态，并核对以下不变量：

- 客户从内容咨询生成后，`customerId` 不变。
- `projectId` 从客户建档到工程接收不变。
- 经办业务始终为李业务，责任人 ID 不因页面跳转改变。
- 客户的 `originPublicationId` 与发布记录一致，`acquisitionSnapshot.workId` 与创作作品一致。
- V1 修改后形成 V2；设计费订单和付款数组保持不变。
- 移交文件必须等于总部本版下发文件，模拟文件还校验客户、项目和图纸版本元数据。
- 工程退回后重提增加移交版本，但不重建客户、项目或设计委托。
- 工程接收记录保存移交版本和 V2 图纸版本，后续工程链可直接读取同一状态继续。

## 4. 跳转与卡顿分析

### 4.1 符合中小乡墅公司的跳转

- 创作结果直接进入发布设置，发布链接保存后回业务工作台；日常内容任务与客户待办在一个工作台汇合。
- 已发布作品详情提供“登记咨询客资”，登记成功直接进入客户工作区，避免“先建线索、再等分配、再接受”的三次交接。
- 预算结果直接进入设计委托，面积、范围和预算版本自动引用。
- 一次性体验支付完成后自动推进，总部设计行政从本人待办接续。
- 设计下发后业务员进入成果确认和移交；工程接收后直接创建工程项目。
- 退回补充仍在同一移交单办理，业务补件后原工程人员继续接收。

### 4.2 仍存在但不应误报为代码闭环的等待

- 内容生成、设计生产、专业审核均为体验模拟或线下事实登记；尚未连接真实生成服务和真实设计协同后台。
- 总部设计行政是跨组织串行责任人。当前有站内待办，但真实微信通知仍需生产通知服务。
- 发布链接由业务员人工登记，内容数据回采仍处于“待回采”；该状态不阻断客户建档。
- 设计支付为体验模拟，不代表真实扣款或银行到账。
- 六角色连续测试证明本地 Page/WXML 和领域状态闭环；实体手机、真实账号、真实多端并发仍需体验版逐角色验收。

## 5. 详细修改方案与实施结果

### 修正 A：恢复工程接收页的退回闭环

实施：

- 委托旅程模板接收 `canReturn`。
- 工程接收页显示当前电子交底，同时增加退回原因输入区。
- 接收页同时提供“退回补充”和“接收并创建项目”，退回必须填写具体原因。
- 六角色 B10 从直接调用领域命令改为真实页面输入和按钮事件；随后业务补件、重新移交、工程接收。

验收：`node scripts/verify-six-role-flow.cjs` 的 B01–B10 全部通过，B10 由真实 Page/WXML 控件完成退回、重提和接收。

### 修正 B：咨询转客户保持原子一致

实施：

- 在首次咨询转客户前保存客资和客户存储快照。
- 客资初写、客户建档和客资标记为已转客户三次写入纳入同一个回滚区间；任一步抛错时同时恢复客资、客户、管理责任三份状态及修订号。
- 新增两类失败注入回归：客户建档失败，以及客户已建好但最终客资落盘失败；回滚后重试只能生成一个客户、一条已关联客资和一个责任工作项。

验收：`node scripts/verify-content-customer-atomicity.cjs` 两项通过；既有 `node scripts/verify-sales-creation-chain.cjs` 8 项通过。

### 修正 C：同步金额格式回归断言

金额展示已统一为两位小数后，设计支付通知仍按旧的 `20/㎡` 文本断言，导致产品行为正确但完整设计链检查失败。本轮把断言同步为页面实际统一口径 `20.00/㎡`，没有放宽金额、面积或支付渠道校验。`npm run check:design-journey` 重新通过。

## 6. 体验版验收建议

体验版用同一组六人账号连续办理，不能用历史样例拼接结果。重点观察：

1. 李业务登记发布链接后，从发布记录进入该作品并登记“周建国家”咨询。
2. 客户页显示作品来源、原作者、发布账号和链接，预算及委托仍为同一个项目。
3. 林设计下发 V1；李业务提交修改；林设计下发 V2，费用没有新增。
4. 李业务确认 V2 并移交；张工程在接收页可看到退回原因输入和两个动作按钮。
5. 张工程退回后，李业务原客户出现待补充并可重提；张工程再次进入同一项目接收。
6. 接收后工程项目的来源客户、项目编号、工程负责人和 V2 图纸版本与前段一致。

页面可操作通过仍不等于真实服务完成。体验版报告应分别记录本地连续测试、微信原生模拟器、体验版真机六角色和真实外部服务四类证据。
