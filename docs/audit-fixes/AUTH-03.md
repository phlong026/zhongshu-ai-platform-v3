# AUTH-03：普通停用纳入交接清单

## 行为与复用范围

普通 `staff-status(false)` 改为调用既有 `DepartureHandoverService.emergencyRevoke`，保留旧接口的 Boolean 返回契约。撤权在独立事务先提交，客户、设计委托、工程、财务的扫描与待分配记录分别在自己的事务中执行；不在控制器增加包住全流程的事务。某域 SQL 失败不会回滚已经生效的撤权，仍使用原有 `SCAN_FAILED` 与 `in_flight=-1` 待核记录。

Web 和小程序的普通停用按钮直接使用既有 `/staff-emergency-revoke` 清单接口，停用确认说明事后补交接要求，结果逐域展示；失败域显示扫描失败和数量待核，并刷新待分配列表。原有正常离职、紧急撤权入口继续使用同一服务。

单岗撤销先复用 AUTH-02 的用户、岗位与组织锁以及保留角色、最后管理岗位检查，再调用已注册的责任端口扫描。现有端口只能按员工和组织统计，因此兼岗员工也保守检查本组织全部在途事项，不推测哪个岗位承担某项责任：

- 任一域有需承接的业务责任：保留岗位，提示先处理责任、办理正常交接，或在需要立即收权时使用停用/紧急撤权。
- 任一已知域缺少端口、扫描失败或返回未确认数量：保留岗位，不能把未知状态视为零。
- 四个已知域和所有扩展端口均确认无在途事项：撤销目标岗位，保留其他岗位。

没有增加审批层级或更改总部管理能力例外。普通停用、正常离职、紧急撤权和补交接共用同一套业务 Port。

## 真实业务域责任与历史边界

专项评审核实原完整应用实际只有 CRM Port，并非四个域都已接入。本修复补齐三个生产适配器；四域缺失检查保留，不能把未接入当成无责任。

| 业务域 | 承接范围 | 保留不变的历史 |
| --- | --- | --- |
| 客户 | 继续复用 `CustomerService.countInFlightByOwner / bulkTransferByOwner`；客户 owner 和接收人团队更新，revision 推进 | 历史跟进与原经办记录 |
| 设计委托 | 委托状态为 `HANDOVER_SUBMITTED`、版本等于当前 `handover_version` 的 `PENDING` 移交包工程接收人；委托 revision 推进 | 旧版与已接收包、提交人、决定人、附件冻结快照 |
| 工程 | 当前 manager / assignedEngineer，含归档后的催收等办理责任；同项目兼任只计一次，仅替换指向离职人的角色字段；未完成节点的当前 delay_owner 同步承接，项目 revision 推进 | 另一在任负责人、原 author、完工节点责任人、归档/结算经办人、delay_history 内原 actor/ownerName/ownerUserId |
| 财务 | 经核实目前无个人独占办理 owner；待办按组织向有效 finance / finance-lead 岗位共享，清单显示 `ORGANIZATION_SHARED` | payer 是实际垫付人，operator / registrar / matched_by 等是历史经办人，账款与上述主体不改写 |

设计与工程接收人都须具有本组织有效 engineer / project-manager 岗位。设计移交继续遵守提交人与接收人分离：接收人即使兼工程岗，也不能承接自己提交的当前移交包；加锁后逐包核验，拒绝会回滚此前客户转移。

工程历史换负责人可能遗留未完成节点的旧 delay_owner；扫描也计入此类项目。若接收人已是项目现任负责人，可只承接延期责任而不覆盖项目其他负责人；否则明确要求现负责人先调整延期责任或选择其接收，正常交接整体回滚。紧急撤权仍将该责任写入可检索的待分配清单，不漏报。

`ORGANIZATION_SHARED` 与 `NONE`、`NOT_INTEGRATED` 分开展示，双端使用“组织共享事项，需财务岗继续处理”，不显示“0 项已转移”，也不虚构个人待分配记录。它不承诺组织必然还有其他财务人员；本项没有新增最后财务岗位保护规则。

## 提交后复核与并发边界

单岗撤销提交后沿用正常交接的残留复核；复核统一复用紧急撤权的逐域隔离扫描与未知记录补偿。发现新责任时写 OPEN 待分配行，扫描异常时另起事务写数量为 -1 的待核行。若复核不能确认，单岗接口明确返回 `STAFF_POST_REVOKED_VERIFY_REQUIRED`：岗位已经撤销，需核对待分配清单或查找原员工补交接。两个客户端都会在失败响应后刷新任职和清单，不假定岗位仍存在。

用户锁串行化现有任职、撤权与交接流程；各业务域的所有新建/指派路径并未统一参加该锁协议。本修复不宣称阻断全部并发新增责任。真实独立连接回归覆盖“初次扫描之后提交新的责任，撤岗后复核将其写入待分配”的交错。更晚出现的残留仍可通过历史来源检索补交接。

新增适配器在调用方交接事务内锁定当前责任行并重核。设计按既有接收动作的移交包→委托顺序锁定；工程既有写入包含项目→节点和节点→项目两种顺序，因此交接使用 `FOR UPDATE NOWAIT` 获取项目与当前延期节点，冲突即回滚为可重试的交接失败，不等待反向锁。后续转移只更新已锁行，聚合 revision 推进使交接前打开的旧表单不能覆盖新责任。

若数据库整体不可用，未知行补偿也可能无法持久化。此时单岗接口会明确报告撤岗后复核未确认，紧急撤权清单保留 `SCAN_FAILED`；恢复后可通过历史来源检索再次办理补交接。保留原服务“撤权先提交”的设计，避免扫描故障延长已要求终止的权限。

## 历史员工补交接

新增 `/platform/org/handover-sources`，要求当前岗位拥有 `platform:org:manage` 且请求组织与当前组织一致。查询只返回当前租户、当前组织有历史或现行任职记录的员工，不查询全局手机号用户池；参数化检索姓名、手机号或员工编号，每页 20 人，重复岗位去重，输入中的通配符按字面匹配。软删除账号只按历史编号检索，姓名匿名化且不返回原手机号。

历史来源可以没有有效岗位，也可以没有现存 pending 行。选择后仍由既有交接服务复核本组织的岗位、待分配记录或实际责任证据，接收人仍须满足原有任职和各域资格检查。AUTH-02 的门店保留角色限制继续执行。前端检索有岗位/会话与请求代次守卫，修改关键词、离开页面或切换身份会使旧响应失效。

## 验证

加入 Backend CI `release-regression` 固定测试清单：

- `DepartureHandoverDomainsIntegrationTest`：真实四个生产 Port 装配后空岗可撤；客户/设计/工程真实责任分别阻断单撤；紧急撤权后补交接、跨组织隔离、当前与历史角色区别、工程同项目兼岗计数、延期责任与历史、归档后通过真实催收服务继续办理、财务共享待办仍可见；原提交人不得自接，孤立延期拒绝时前序客户转移回滚。
- `FinWorkbenchIntegrationTest`：真实撤岗后新财务可继续查看待报销、公司报销、员工退款与归还；原垫付人、付款经办与收款登记人不变；跨组织不可读写，离职员工不能新增垫付。
- `OrdinaryMemberRemovalIntegrationTest`：使用测试责任 Port 验证编排与故障边界；真实 SQL 扫描失败不回滚撤权并留下未知行；逐域阻断单撤；兼岗与失败保留岗位；独立连接交错新增责任；提交后扫描失败明确已经撤岗；无 pending 的历史离职者仍可补交接。该测试不代替真实业务域验收。
- `StaffHandoverHistoryQueryIntegrationTest`：分页、去重、租户/组织/任职证据范围、已删除资料隐藏、字面通配符和参数边界。

- `StaffIdentityWorkflowIntegrationTest`：原真实身份 HTTP 旅程装配新的交接服务，保留撤岗后旧身份失效、其他组织任职保留与原手机号恢复；该平台模块以明确零责任端口模拟没有业务对象，实际业务查询由上方加盟域测试覆盖。
- 既有 `DepartureHandoverServiceIntegrationTest` 增加缺少业务域端口时单撤失败保留岗位的用例。
