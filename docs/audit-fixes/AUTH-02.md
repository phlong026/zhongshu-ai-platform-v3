# AUTH-02：老板身份和最后管理岗位保护

## 行为

- 门店普通成员操作不能撤销 `boss` / `owner`。单岗撤销按目标岗位判断，整员停用、正常离职、紧急撤权检查该用户在本组织的全部岗位，兼有员工岗位也不能绕过保留角色限制。
- 撤权目标包含有效管理岗位时，必须保留本组织另一个有效管理岗位。同一用户另一个管理岗位可以承接单岗撤销，不能承接该用户全部岗位撤销。
- 管理岗位沿用 `SystemDirectory.roleHasPermission(roleCode, "platform:org:manage")`，同时要求账号可用、岗位模板存在、任职 ACTIVE、组织及底座部门可用。不是按角色名或负责人标志猜测，也不会将其他组织任职、停用账号当作保底管理员。
- 规则集中在 `StaffPostService`，四个普通成员入口全部执行。正常离职在业务转移前先用同一规则校验，已撤岗人员的补交接仍然允许；紧急撤权不绕过保留角色或最后管理岗位保护。
- 已经没有管理能力的历史组织仍可清理普通员工岗位，不借此扩大问题范围。

## 并发和总部交接

撤权沿用用户 advisory / 岗位锁，再获取组织排他锁。在组织锁内重新读取任职并检查剩余管理能力，锁查询刷新 MyBatis SESSION 缓存，两个管理员同时被撤时最多一项成功。正常离职持有组织锁至业务转移和撤权事务一起提交。

`OrganizationProfiles.transfer` 继续使用既有 `OperationsGuard`（总部租户、可用超级管理员）授权。流程改为在同一事务先建立接任老板岗位，再使用总部内部撤销方法撤掉旧老板岗位。该内部方法只放开保留角色规则，仍保护最后管理岗位，未新增可由客户端开启的豁免参数或普通控制器入口。

全局账号删除/禁用和整组织关闭属于已有总部安全清理能力，不属于四种普通成员撤权入口；删除用户后的授权回收仍可清除残留老板岗位。本修复不保证总部主动关闭账号、组织或权限配置后仍保留门店管理能力。

## 验证

新增 `MemberRevocationPolicyIntegrationTest`：四入口的保留角色与最后管理岗位拒绝、兼岗用户、停用账号、权限映射变化、跨组织候选、总部接续、删除回收例外，以及两个真实事务先读取缓存列表再并发撤权。

既有 `DepartureHandoverServiceIntegrationTest` 验证正常/紧急交接、失败回滚和补交接不退化；`OperationsIntegrationTest` 的总部老板交接使用真实管理权限判断，并验证普通老板不能调用总部交接。

上述三个类均加入 Backend CI 的 release-regression 固定测试清单。本地缺少 Maven/JDK 编译器和 PostgreSQL 容器，未在本地执行 Java 集成测试；本地仅进行源码核对和 `git diff --check`，运行结果以 CI 为准。

Web 部门与员工页和小程序配对提交都为保留角色显示总部办理原因，兼岗用户的整员操作同时受保护，仍允许独立撤销该人的普通员工岗位或选其作为接收人。Web 回归放入既有 `platform-staff-workspace.test.js` 并纳入 Backend CI 的前端任务；本地缺少 Vue/TypeScript 等依赖，未执行该文件。

无需数据库迁移。动态最后管理岗位保留服务端最终判断。
