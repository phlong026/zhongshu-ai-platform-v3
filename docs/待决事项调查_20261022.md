## 一、加盟商“服务订单”与设计师派单

### 现状：能下单，但没有人能接单
用户能走到的入口：
- 我的页 → “加盟商服务 → 展陈设计”（仅门店组织或未登录可见，`pages/profile/index.wxml` 的 `showStoreServices`）→ 店招设计 / 展厅设计 / 品牌物料 → 提交服务需求。
- 我的页 → “我的订单”（`view=orders`），以及通知、老板工作台里的“服务订单”快捷入口（`pages/admin/owner-page.js` 的 `services`、`utils/dashboard.js` 的 `serviceOrders`）。

提交需求后的处理方完全被关掉了，`miniprogram/utils/account.js` 里写死了 `&&false`：
| 位置 | 作用 | 现状 |
| --- | --- | --- |
| `provider(s,o)` | 判断是否总部服务人员 | 恒为 `false` |
| `serviceDispatcher(s,o)` | 判断是否设计负责人（可派单） | 恒为 `false` |
| `transition` 的 `assign-designer` | 负责人派单 | 永远抛“请由本任务团队设计负责人派单” |
| `transition` 的 `demo-plan` / `demo-delivery` / `demo-redelivery` / `cancel-resolve` | 出方案、交付、重交付、处理取消 | 要求 `fromProvider`，恒为 `false`，永远抛错 |
| `pages/account/index.js` 的 `serviceDesigners` | 派单候选设计师 | 过滤条件含 `&&false`，恒为空 |
| `pages/account/index.wxml` 第 32 行“负责人派单” | 派单区块 | `isServiceDispatcher` 恒为 `false`，永远不显示 |

结果：门店用户提交的订单停在“待沟通”，没有方案、没有交付，用户只能取消。这是设计师/设计负责人流程下线后留下的半成品，用户可见但走不通。

### 涉及文件
- 模型：`miniprogram/utils/account.js`（订单、`submitRequest`、`transition`、`provider`、`serviceDispatcher`、服务目录 `services`、种子订单）
- 页面：`miniprogram/pages/account/index.js` / `index.wxml`（`services`、`service`、`request`、`orders`、`order`、`plan`、`delivery`、`cancel` 等视图）
- 入口：`pages/profile/index.wxml`、`pages/account/sales/index.js`、`pages/admin/owner-page.js`、`utils/dashboard.js`、`utils/page-navigation.js`
- 测试：`scripts/verify-full-logic-simulator.cjs`、`verify-management-profile.cjs`、`verify-management-profile-simulator.cjs`、`verify-role-complete-pages.cjs` 引用了订单与派单。`verify-management-profile` 目前就是失败的，修它时要一并处理这块。
- 注意：“众墅甄选”采购（`procurement`、`purchases`）是另一条线，与服务订单无关，不能误删。

### 方案对比
| | A. 只删派单代码 | B. 隐藏入口，保留数据结构 | C. 整条服务订单一起删（推荐） |
| --- | --- | --- | --- |
| 做法 | 删 `assign-designer`、`serviceDispatcher`、派单区块 | 去掉“展陈设计”和“我的订单”入口 | 删店招/展厅/品牌物料需求、订单列表与详情、方案/交付/取消视图及对应模型、种子、测试 |
| 用户可见变化 | 无 | 少两个入口 | 同 B |
| 残留 | 订单仍能下、仍走不通 | 死代码仍在 | 无 |
| 风险 | 低，但没解决走不通 | 低 | 中：要同步改 4 个旧脚本和导航映射 |

### 推荐：C
理由：你已决定“只保留设计行政、整条旧链路一起删”；服务订单的处理侧已经被关死，继续保留只会让用户下单后没有任何回应。如果之后要做店招/展厅设计服务，应按新流程（委托→付款→设计行政）重做，而不是复活这套派单模型。若近期要对外演示这块功能，先做 B，之后再做 C。

## 二、隐私政策与用户协议

### 现状：占位页，内容是开发口吻
- 入口：登录页“同意《用户协议》”“《隐私政策》”（`pages/account/index.wxml` 第 36 行，`view=agreement` / `view=policy`）、我的页“隐私政策 / 账号与隐私”、`view=privacy`。
- 两个视图共用同一段话（`index.wxml` 第 41 行）：“当前为本地交互演示……正式上线前需由运营主体提供完整协议……当前页面不构成正式运营服务协议。”`privacy` 里还有账号绑定、短信登录、微信授权、账号注销，提示均为“暂未开通”。
- 这是给开发看的说明，不是给用户看的协议。商用上线不能这样。

### 小程序实际用到的个人信息相关能力（需要在隐私指引里声明）
`wx.chooseMessageFile`（7 处）、`wx.chooseMedia`（4 处）、`wx.saveImageToPhotosAlbum`（2 处）、剪贴板读写（各 1 处）；登录为演示账号体系，未接入微信手机号。`app.json` 里没有隐私相关配置，需要在微信公众平台“服务内容声明 → 用户隐私保护指引”里填写，并与小程序内正文保持一致。

### 需要你提供的内容
1. 运营主体全称、联系方式、客服渠道。
2. 隐私政策正文：收集哪些信息（姓名、手机号、客户资料、图片/文件、收付款凭据）、用途、保存期限、第三方共享、用户权利、注销方式。正文必须由法务确认，我不代写。
3. 用户协议正文：账号与权限、服务内容、费用与结算、数据归属（业务数据属于所在组织）、争议处理。
4. 账号注销入口：当前“暂未开通”，上线前要有可用路径或明确的客服渠道。

### 推荐
- 先不动正文，等你提供法务文本。
- 同时做一个低风险的过渡改动：把开发口吻的说明改成中性提示，并把短信登录、微信授权、账号绑定这些“暂未开通”的行从用户可见界面移除，避免对外出现“演示/未开通”字样。这一步我可以马上做，不涉及协议内容本身。
- 正文到位后，把两个视图拆成独立页面（现在共用一段话），并在登录页勾选前要求先查看。
