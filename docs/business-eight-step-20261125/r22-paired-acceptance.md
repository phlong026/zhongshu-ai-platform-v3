## 自动化配对方法

沿用 `.github/workflows/paired-release.yml` 和 `平台程序/script/release-rehearsal/freeze_pair.py`，不建立另一套发布机制。

公开源码上传授权已经由用户明确确认。两个候选上传时必须逐提交校验 tree 一致，并执行：

1. #146/#149/#152 的修复已在准确新 head 通过 CI，#157 薪酬真实 PG 也已通过。继续执行 R10/总部增量和最终组合的 Backend CI；成功结果必须对应当前远程 head。
2. 读取两个候选的远程完整 40 位 SHA，记录到验收工单。不要凭本地 SHA 推断远程 SHA；Git Data 导入时提交元数据可能不同，应同时核对 tree。
3. 手动运行配对 workflow，`frontend_sha` 与 `backend_sha` 均传这两个具体 SHA。运行工作流的 ref 选择包含本次新配对步骤的后端候选分支。
4. `freeze_pair.py` 对照已检出的后端和获取的前端 SHA，只创建固定提交工作树；后续步骤复用该组合，不再跟随移动分支。
5. 下载该次 `paired-release` 证据，核对 `acceptance.json` 的 `frontendCommit` / `backendCommit` 与工单完全一致，并保存对应 run URL。

示例仅在已上传候选存在时执行，SHA 变量必须替换为刚核验的实际远程值：

```bash
gh workflow run paired-release.yml \
  --repo phlong026/zhongshu-ai-platform-v3 \
  --ref task/r22-paired-candidate-backend-20261125 \
  -f frontend_sha="$FRONTEND_CANDIDATE_SHA" \
  -f backend_sha="$BACKEND_CANDIDATE_SHA"
```

### 新链配对覆盖

真实后端 fixture 先通过业务服务完成前六步、付款草案和合同签署，并上传实际扫描通过的资料。固定小程序中的 `verify-paired-external-handover.cjs` 复用真实 `external-entrust` / `external-handover` 模型与 API，只将 HTTP transport 接到测试协议。

请求经过真实 Spring 控制器、生产日期/大整数序列化和 PG 业务服务：登记外部委托→登记三份成果→核对并提交四份冻结包→指定工程人员接收→原命令原键重试。断言同一个工程、一条接收审计、四份资产和正式合同两期计划。

接收后八步仍为七步；随后由真实工程准备、开工前收款和带证明的实际开工使第八步完成，进度为 100%。继续断言没有旧设计行政审批、模拟费用订单或自动设计费用应付。

测试中的收款沿用 `BusinessReceiptPortTestStub` 写入真实财务表，覆盖工程付款门禁和净额读取，不等于完整财务凭证核实链或真实支付渠道验收。上述页面模型、委托和工程服务的真实 PG 组合尚待 CI 执行。

此测试验证接口和业务组合，没有覆盖微信渲染层、真实身份令牌获取或手机摄像头；这些必须按后面的设备清单验收。既有配对流程继续覆盖旧移交兼容、真实内容格式、不可变包、迁移失败恢复和健康回滚。
