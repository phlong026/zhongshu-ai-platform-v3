# R10 小程序：外部成果移交与工程接收

## 页面和办理边界

新分包 `pages/external-handover`，通过 `index?commissionId=...` 进入。沿用白底、棕色操作按钮，页面分“本次移交”和“历史版本”。

- 业务员/业务主管按服务端动作权限提交，填写真实客户确认日期、客户确认文件、同公司接收人及交底说明，主动确认已核对。老板只读。
- 三份外部成果与其需求版本中的付款约定直接展示，不重复登记。首次移交尚无包时，仅当前可提交业务岗读取 R09 外部成果接口，并核对客户、委托、成果及需求版本；工程接收岗不读取 CRM 委托需求接口。
- 当前指定工程师/项目经理按服务端 `canDecide` 和动作集合接收或退回。退回原因必填；接收需主动确认本版资料。接收采用服务端返回的真实项目编号，不创建本地工程、合同或开工事实。
- 每版移交的四个文件槽位、接收人、交底、处理说明和付款快照均可回看。重新移交形成新版本，客户确认文件、日期和确认勾选须重新填写。
- 接收后具有工程查询权限的工程/老板/财务岗可“查看工程记录”，业务岗继续查看已接收包和项目编号，不越过工程域授权。实际开工继续走工程原流程；客户第八步由后端真实开工证据派生。

## 接口与已有页面

所有业务命令及包内资料读取采用 R10 `external-handover.md` 契约。提交前的三份成果仍走 R09 `results/{version}/assets/{assetId}/download-tickets`；提交后的四份资料使用 R10 `versions/{version}/assets/{slot}/download-tickets`，不使用通用 BUSINESS_DOCUMENT 下载。

R09 外部成果页新增工程移交入口。原 `commission/index?view=handover/receive` 链接在授权读取确认 `workflowMode=EXTERNAL` 后转新页，原历史流程及 `history=1` 保留原只读入口。

工程分包新增 `external-handover.js`，仅当工程详情明确 `canReadHandover=true` 时，将真实项目 `documents.fileRef` 的十进制字符串与该项目已接收移交包文件精确匹配，补充委托、版本和槽位范围。缺失/false 时保留基本工程只读，不拉移交包或展示移交资料。保留大于 JS 安全整数的编号，不把数字字符串转成 Number，不回退通用下载。原 dispatch 资料及工程合同附件继续走各自入口。工程概览、开工准备和资料页提供移交历史入口；随包付款快照只读展示，正式付款与开工准备仍采用 R12 当前签约计划。

## 异常和会话

未知提交结果锁定原命令和原 Idempotency-Key，重试不自动换键。版本冲突保留未保存填写，需明确载入新版本；迟到 GET 和旧 revision 不覆盖已保存结果。

客户确认附件为 BUSINESS_DOCUMENT，PDF/JPEG/PNG，最多 30MiB；字节上传的一次性票据只尝试一次 PUT。结果未知时先 complete 核对同一资产；后端明确“尚未上传完成”后才显示“重新上传”并换票，保留已读字节。切岗或会话失效不继续关联附件。

每次预览下载完成后再次读取业务范围，工程转交/移交改派/撤权时清空私有数据和待处理文件。工程页额外使已在途读取和写入的本地响应失效，防同会话旧响应重新显示已撤权项目。

## 验证与组合依赖

`npm run check:external-handover` 运行真实 Page/WXML 行为、模型/API 契约、上传一次性票据及工程数字文件读取回归。原工程和 R09 专项继续保留。没有微信开发者工具/wcc/wcsc，因此不把 Node 检查称为原生编译或真机验证。

本分支基于 R09 小程序提交；R22 需与 R10 后端、R06 八步入口、R11/R12 付款计划组合。与 R12 的前端交集为 `pages/build/record/index.js`、`index.wxml`；本次未调整主包工程工具函数或付款计算。
