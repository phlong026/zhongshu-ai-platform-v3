## 一、总览：两条实现路线与统一主链

工程模块存在**两条并存的处理路线**，由项目上的 `recordFlow` 标记决定（判定：`engineering-records.is(p)`，见 `miniprogram/utils/engineering-records.js:5`）：

| 路线 | 适用项目 | 承载页面 | 特点 |
| --- | --- | --- | --- |
| **现场记录流程（当前主线）** | 业务线下设计流程（sales-flow）接收建档的项目，接收时自动初始化 `recordFlow v1` | `pages/build/record/index` 单页多视图 | 单人记录制：工程负责人记录事实，收款由门店财务登记，材料付款交财务办理，无工程内审批链 |
| **经典全流程（存量/复杂场景）** | 无 recordFlow 的存量项目、演示种子数据 | `pages/build/index` 多视图容器 | 六项开工核查、节点独立验收审批、供应承诺/收货/补发、供应付款补全等完整链 |

路由互斥已强制：`build/index.js:12` 发现 recordFlow 项目一律重定向到 record 页；`model.js:49` 对 recordFlow 项目抛出"请从项目记录页继续办理"。

**岗位与入口**（`miniprogram/utils/organization.js:15`）：工程岗（engineer/project-manager）底部导航为「首页 build/home / 项目 build/projects / 材料 build/materials / 我的」；老板/门店负责人从工程 Tab 工作台（`pages/engineering/index` 登录态）进入；其他岗位在工程 Tab 只能看到授权范围内的只读工作台。工程岗登录后 `pages/engineering/index.js:7` 直接重定向到 `build/home`。

## 二、主链路总图

```mermaid
flowchart TD
    A[业务：移交资料 packet-submit<br/>指定工程负责人] --> B[工程：核对接收<br/>确认接收 / 退回补充]
    B --> C[自动建档：同一项目工程档案<br/>初始化 recordFlow 与默认施工计划]
    C --> D[开工准备：已签合同 + 开工款约定<br/>+ 施工计划（模板/Excel导入/手工）]
    D --> E[老板确认两期收款约定<br/>（管理端 plan-approve）]
    E --> F[开工款：门店财务登记实际收款]
    F --> G{资金门禁 gate(start)<br/>开工款足额或老板例外}
    G --> H[记录实际开工<br/>第一个节点转为施工中]
    H --> I[施工节点循环<br/>现场记录·材料计划·到货·付款信息·节点完成]
    I --> J{是否主体封顶节点}
    J -- 是 --> K[封顶款：财务登记实际收款]
    J -- 否 --> L{还有后续节点?}
    K --> L
    L -- 有 --> I
    L -- 无 --> M{资金门禁 gate(delivery)<br/>封顶款收齐}
    M --> N[竣工交付：业主签收]
    N --> O[施工资料归档]
    O --> P[保修记录 · 款项收尾（线下结清）]
    I -.-> Q[材料链：计划→到货→付款信息→财务付款]
    I -.-> R[更正与撤回：到货/现场/节点完成]
```

经典全流程在"施工节点循环"处展开为更细的链：检查登记 → 负责人独立验收 → 整改复验 → 节点完成；材料走 供应安排 → 收货 → 差异补发 → 质量处置 → 耗用台账。详见第五节。

## 三、分阶段业务逻辑详解

### 阶段 0：业务侧移交（工程模块的输入）

- 业务在 `pages/workflow/commission/index?view=handover`（新流程）或 `pages/workflow/index?view=handover`（存量）完成「收图并移交」：核对正式成果、施工图、专业审核依据、客户确认凭据与电子交底，系统选定工程负责人（`sales-flow.js:137`：优先移交记录原负责人，否则取组织默认工程负责人）。
- 移交成功写入 `handover{status:'pending', managerId, drawingVersion, documents}`，工程侧待办与列表的判定条件为 `c.handover && !c.acceptance && handover.status==='pending'`（`workbench.js:10`）。
- 业务移交**完成接收后才算交付给工程**；接收动作在工程侧（阶段 1）。

### 阶段 1：接收业务移交与工程建档

**入口按钮**：工程首页「待我办理 → 业务移交待接收 · 核对接收」；项目列表「业务移交待接收」区「核对接收」/「查看移交」（`build/projects/index.wxml:15`）。

**页面**：线下流程 `pages/workflow/commission/index?view=receive`；存量 `pages/workflow/index?view=receive`（由 `SF.entry` 自动重定向）。

**按钮与动作**：
| 按钮 | 动作 | 业务逻辑 |
| --- | --- | --- |
| 确认接收 | `packet-receive`（新）/ `receive`（存量） | 勾选"本版图纸、客户确认、审核依据及交底已核对"后提交；`handover.status='accepted'`，写入 `acceptance{managerId, handoverVersion, drawingVersion}`（`sales-flow.js:147`） |
| 退回资料 | `packet-return` | 必填退回原因；`handover.status='returned'`，业务侧生成"移交资料待补充"待办，业务补充后以新版本重新移交 |

**自动建档**（关键衔接，`miniprogram/utils/business.js:29-33`）：`business.write` 检测到 `acceptance` 从无到有时，在同一事务中调用 `engineering-acceptance.receive(customerId)` —— 避免业务显示已接收而工程档案未建。建档逻辑（`miniprogram/utils/engineering-acceptance.js`）：

1. 权限校验：仅本次资料接收的工程负责人本人（`handover.managerId === 当前staffId === 项目managerId`）；已有工程档案时校验公司归属、项目编号、负责人一致，防止借接收越权。
2. `merge()` 生成/刷新工程档案：名称"客户 · 城市乡墅"，面积/层数取自项目基础信息，`documents` 为业务移交包五件套（正式成果/施工图/审核依据/客户确认/电子交底），施工图与版本号随包带入；工程侧只读，不得从工程端改写业务来源资料（`model.js:58` 显式断言）。
3. 线下流程项目执行 `engineering-records.init()`：初始化 `recordFlow`、执行工程人员=工程负责人、按层数自动生成默认施工节点（基础工程 / N层主体 / 主体封顶 / 后续合同工程）。
4. 建档后工程首页生成「开工准备待记录」待办，主链正式进入工程阶段。

### 阶段 2：开工准备与施工计划

**入口**：待办「开工准备待记录」→ `pages/build/record/index?view=prepare`（经典流程为 `build/index?view=prepare`）。

**表单**：已签工程合同总额、开工款（必须小于总额，余款自动为封顶款）、双方已签合同凭据、现场/班组/开工准备记录。

**施工计划编制**（`record/index.wxml`）——节点清单随项目接收自动创建，日期一律由工程人员填写，系统不预填工期：
1. **逐节点填写**：每行的名称/开始/结束日期直接编辑；保存开工准备时校验全部节点日期有效且顺序合法（提示「请为每个节点填写计划开始和结束日期」）。
2. **恢复标准一级计划节点**：`applyTemplate`（`engineering-records.js`）——按内置「合家美宅标准进度计划」或账簿自定义模板重置节点结构与顺序（主体层按项目层数展开；带圈 ①②③ 二级分项不进系统施工节点），**日期清空待填**；「封顶验收」节点承接 `milestone='topping'`（封顶款链路依赖此标记，不依赖节点名）。
3. **Excel 导入**：`importPlan` → `schedule-import.js`——只认 xlsx 三列（节点名称/开始/结束），≤20行；纯数字日期拒绝，日期随表带入；缺少封顶验收（主体封顶）节点时自动补在最后并提示。

**保存「开工准备」的规则**（`engineering-records.js:51`）：金额>0、开工款<总额、合同凭据有效、说明非空；已有已核算收款时金额与凭据不可变更；计划必须保留主体封顶节点。保存后：`recordFlow.contract` + `prepared` + `planSaved` 落库，**并自动调用 `submitTerms()` 把两期收款约定（开工款/封顶款）写入公司账簿 `operations.plans`（pending）**——老板确认待办随之生成。

**经典流程对应**：六项开工条件核查（图纸与范围/现场与标高/道路与水电/人员与班组/主材供应准备/业主交底），逐项弹窗登记核查人/日期/记录/凭据；第 0 项"图纸与范围"必须先有专业审核通过并绑定图纸版本签名（`model.js:56`、`ready()` 判定 `model.js:28`）。

### 阶段 3：收款约定确认与开工款（资金门禁）

- 老板在管理端「合同收款约定」审批（`plan-approve` / `plan-return`，`operations.js:48`）；退回时工程侧待办变为"合同收款约定需补充"。
- 约定批准后生成**开工款待办**：门店财务在 `record?view=collection&stage=start` 登记实际收款——金额不超过本期剩余应收、收款流水全公司唯一（`business.referenceUsed` 防重）、凭据必须留存（`engineering-records.js:55`）。
- **资金门禁** `operations.gate(id,'start')`（`operations.js:36`）：本阶段累计已核算收款 ≥ 开工款额才放行；不足时可由老板登记限额限期的例外（`credit-exception`）；约定未批准则直接禁止开工。
- **催收分级**（本轮改造，`engineering-records.js:93`）：已过约定收款日 → 待办升级为"开工款已过约定收款日N天，请催收登记"（pending）；7天内到期 → "约定收款日临近"（waiting）。

### 阶段 4：记录实际开工

- **现场记录流程**（`record?view=start`）：实际开工日期（不早于接收、不晚于今天）+ 开工凭据；校验前置"开工准备已保存 + 计划已存 + 门禁放行 + 未重复开工"。成功后 `actualStart` 落库，**第一个节点转为"施工中"**。
- **经典流程**（`build/index?view=start`）：还需登记实际开工时间、现场人数、技术负责人，并指派执行工程人员——只能选本工程团队在岗 engineer（`model.js:59`），由工程负责人（project-manager）提交；必备资料三项：现场人员照片、交底记录、业主确认凭证。开工记录绑定当时图纸版本签名 `signature`，图纸后续变更会使开工与验收记录失效。

### 阶段 5：施工节点循环（核心执行层）

节点页 `record?view=node&nodeId=…`，子导航一行四列：**施工记录 / 验收记录（页内锚点）/ 材料计划 / 资金计划**（`record/index.wxml:9`，本轮改为四列布局）。

**5.1 现场记录**
- 「先保存现场记录」：日期 + 现场情况 + 凭据；凭据支持**拍照/相册多图（≤9张）留证**（本轮改造，`record/index.js:44`），演示环境可用参考凭据。
- 更正：`site-correct` 需填更正原因，原记录进 `corrections` 历史；节点完成记录不能按普通现场记录更正（`isCompletionRecord` 保护）。

**5.2 材料计划与到货（材料子链，可先款后货/先货后款）**
1. 「提交材料计划」（`material-plan`）：选未完成节点 + 需到场日期 + 材料清单（名称/规格/数量/单位）；每行材料同时生成对应供应事项（初始"采购信息待记录"）。
2. 「确认本次到货」（`arrival`）：逐行填实际合格到货数量 + 到货凭据；累计到货不得超过计划数量。
3. 「调整需用数量」（`material-adjust`）：多报/取消按实际改，填 0 为取消；**不能少于已到货数量；已有财务付款的材料由财务处理，工程不能改；节点已完成时不能加大需用**（`engineering-records.js:70`）。
4. 「更正到货数量」（`arrival-correct`）：更正后数量 + 原因，历史保留；节点完成后改少需先撤回节点完成。
5. 「保存付款信息，交财务办理」（`material-terms`）：实际供应方、实际单价、运费、采购凭据 → 供应事项转"待财务办理"，生成财务付款待办（材料详情行内按钮直达管理端 `pay` / `pay-supplement` / 待审批 `pay-approval`）；已有实际付款的供应事项金额/凭据锁死。
6. ~~「查看采购原单」~~：原为无响应死按钮，已随 8.1 修复移除（甄选采购闭环接入时恢复）。

**5.3 节点完成**
- 「记录本节点完成」/「记录主体封顶完成」（`node` 动作，`engineering-records.js:63`）前置校验：必须是当前施工中节点、已留存现场情况与凭据、**本节点材料合格到齐**（`materialReady`：全部提交且合格实收 ≥ 需用，无未处置质量异常）、无正数材料计划时必须勾选"本节点无需新增材料，现场材料已核对"。
- 成功写入：完成标记的现场记录 + 单人记录制验收（`inspection.result='通过', reviewMode='single-person-record'`）+ 节点"已完成" + **下一节点自动转"施工中"**；封顶节点同时写 `recordFlow.topping`（封顶款待办依据）。
- **更正本节点完成**（`node-correct`）：受日期链约束——不早于实际开工/上一节点完成、不晚于下一节点首条记录、封顶不晚于封顶款收款日；原因必填、原值入历史。
- **撤回本节点完成**（`node-reopen`，`reopenBlock` 判定）：仅"最近完成的节点 + 下一节点无现场记录 + 封顶节点未登记封顶款"可撤回；撤回后验收记录移入 `reopenHistory`，完成现场记录降级为普通记录。

**5.4 节点资金计划**
- 「保存本节点资金计划」（`funding-plan`）：预计用款、计划用款日期、用途；仅汇总展示（计划/已承诺材料及费用/实付/待付），不产生新的应付；「本节点人工及其他费用」跳转管理端费用登记（`admin/operations?view=expenses`）。

**5.5 经典流程在节点层的扩展**（`build/index` views/model，仅无 recordFlow 项目）：
- **检查与验收**：3 项检查（轴线尺寸与标高/钢筋型号与保护层/排水预埋与接地）逐项登记 `inspect` → 按 `approval-policy.inspectionSubmission` 提交：负责人与经办人为同一人时自动通过；否则 `reviewStatus='pending'`，由配置的工程负责人在 `inspection-review` 独立验收（通过/退回，且不能审核自己提交的记录，负责人代办需另一名同团队负责人复核）。
- **整改与复验**：验收"需整改"生成整改待办 → `rectify` 登记整改+复验（复验结论也走独立验收）→ `inspectPassed`（`model.js:33`）要求最新验收签名匹配当前图纸版本、审核通过、且每个问题都有通过的复验。
- **完成本节点**（`complete-node`）：前序节点全部完成、当前版本图纸审核+版本核查有效、`inspectPassed`、本节点材料清单已提交且足量合格，四者齐备才可完成。
- **供应与收货链**：`material` 新增材料 → `demand` 提交需求（提交≠下单）→ `supply` 安排供应（数量≤未安排量）→ `supply-promise` 供应承诺改期（保留原日期用于交期归因，已有到货不可覆盖）→ `receive` 收货（实收/质量结论/送货单号唯一）→ 数量差异自动转 `reship` 差异补发 → `reship-receive` 补发实收（数量必须与补发一致）→ `quality` 不合格处置（更换后合格）→ `material-usage` 耗用/报损/退回/余料结转台账 → `stock` 公司余料领用（按原成本结转，不产生对外应付）。
- **改期**（`reschedule` 弹窗）：该节点及后续节点整体顺移、材料到场日随移；已有供货承诺保留需另行协调；已完成节点不可改期。

### 阶段 6：主体封顶与封顶款

- 封顶节点完成 → `recordFlow.topping` 落库 → **封顶款待办解锁**（`tasks()`：`stage==='topping'` 且已 topping 才生成）。
- 门店财务在 `record?view=collection&stage=topping` 登记「工程尾款」实际收款，规则同开工款（金额≤本期剩余、流水唯一、凭据留存）。

### 阶段 7：竣工交付

- **前置**：全部施工节点已完成 + 材料合格到齐 + **资金门禁 `gate(delivery)`**（开工款+封顶款足额，或老板例外放行）。
- **现场记录流程**（`record?view=delivery`）：实际交付日期、业主/授权签收人、交付记录、业主签收凭据 → `deliver` → 状态"已交付"，生成「交付资料待归档」待办。
- **经典流程**（`build/index?view=delivery`）：先展示交付条件三项核对（节点全完成 / 整改与材料差异闭环 / 施工资料已留存），再登记交付信息（日期/现场交付负责人/业主接收人）+ 交付凭据（交付现场照片、业主签收凭证）+ "场地清理与余料交接已核对"勾选；校验交付日期不早于开工、不早于任何验收复验日期、不晚于今天（`model.js:79`）。
- **交付后锁定**：施工资料只读（`build/index.js:28`：`primaryDisabled='施工资料已锁定'`；弹窗一律拒绝），款项仍可单独收尾。

### 阶段 8：归档、保修与款项收尾

- 「归档施工资料」（`archive`）：交付后才可归档；归档后仅保修、材料付款信息补充、收款登记可继续。

## 五、经典全流程专有链路补充说明

1. **验收审批独立性**是经典链的硬约束：`approval-policy.js` 保证"实际办理人 ≠ 独立验收人"，同人兼岗自动通过但留痕 `reviewMode:'same-person'`；图纸版本变化会使未闭环验收整体失效（`signature` 校验）。
2. **材料四态闭环**：需求（demand）→ 安排（supply）→ 实收（receive，含差异补发）→ 质量闭环（quality/material-use/stock）；`complete-node` 强制"节点材料足量合格"。
3. **付款三分离**：供应付款由 `supply-payment` 补全付款责任/金额/依据 → 财务在管理端办理；工程收款由工程备案 → 财务独立核算（`collection-review` 在工程端被拒绝，`model.js:49`）；业主直付走非现金核对。已有付款后供应原单锁定，只能原单补证。

## 七、待办引擎（主链的驱动方式）

工程首页/项目列表的"待我办理"不是静态菜单，而是由状态推导（`engineering-records.tasks()` + `workbench.snapshot()`）：

```
开工准备待记录 → 合同收款约定待老板确认(等待/退回需补充) → 开工款（临期提示/逾期催收）→ 记录开工
→ [节点N待记录] ×N（含主体封顶） → 封顶款 → 工程完成待记录交付 → 交付资料待归档
横向插入：材料待到货(pending)/材料待付款(waiting)、收款退回补充、节点更正与撤回恢复的原待办
```

每条待办携带直达 URL，点击即进入对应办理视图——这就是"所有按钮纳入主流程"的运行时保障：按钮不再是自由导航，而是状态机在 UI 上的投影。

## 九、结论

工程模块主链路为**状态机驱动的一条线**：业务移交 → 接收建档（自动）→ 开工准备（合同+两期约定+计划）→ 老板确认约定 → 开工款到账（门禁）→ 实际开工 → 节点循环（现场记录/材料/资金/完成，含更正撤回）→ 封顶款（门禁）→ 竣工交付（门禁）→ 归档 → 保修与款项收尾。所有办理按钮都挂在这条状态机的节点上，由待办引擎或页面视图按当前状态渲染；资金类动作与施工记录在岗位与门禁上双重隔离。梳理中发现的按钮缺陷与残留入口已当日修复（8.1–8.3，含全页面 bindtap↔方法交叉核对验证）；8.4 采购闭环为预留能力，接入时统一恢复相关入口。
