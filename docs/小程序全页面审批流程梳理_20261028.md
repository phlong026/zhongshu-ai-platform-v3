## 一、梳理范围与判定口径

覆盖 `app.json` 全部 **33 个页面**（6 个主包 Tab 页 + 10 个分包 27 个页面）及其直接消费的 utils 数据层。搜索关键词：审批 / 审核 / 待审 / 驳回 / 复核 / 批准 / approve / review / pending。

每个审批触点按四档定性：

| 档 | 定义 | 判定标准 |
| --- | --- | --- |
| **A 现役真审批** | 有状态字段 + 独立人审动作 + 可用入口/待办 | 状态可流转、有角色断言、待办可达 |
| **B 封存** | 代码完整，但被 `approval-policy.js` 的 deferred 黑名单拦截 | UI 按钮在、提交即抛"该事项在线下办理" |
| **C 死代码/残留** | 无写入方、无渲染配置、或恒真恒假 | 状态字段只读不写、按钮点了报"操作尚未定义" |
| **D 仅文案/模拟** | 界面出现"审核"字样但无流程逻辑 | 纯展示文字、演示剧本、模拟数据 |

全局机制（影响所有财务类触点）：
- `utils/approval-policy.js:3` `deferred()` 黑名单 + `pages/admin/model.js:18` 命令入口统一拦截（commit `21f4ac7` "财务仅登记收付款 record-only-v1"）；
- `moneyBoss()`（approval-policy.js:4）：金额类审批人必须是本组织老板；
- `utils/finance-participation.js` 参与人回避：申请/登记/审批过本笔的人不能做该笔的独立复核；
- `utils/finance-auto-review.js` 同人兼岗自动复核：登记人=财务负责人同人时系统自动复核留痕（不替代老板审批）。

## 三、现役真审批流明细（13 条）

### 3.1 金额类（审批人=本组织老板，`moneyBoss`）

#### ① 老板金额审批 money-review（报价总额 / 设计服务费）——业务域核心审批
- **对象**：客户维度的金额事项，`kind` 两种：`quote`（正式报价及合同金额）、`service`（设计服务费/委托费用约定）。
- **角色链**：业务员提交设计委托（`commission-submit`）自动登记 pending → 本组织老板审批。
- **状态机**：`moneyApprovals[].status`: `pending → approved / returned`；批准绑定版本签名 `signature`，金额或依据变化须重新审批；每次仅允许办理一笔、不能改原金额/依据/申请人（`utils/commercial-approval.js:5-13`）。
- **下游放行**：`approved` 才能生成设计款应付单、放行设计流程（`utils/sales-flow.js:48`）；`returned` → 业务员待办「委托费用待修改」可重提（`sales-flow.js:86`）。
- **免审通道**：老板预设「标准设计费用政策」且金额精确匹配时视同已审批（`sales-flow.js:33-38` `standardApproved`）。
- **UI**：执行页 `/pages/workflow/index?view=money-review`（标题"老板金额审批"，`pages/workflow/index.js:7`）；表单结论 choice【批准/退回】+ 意见 + 核对勾选（`pages/workflow/organization-views.js:4-11`）；待办入口：业务 Tab「审批待办」区（`pages/business/index.wxml:44`）、老板首页金额审批分组（`pages/admin/owner-home.js:210-216`）。

#### ② 付款申请审批 pay-approval（应付单付款授权）
- **对象**：应付事项（设计首款/尾款、材料采购、费用应付）的本版金额约定。
- **角色链**：经办/财务申请 → 老板 `approve-pay` / `approval-return`；强校验"金额约定由本组织老板确认""不能批准本人申请"（`pages/admin/finance-actions.js:21-23`）。
- **状态机**：`payable.status`: `需补充 →(pay-supplement 重送审)→ 待审批 →(approve-pay)→ 待办理 → 部分已付 → 已付清`；退回置 `needsSupplement=true`、`approval=null`（`finance-actions.js:28-31`）；审批签名=版本指纹，签名变了授权失效（`utils/finance-ledger.js:30`）。
- **下游**：付款登记本身无需再人审——`pay` 登记 即 `已核实`（record-only-v1，`finance-actions.js:38`）。
- **UI**：`/pages/admin/index?view=pay-approval`（"付款申请审批"，`pages/admin/finance-views.js:25`）；材料付款在工程端也有入口：材料计划行「办理付款」按钮在 boss+待审批 时指向 pay-approval（`utils/engineering-records.js:41`、`pages/build/record/index.wxml:27`）。

#### ③ 费用审批 expense-approve / expense-return（项目费用 + 公司日常费用）
- **对象**：`operations.expenses`（节点人工/运输等费用、`company:<id>` 日常费用）。
- **角色链**：工程/业务/财务岗提交（`expense-submit`）→ 老板批准/退回；禁止自批（`applicantPersonId/custodianPersonId !== 审批人`，`utils/operations.js:53`）。
- **状态机**：`pending → approved / returned`；退回后原经办 `expense-resubmit` 回 pending；未批准可 `expense-cancel` 撤回；批准后自动生成应付单并**预置老板审批**（`status:'待办理'`，`operations.js:53`）。
- **UI**：`/pages/admin/operations/index?view=expenses`（"批准费用/退回补充"按钮，`operations/index.wxml:22`）；工程端发起入口：记录页「本节点人工及其他费用」按钮（`pages/build/record/index.wxml:34`）。
- **旁支**：`expense-transfer`（老板/财务负责人把待处理费用交接给在岗财务）现役（`operations.js:52`）。

#### ④ 绩效金额结算核准 payroll（三段）
- **流程**：老板配置计费规则（`payroll-policy`，assert"规则由老板按已确认制度配置"）→ 财务生成结算单（`payroll-submit`，`pending`）→ 老板核准/退回（`payroll-approve/return`，"由另一位老板核准"，禁自批）。
- **状态机**：`settlement.status: pending → approved / returned`；核准后自动生成应付并预置老板授权（`utils/payroll.js:6-10`）。
- **UI**：`/pages/admin/operations/index?view=payroll`（"核准结算金额/退回核对"，`operations/index.wxml:10`）；老板待办 `operations.pending()`（`operations.js:44`）。

#### ⑤ 业主直付 material-finance（三段：老板确认 → 财务登记 → 独立复核）
- **对象**：业主直接支付的材料供应约定与直付流水（非公司现金事实）。
- **状态机**：老板 `direct-approve` 确认本版约定（按 signature 版本化，禁本人批本人）→ 财务 `direct-register` 登记（`待复核`；同人兼岗走 `same-person-routing.audit` 直接 `已核实`）→ 另一位财务负责人 `direct-review/direct-return` 独立复核（`已核实/已退回`）（`utils/material-finance.js:8-13`）。
- **UI**：`/pages/admin/operations/index?view=direct`（"确认本版业主直付约定/登记本笔业主实际直付/独立核实本笔直付"，`operations/index.wxml:12`）。

#### ⑥ 项目回款提成 collection-commission（授权内嵌型）
- **流程**：老板确认提成规则（`commission-policy`，总额+归属人+凭据）→ 财务在开工款/封顶款净实收足额后生成应付，应付单**预置老板授权** `approvalValid=true` → 退款/冲正导致收款签名变化时老板 `commission-reconcile` 人工核对后恢复付款；付款时再验授权有效（`utils/collection-commission.js:64-138`）。
- **状态**：`待足额到账 → 可生成应付 → 待付款 → 待人工核对 → 已付清`（`collection-commission.js:151`）。
- **UI**：`/pages/admin/commission/index`（"生成应付/登记付款/人工核对"，`collection-commission.wxml:19`）。

#### ⑦ 资金门禁例外 credit-exception
- **对象**：开工/交付阶段合同款未收齐时的限额限期放行。
- **角色**：老板（`operations.js:48 boss()`）；生效于 `gate()`（"老板已批准本阶段限额限期放行"，`operations.js:36`）。
- **阻塞面**：开工 `assertGate('start')`（`engineering-records.js:58`）、交付 `assertGate('delivery')`（`engineering-records.js:90`）——例外未批准则工程无法开工/交付。
- **UI**：管理端应收账款视图，无独立待办卡。

### 3.2 结果复核类

#### ⑧ 绩效周期复核 performance review
- **流程**：本人或老板 `performance-submit` 置 `待复核` → 老板 `review` 复核归档（冻结来源快照）或 `review-return` 退回；回避校验：不能复核本人周期、来源签名未变、无未处理申诉（`utils/performance.js:32-37`）。
- **UI**：`/pages/admin/index?view=review`（"复核并归档/退回重新核对"，`pages/admin/performance-views.js:12`）；老板首页"结果复核"分组。
- **注意**：归档后来源变化自动生成"另版复核"新周期（`performance.js:29`）；申诉处理入口被 deferred 屏蔽（见第四节）。

#### ⑨ 工程阶段验收独立审核 inspection-review（仅旧链路）
- **对象**：工程人员提交的节点阶段验收/整改复验记录。
- **角色链**：工程人员提交 `inspect` → 指定工程负责人（`inspectionLead`，不得为提交人本人；负责人与提交人同人时自动通过 `reviewMode='same-person'`）通过/退回。
- **状态机**：`inspections[].reviewStatus: pending → passed / returned`（提交时由 `approval-policy.js:11 inspectionSubmission()` 写入）；`passed` 才能完成节点、交付（`pages/build/model.js:33,74,79`）——**验收不过审则节点不能完成**。
- **UI**：`pages/build/index` view=`inspection-review`（"阶段X待负责人审核/去审核"，`pages/build/workbench.js:16-17`）。
- **重要**：新 recordFlow 链路**不存在此审批**——节点完成时自动写入 `reviewMode:'single-person-record', reviewStatus:'passed'`（`utils/engineering-records.js:68`）。此条仅旧链路存活。

### 3.3 核对确认类（有状态、有指定人、可退回，但非金额审批）

#### ⑩ 业务移交接收 packet-receive / packet-return
- **对象**：业务向工程移交的成果包（正式成果、施工图、审核依据、客户确认凭据）。
- **状态机**：`handover.status: pending → accepted（生成 acceptance）/ returned（退回补充，可重提）`；退回原因必填（`utils/sales-flow.js:141-148`）。
- **角色**：经办业务提交 → **指定工程负责人**（`handover.managerId`）接收或退回。
- **UI**：`/pages/workflow/commission/index?view=receive`（"确认接收/退回补充"，`commission/index.wxml:55-57`）；工程工作台重点待办「工程移交待本人接收」（`utils/workbench.js:9`）。

#### ⑪ 客资负责人关联 link-existing（成长域）
- **对象**：同手机号老客户关联申请（防重复建档、保留咨询来源）。
- **状态机**：`跟进中 → 待负责人关联（request-link）→ 已转客户（负责人 link-existing 办理）`；审批人须有 `manages()` 团队权限（`utils/growth.js:60-76`）。
- **UI**：客资详情页「提交负责人关联已有客户」「关联已有客户并保留咨询来源」+ 提示"已交负责人核对原客户"（`pages/growth/index.wxml:10`）。

#### ⑫ 客户成果签认 / 门店收图确认
- **对象**：正式成果下发后的客户签认（`confirmation`，版本须与 release 一致；design-first 还需 `designReceipts` 收图回执）。
- **角色**：下发=获授权设计人员；收图核查与签认登记=业务人员（boss / sales-lead / 归属业务员，`utils/authority-v2.js:22`）。
- **定性**：版本绑定 + 角色校验的**登记确认流**，非驳回型审批（`utils/design-coordination.js:11-12,30-32`）。

#### ⑬ 加盟商服务方案确认（账号域，本地单机）
- **对象**：门店形象/品牌服务订单的设计方案与交付成果。
- **状态机**：总部提交方案（demo-plan）→ `待确认` → 门店负责人（仅 owner/boss）`confirm-plan`（版本核对勾选）→ `进行中`；`return-plan` 退回需填意见；成果 `receive` 需 owner/boss 确认 → `已完成`；订单取消走 `cancel → 服务方正在核实 → cancel-resolve`（`utils/account.js:54-62`）。
- **UI**：`/pages/account/index`（"方案待负责人确认"卡、"确认此方案/返回修改"、"待确认"tab，`pages/account/index.wxml:31-34`）。
- **注意**：提交侧三个 demo 动作是演示剧本；确认/退回/接收/取消核实四类动作是带角色与版本校验的真流程（本地存储实现，无跨设备审批人）。

### 新增待拍板项（本轮梳理新发现，按影响排序）

1. **money-review（报价/设计服务费老板审批）去留** —— 业务域现役最大的审批流，阻塞设计款应付生成与设计流程放行；已有"标准费用政策"免审通道。若走"生成即生效"同款口径，需同时决定免审通道是否升级为唯一通道。
2. **pay-approval（付款申请老板审批）去留** —— 所有对公付款（设计款/材料款/费用）支付前的最后一道老板闸；record-only-v1 已把付款登记简化，但审批这道保留着。删它=老板对付款的事前控制全部消失（仅剩 credit-exception 与直付确认）。
3. **管理域金额审批族（费用/工资/直付/提成）** —— 四条都是"老板内控"性质，与小程序外线下场景重叠度高；可整体保留（推荐，改动为零）或逐条简化。
4. **旧链路 inspection-review 独立验收** —— 仅 `pages/build/index` 旧链路存活，新 recordFlow 已单人记录自动通过；若旧链路整体淘汰则随之消失。
5. **封存的 12 类财务审批代码** —— 现状"有 UI、提交即报错"，其中绩效申诉按钮是用户可点中的**死按钮**（报错文案暴露）；建议随批次 B 一并正式删除或隐藏按钮。
6. **轻量确认流（移交接收/客资关联/客户签认/账号方案确认）** —— 均为"指定人核对+可退回"型，不属老板金额审批，建议保留。
