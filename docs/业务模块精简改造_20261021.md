# 业务模块精简改造（2026-10-21）

本次按三批完成业务流程、业务页面与必要协作接口的调整。适用对象为约 10 人的加盟商团队。新业务主链从内容创作开始，到工程负责人确认接收业务资料结束。

## 当前完整主链

| 顺序 | 经办岗位与动作 | 完成后自动接续 |
| --- | --- | --- |
| 1 | 业务创作内容；生成完成后收到“保存成品”待办，保存作品 | 业务“发布作品”待办，关闭保存成品待办 |
| 2 | 业务选择账号发布，登记真实发布链接 | 关闭发布待办，保留内容跟踪入口与作品来源 |
| 3 | 出现真实咨询后，业务登记客资 | 直接建立本人客户；同手机号关联原客户，生成首次跟进待办 |
| 4 | 业务沟通需求、记录跟进；需求明确后点击进入方案预算 | 业务“方案与预算”待办；预约回访按日期提示 |
| 5 | 业务按需使用灵感、AI 平面、AI 立面，保存参考预算 | 业务“提交设计委托”待办；参考方案按实际需要选用 |
| 6 | 业务一次提交需求、资料来源、交付范围、设计费用与首尾款 | 匹配老板预授权标准时，直接生成财务首款待办；超出标准或未配置标准时，由老板审批一次 |
| 7 | 门店财务登记实际首款付款；总部收款财务核实实际到账 | 自动生成总部到账待办并记录实收；费用授权后行政即可安排线下设计 |
| 8 | 总部在线下安排设计、沟通与专业审核；设计行政在自己页面点击“设计完成” | **立即生成业务“跟进尾款支付”待办，同时生成门店财务尾款付款待办** |
| 9 | 业务跟进支付，门店财务登记实际尾款，总部收款财务确认实际到账 | 门店足额登记关闭付款待办；设计完成且本版首尾款足额实收后，自动生成行政下发待办及站内消息 |
| 10 | 设计行政实际下发正式成果，登记接收人、渠道或清单并点击“成果已下发” | 业务“收图并移交”待办 |
| 11 | 业务在同一页面收齐文件、记录本版客户确认、填写电子交底并选择在岗工程负责人，一次提交 | 工程负责人生成业务资料“核查接收”待办，业务显示等待接收 |
| 12 | 工程负责人核对资料后确认接收 | 关闭本条业务主链待办，业务显示“业务移交完成” |

业务不需要另行发起尾款申请，不为首款、尾款重复走老板审批。2026年10月22日补齐总部实际到账确认：门店付款与总部实收分别保存，财务确认后自动更新行政待办和站内消息，不再勾选“财务线下通知”。设计启动沿用费用授权，正式下发要求当前版本首尾款足额实收。详见 [到账联动](设计行政工作台与到账联动_20261022.md)。平台不派发设计师、不办理设计生产与专业审核；设计行政记录的是线下实际完成事件。

## 页面与角色入口

- 业务首页统一展示“待我办理”和“办理中”，覆盖创作发布、客户跟进、预算、委托、尾款跟进与移交。重复刷新按原单投影待办，不反复新建任务。
- 业务导航为“首页、创作、方案、客户、我的”。新客户工作区保留参考预算、委托和进度入口。
- 新委托使用“设计委托”合并表单；正式成果下发后使用“成果与移交”合并表单。新流程不要求施工报价或合同签订。
- 总部新增“设计行政”岗位及独立页面，主操作为“设计完成”“成果已下发”，并可查看本委托需求与修改意见。
- 加盟商老板可在管理个人页进入“标准设计费用”，配置交付范围、总额、首尾款与总部实际收款方。每次配置保存新版本；既有委托继续引用提交时的已授权规则。
- 门店及总部财务继续使用已有财务工作台。工程仅复用现有接收入口。

## 精简后仍保留的必要资料

“成果与移交”一次保存正式成果、正式施工图及版本、对应线下专业审核依据、客户对本版成果的确认凭据及日期、电子交底、接收负责人。没有拆出单独的收图、签认、图纸归档或交底审批节点；可暂存齐备后一次提交。

标准费用必须同时匹配交付范围、总额、首尾款、收款方和规则版本，才使用老板预授权。未匹配时交老板审批；退回后由原业务在原委托补充重提。授权来源保留真实人员、时间和版本，不生成虚构的逐单审批记录。

## 退回与修改

1. 客户对下发成果提出修改：业务在移交提交前登记修改意见，待办回到设计行政；线下修改完成后，行政再次登记完成和下发。沿用原委托、原费用和原付款，保存历次完成与下发记录。新下发版本不恢复旧版签认草稿，业务需重新核对本版文件和确认凭据。额外收费不在本次修改动作中自动产生。
2. 工程负责人退回资料：明确原因，原业务收到补充待办，在同一页面补齐重提，保留移交版本与退回历史。
3. 部分付款或到账保留累计有效金额及各自剩余待办；当前版本首尾款未足额实收时，命令层阻止正式下发。撤销、更正和已核实退款按净额重算，差额补齐后重新生成行政未读通知。无权岗位、重复流水、过期版本或旧表单覆盖被阻止。
4. 已接收移交资料不能被本轮业务表单覆盖。后续工程办理沿用原模块规则。

## 三批交付与兼容范围

| 批次 | 已实现内容 | 验证 |
| --- | --- | --- |
| 第一批 | 新委托事件、费用授权、首尾款触发、行政完成及下发、资料移交和回执 | 主链 11 项检查 |
| 第二批 | 业务首页待办合并、委托及移交页面、行政独立入口、老板标准规则页面、旧入口转接 | 真实 Page/WXML 事件 15 项检查 |
| 第三批 | 内容获客衔接、异常审批、客户修改、版本草稿、退回重提、历史链及财务回归、改动范围核对 | 新异常与接口 12 项、残留专项 8 项、全岗位衔接专项 61 项通过；共 20 组回归脚本通过 |

新委托标记为 `businessFlow.type = sales-offline-v1`。已有委托沿用原流程、审批及历史资料，不自动补造新状态。旧设计角色保留处理历史委托的入口；新委托仅由设计行政办理本轮定义的行政动作。

追加残留检查已完成：统一旧链接映射，阻止新客户或新委托通过旧模型动作办理，删除首页重复待办及无绑定处理器，清除角色失效后的旧资料缓存。历史报价、服务单、合同及付款事实保留原流程；历史记录误入新表单时转回原页面。新移交按已校验人员 ID 保存，避免旧姓名匹配逻辑干扰同名接收人。详见 [残留检查与清理记录](../qa/business-module-simplification-20261021/residual-audit/检查与清理说明.md)。

全岗位待办复查已补齐生成完成后的保存成品事项，并修复财务负责人身份下只显示复核任务而隐藏本人可办付款、到账登记的问题。首页和全部待办均覆盖当前身份有权办理的事项，复核指标保留专门入口。已走通 31 次岗位待办跳转，详见 [全岗位衔接清单](../qa/business-module-simplification-20261021/todo-handoff-audit/全岗位待办衔接检查.md)。

工程代码仅增加已接收业务资料的来源适配，读取本轮移交的图纸、版本及五项资料；没有修改施工、采购、验收、整改、竣工、结算功能或其开工条件。范围检查基于开工前 544 个源文件快照，区分了工作区原有修改与本轮修改。

```powershell
npm run check:business:simplified:batch1

```

本轮验证使用隔离的本地数据与模拟人员，实际调用业务/财务模型及原生页面的 Page 处理器和 WXML 按钮事件。未发生真实付款或内容发布，未上传微信版本。

目前项目仍使用现有本地存储模型。自动待办已在同一数据状态内接通，**尚不等于多设备、多账号在线实时协作已上线**；生产使用仍需后端持久化、权限校验与事件同步支持。没有在本轮另起后台系统。
