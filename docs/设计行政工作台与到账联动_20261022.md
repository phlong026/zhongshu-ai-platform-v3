# 设计行政工作台与到账联动核查

## 本轮页面修改

设计行政采用“首页、项目、我的”三项导航。“项目”覆盖该总部设计组织负责的全部已授权委托，包括设计、修改、待下发、已下发及后续移交完成的历史记录。

首页顺序与业务首页保持一致：问候语和日期、设计与修改／待财务通知／待下发三张统计卡、今日待办、最近办理。首页只预览三条本人可办理事项，标题显示完整数量；最近办理取当前人员真实完成和下发事件，最多五个项目。外部等待不计入今日待办。

项目可按客户、项目编号、加盟商、城市及经办业务搜索，支持六个状态筛选。设计与修改统计卡进入组合筛选，同时显示当前筛选说明。切换首页和项目时保留项目搜索条件。首屏展示20条，加载更多或触底每次增加20条；总数按完整项目统计，搜索与筛选复用本次页面展示时加载的数据，再次进入页面时重新读取。

详情增加尺寸依据与需求附件入口，复用原设计完成、下发、修改和移交表单；操作区随内容滚动。显示数据继续使用总部授权投影，不向行政页面输出客户电话、微信、服务费用和付款明细。

## 财务流程的当前事实

本轮核查发现，旧文档描述的总部到账门禁与当前 `sales-offline-v1` 实现不一致：

1. 加盟商财务在批准的原单下登记实际付款，分笔累计计入门店已付。
2. 总部财务能查看费用抄送和门店登记进度，目前没有本流程的“确认已到账”操作。
3. 设计行政登记完成后，代码直接开放下发入口。表单中的“已收到财务线下通知”只是人工确认，没有系统到账记录支撑。
4. 所谓自动待办来自本地存储与页面刷新，当前没有跨设备事件同步或微信订阅消息发送。

证据分别位于 `utils/transfers-v2.js`、`pages/admin/finance-actions.js`、`utils/authority-v2.js`、`utils/finance-ledger.js`、`utils/finance-desk.js` 与 `utils/sales-flow.js`。现有主链及财务验收脚本也明确断言总部不办理该设计款收款。

页面的“待财务通知”分类依赖上游真实流程状态，不凭门店付款记录伪造总部到账或财务已通知。当前上游未产生这个状态时，数量为零。“待下发”文案要求核对财务通知，不宣称系统已确认到账。

## 待明确并接入的闭环

用户描述的闭环为：加盟商登记已付款 → 总部财务确认实际到账 → 行政项目转为待下发 → 行政登记正式图纸实际下发 → 业务收图并移交。

需要明确财务指收款的总部财务，而不是付款的加盟商财务。确认实际到账与仅登记已付款是不同事实；本次页面修改不擅自改变财务记账规则。

如采用总部实际到账确认，应复用总部原账簿与到款来源关联，保留确认人员、时间、金额、银行流水、凭证和服务版本。分笔未足额、旧费用版本及其他组织的确认不能放行正式成果；命令层也必须校验，防止绕过页面。不得新建一份客户合同收款而重复计算设计款。

这一闭环尚未在本轮修改中实现，真实跨设备通知也未接入。验收不能把当前页面分类或人工勾选称为财务系统放行。
