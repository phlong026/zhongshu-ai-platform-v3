## 存储具体建议

1. 短期受控试点：现有盘可作为候选，固定 B 根目录为 `/mnt/datadisk0/zhongshu-platform-b`，12 GiB 运维余量后约 25.06 GiB 业务头寸。必须先解决校验门禁并通过隔离恢复验证，不承诺既定生产规模。
2. 正式生产建议：新增 **100 GiB 加密 B 数据盘**，挂 `/mnt/zhongshu-platform-b-data`；另新增 **200 GiB 加密 B 备份盘**，挂 `/mnt/zhongshu-platform-b-backup`。都要位于上海五区才能挂到当前实例，不扩容、格式化或重用 A 系统盘。
3. 两个 PostgreSQL（含 WAL）、两个 Redis（含 AOF/RDB）和 Runtime journal 分别落 B 数据根下的固定子目录。`backup-staging` 只作暂存，不能算备份。完整备份只写另一块 B 盘的 `zhongshu-platform-b-backups/backup-<UTC时间>`。
4. 正式初始规划为数据余量 25 GiB、备份余量 32 GiB、单次备份上限 96 GiB；最终用实际全备、恢复空间和增长曲线修订。200 GiB 不能保证保留多份 96 GiB 上界备份。备份保留不自动删除现有文件，先测再定份数，并另保留 B 专属异地副本/备份服务。
5. Runtime 已完成 journal 暂无清理策略：100 个最大图片任务约 2.81 GiB 在途预留，100 张最大图片持久记录理论约 2.61 GiB。需制定完成记录保留和容量报警，不能用每日业务限额替代治理；仍按公司积分与权限使用。
6. Docker 镜像和容器日志仍占根盘；最终镜像 unique/shared、导入与回滚空间须实测。建议导入后根盘至少留 8 GiB 作为初始运维评估值。B Nginx access 受现有 `/var/log/nginx/*.log` 的 daily/14/compress 轮转覆盖，但这是日轮转，不是实时大小硬上限。

两套配置片段已准备在 B 后端 `deploy/platform/site-plan/`，proof hash/签名故意不填，不能直接执行部署。

## 当前部署脚本的真实兼容阻塞

控制台与 guest 已对应：系统盘 `disk-731jrb7z`，数据盘 `disk-aqc9ak09`。guest 的数据盘有 serial，系统盘 `vda` 的 serial/WWN 都为空。
当前 `same_host_storage.py` 要求全部物理祖先具有稳定 serial/WWN，并要求 thick 供应证明及受信签名；将实际采样拓扑送入生产纯函数，返回预期拒绝：`Physical block ancestor lacks a stable WWN/serial identity`。

这说明当前门禁模型尚未适配这台腾讯云主机。不能要求用户填造 serial，也不能把云盘 ID/UUID 等同为物理故障域独占或 thick 保证。
下一开发项应为受审查的腾讯云控制面身份模式：只读 `DescribeDisks/DescribeInstances`，校验账号、实例、可用区、盘用途、挂载关系、加密和容量，与 guest 挂载证据绑定，再由受信方对证据哈希签名。API RequestId 只可追溯，不是审批签名；不能静默弱化旧门禁。

本轮没有改写校验器、创建运行卷目录、伪造 proof/attestation、挂载新盘、改 fstab、加载镜像或启动 B。只读采样与纯函数校验见 [兼容核验](部署门禁兼容核验.json)。

官方依据：[DescribeDisks](https://cloud.tencent.com/document/product/362/16315)、[DescribeInstances](https://cloud.tencent.com/document/product/213/15728)、[DescribeSnapshots](https://cloud.tencent.com/document/product/362/15647)。官网部分正文访问受限，字段以腾讯维护的官方 SDK 模型交叉核实；没有找到 guest serial/thick/物理故障域保证。

| 用途 | 建议 | 生效方式 |
| --- | --- | --- |
| B API | `platform-api.zszhj.com` | 新 A 记录 → `124.223.61.18`，新站点 → `127.0.0.1:48081`，保留 `/admin-api` 和 `/app-api` 路径 |
| B 管理后台 | `platform-admin.zszhj.com` | 新 A 记录 → 同主机，新静态目录 `/srv/zhongshu-platform-b/web/current`；`/admin-api` 同源代理 B |
| B WebSocket | 两个 B 域名的精确 `/infra/ws` | Upgrade 到 B，额外路径不升级；不用 SPA 吞掉连接 |
| B 对象存储 | 首发沿用已验的 B 原生 HTTPS 对象域 | 在微信登记并真机验收；不代理到 A |
| 后续自定义对象域 | `b-assets.zszhj.com` | 可选，先适配签名 Host、SDK 与 Runtime 唯一 origin，再考虑 CNAME；不能只改 DNS |

同一腾讯账号已能看到 DNSPod `zszhj.com` 的三条记录：`@`、`api`、`api2` 都指向当前主机，保持原状。两个 B 业务域与 `b-assets` 的权威查询均 NXDOMAIN，见 [DNS 采样](B候选域名权威DNS核查.txt)。本次没有修改 DNS。

nginx 当前 `api`、`api2` 均指 A 的 48080，`zszhj.com/admin/` 仍为 A 的静态目录。A 两套证书 SAN 均不覆盖 B 候选域，因此 B 要独立签发、续期与回滚，不替换 A 证书。
A `zszhj.com/api.zszhj.com` 证书到期为 2027-01-01 01:04:38 CST；`api2` 证书到期为 2027-02-06 08:25:53 CST。

B 管理端保持空 `VITE_BASE_URL` + `/admin-api`，不向 A 增加 CORS。小程序默认仍指 `api2`，正式 B 联调版本才切到 `https://platform-api.zszhj.com/admin-api`；钱包按已有规则替换 `/app-api`，并核对 `zs-api-base/zs-wallet-base` storage 覆盖。未准备后端前不切换默认值、不上传新版本。

切换顺序：解决存储兼容与独立备份 → B 内网服务/账本验证 → B 专属站点和证书准备 → 全配置 `nginx -t`、A/B Host 验证与受控优雅 reload → DNS/微信合法域名 → B 客户端联调。DNS-01 可用于提前签发 B 证书；若采用 HTTP-01，先仅启用 B 专属 challenge/维护响应再配 DNS，不把新 B Host 导到 A 默认服务。本次没有启用站点、申请证书或 reload。
