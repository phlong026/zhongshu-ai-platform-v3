# 绩效任务化实施

## 清理与迁移计划

1. 先用回归脚本锁定现有业务事实、历史责任人、组织权限、归档冻结和奖金汇总，再接入新页面。
2. 新建独立的 `performance-tasks` 本地存储，不覆盖 `zhongshu-owner-goals-v1`、旧绩效归档、薪酬策略或工资结算。
3. 自动任务只读 `performance.sourceRows()` 和 `owner-performance.facts()` 的原业务事实；签约只计 `auto:contract` 正式合同，不把设计委托额冒充签约；回款按元汇总并减去当月已核实退款。缺少历史责任证据时不用当前负责人补猜。
4. 老板可为本组织任意在岗人员派任务，任务同时冻结 `assigneePersonId`，改派另记历史；员工只看真实 person 属于本人的任务，且只能提交本人手动任务的说明和 0–6 张选填照片。
5. 月度归档冻结任务定义、事实签名和已完成奖金；归档后原业务变化时只能新建修订版，不改写旧版。
6. 奖金归档通过授权命令按组织、月份和真实人员汇总生成稳定应付；已有通用付款页登记实际支付。旧版已有付款或预留时阻断覆盖；零奖金修订可核销旧版未付应付。

## 不变行为

- 不删除历史指标、旧归档、薪酬规则和工资数据。
- 不修改业务原单的责任人，也不把任务被派人写回原单。
- 归档版本可追溯、可修订，但不就地更新。
- 同一归档的奖金应付草案键恒定，重试不产生第二条衔接记录。
- 任务命令的幂等键同时包含命令名和真实 person；即使命中旧结果，也先复核当前权限和对象归属。
- 每个自动任务同时返回 `sourceIds` 与原单 URL，不允许只展示一个无法追溯的汇总数。

## 交付边界

- 本页提供“团队任务 / 我的任务 / 奖金归档”三个视角和可操作表单。
- 当前绩效入口进入任务单；旧指标通过 `history=1` 只读查看。旧目标和薪酬新建入口下线，历史归档、规则及已生成结算保留。
- 老板派发、责任人完成、归档生成应付、财务登记付款已由真实 Page/WXML 事件及 `Model.mutate` 回归覆盖；真实后端、多设备同步及真实银行支付仍须另验。
- 本轮以本地事实模型为准；暂不迁移或覆盖旧指标数据。
