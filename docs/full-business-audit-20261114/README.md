## 2. 排查方法：从前端动作追到业务结果

每个场景建立以下映射，并保留实际版本和证据：

`正常入口 → 页面/子视图 → 按钮处理函数 → API 请求 → Controller/DTO → Service 门禁及状态 → 数据与账本 → 下一岗位待办 → 下游页面/报表`

前端现有可操作流程是排查主线。对字段、权限、状态和财务口径同时核对已确认业务规则；遇到代码与规则不一致时记录冲突及依据，不能以“前端大致正常”或“后端有接口”直接判通过。

验收单元是“一个业务动作完成后，正确的人能接着处理，数据和金额一致”。每个动作至少检查：

1. 当前人是否有权操作；正常入口和按钮是否可见、可达。
2. 请求方法、路径、字段类型、长整型 ID 精度、金额单位和舍入、版本、幂等键是否与后端一致；零/负值/边界值和业务日期跨日时区分别有校验。
3. HTTP 状态及业务码是否成功；失败时是否保留可恢复的表单和原任务。
4. 状态是否正确推进；重复点击、超时重试是否重复建单、扣点或记账。
5. 下一岗位是否收到唯一、可访问、可办理的待办；原待办是否正确关闭。
6. 刷新、退出重登、换岗位后，仍能查到同一份持久化事实。
7. 关联客户、项目、委托、合同、版本、附件和账目能否对上。

### 3.3 先冻结这些规则

- 建房合同按目前正式规则为**签约后、基础完成后、封顶后三期**，三期约定合计等于合同总额；不沿用旧两期样例。
- 施工事实与收款事实分开：基础、封顶是否完成按实际凭据记录，不能为收款门禁歪曲节点事实。资金条件约束具体后续放行。
- 设计委托支出、建房合同收入、材料/劳务支出、公司积分分别核对。设计款与合同款不合并成一个订单余额。
- 财务登记线下真实收付与退款，不等于发起微信转账/退款。支付渠道订单另设场景，不能用模拟支付解锁正式资金事实。
- 当前前端委托页已注明取消模拟支付，实际对接 `/franchise/commissions`。同时保留总部面积计价及历史费用授权视图；**新标准计价与历史首尾款模式分别建契约，不把历史文档拼成一个流程**。
- 规则依据以当前用户决策、有效规则和匹配版本代码核对为准。[旧模拟支付说明](../设计委托面积计价与模拟支付_20261023.md)只作为历史差异来源。后端规则入口是 `平台程序/docs/business-flow-audit-20261103/16-业务规则与角色职责-最终版.md`，执行时结合后续决策检查其版本。
- B 首发充值关闭；[商城/服务展示入口](../../miniprogram/pages/account/index.js)目前会把部分订单/采购路由转为展示页。清点时标记“已交付交易、展示、待建设、已关闭、旧 A 能力”，不能默认恢复被明确关闭的功能。

## 4. 三个关联案例：使用同一份客户和项目事实

桌面推演数据见 [simulation-data.json](simulation-data.json)。以下名称、金额和单价均为测试样例，不是新增正式定价。执行时在隔离组织中配置有效规则，记录计价版本；缺规则即登记前置阻塞，不暗设默认价。

主例：“联调客户周先生，300㎡三层建房”，测试加盟商甲，业务员甲负责。建房合同 480,000 元，三期 150,000 / 180,000 / 150,000 元。新委托按当前标准计价契约演练，样例为 300㎡ × 80 元/㎡ = 24,000 元；**正式收费通道、单期/分期及设计放行条件必须先冻结**。当前候选存在契约差异，未冻结时相关写步骤标阻塞，其他独立检查继续。历史首款 10,000、尾款 14,000 元只放入独立历史兼容样例，不用新客户创建历史模式。

独立资金异常支线：同笔/超额退款、供应商退回款、设计退款、重复流水、日期未知、跨月补录、合同变更、退款后的提成差异。示例客户退款 10,000 元并不自动改变合同 480,000 元；净实收变为 470,000、相应期次/待核销与剩余应收明确，月报重新生成版本。合同若另有批准变更，再核对其新总额和三期分配，不用退款代替变更。

## 6. 开发者工具中的逐步取证

1. 每轮先核对导入路径与构建版本，选择真实测试岗位，从正常工作台入口进入。直接跳路由仅用于定位，单独标记，不能替代入口验收。
2. 打开 **Network + Console**；保留本场景请求上下文，记录起始时间。Network 先看完整请求，随后按 API/存储/媒体域名过滤；不能只看 `/admin-api/` 而漏掉 COS PUT、下载和其他通道。异常发生后先保全证据，不先清日志。
3. 每一步记录：场景/步骤、角色与组织、动作、页面状态、脱敏请求方法/URL/参数、HTTP/业务码、业务 ID、版本、幂等键关联、耗时、控制台异常及截图。收敛单次动作对应请求，避免把后台轮询归因于最后一个按钮。
4. 同时按请求 ID、任务 ID、单据 ID、业务键和时间窗口关联 API/AI Worker/存储或支付通道日志；缺 traceId 时记录关联依据。数据库只读核查持久化、审计事件、待办及账本，不能用直接改库代替办理。
5. 切下一岗位，从其工作台待办办理，验证权限、上下文及默认负责人；财务同时核对项目账与公司/总部汇总。
6. 在隔离环境复演无权限、旧版本、断网、重复提交、外呼超时、执行成功但响应丢失等分支。未知任务先查原收据，禁止用新任务掩盖未知结果。
7. 结束检查刷新/重登后的状态，保存脱敏证据与问题单，收集后台任务最终结果。前端成功提示、HTTP 200 和页面无红错均不能单独作为通过标准。

所有 UI 操作使用当前可用的开发者工具操作面；已验证脚本可承担非 UI 断言。原始 token、Cookie、AppSecret、完整签名 URL、手机号和私有文件不得写进 Git 或报告。

## 7. 发现断点后的处理与解决方案格式

每个问题一张单，关联失败场景：

```text
编号 / 优先级 / 场景步骤 / 前后端与运行版本 / 首次发现时间
预期业务结果 / 实际结果 / 最短复现步骤
页面与请求证据 / 控制台 / 后端日志 / 数据账本 / 下游待办
分类：缺运行接口、缺实现、字段契约、权限、状态门禁、前端映射、外部配置、异步任务或账目
根因及置信度 / 已排除原因 / 仍需证实的部分
临时处理 / 最小修复方案 / 影响模块与文件 / 数据修复需求 / 回退步骤
复现测试 / 本模块复测 / 上下游及其他岗位回归 / 真实渠道待验
负责人 / 状态 / 修复提交 / 运行版本 / 验证证据
```

- P0：资金/点数重复或错误扣记、跨组织泄露等，停止受影响写入，保全证据，继续独立模块。
- P1：主链无法提交/接续、缺必需接口、单据/成果/待办错误。先记录失败请求与状态，再按契约及实际日志定位。
- P2：不阻断办理的展示、文案和交互问题，记录影响及回归要求；若掩盖错账或误导办理，应提高等级。

修复路径优先保持已确认前端业务顺序，在接口边界或后端状态衔接做最小修复；前端映射/校验/入口自身有错时同步修复。不能为迎合错误请求放松鉴权、取消确认门禁、伪造附件或直接改账。

实现时先复现，再补行为测试、修复、复测原步骤及上下游、核对完整 diff 和回退，独立逻辑独立提交。发布及生产数据修复按相应授权和具体方案进行。问题可标“源码已修复/本地通过/已部署/真实链路通过”，不能合并成一个“已完成”。

## 8. 执行顺序与交付

| 阶段 | 主要工作 | 结束证据 |
|---|---|---|
| 0：盘点与准备 | 路由、子视图、动作、API、后台菜单、状态机和定时任务盘点；锁版本、规则、角色、隔离数据及外部通道 | 业务图、契约表、岗位表、run manifest；全部功能已分类，阻塞有归属 |
| 1：基础贯通 | 登录任职、组织隔离、公司积分、文件上传下载、关键契约预检 | 基础场景通过；关键资源与状态接口可用 |
| 2：连续主例 | 按 A/B/C 依赖推进同一客户与项目；必要处转到正确岗位与总部 Web | 从获客到交付的操作时间线、ID 链、成果版本、双边设计款和工程项目账 |
| 3：扩展与故障 | 全部 AI 能力、绩效经营、服务商城范围、失败恢复、并发、权限与跨月补正 | 场景清单结果及问题单；付费/真实通道证据单独列明 |
| 4：修复回归及验收 | 按问题优先级修复，复跑受影响上下游和关键主链，核对真实角色及发布版本 | 修复提交、部署结果、回归证据、角色验收和剩余限制 |

静态清点、契约复核和证据审查可并行；共享开发者工具 UI 由一个操作者串行办理，避免多个操作者改同一岗位/项目。依赖缺失的步骤标“阻塞”，独立步骤继续。

每阶段交付：覆盖矩阵、连续案例时间线、接口/状态契约表、问题及解决方案、脱敏证据。进度按“已通过/失败/阻塞/未执行/当前范围不适用”统计，列出实际分母；不以点击次数统计通过率。

结束标准：约定范围内所有动作、状态转换、角色接续和关键失败分支均有结果；三个主例可从正常入口连续完成；原单、成果版本、合同三期、双方设计资金及公司积分分别对账；无未关闭 P0/P1、无关键步骤阻塞；P2 有清晰影响和处理安排。真实支付、真实 AI、真机及生产发布分别留验收状态，不能互相替代。

## 9. 本轮已发现的重点与下一步验证

1. **设计委托存在候选源码契约不一致。** 当前前端 `commandPayload()` 使用 `checked` 等字段；独立 B 候选 `CommissionController` 命令读取 `confirmed`。预检应逐一核对提交、完成、下发、移交和接收的请求/响应，先构造最短契约复现，再在隔离环境实际办理。详细差异与修复建议见 [initial-findings.md](initial-findings.md)。这不是线上复现结论。
2. **运行版本与测试入口需先对齐。** 开发者工具导入路径与方案 worktree 不同，默认还是 api2；不能直接假设它在测试独立 B。先固定 manifest 与隔离配置，保留 A 运行边界。
3. **商城和设计支付必须按现行范围分类。** 现有商城部分入口展示化，B 首发充值关闭，旧模拟支付文档尚在。先记录真实入口和规则归属，再验已开放交易；需要新增正式交易能力时单列需求及缺口，不能在巡检中默认已经交付。
