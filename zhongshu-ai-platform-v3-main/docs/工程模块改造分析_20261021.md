# 工程模块改造分析

本文保留实施前的代码分析。最新实际实现以[工程主链路](工程模块主链路_20261021.md)和[验收说明](../qa/engineering-records-20261021/验收说明.md)为准；本轮按日常记录流程实现，工期、人员和问题回原事项继续。

2026年10月21日。目标为一项目一名工程人员，工程款分开工前和主体封顶两次收取。沿用[工程主链路方案](工程模块主链路_20261021.md)，本次对照现有页面结构、业务模型、权限和财务接口分析改造范围。

现有工程四个导航入口、施工及材料记录、财务核对能力可继续使用。主要工作是统一工程经办人，接通最新业务移交与开工条件，建立两期应收和主体封顶触发，再将页面及待办围绕同一个项目收简。

| 已有能力 | 复用方式 |
| --- | --- |

| 现场记录、验收、整改、复验、交付及归档 | 复用实际记录，调整办理入口与人员规则 |
| 材料需求、供应批次、收货、质量处置和补发 | 沿原材料及批次继续，减少重复填写和跳转 |
| 实际收款凭据、财务核对和原笔补证回写 | 增加两期归属与金额汇总，保持财务确认独立 |

## 需要优先解决的主链缺口

### 一项目一人的权限和责任

现状：新业务移交只能选择具有 `project-manager` 岗位的人员，接收动作也要求负责人身份。实际开工再次选择执行工程人员。验收又按负责人、执行人及实际人员关系决定是否独立审核。现有 `engineeringExecutor()` 同时认可负责人和指派执行人，工程写入还包含团队和协作者授权。

改造：新流程以接收时选定的一名项目工程人员为日常经办依据。工程权限人员可被选择并接收本人项目；开工自动沿用此人，验收及整改结果由其据实登记后生效。页面显示“项目工程人员”。人员离岗或更换通过原责任交接办理，旧经办记录保留。老板和财务继续使用各自授权入口。

需要同步修改业务端人员选择、接收动作校验、工程写入权限、页面按钮、草稿和责任交接。历史多岗位项目保留原授权和审核记录，避免全局删除旧角色造成历史任务失效。

涉及：[业务新流程](../miniprogram/utils/sales-flow.js)、[移交页面](../miniprogram/pages/workflow/commission/index.js)、[权限模型](../miniprogram/utils/authority-v2.js)、[页面权限](../miniprogram/utils/page-visibility.js)、[工程模型](../miniprogram/pages/build/model.js)、[验收规则](../miniprogram/utils/approval-policy.js)、[财务及责任回写](../miniprogram/pages/admin/finance-save.js)。

### 新业务移交与开工条件

现状：工程同步已能读取最新移交包中的图纸及五项资料，但 `reviewed()`、图纸校验签名和 `ready()` 仍按旧业务审图记录、固定资料名称核查。新的业务流程接收前不要求建造合同，工程端又禁止编辑业务来源项目的合同、交底和图纸。收款计划的提交权限目前仅给业务或老板。

隔离模型验证中，最新业务移交已接收、五项资料和图纸已带入，旧审图记录为空，工程审核状态仍为不认可。工程补合同和提交合同付款约定也分别被只读规则、岗位规则阻止。

改造：按有效移交版本读取施工图、线下专业审核依据、客户确认和交底，复用已完成的专业审核事实。将业务移交资料与工程新增的建造合同分开保存；工程人员可在开工准备中关联已有合同或登记双方已签合同、合同总额及两期金额，老板按原金额权限确认，已有有效确认直接沿用。

工程刷新同步只更新移交来源，工程新增合同及准备资料持续留存。开工检查集中为一页，资料自动引用，现场核查补实际情况。开工需同时满足准备齐备、施工计划已保存和开工款经财务足额确认。

涉及：[工程同步及开工条件](../miniprogram/pages/build/model.js)、[开工页面及弹层](../miniprogram/pages/build/index.js)、[工程视图](../miniprogram/pages/build/views.js)、[合同和分期模型](../miniprogram/utils/operations.js)。

### 两次收款与财务归属

现状：工程收款是通用登记，所属节点由文本填写。合同付款计划可以配置任意期次和金额，放行阶段仅有设计、开工、交付。项目实收先汇总，再按期次到期日分配，尚无固定的开工款、封顶款及施工里程碑触发。

改造：新项目固定两期应收，开工款和封顶款合计等于有效工程合同总额，封顶款带出剩余金额。金额、合同版本及老板确认来源绑定保存。两期各自具有稳定标识，实际收款明确关联项目、期次和流水，支持分笔到账；已有财务收款直接回显。

两期分别显示应收、财务已确认、待确认和待收金额。上传凭据进入待财务确认，核实后计入有效实收。补证沿原笔继续，重复流水或重复提交不能重复累计。设计服务费、供应付款、业主直付材料等保持各自归属。

开工款在合同及两期约定确认后生成跟进事项，财务足额确认后才能实际开工；封顶款由主体封顶事件触发。封顶后的施工安排沿合同执行，交付前核对约定收款条件，沿用已有老板例外权限及依据。

涉及：[工程收款表单](../miniprogram/pages/build/views.js)、[工程收款写入](../miniprogram/pages/build/model.js)、[合同分期及放行](../miniprogram/utils/operations.js)、[财务来源合并](../miniprogram/utils/finance-ledger.js)、[财务回写](../miniprogram/pages/admin/finance-save.js)、[财务工作台](../miniprogram/utils/finance-desk.js)、[项目结清](../miniprogram/utils/project-settlement.js)。

### 主体封顶与施工节点

现状：新建工程的默认计划为基础、一层主体、二层主体三个节点，带固定演示日期。节点没有主体封顶标记，全部节点完成后直接进入待交付。验收检查项对所有节点复用同一组三项；验收通过与节点完成需要分别办理。

改造：按楼层和承包范围生成可调整模板，计划日期由实际项目保存。明确主体封顶里程碑，按该里程碑及前序主体节点、验收整改是否完成判断封顶条件。工程人员登记一次实际封顶日期和凭据，自动接续唯一的封顶款待办。

各施工节点使用匹配的检查内容。验收通过且相关材料及整改条件满足时，提供同页完成节点的操作；条件不足时明确列出原单入口。完成封顶后继续按合同范围办理屋面、外装等剩余节点，项目整体进度与收款状态分别展示。

涉及：[工程默认节点](../miniprogram/utils/engineering-seed.js)、[计划及节点动作](../miniprogram/pages/build/model.js)、[节点及验收视图](../miniprogram/pages/build/views.js)、[页面操作](../miniprogram/pages/build/index.js)。

### 首页及项目待办

现状：首页显示今日待办、常用入口和最近项目，待办来自多种原工程动作。列表中缺少固定两期的催收事项，页面也未像业务模块一样统一分为待我办理与办理中。项目卡片的下一步主要依据是否开工、是否验收和是否交付判断。

改造：建立同一份工程进度和待办计算结果，供首页、项目列表、项目详情和下一步按钮复用。接收、开工准备、开工款、实际开工、当前节点、整改、收货、封顶款和交付，全部关联具体原单。

待我办理显示当前工程人员可操作的事项；办理中显示老板金额确认、财务到账核对等实际等待环节。工程首页的收款跟进与财务待核对共享原期次和凭据状态。重复刷新保持任务标识稳定，完成或退回后同步更新。

涉及：[工程工作台及待办](../miniprogram/pages/build/workbench.js)、[首页](../miniprogram/pages/build/home/index.wxml)、[项目列表](../miniprogram/pages/build/projects/index.js)、[项目详情](../miniprogram/pages/build/index.js)。可参考[业务待办](../miniprogram/utils/sales-todos.js)和[业务进度计算](../miniprogram/utils/sales-flow.js)的组织方式。

## 页面改造清单

| 现有页面 | 改造内容 | 范围 |
| --- | --- | --- |
| 业务成果与移交、工程接收 | 选择在岗项目工程人员；同一身份核对接收；保留资料原单退回 | 必须联动 |
| 工程首页 | 待我办理、办理中；增加开工款和封顶款提醒；统一下一步 | 重点调整 |
| 工程项目列表 | 项目卡显示当前节点、下一步和两期收款摘要，筛选沿统一状态计算 | 保留列表结构 |
| 工程项目详情 | 顶部统一项目工程人员、当前节点、主操作和两期金额；集中连接进度、材料、款项、资料 | 主要办理入口 |
| 开工准备及实际开工 | 合并准备入口，自动引用资料，补合同和两期约定；开工沿用项目工程人员 | 主链关键改造 |
| 工程款项及收款登记 | 固定两期卡片，自动带出期次、应收和差额，查看分笔实收及财务状态 | 替换通用填写方式 |
| 施工计划、验收和整改 | 项目模板、封顶里程碑、按节点匹配检查内容、同页完成节点 | 复用记录能力 |
| 材料页及供应、收货弹层 | 收为提交材料计划、付款、到货确认三类操作；公司线下采购，分批到货和异常沿原计划继续；自动联动节点和财务 | 按最新口径重点收简 |
| 交付及归档 | 自动核对施工与收款条件，汇总原资料；缺项直达原单，保存签收后交付归档 | 复用并串联 |
| 保修与服务 | 当前为说明及合同查看；补充报修、处理、完成记录即可 | 主链完成后补齐 |
| 我的 | 沿用个人信息、消息、学习和设置 | 少量文案及消息适配 |
| 财务和老板相关页面 | 工程合同及两期约定确认、两期应收展示、实际到账核对后回写 | 复用原工作台和权限 |

当前材料节点完成还要求有材料清单且足量合格收货。按最新[材料计划精简流程](材料计划精简流程_20261021.md)，工程提交计划、公司线下采购、工程确认到货并通知财务。付款与到货分别记录，系统自动维护需求、供应、收货、成本和财务所需关联。甲供、余料和无需新购节点按实际情况核查，分批到货和异常在原计划继续办理。

交付与财务结清保持各自事实：交付按合同核对工程与约定收款条件；供应商待付、成本核对和往来收尾继续在原项目办理。

## 改造顺序和验收

| 批次 | 必须完成的范围 | 可验收的结果 |
| --- | --- | --- |
| 第一批 接通基础逻辑 | 一人权限、新移交资料校验、工程合同、两期应收和实际到账归属、主体封顶事件、材料三类操作与节点及财务联动 | 使用一个工程身份，从最新业务接收走到实际开工，材料到货和付款正常接续，再到主体封顶和第二次收款；所有数据保持原项目关联 |
| 第二批 调整办理页面 | 首页及项目统一待办、项目详情、开工准备、两期收款、节点及材料操作、交付归档 | 用户从待办进入原单，完成一步后看到下一步，等待环节显示实际办理岗位 |
| 第三批 完整回归 | 新主链、异常补充、历史流程、财务回写、责任交接、轻量保修 | 新主链能完成，历史项目原金额、凭据、经办人和审核记录持续可查 |

验证至少覆盖：

1. 业务移交选择工程人员，接收后生成唯一工程档案；同一个工程身份完成全链路。
2. 新移交包的审核依据和客户确认被正确引用，资料退回后在原单补齐，工程新增合同不被刷新覆盖。
3. 合同总额、两期金额及批准版本一致；开工款部分到账、待财务确认时开工入口保持等待。
4. 主体封顶按实际节点完成触发；重复确认和刷新不重复创建封顶款事项。
5. 两期分笔到账、财务直接登记和工程提交后核对均只累计一次；凭据退回沿原笔补证。
6. 材料计划提交、先款后货、先货后款、分批实收、分笔实付和异常处理都能在原单继续，合格可用材料进入节点核查；验收整改完成后继续施工，封顶后存在剩余范围时推进至交付。
7. 工程交付、资料归档与财务结清分别显示；总部代垫、业主直付和原供应付款沿原口径核对。
8. 历史项目、项目范围隔离、责任交接、无权人员、重复事件、旧版本提交及并发覆盖回归。
